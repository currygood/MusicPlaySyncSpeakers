## Phase 2 上板失败 → 根因定位 + 修法（2026-10-27 晚）

上板日志暴露两个严重问题，都发生在 FreeType 打开 face 期间：
1. `task_wdt`：CPU0 被 UI_Task 占住 >5s（IDLE0 饿死），tcpip 那一次也是同一原因；
   backtrace 明确停在 `FT_New_Face → tt_face_load_hmtx → ft_ansi_stream_io → fseek
   → vfs_spiffs_lseek`。
2. BT 播放 ~80s 后 `Interrupt wdt timeout on CPU1`，`Music_Play_Task` 卡在
   `xQueueReceive` 的自旋锁（queue 在 PSRAM）。机制：SPIFFS 随机读每次都要
   `spi_flash_disable_interrupts_caches_and_other_cpu()`，另一核正在临界区时两边互等。

根因（已读 SPIFFS 源码确认）：`spiffs_object_read` 只在**同一对象索引页内连续读**时
复用 `fd->cursor_objix_spix`；跨索引页要 `spiffs_obj_lu_find_id_and_span` 全盘扫
LU 页（7.25MB/256B ≈ 116 页）。FreeType 打开 face 在 head/maxp/hhea/hmtx/cmap/glyf
之间反复跳 → 每次 20~25ms，一个 face 10s+。

结论：**FreeType 绝对不能用 SPIFFS 路径直读**，哪怕只为打开一次。

修法（已落地，替代原"直接给路径"方案）：
- 新增 `components/App/UI/ui_font.c/.h`
  1. 开机用 POSIX `open/read` 顺序把 /storage/font/ui_font.ttf（1,542,592B）
     读进 **PSRAM**（heap_caps_malloc MALLOC_CAP_SPIRAM），顺序读走 cursor 快路径，
     每 32KB `vTaskDelay(1)` 让出 CPU 防 task_wdt；
  2. 注册只读内存 VFS `/fontmem`（esp_vfs_t + ESP_VFS_FLAG_DEFAULT，
     open/close/read/lseek/fstat/fcntl/write/fsync，单文件多句柄）；
  3. FreeType 路径改成 `/fontmem/ui_font.ttf` → 标准 fopen/fread 读内存，
     渲染热路径完全不碰 flash，**不需要** `LV_FREETYPE_USE_LVGL_PORT`
     （也就绕开 FT_Stream_Open 重复符号坑）；
  4. 校验：size 与 ui_font.meta 的 `size=` 对齐 + TTF 魔数；不做全量 CRC；
  5. 12/16/20 三档一次创建，打印实测 line_height/base_line/耗时/堆余量。
- `ui.c`：`ui_run()` 里 `ui_theme_init()` 之前调用 `ui_font_init()`，
  用 `ESP_LOGI("UIFONT", ...)` 打印（注意 `UI_DEBUG_LOGS=false`，UI_LOGx 全被编译掉，
  之前 PHASE2 日志一条都没出来就是这个原因）。
- `scr_settings.c`：删掉 `settings_title_font()`，改 `s_ui_font(UI_FONT_TEXT_16)`，
  四个分区标题全部走运行时字体（回退到烘焙字体时打 `UIFONT` 错误）。

关键坑备忘：`CONFIG_LV_USE_FREETYPE` 下 LVGL 的 `font->line_height =
face->size->metrics.height >> 6`，与本字体 hhea 推算一致：12→15、16→21、20→26
（任务书里的 17/23/28 是 PIL ascent+descent 口径，差 2px）。Phase 4 按实测值排。

## Phase 2 上板通过（2026-10-27 晚第二版）

实测（`UIFONT` / `UI` 标签，注意 `UI_DEBUG_LOGS=0` 时 UI_LOGx 是空宏，诊断必须用 ESP_LOGx）：

```
UIFONT: preload 1542592 B in 5330 ms (289 KB/s), psram free=2281120
UIFONT: validate ok: 1542592 B matches meta
UIFONT: 12px created in 60658 us: line_height=16 base_line=4
UIFONT: 16px created in   256 us: line_height=21 base_line=6
UIFONT: 20px created in   333 us: line_height=27 base_line=7
UIFONT: init ok in 7878 ms | internal free=69231 largest=51200 | psram free=2207444
UI: stack[after pages built]: headroom=7900 B, used<=2340 B, stack=10240 B
```

关键结论：
- **IDF 的 `uxTaskGetStackHighWaterMark()` 返回字节数（不是标准 FreeRTOS 的字）**，
  且是"最小剩余"。之前把 headroom 和 used 写反了：实际 used≈2340B、余量 7.9KB，
  ≥4KB 判定线**通过**，栈保持 10240（宏收敛到 ui.h 的 `UI_TASK_STACK_BYTES`，
  app_main 的 `APP_UI_TASK_STACK` 引用它，避免两处不同步）。
- app bin 2,759,216 B（4MB 槽 65.8%），FreeType 净增 ~417KB，预算充足。
- 行高实测 **12px=16 / 16px=21 / 20px=27**（任务书的 17/23/28 是 PIL ascent+descent
  口径，差 2px）。Phase 4 一律按 16/21/27 排。
- 启动代价：ui_font_init 共 7.9s（预载 5.3s + meta 校验 1.0s + 建字体 61ms）。
  SPIFFS 顺序读 289KB/s，瓶颈是 `esp_partition_read` 每 256B 页一次调用（cache 关/开）。
  可选项：CONFIG_SPIFFS_PAGE_SIZE 256→1024（需重烧 storage，预计 ~1.3s）；
  或只留 GB2312 一级（841KB，覆盖减半）；或接受现状。

## 设置页卡死 + wifi_mcast_rx 栈溢出（2026-10-27 晚第三版修复）

现象：点设置页 → `[PHASE2] page 1 first frame: 743897 us` → 紧接着
`A stack overflow in task wifi_mcast_rx`（backtrace CORRUPTED）。

根因链：
1. **是我自己加的 `lv_refr_now(NULL)` 造成的**。它在 UI 循环里把"切页→整屏渲染"
   一次性同步跑完（744ms：SPI 刷屏 ~123ms + 首次字形光栅化），UI_Task 是
   core0/prio10，期间完全不让 CPU。
2. 同核的 `wifi_mcast_rx`（core0/prio6、栈 4096）被饿死，UDP backlog 后
   recvfrom 走错误/日志路径把 4KB 栈顶穿。

修法：
- `ui.c`：删掉循环里的 `lv_refr_now()`；切页耗时改由 display 的
  `LV_EVENT_REFR_READY` 回调统计（零阻塞），回调里顺便采栈峰值，日志 `[REFR]`。
- `ui.h`：`UI_TASK_STACK_BYTES 10240 → 12288`。实测**渲染期**栈用量 6276B
  （构建期只有 2340B），10240 时余量只剩 3964B，不够 4KB 线。
- `sdkconfig`：`CONFIG_LV_CACHE_DEF_SIZE 16384 → 131072`。这是 744ms 的另一半原因：
  LVGL 字形缓存只有 16KB，而 16px A8 字形约 300B/个、一屏约 150 个字 → 约 50 个就满，
  每帧都在重新光栅化。同时 `CONFIG_LV_FREETYPE_CACHE_FT_GLYPH_CNT 128 → 256`。
- `wifi_manager.c`：`WIFI_MCAST_RX_TASK_STACK 4096 → 6144`（破例动了 WiFi 域，
  只为这条已实测的崩溃兜底；若用户不接受可回退）。

待验证：反复切页后 `[REFR] page N done in ? us` 的数值分布（首次 vs 二次），
以及 `stack[after render]` 的余量。

  **默认轴是 100=Thin**，不显式实例化会渲染成最细）、`--layout-features=kern`、
  丢弃 DSIG/BASE、产出 meta 里带 line_height 推导值。
- 产物：`storage/font/ui_font.ttf` **2,122,276 B**，6876 字形，GB2312 6763/6763、
