# 2026-10-29

## 崩溃：Core0 Interrupt WDT timeout，PC 在 i2c_master_isr_handler_default

运行 8453s（≈2.35h）后崩，coredump 已写入 0xFE0000。
- `CONFIG_ESP_INT_WDT_TIMEOUT_MS=3000`（已比默认 300ms 放宽 10 倍）仍触发。
- PC = `i2c_master.c:805`，那行是 `portBASE_TYPE HPTaskAwoken = pdFALSE;`（函数序言），
  说明是**反复重入**（中断风暴），不是卡在循环里。`_xt_lowint1 → shared_intr_isr
  → i2c_master_isr_handler_default`。Core0 同时在 ISR 里打过 UART 日志。
- 两个核都停在 IDLE；崩溃前 15 分钟没有 `[REFR]`，`blk/s 0` / `a2dp_cb=0`
  → **与 UI/字体、音频都无关**，是触摸 I2C 的独立故障。

为什么软件救不回来：level-1 ISR 占用 CPU 时任何任务都跑不了；
`LCD_Touch.c` 的退避策略、以及 IDF 里的 `LOCAL PATCH 2026-10-27`
（`esp_intr_disable/enable` 只护住 `s_i2c_hw_fsm_reset` 那个窗口）都碰不到这条路径。
只剩 INT_WDT abort → 重启。

最可能根因：I2C 电气质量。证据：
- `i2c f=3128 ok=33402` → 累计 **8.5% 读失败**，`last=ESP_ERR_INVALID_RESPONSE`
- `bsp/i2c_driver.c` 只开了 `enable_internal_pullup = true`，**没有外部上拉**；
  ESP32 内部上拉约 45kΩ，100kHz 下上升沿远超 1µs 规范 → NACK/总线拉死
- `I2C_FREQ 100000`、`I2C_TRANS_TIMEOUT_MS 150`、`I2C_DRIVER_SILENCE_BUS_ERRORS=1`
  （后者把 `i2c.master` 日志全关了，所以串口上看不到驱动层细节）

候选处置（未实施，待用户决定，属字体任务范围外）：
A 硬件：SDA/SCL 各加 4.7kΩ 上拉（首选，8.5% 失败率对板级 I2C 不正常）
B 软件：`I2C_FREQ` 100k → 50k，一行回退，用来验证"是否电气问题"最便宜
C 软件：触摸改寄存器级单次传输或 bit-bang，绕开 IDF i2c_master 的 ISR 路径（最彻底）

顺带确认：本次 `up=8453s` 期间无栈溢出、无 `spi_master` 报错 → 前两轮修复站住了。

## 选定方案 C：触摸 I2C 改 GPIO 模拟（bit-bang），彻底删掉 i2c_master（2026-10-29 10:30）

改动文件：
- `components/middlewares/LCD_Touch/LCD_Touch.c`
  - 新增「软件 I2C」一节：`ft_i2c_bus_init / ft_i2c_bus_recover / ft_i2c_start /
    ft_i2c_stop / ft_i2c_write_byte / ft_i2c_read_byte / ft_i2c_read_reg / ft_i2c_write_reg`
  - 引脚沿用 `I2C_SDA_GPIO=32 / I2C_SCL_GPIO=33`（宏在 bsp/i2c_driver.h，避免两处漂移）
  - `GPIO_MODE_INPUT_OUTPUT_OD` + `GPIO_PULLUP_ENABLE`，半周期 10µs ≈ **50kHz**
    （原来 100kHz + 仅内部 45k 上拉，上升沿不合规，这是 8.5% NACK 的根源）
  - 总线恢复（9 个 SCL + STOP）现在安全了，**连续失败每 20 次**执行一次
  - 删除 `Ft6336I2cHandle`，改用 `s_ftI2cReady`
  - `LCD_TOUCH_FT6336G_Init(void)` / `LCD_TOUCH_Init(void)`（签名去掉了总线句柄）
- `components/middlewares/LCD_Touch/LCD_Touch.h`：`LCD_TOUCH_Init(void)`
- `components/App/UI/ui_disp.c`：删掉 `I2c_Init_Bus(...)` 与 `s_i2cBus`，
  `LCD_TOUCH_Init()` 直接调用；文件头注释同步更新

结果：全工程**没有任何 `I2c_Init_Bus` / `I2c_Add_Device` 调用**，
i2c_master 的中断永远不会被注册 → 那条会自锁的中断路径彻底不存在。
`bsp/i2c_driver` 保留（以后别的 I2C 设备还能用），IDF 里那个
`[LOCAL PATCH 2026-10-27]`（给 s_i2c_hw_fsm_reset 套 esp_intr_disable）也随之失效，
但可以留着不碍事。

代价（已核算）：一次 6 字节读 ≈ 9 字节 × 9 bit × 20µs ≈ **1.6ms 忙等**；
`Touch_Task` prio=3 / core0 / 栈 2048，随时可被抢占；40ms 轮询下约 3% CPU。

文档：新增 `docs/03-开发/触摸I2C改为GPIO模拟.md`（崩溃解读、为什么软件救不回、
方案对比、时序实现、代价表、验证判据、回退方法）。

验证判据：心跳里 `i2c f=` 的增速应显著低于改造前（2.35h 累计 3128 次失败）；
连续跑 >3 小时不再出现 `Interrupt wdt timeout on CPU0`。

## 方案 C 上板验证通过；开机 task_wdt 判定为噪声（2026-10-29 11:00）

实测：
```
UIFONT: preload 2122276 B in 3674 ms (578 KB/s)      ← 之前 5625ms/377KB/s
UIFONT: 12px line_height=14  16px=19  20px=24        ← 与 hhea 推导逐像素一致
UIFONT: init ok in 6636 ms | internal free=43511 largest=23552 | psram free=1602908
[heap] after ui_init: int free=26111 largest=23552   ← 32KB 栈的代价（原 54607）
E task_wdt: IDLE0 ... CPU 0: wifi  (ppTask, ieee80211_output_process)
```
用户反馈：**触摸正常、比之前更流畅** → 软件 I2C（50kHz，半周期 10µs）时序可用。

task_wdt 定性（重要，别再当故障查）：
- `CONFIG_ESP_TASK_WDT_PANIC` **未开** → 只打印回溯，**不重启、不丢功能**。
- 触发瞬间 CPU0 跑的是 `wifi/ppTask`（prio 23），回溯全是 `ieee80211_output_process`
  → 不是 UI_Task 在跑，是**关联期 WiFi TX burst 把 IDLE0 排到队尾**，
  叠加本任务开机 9s 的工作量（字体 6.6s + 建页 2.5s）。
- `CONFIG_FREERTOS_HZ=1000` → vTaskDelay(1) 只有 1ms，WiFi burst 常未结束，
  IDLE0 仍轮不到，所以旧的 1ms 让出等于没让。

本轮微调（只为压这条告警，不改任何逻辑）：
- `ui_font.c`：FONT_PRELOAD_YIELD_MS=2（原 1），预载 +65ms；
  `ui_font_init` 在 validate 之后（meta 读实测 ~1.1s）插一次 2ms 让出。
- `ui.c ui_pages_create`：四页之间各 vTaskDelay(2)，共 +8ms。
代价合计约 +75ms 开机；若告警仍在，属 WiFi 侧，处理选项只有
①接受（本来就不 panic）②`CONFIG_ESP_TASK_WDT_TIMEOUT_S` 5→15。

SPIFFS 提速已到顶：`SPIFFS_PAGE_SIZE` Kconfig range 是 **256..1024**，当前已是 1024，
没有 4096 这一档，578KB/s 就是这个设计的上限（瓶颈是每 1KB 一次
`esp_partition_read` 的 cache 关/开）。

## Phase 6 收尾 + 任务完成（2026-10-29 11:10）

最终实测（2.12MB Noto、16 行窗口、-Os）：
```
[REFR] page 0 total 363672 us | flush 101009 us / 15 win | draw 252307 us / 14 win (avg 18021, max 41965)
```
对比 8 行 + -Og 的 599710 us（flush 135071/30, draw 464639）→ **599→364ms，降 39%**。
线性模型（两组数据解出）：`draw ≈ 14.7ms × 窗口数 + 0.41µs × 像素数`，
即 252ms 里约 220ms 是**每窗口固定开销**，纯像素只占 31ms。
再降到 10 段（24 行）预计 ~280ms，但要 15KB 内部 RAM（现余 26KB，临界）→ 暂不做。

音频隔离测试：不碰屏播放 3 分钟 **无滋滋/啵啵** → 之前的杂音确认由切页 500ms 阻塞引起。
`i2c f=0 ok=0`：i2c_driver 计数器不再被触碰（触摸已完全脱离 i2c_master）。

确认 -Os 真生效：lvgl `lv_obj_style.c` 编译命令 `-Og ... -Os`（后者覆盖），
freetype 50 个文件同样 `-Os`。app bin **2,588,192 B = 61.7% of 4MB 槽**。

收尾改动：
1. 根 `CMakeLists.txt`：诊断开关 `UI_STACK_USAGE`(默认 ON) → **`UI_DIAG_STACK_USAGE`(默认 OFF)**。
   换名是因为旧键已被 CMakeCache 缓存成 ON，改默认值不生效（这个坑已经踩过两次）。
   代价：下次构建因编译命令变化会**全量重编**一次。
2. `main/app_main.c` 心跳加 `int=空闲/最大连续块`（内部 DRAM）。用户看到
   `heap=1529708` 以为内存很宽裕，其实那是 `esp_get_free_heap_size()`，
   在 `SPIRAM_USE_MALLOC + ALWAYSINTERNAL=0` 下把 PSRAM 算进去了；内部其实只有 26~43KB。
3. 新增 `docs/03-开发/FreeType字体接入-行高适配与内存实测报告.md`（8 节：结论表、
   加载链路、行高口径纠正、实测数据、10 条坑、遗留项、验收清单、相关文档）。

字体任务到此完成。开机那条 `task_wdt: IDLE0` 仍可能出现（不 panic、不影响功能），
原因是 WiFi 关联期 ppTask(prio23) 的 TX burst 把 IDLE0 排在队尾，叠加开机 9s 负载。
