# ESP8266 网络学习路线 —— 从 IP 到 MQTT，自下而上

> 环境：ESP-01S（**1MB** flash）· ESP8266_RTOS_SDK v3.4（`v3.4-115-g858c7c2e`）
>
> 这份路线只依据 `main/` 里的源码和 [README.md](../README.md) 写。
> 每一条知识点都挂回本项目里一个具体的文件或符号 —— 学它不是为考试，
> 是为了看懂自己写的那几行。
>
> 怎么用：§0 先把边界划出来（哪几层跳过、为什么跳过）；§1–§4 自下而上四站；
> §5 把四站串成一次真实的排查；§6 一页速查。

---

## 0. 边界怎么划

判据一句话：

> **学那些会从下层漏上来、改变你代码写法的东西；
> 不学那些被封装得很干净、你一行都碰不到的。**

按这条判据过一遍，边界自己就出来了：

| 层 | 学吗 | 套用判据 | 本项目里的落点 |
| --- | --- | --- | --- |
| 物理层 | **不学** | 在 lwIP 下面，是 SDK 和硬件的地盘 | 无 |
| 链路层 | **只学它漏出来的那一面** | 802.11 的帧格式、CSMA/CA 你碰不到；但它**断开的原因码**会漏上来 | `wifi_sta.c` |
| 网络层（IP） | **重点，但只学会漏上来的五件** | 路由协议是路由器的事；地址怎么分配是你的事 | `tcp_client.c` · `udp_client.c` · `mqtt_link.c` |
| 传输层 | **重点** | 重传、拥塞控制在 lwIP 里，你写不了也不用管；接口和失败模式全是你的 | `tcp_client.c` · `udp_client.c` |
| 应用层 | **重点** | 这一层就是你写的代码 | `cmd.c` · `link.c` · `ap_prov.c` |

**所以"自下而上"的起点选在 IP 层，不是物理层。** 再往下不是"学得深不深"的问题，
是那些代码根本不在你的仓库里。

---

## 1. 第一站：IP 层

IP 层只回答一个问题：**这段数据该往哪儿送？**

剩下全是它的配套：地址谁给的（DHCP）、对方的 MAC 怎么找（ARP）、
一次能装多少（MTU）、名字怎么变成地址（DNS）。

下面五件，是**会漏到应用层、改变你代码写法**的全部。

### 1.1 地址、子网掩码、网关 —— 决定"谁必须知道谁"

**机制**：IPv4 地址是 32 位，写成 4 个十进制数（如 `192.168.137.1`）。
子网掩码（如 `255.255.255.0`）决定**前多少位是"网段号"**。
每发一个包之前，协议栈先做一次比较：

```text
(我的 IP & 掩码) == (对方 IP & 掩码) ?
    相等  →  同一个网段，直接发（接下来靠 ARP 找 MAC，见 §1.3）
    不等  →  不同网段，扔给网关，由网关去转
```

这就是"网段"这个词的意义：**它决定了你的包是直接到，还是要绕一圈。**

**它怎么漏上来的**：因为它决定了**谁必须知道谁**。

[README.md](../README.md) 里那句话说的是同一件事：

> 节点不等着被"找到"—— 它主动连出去，所以主节点的地址是编译期写死的常量，
> 运行期不用谁去查 IP。

代码里就是两行常量：

| 文件 | 符号 | 写的是什么 |
| --- | --- | --- |
| `tcp_client.c` | `TCP_SERVER_IP` | 裸 IP |
| `udp_client.c` | `UDP_SERVER_IP` | 裸 IP |
| `mqtt_link.c` | `MQTT_BROKER_URI` | 域名（`mqtt://…`） |

**"编译期写死的常量"能成立，前提是那个地址不会变。**
反过来说：如果主节点的地址也变成 DHCP 发的（比如两个节点都挂在路由器上，
谁连谁就反过来了），那这行 `#define` 就废了 —— 主节点一重启、地址一变，
从节点就得重新烧录。

> ### 为什么这是"主动连出去"换来的最大好处
>
> 从节点**自己**的地址是 DHCP 给的、随时可能变 —— 但**没有人需要知道它**。
> 因为永远是它去连别人，不是别人来找它。
>
> **一个地址只要没人需要知道，它变不变就无所谓。**
>
> 这句话是 §1.2 的伏笔，也是整个项目拓扑的地基。

### 1.2 DHCP —— 决定"谁的地址是写死的"

**机制**：DHCP 是开机时往网段里喊一声"有人吗，给我个地址"，服务器租一个给你，
**而且有租期**。所以设备从来不"拥有"一个地址，只是"租着"。

**它怎么漏上来的**：它决定了 `wifi_sta.c` 里"到底算不算连上了"的判据。

`wifi_sta.h` 里 `wifi_sta_wait_ip()` 的注释写得很直接：

> "连上了"的标志是【拿到 IP】，不是"关联上 AP"：关联成功时还没有 IP，
> 那个阶段建 socket 一样是白建。

于是整条启动链变成（`main.c` 的 `app_main()`）：

```text
wifi_sta_init()        异步发起连接，返回时【还没连上】
wifi_sta_wait_ip()     ← 阻塞在这里，等的就是 DHCP 那一步
link_init(LINK_TCP)    有 IP 了才建 socket、才去连 broker
```

**为什么非等不可**：

- `mqtt_link.c` 的 broker 是**域名**，没有 IP 就没有 DNS（§1.5）
- `tcp_client.c` / `udp_client.c` 的 `connect()` / `sendto()` 没有 IP 就是
  `errno = 101`（`ENETUNREACH`，网络不可达）

> **一个反直觉的点**：WiFi 有**两种**"成功"，只认后一种 ——
>
> | 事件 | 意思 | 算连上了吗 |
> | --- | --- | --- |
> | `WIFI_EVENT_STA_CONNECTED` | 和 AP 说上话了 | **不算** |
> | `IP_EVENT_STA_GOT_IP` | DHCP 把地址给你了 | **算** |
>
> 前者只说明你进了这栋楼，还不知道自己住哪间房。

### 1.3 ARP —— 发包前得先问到 MAC

**机制**：IP 是"逻辑地址"，网卡真正认的是 MAC（6 字节）。同一个网段里发包之前，
必须先问一句"谁是 `192.168.137.1`？"，对方答"我是，我的 MAC 是 xx:xx:…"。
这就是 ARP。**ARP 表有有效期**，过期要重问。

**它怎么漏上来的**：它决定了 UDP 那边**必须先发一包**。

`udp_client.c` 里 `UDP_ANNOUNCE_MS` 上面那段注释说的就是这件事：

> TCP 里主节点靠 `accept()` 就知道谁连上来了；UDP 没有连接，
> 主节点对我们的存在【一无所知】，只能靠我们主动发一包过去，
> 它才能从源地址学到"该往哪儿回"。

往下再挖一层就是 ARP：**你不发那包，对方连你的 MAC 都没有**，
回包根本组不出来。

那为什么不能只发一次？同一段注释也答了：

> 主节点一重启，它记的地址就没了 —— 而它重启时我们这个从节点是【收不到任何通知】的
> （UDP 无连接，也无从感知对端重启）。没有周期心跳的话，从节点会一直以为
> 链路好好的，主节点却再也找不到它，直到从节点自己也重启一次。

于是有了代码里的做法：每 `UDP_ANNOUNCE_MS`（30 秒）调一次 `udp_announce()`，
发出去的内容是 `"hello from ESP-01S\r\n"`。

> ### 为什么 UDP 有这个问题、TCP 没有
>
> TCP 有 `connect()`，连接是**双方都记着的状态**。你连着，对方就知道你在。
>
> UDP 没有连接，对端手里只是一条"上次从哪儿收到过包"的记录 ——
> 那是**推断出来的**，不是约定出来的。推断出来的东西当然会过期。
>
> **一句话：TCP 的"对方在不在"是记着的，UDP 的是猜的。猜的就得反复确认。**

### 1.4 MTU —— 一次 `send()` 不保证一次 `recv()`

**机制**：链路层一帧能装的数据有上限（WiFi 上一般 1500 字节，
减去 IP 头和 TCP 头，留给应用的大约 1460）。超过就分片。

但**日常更常见的不是分片，是"字节流本来就没有边界"**：

```text
你 send(100 字节)  →  对方 recv() 可能拿到 30 字节，下一次再拿到 70 字节
```

**它怎么漏上来的**：这是 `cmd.c` 里那整套"攒字节"逻辑存在的**唯一理由**。

```text
cmd_on_rx_from(src, data, len)   ← len 是这一批到手的字节数，不保证是一条完整命令
  └─ cmd_on_rx(src, data, len)   ← 追加进 s_rx[src] 那块缓冲区
       └─ while (cmd_try_one(src))  ← 从缓冲区里找完整命令，可能一条都找不着
```

**"开灯"这两个字可能分两次到达** —— 第一次只到了"开"。缓冲区就是为这种时候准备的。
（`cmd.c` 里 `CMD_BUF_SIZE` 那个 64 字节的存在意义，也是它。）

> ⚠️ 这一条和"TCP 是可靠的"**不矛盾**。TCP 保证的是**字节按顺序、不丢不重地到达**，
> 它**不保证**"你发几次我就收几次"。这是两个完全不同的承诺 ——
> 把可靠当成"有边界"，是初学者最常踩的一个坑。

### 1.5 DNS —— 域名得有人翻译

**机制**：域名（`mqtt.bemfa.com`）要先解析成 IP 才能连。
DNS 服务器的地址通常也是 DHCP 一起发下来的。

**它怎么漏上来的**：它是 `mqtt_link.c` 和另外两个传输模块**唯一的一处结构性差别**。

| 文件 | 对端写的是什么 | 要 DNS 吗 | 结果 |
| --- | --- | --- | --- |
| `tcp_client.c` | `TCP_SERVER_IP` = 裸 IP | **不要** | 只要那个地址在网段里可达就行 |
| `udp_client.c` | `UDP_SERVER_IP` = 裸 IP | **不要** | 同上 |
| `mqtt_link.c` | `MQTT_BROKER_URI` = 域名 | **要** | 热点必须下发 DNS 服务器 |

`main.c` 里把结论写死了：

> MQTT 还有个门槛：broker 是域名，热点得会下发 DNS —— ESP32 自己开的 SoftAP
> 没有 DNS，那条路走不通，得用手机热点或路由器。

**这就是"MQTT 需要什么热点"这个问题的完整答案**：
主链路写的是裸 IP，所以它对热点只有一个要求 —— 那个地址能通；
MQTT 写的是域名，所以它对热点多一个要求 —— **得有人能把这个名字翻译成地址**。

## 2. 第二站：传输层

IP 层负责"送到哪台机器"，传输层负责"送到那台机器的哪个程序，以及要不要保证送到"。

### 2.1 socket —— 一次对话的句柄

`socket()` 返回一个 `int`。它**不是"网络"，是"一次对话的句柄"** ——
后面所有 `send` / `recv` / `close` 都对着这个整数做。

`tcp_client.c` 和 `udp_client.c` 用的是同一套 BSD 风格 API，头文件都是：

```c
#include "lwip/sockets.h"
```

区别只在下面几节。

### 2.2 端口 —— 一台设备上怎么区分不同的对话

一台设备上同时开着好几条对话（配网页、MQTT、调试口），**靠端口号区分**。
端口是 16 位：`0–65535`，1024 以下是系统保留，往上的随便用。

本项目的两个端口：

| 文件 | 符号 | 值 |
| --- | --- | --- |
| `tcp_client.c` | `TCP_SERVER_PORT` | `8086` |
| `udp_client.c` | `UDP_PORT` | `8087` |

UDP 那边还多一步 `bind()`，把**本机端口**也固定成 `UDP_PORT`
（`local.sin_addr.s_addr = INADDR_ANY`，意思是"收本机所有网卡上的这个端口"）。
`udp_client.c` 里解释了为什么非 bind 不可：

> 不 bind 也行（lwIP 会在第一次 `sendto` 时随便挑一个临时端口），
> 但那样主节点就只能记"从哪个端口来的"，端口一变回包就发错地方。
> 固定住之后，主节点的回包规则是死的：回 `源IP:UDP_PORT`。

> ### 为什么 TCP 不用 bind 而 UDP 要
>
> TCP 客户端 `connect()` 的时候，协议栈**顺手就给你定了一个本地端口** ——
> 因为 `connect()` 本来就是在建立一条"双方都记着"的连接，它得知道回包往哪个端口送。
>
> UDP 没有 `connect()`，就没有那个"顺手"。本地端口得**你自己说**，
> 不然每次发都是个新的临时端口，对面的回包规则就无从写起。

### 2.3 TCP：六步

`tcp_client.c` 的骨架：

```text
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)
  → setsockopt(SO_RCVTIMEO)      ← 给 recv() 设超时，不然它会永远阻塞
  → connect()                    ← 这一步之后，协议栈替你维护"可靠、有序"
  → send() / recv()
  → close()
```

`SO_RCVTIMEO` 那一步**不是可选的**，`udp_client.c` 里把理由写得很清楚：

> 没有它的话 `recvfrom()` 会永远阻塞，这个任务既看不到 `s_running` 变成 false，
> 也没机会发心跳。

**这是 RTOS 上写网络代码和 PC 上最大的不同**：你的收发在一个任务里，
阻塞住的不只是这次收发，是**整个任务的循环** —— 包括它该做的所有别的事
（看标志位、发心跳、重连）。PC 上多开一个线程就绕过去了，这里不行。

### 2.4 UDP：五步，以及为什么必须有心跳

```text
socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)
  → setsockopt(SO_RCVTIMEO)
  → bind()                       ← 见 §2.2
  → sendto() / recvfrom()
  → close()
```

比 TCP 少了 `connect()`，多了 `bind()`。心跳的理由见 §1.3。

### 2.5 errno —— 失败模式才是重点

网络代码里，**成功路径只有一条，失败路径有十几种**。所以学 socket 编程，
一半的工夫花在认这几个数字上（值取自 lwIP 的 `errno.h`）：

| errno | 名字 | 人话 | 通常是什么情况 |
| --- | --- | --- | --- |
| 11 | `EAGAIN` / `EWOULDBLOCK` | 现在没数据 | **不是错误** —— `SO_RCVTIMEO` 超时就是这个 |
| 98 | `EADDRINUSE` | 端口被占 | UDP 那个 `bind()` 失败 |
| 101 | `ENETUNREACH` | 没有网络 | 还没拿到 IP 就建 socket |
| 104 | `ECONNRESET` | 被对端掐断 | 对方进程崩了 |
| 110 | `ETIMEDOUT` | 超时 | 对方不在（地址对，但没人应答） |
| 111 | `ECONNREFUSED` | 对方拒绝 | 服务端没在监听那个端口 |
| 113 | `EHOSTUNREACH` | 主机不可达 | 不在同一网段，又没有网关 |

**11 号要单独记住**：它是"超时"，是**正常现象**，不是错误。
`tcp_client.c` 和 `udp_client.c` 里都专门有一句

```c
if (errno == EWOULDBLOCK || errno == EAGAIN) { … }
```

把它和真错误分开。混在一起的话，链路会每 5 秒（`TCP_RECV_TIMEOUT_S` /
`UDP_RECV_TIMEOUT_S`）自己断一次。

> `EWOULDBLOCK` 和 `EAGAIN` 是**同一个值**，lwIP 里就是这么定义的
> （`#define EWOULDBLOCK EAGAIN`）。两个都写一遍是移植习惯 ——
> 在别的系统上它们曾经不同。

## 3. 第三站：应用层

**传输层往上是应用层 —— 也就是你真正在写的那一层。**

### 3.1 边界在哪

```text
        ┌──────────────────────────────────────┐
        │  应用层                               │  ← 你的代码从这里开始
        │  cmd.c        命令解析                │
        │  link.c       选路                    │
        │  ap_prov.c    网页配网（HTTP）        │
        │  mqtt_link.c  "发到哪个主题"的那部分   │
        ├──────────────────────────────────────┤
        │  socket API   ← 分界线                │
        ├──────────────────────────────────────┤
        │  传输层 / 网络层 / 链路层 / 物理层      │  ← lwIP 和 SDK 的地盘
        └──────────────────────────────────────┘
```

**为什么这条线画在 socket API**：因为它是 SDK 暴露给你的最下面一层。
线以下的代码不在你的仓库里 —— 出问题你能做的只有换 SDK 或报 bug，改不了。

> ⚠️ `mqtt_link.c` 是**横跨这条线**的：它调 `esp_mqtt_client_*`（应用层），
> 而那些函数底下走的是 lwIP 的 `send()`（传输层）。
> 这也是为什么它比另外两个传输模块"厚" ——
> 它把一整个应用层协议装进了一个模块里。

### 3.2 本项目用到的两个应用层协议

| 协议 | 在哪 | 干什么 |
| --- | --- | --- |
| **HTTP** | `ap_prov.c` | 配网时那个网页 —— 手机浏览器发 HTTP 请求，板子当服务器 |
| **MQTT** | `mqtt_link.c` | 连 broker、订阅 `MQTT_TOPIC`、发布到 `/up` 和 `/set` |

`ap_prov.c` 里那条 `GET /`（表单页）+ `POST /save`（保存），
就是一套**完整的、最小的 HTTP 服务** —— 用 `esp_http_server` 那套
（`httpd_req_t`、`httpd_resp_send`、`HTTPD_200` / `HTTPD_400`）搭起来的。

> 顺带一个应用层才知道的细节，`ap_prov.c` 里写了：
> **HTTP 正文不保证以 `'\0'` 结尾，只能按长度收**。
> 这和 §1.4 是同一件事的两个面孔 —— 字节流就是字节流。

**HTTP 和 MQTT 是同层的**，都是应用层协议，只是形状完全不同：

| | HTTP | MQTT |
| --- | --- | --- |
| 形状 | 请求 → 响应，一问一答 | 发布 / 订阅，经 broker 中转 |
| 谁主动 | **客户端**（浏览器） | **双方都可以**（靠 broker 推） |
| 连接 | 短，答完就断 | 长，一直挂着，靠心跳保鲜 |
| 适合 | 人主动去点的地方 | 设备上报 / 被远程下发 |

> ### 为什么设备用 MQTT 而不是轮询 HTTP
>
> HTTP 是"我问你答"，所以设备想知道有没有新命令，只能**自己不停地去问** ——
> 既要一直发请求，又有延迟（**问的间隔就是最大延迟**）。
>
> MQTT 是 **broker 推给你**：连接一直挂着，有消息立刻到。
> 代价是这个连接必须**保活** —— 这就是 `MQTT_KEEPALIVE_S` 和那一整套重连逻辑的来源。
>
> 一句话：**HTTP 的代价花在带宽和延迟上，MQTT 的代价花在"连接得一直保着"上。**

### 3.3 应用层的重点不是协议，是"你写了什么"

`cmd.c` 里那张命令表、`link.c` 里的选路、`relay.c` 里的 GPIO0 ——
这些**都不是标准协议**，但它们在应用层，而且是这一层最重要的工作。

协议只管"怎么把字节送过去"，**送过去之后干什么，是你定义的**：

```text
mqtt_link.c  : 把 broker 推来的字节交给回调      ← 协议的事
link.c       : 决定回执发回哪条链路              ← 你的事
cmd.c        : 把那些字节解析成"开灯"             ← 你的事
relay.c      : 拉高 GPIO0                        ← 你的事
```

---

## 4. 链路层：只学它漏出来的那一面

802.11 的帧格式、CSMA/CA、信道扫描 —— **跳过**。
你在 `wifi_sta.c` 里碰到的链路层只有两样东西：

**① 事件**：`WIFI_EVENT_STA_CONNECTED`（关联上）和 `IP_EVENT_STA_GOT_IP`（拿到 IP）。
记住"关联 ≠ 连上"就够了（见 §1.2）。

**② 断开原因码 `reason`** —— 这是链路层唯一真正漏上来的东西，
**它告诉你为什么断的，而你只能靠它判断该不该重连、该不该换凭据**。

`wifi_sta.c` 里把最常撞见的两个列了出来：

| reason | 意思 | 你该做什么 |
| --- | --- | --- |
| `201` | 找不到这个 SSID | 检查热点名是不是写错，**或者热点开在 5GHz 上**（ESP8266 只认 2.4GHz） |
| `15` / `202` / `204` | 密码不对 | 检查密码 |

整个重连逻辑就是围着它转的：连不上就重试，重试 `WIFI_RETRY_BEFORE_AP`（30）次
还不行，就交给 `ap_prov.c` 去开热点出网页。

> **为什么这一层不用学协议**：因为协议失败的原因是**有限且已经被编号的**。
> 你不需要知道帧是怎么调制的，只需要知道"201 该查名字、15 该查密码"——
> **这就是全部要学的东西。**
>
> 而且 `wifi_sta.c` 里还有一条链路层带来的实时性约束：
> 断开事件是在**默认事件循环**的回调里处理的，那里**不能 `vTaskDelay`** ——
> 睡一下就把整个事件循环卡住了。所以它选择直接 `esp_wifi_connect()`，
> 让重连自己去花那几秒扫描时间。

## 5. 把四站串起来：一次排查

现象：**串口说 WiFi 连上了，但 MQTT 一直连不上。**

自下往上逐层排除，每一层都有唯一的判据：

| 顺序 | 层 | 问什么 | 怎么答 | 落点 |
| --- | --- | --- | --- | --- |
| 1 | 链路层 | 关联上了吗？ | 看 `reason` 码 | `wifi_sta.c` 的 `[wifi] 第 N 次失败，reason=…` |
| 2 | 网络层 | 拿到 IP 了吗？ | `wifi_sta_wait_ip()` 返回了没有 | 只有它返回了才轮到后面 |
| 3 | 网络层 | 名字解析得了吗？ | 热点有没有下发 DNS 服务器 | `MQTT_BROKER_URI` 是域名 |
| 4 | 网络层 | 出得去吗？ | 主链路通不通（它写的是裸 IP，只考局域网） | `TCP_SERVER_IP` |
| 5 | 应用层 | 连上 broker 了吗？ | `MQTT_EVENT_CONNECTED` / `MQTT_EVENT_ERROR` | `mqtt_link.c` |
| 6 | 应用层 | 订阅上了吗？ | `MQTT_EVENT_SUBSCRIBED` | clean session，每次重连都要重订 |

**这个顺序不能跳。** 第 3 步不通的时候，第 5 步的日志只会告诉你"连接失败" ——
它不知道是名字没解析出来、还是路由不通。**下层的错，上层看不见。**

> 这就是分层排查法的全部逻辑：
> **每一层只能看到自己这一层和它下面那一层的接口。**
> 从最下面开始，找出**第一个**"不通"的层，那就是问题所在 ——
> 上面的层不用再看了，它们只是被拖累的。

⚠️ 还有一个**最容易被跳过**的检查：**第 3 步和第 4 步之间，别忘了"这台设备到底连上哪个网"**。
`TCP_SERVER_IP` 和 `UDP_SERVER_IP` 是写死的，热点一换（比如从电脑热点换成
ESP32 自己开的），那个地址多半就不再可达了 —— 而这时 WiFi 日志一切正常，
只有 `connect()` 会给你一个 `errno = 113`。

## 6. 一页速查

```text
边界：
  学"会从下层漏上来、改变你代码写法"的
  不学"被封装得很干净、你一行都碰不到"的
  → 起点选在 IP 层，不是物理层

IP 层（只学会漏上来的五件）：
  地址 / 掩码 / 网关   (我的IP & 掩码)==(对方IP & 掩码)?  相等直接发，不等走网关
                      → 决定"谁必须知道谁"：主节点地址写死，前提是它不变
  DHCP                → "连上了" = 拿到 IP，不是关联上 AP
                      → 只认 IP_EVENT_STA_GOT_IP，不认 WIFI_EVENT_STA_CONNECTED
  ARP                 → 你不先发一包，对方连你的 MAC 都没有（UDP 心跳的根）
  MTU                 → 一次 send() 不保证一次 recv()（cmd.c 攒字节的根）
  DNS                 → 裸 IP 不要 DNS，域名要；热点必须下发 DNS 服务器

传输层：
  socket() 返回的是"一次对话的句柄"，不是网络
  端口 16 位，1024 以下保留
     TCP 客户端 connect 时自动定本地端口；UDP 没有 connect，要自己 bind
  TCP 六步：socket → setsockopt(SO_RCVTIMEO) → connect → send/recv → close
  UDP 五步：socket → setsockopt → bind → sendto/recvfrom → close
  SO_RCVTIMEO 必须有 —— 不然整个任务永远阻塞在这一句上
  errno: 11 超时(不是错误!) · 98 端口被占 · 101 没网 · 104 被掐断
         110 超时(对方不在) · 111 对方拒绝 · 113 主机不可达

应用层：
  HTTP(ap_prov.c 的配网页) vs MQTT(mqtt_link.c)：一问一答 vs 发布订阅
  HTTP 短连接靠"人主动来问"；MQTT 长连接靠"心跳保活"
  协议只管"怎么把字节送过去"，"送过去干什么"是你定义的（cmd.c / link.c / relay.c）

链路层（只学漏出来的那一面）：
  关联 ≠ 连上
  reason 201 = 名字不对（或 5GHz）· 15/202/204 = 密码不对
  断开事件在事件循环回调里，那里不能 vTaskDelay

排查顺序：链路 → IP → DNS → 外网 → broker → 订阅
  下层的错，上层看不见 —— 从最下面找【第一个】不通的
```
