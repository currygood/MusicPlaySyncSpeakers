# ESP8266 分区表笔记

> 环境：ESP-01S（**1MB** flash）· ESP8266_RTOS_SDK v3.4（`v3.4-115-g858c7c2e`）
>
> 本笔记里的结论都在本仓库实测或查源码验证过，验证方法见 §12，你可以自己复现。
>
> ⚠️ **这份笔记是按一次真实事故重写的。** 之前整篇建立在"ESP-01S 是 2MB"这个错误前提上，
> 而那个前提把板子擦成了砖。事故始末见 §2 末尾——**先看那段，再看布局图**。

## 1. 分区表是什么

flash 在硬件层面是一条**扁平的地址线**：`0x000000` 到 `0x0FFFFF`，就这么长。
芯片分不出哪一段是代码、哪一段是数据。

分区表就是一张**地图**，告诉 bootloader 和程序：

- 哪一段**是什么**
- **在哪**（Offset）
- **多大**（Size）

它自己放在 flash 的**固定位置** `0x8000`（由 `CONFIG_PARTITION_TABLE_OFFSET` 决定）。

> **为什么位置要固定？**
> 因为 bootloader 上电时**还不知道地图在哪**。这是个鸡生蛋问题——
> 只能硬编码一个约定位置，让所有人去那儿找。

> **为什么要有这张表？**
> 也可以不用分区表，把地址硬写进代码。但那样一旦要挪布局，所有代码都得改。
> 分区表把**"东西放在哪"**和**"代码怎么用"**解耦了（详见 §5）。

## 2. 1MB 长什么样

```
0x000000 ┌──────────────────────────┐
         │  bootloader      32 KiB  │  不在分区表里，固定在这
0x008000 ├──────────────────────────┤
         │  分区表自己       4 KiB  │  上电第一件事就来这儿读地图
0x009000 ├──────────────────────────┤
         │                          │
         │  nvs             24 KiB  │  键值存储
         │                          │
0x00F000 ├──────────────────────────┤
         │  phy_init         4 KiB  │
0x010000 ├──────────────────────────┤
         │                          │
         │                          │
         │  factory        960 KiB  │  ← 唯一的 app 槽，固件烧这儿
         │                          │
         │                          │
0x100000 └──────────────────────────┘  1MB 到头
```

**前 64 KiB 为什么空着？**

```
0x0000 – 0x7FFF   bootloader（32 KiB）
0x8000 – 0x8FFF   分区表自己（3 KiB 内容 + 余量）
0x9000 →          你的分区从这里开始
```

这两块是 ROM 和 SDK 约定的**禁区**，不能动。

### 对照：出事的那个 2MB 布局

这是本项目**曾经**用的表，也是把板子擦成砖的那张：

```
0x000000 ┌──────────────────────────┐
0x008000 │  分区表           4 KiB  │
0x009000 │  nvs             16 KiB  │
0x00D000 │  otadata          8 KiB  │
0x00F000 │  phy_init         4 KiB  │
0x010000 │  ota_0          992 KiB  │
0x108000 ├──────────────────────────┤  ← 这里开始就不存在了
0x200000 └──────────────────────────┘  2MB 到头（芯片根本没有）
```

`ota_1` 排在 `0x108000`。可是 1MB 的芯片地址只到 `0x0FFFFF`。

### 事故复盘：为什么一个"填错数字"能擦掉半颗芯片

这是本笔记最该记住的一段。

#### 第一步：SDK 从来没探测过 flash 大小

同一个 `CONFIG_SPI_FLASH_SIZE` 有两个去处：

```c
/* spi_flash.c 里给 g_rom_flashchip 赋值那段 —— 结构体初始化，chip_size 是第二个字段 */
esp_rom_spiflash_chip_t g_rom_flashchip = {
    0x1640ef,
    CONFIG_SPI_FLASH_SIZE,   /* ← chip_size：把配置直接抄过来 */
    64 * 1024,
    4 * 1024,
    256,
    0xffff
};
```

```c
/* spi_flash.c —— 名字叫"获取芯片大小" */
size_t spi_flash_get_chip_size()
{
    return g_rom_flashchip.chip_size;   /* ← 还是那个配置值 */
}
```

**函数名骗人。** `get_chip_size()` 不 get 任何东西。
（`port.c` 里的 `MBPortSetMode()` 还有一份同样的赋值。）

启动日志里那行也是同一个来源，绕了个远路而已：

```
sdkconfig: CONFIG_ESPTOOLPY_FLASHSIZE_2MB=y
    ↓ 构建系统生成
build/flasher_args.json:  "flash_size": "2MB"
    ↓ make flash 把它作为参数交给 esptool
esptool --flash_size 2MB
    ↓ esptool 把这个值写进 .bin 的镜像头
esp_image_header_t.spi_size        (esp_image_format.h，一个 4 bit 字段)
    ↓ bootloader 从 flash 把镜像头读出来
bootloader_init.c 里的 print_flash_info()   ESP_LOGI(TAG, "SPI Flash Size : %s", str)
```

**从头到尾，芯片没被问过一次。** 那行日志是配置照镜子。

#### 第二步：边界检查拿错误证明错误

```c
/* spi_flash.c 里的 spi_flash_erase_sector() —— 擦除前的边界检查 */
if (sec >= (g_rom_flashchip.chip_size / g_rom_flashchip.sector_size)) {
    return ESP_ERR_FLASH_OP_FAIL;
}
```

**被检查的对象，和被检查用的那把尺子，是同一个值。** 配置写错，这个检查就形同虚设。

#### 第三步：1MB 芯片只解码 20 根地址线

这是硬件行为，不是软件能拦住的：

```
0x108000 & 0xFFFFF = 0x008000
    ↑ 第 20 位被芯片直接丢弃 —— 这叫地址回绕（alias），不叫越界
```

`ota_1` 的擦除请求，实际落到了**分区表自己头上**。

#### 第四步：连锁毁灭

```
擦 149 个扇区（149 × 4096 = 610304 字节），从 0x008000 一路往上
              ↓
0x008000  分区表        ← 地图没了
0x009000  nvs           ← 配置没了
0x00D000  otadata       ← 启动选择没了
0x00F000  phy_init      ← 射频校准没了
0x010000  正在运行的固件 ← 被啃掉 577536 / 606544 字节 = 95.2%
```

> 这里那个 606544 是**出事当时**那块固件的大小。别拿它跟别处的数字对 ——
> 现在这块是 496448 字节（`ESP8266开发流程.md` §9.9 记了为什么拿今天的数
> 就已经能证明"双槽放不下"）。

> **为什么连一句报错都没有？**
> 因为负责打印的那段代码，自己也在被擦的范围内。
> 芯片先把 `printf` 所在的 flash 擦成 0xFF，再继续调用它——于是串口安静地死掉。
> 这不是"日志看不懂"，是**根本没有机会打印**。

#### 正确的做法

问芯片本身，而不是问配置：

```bash
python $IDF_PATH/components/esptool_py/esptool/esptool.py --port COM8 flash_id
```

```text
Manufacturer: 68
Device: 4014           ← esptool 发 JEDEC RDID (0x9F)，芯片当场回答
Detected flash size: 1MB
```

`Device` 的后两位就是容量：`14`=1MB，`15`=2MB，`16`=4MB，`17`=8MB，`18`=16MB。

> **一句话记住**：凡是"SDK 打印出来告诉你"的硬件参数，
> 先问一句它是**问来的**还是**抄配置抄来的**。

## 3. 每个分区是干什么的

本仓库的表里有三行：

| 名字 | 类型 | 干什么 | 谁在用它 |
| --- | --- | --- | --- |
| `nvs` | `data` / `nvs` | **键值存储**，像芯片自带的小 EEPROM | WiFi 驱动存射频数据；应用用命名空间 `app_cfg` 存 SSID/密码 |
| `phy_init` | `data` / `phy` | **WiFi 射频初始化/校准数据** | 每颗芯片射频特性有微小差异，校准一次存这儿，免得每次开机重算 |
| `app` | `app` / `factory` | **应用程序** | 固件就烧在这儿 |

这些分区**本仓库没有**，但你会在别处见到：

| 名字 | 类型 | 干什么 | 为什么这里没有 |
| --- | --- | --- | --- |
| `otadata` | `data` / `ota` | OTA 状态记录，只记 `ota_seq` | 没有第二个槽可切，不需要（§9） |
| `ota_0` / `ota_1` | `app` / `ota_0`… | A/B 两个固件槽 | 1MB 装不下两个槽（§9） |

> **注意 `nvs` 是 24 KiB，不是常见的 16 KiB。** 因为它同时顶了两份活：
> 原来 2MB 表里 `nvs`(16K) + `otadata`(8K) 占的 `0x9000`–`0xEFFF` 这一段，
> 现在整段给了 `nvs`。这样布局前段不用挪位置。

## 4. Type 和 SubType

`Type` 只有两大类：

| Type | 含义 |
| --- | --- |
| `app` | 里面放**可执行镜像**。bootloader 挑一个 app 分区，把镜像搬进内存然后跳过去执行 |
| `data` | 放**数据**，CPU 不去执行它。程序自己读写 |

`SubType` 是大类里再分小类，决定**谁在用、怎么用**：

| Type | 可用的 SubType |
| --- | --- |
| `app` | `factory` / `ota_0` / `ota_1` / `test` |
| `data` | `nvs` / `ota`（即 otadata）/ `phy` / `nvs_keys` / `spiffs` / `fat` / `coredump` |

> CSV 里 `Type` 也可以写数字：`app` = `0`，`data` = `1`。
> SDK 自带的 `partitions_two_ota.csv` 就写成 `ota_0, 0, ota_0, ...`，和 `app` 等价。
> 写名字更可读。

## 5. 找分区的两种方式：名字 vs SubType

**这是最容易想当然的一节。** 代码和 bootloader 找分区的规则**不一样**。

### 代码：Type + SubType + 名字，三个都要对

`nvs_flash_init()` 没有任何地址参数，它自己去查表。查表条件写在
`nvs_partition_lookup.cpp` 里的 `lookup_nvs_partition()`：

```c
esp_err_t lookup_nvs_partition(const char* label, NVSPartition **p)
{
    const esp_partition_t* esp_partition = esp_partition_find_first(
            ESP_PARTITION_TYPE_DATA, ESP_PARTITION_SUBTYPE_DATA_NVS, label);
```

第三个参数 `label` 从哪来？`nvs_api.cpp` 里的 `nvs_flash_init()`：

```c
return nvs_flash_init_partition(NVS_DEFAULT_PART_NAME);
```

而 `NVS_DEFAULT_PART_NAME`（`nvs.h`）就是字符串 **`"nvs"`**。

**所以名字也是条件之一。** 你把分区表里那行改名成 `storage`，
即使 subtype 还是 `nvs`，`nvs_flash_init()` 也会返回 `ESP_ERR_NOT_FOUND`。

- 把 `nvs` 从 `0x9000` 挪到别处 → **代码一行都不用改** ✅
- 把 `nvs` 那行改个名字 → **直接报错** ❌

> **解耦解的是"地址"，不是"名字"。** 名字是接口，地址是实现。

### bootloader：只看 SubType，完全不看名字

```c
/* bootloader_utility.c 里的 bootloader_utility_load_partition_table() */
case PART_SUBTYPE_FACTORY: /* factory binary */
    bs->factory = partition->pos;
```

它匹配的是**子类型** `factory`，`partition->pos` 拿的是位置。
名字是什么它根本不关心。

**这就是本仓库那行的名字叫 `app` 而不是 `factory`，却照样能启动的原因：**

```
app,       app,  factory, 0x10000,  0xF0000,
 ↑               ↑
 名字随便起       SubType 必须是 factory
```

启动路径也简单：**没有 otadata 分区**时，bootloader 直接选 factory，
不需要任何槽位选择逻辑参与（`bootloader_utility.c` 里的 `index_to_partition()` 返回 `bs->factory`）。

## 6. Offset 是位置，Size 是长度

**同一个数值，在不同列里角色不同。**

看这张表——`0x10000` 出现了两次：

```
                          Offset      Size
nvs,       data, nvs,     0x9000,   0x6000,
phy_init,  data, phy,     0xf000,   0x1000,
app,       app,  factory,  0x10000,   0xF0000,
                             ↑            ↑
                           位置          长度
```

`0x1000` 也出现两次：在 `phy_init` 行是 **Size**（长 4 KiB），
在 `app` 行的 **Offset** 里是 `0x10000` 的一部分。

- 在 **Offset** 列 → "从第 N 个字节开始"，是个**坐标**
- 在 **Size** 列 → "长 N 字节"，是个**长度**

**坐标和长度不能互换。** 把 Size 填进 Offset，整张表就乱了。

### 硬性规则

```
这一行的 Offset  =  上一行的 Offset + 上一行 Size
```

这两个数是**手工填的**，算错只有两种后果：

| 错法 | 后果 |
| --- | --- |
| 重叠 | `gen_esp32part.py` **构建时报错** |
| 留洞 | 不报错，但**白扔空间** |
| **超出 flash 末尾** | **不报错！** —— 见 §2 的事故复盘 |

> ⚠️ **第三行是这份笔记存在的理由。**
> 前两种错误都有人管，第三种没人管：分区表可以合法地描述一个不存在的地址范围，
> 而 flash 驱动会拿着同样错的配置去"检查"它。

> **最快的自检：最后一行算出来必须正好等于 `0x100000`**（你的 flash 大小）。
> 不等于就说明中间算错了。

## 7. 十六进制 ↔ 大小换算

### 换算只有两步

```
0x10000  = 65536            ← 先把十六进制化成数
         = 65536 字节        ← 分区表规定的单位
         = 65536 ÷ 1024
         = 64 KiB
```

或：`0x10000` = 2^16 字节；除以 2^10（1 KiB）= 2^6 = **64 KiB**。

### ⚠ bit 和 byte 的坑，以及"型号猜容量"的坑

flash 芯片厂商**经常按 bit 标容量**——因为它内部按位组织、按字节传输。两个数都对，只是单位不同。

`16 Mbit ÷ 8 = 2 MByte = 0x200000`——这个换算法本身没错。

**错的是"我以为 ESP-01S 上的 flash 是 W25Q16"这个假设。**

```
假设：W25Q16  →  型号里的 16  →  16 Mbit  →  2 MB
                                 ↓
                        看着特别顺，特别像一个结论
                                 ↓
                        但它是猜的，不是量的
```

实测这块板子上是**博雅（Boya）的 1MB 芯片**，JEDEC ID `0x68 0x4014`：

```
Manufacturer: 68     ← 不是 Winbond 的 0xEF
Device: 4014         ← 0x14 = 1MB，不是 0x15
```

> **教训**：型号和容量之间是"查表"关系，不是"推理"关系。
> 推理链条越长，中间某一环是假设的可能性就越大，
> 而最后那个结论看起来会越确定——**这是最危险的地方**。

**容量只有一个可靠来源：让芯片自己说（`flash_id`）。**

### 记住一个锚点就够

| 十六进制 | 字节 | 怎么叫 |
| --- | --- | --- |
| `0x400` | 1024 | 1 KiB |
| `0x1000` | 4096 | **4 KiB —— 一个 flash 扇区** |
| `0x2000` | 8192 | 8 KiB |
| `0x4000` | 16384 | 16 KiB |
| `0x6000` | 24576 | 24 KiB |
| `0x10000` | 65536 | **64 KiB** |
| `0x100000` | 1048576 | **1 MiB（整颗 flash）** |
| `0x200000` | 2097152 | 2 MiB |

只要记住 **`0x1000` = 4 KiB**，往后每多一个十六进制 `0` 就乘 16：

```
0x1000   = 4 KiB
0x10000  = 4 KiB × 16 = 64 KiB
0x100000 = 64 KiB × 16 = 1024 KiB = 1 MiB
```

### KiB 还是 KB

| 写法 | 含义 |
| --- | --- |
| **KiB** | 1024 字节（2^10） |
| **KB** | 1000 字节（十进制） |

日常混着写没人计较，但**地址、分区、扇区**这类地方全是 2 的幂，看到 1024 就该写 KiB。

## 8. 自己排一张表：四步

### 第一步：先量 flash 有多大

```bash
python $IDF_PATH/components/esptool_py/esptool/esptool.py --port COM8 flash_id
```

**这一步不能跳，也不能用"型号应该是"来替代。** 理由见 §2。

### 第二步：前 64 KiB 是禁区

```
0x0000 – 0x7FFF   bootloader
0x8000 – 0x8FFF   分区表自己
0x9000 →          从这里开始
```

### 第三步：回答一个问题——要不要 OTA？

这决定有几个 `app` 槽。**这是唯一需要动脑的一步**，剩下几步是算术。
判断依据见 §9。

### 第四步：分配，保证首尾相接，然后自检

每行 `Offset + Size` = 下一行的 `Offset`。
最后一行算出来 == flash 大小。

### 例子：算每块 app 槽多大

```
可分配给 app 的空间 = 0x100000 - 0x10000 = 0xF0000 = 960 KiB
一个槽              = 0xF0000         = 960 KiB
两个槽对半分        = 0x70000 每块    = 448 KiB   ← 放不下，见 §9
```

还要**核对固件大小**：

```bash
ls -l build/esp-01S.bin                   # 实际镜像大小
xtensa-lx106-elf-size build/esp-01S.elf   # text / data / bss 分解
```

> `esp-01S.bin` 的大小 = `text + data + 91 字节镜像头`。
> 留 **2 倍以上余量**，因为固件只会越来越长。
> 本仓库实测 **496448 字节（≈485 KiB）**——这是 2026-09-29 的构建。
>
> **数字别记，要量。** 每次关心就重新跑一遍上面那两条命令。

## 9. OTA 布局怎么选

先说结论：**本仓库不用 OTA，因为放不下。**

### 方案甲：`factory` + `ota_0`（不推荐）

跑在 factory 上 → 升级写进 `ota_0` → 切过去。

**问题：只能升级一次。** 第二次升级时，它只能返回 `ota_0` 自己——
也就是**要覆盖你正在运行的那块固件**。写一半掉电，砖。

看 `esp_ota_ops.c` 里的 `esp_ota_get_next_update_partition()` 的实现：

```c
for (t = OTA_0; t != OTA_MAX; t++) {
    p = find_first(APP, t, NULL);
    if (p == NULL) continue;
    if (default_ota == NULL) default_ota = p;   /* 记住找到的第一个 */
    if (p == start_from) next_is_result = true; /* 找到正在跑的那个 */
    else if (next_is_result) return p;          /* 返回它的下一个 */
}
return default_ota;   /* 绕一圈没找到下一个 → 回到第一个 */
```

只有一个 OTA 槽时的执行路径：

```
t = OTA_0 :  p = ota_0
             default_ota = ota_0
             p == start_from   →  next_is_result = true
t = OTA_1..: p == NULL  →  continue
循环结束   →  return default_ota  ==  ota_0   ← 正是你正在跑的那块
```

### 方案乙：`ota_0` + `ota_1`（原理上推荐，**但 1MB 放不下**）

```
跑 ota_0  →  写 ota_1  →  切过去
跑 ota_1  →  写 ota_0  →  切过去
……
```

**永远有一块完整的固件在另一头。** 这是 SDK 自带 `partitions_two_ota.csv` 的形状。

**但在 1MB 芯片上算一下就不行了：**

```
可分配给 app 的空间 = 0x100000 - 0x10000 = 0xF0000 = 960 KiB

切法一：两块对半分 = 每块 480 KiB

切法二：Espressif 自己给 1MB 准备的双槽表
      components/partition_table/partitions_two_ota.1MB.csv：
    nvs,      data, nvs,     0x9000,  0x4000
    otadata,  data, ota,     0xd000,  0x2000
    phy_init, data, phy,     0xf000,  0x1000
    ota_0,    0,    ota_0,   0x10000, 0x70000    ← 448 KiB
    ota_1,    0,    ota_1,   0x80000, 0x70000    ← 448 KiB
      （比"对半分"更紧，因为多了 otadata 那一块）

而本仓库固件实测 496448 字节（≈485 KiB）：
    485 KiB > 480 KiB  → 超出  4.8 KiB   ❌
    485 KiB > 448 KiB  → 超出 36.8 KiB   ❌
```

**两种切法都装不进去** —— 而且这个差距只会越来越大（固件只会变胖）。

> 上面这个 496448 是 **2026-09-29** 的构建产物（`build/esp-01S.bin`），
> 也就是**已经加完配网模式、又没有 OTA** 的那一版。
>
> 这一条很关键：**装不下这件事，不用再把 OTA 自身的体积算进来就已经成立**。
> 把 `ota.c` 放回去只会让这个数更大 —— 而槽里要装的，恰恰是那个更大的版本。
>
> 要拿当前数字，自己量：
>
> ```bash
> ls -l build/esp-01S.bin
> ```

> **SDK 早就知道这件事** —— `partition_table/Kconfig.projbuild` 里的 `PARTITION_TABLE_FILENAME` 配置项：
>
> ```text
> default partitions_two_ota.csv      if PARTITION_TABLE_TWO_OTA && ... && !ESPTOOLPY_FLASHSIZE_1MB
> default partitions_two_ota.1MB.csv  if PARTITION_TABLE_TWO_OTA && ... &&  ESPTOOLPY_FLASHSIZE_1MB
> ```
>
> 只要 `FLASHSIZE` 选 1MB，再选双 OTA，SDK 会**自动换成小槽表**。
> 出事那份配置是 **Custom partition table CSV** —— 手写的表绕过了这条保护，
> 而且手写时用的还是 2MB 的数字。

### 方案丙：单个 `factory`，不要 OTA（**本仓库采用**）

```
nvs,       data, nvs,     0x9000,   0x6000,
phy_init,  data, phy,     0xf000,   0x1000,
app,       app,  factory, 0x10000,  0xF0000,
```

一个槽吃掉全部 960 KiB，固件怎么长都够。

**代价：换固件必须插串口线重烧**（`make flash`）。这个节点是控制灯的，
不需要远程升级，这个代价可以接受。

> **⚠ 但一定要分清一件事：**
>
> | | 换固件 | 换 WiFi 密码 |
> | --- | --- | --- |
> | 手段 | OTA / 串口重烧 | 改 `nvs` 里的配置 |
> | 需要网络吗 | **需要** | 不需要 |
> | 本仓库怎么做 | 串口重烧 | TCP 命令 `wifi <SSID>,<密码>` |
>
> **这两个是正交的。** 而且 OTA 本身要走网络——密码改错、连不上了，OTA 也够不着它。
>
> ⚠️ 原来这里还写着"真正能救失联节点的是 SmartConfig"。
> **那条路已经拆掉了** —— 理由和实测数据见 `ESP8266开发流程.md` §9.7
> 和 `学习笔记/ESP8266配网踩坑(SmartConfig).md`。
> 现在救失联节点的是**网页配网**（`ESP8266开发流程.md` §10）：
> 节点自己开热点、出个页面，人拿手机过去重填。**但它要人到现场** ——
> 所以换凭据的顺序仍然是先发 TCP 命令、再改主节点。
>
> 当初就是为了"能改密码"才想上 OTA，这个方向从一开始就是错的。

### 没有 factory 也能启动吗

能，而且这是双槽表的正常形态（这里作为知识保留）：

`bootloader_utility.c` 里，otadata 全 0xFF（空白）时的分支：

```c
if (bs->factory.offset != 0) {
    ESP_LOGI(TAG, "Defaulting to factory image");
    return FACTORY_INDEX;
} else {
    ESP_LOGI(TAG, "No factory image, trying OTA 0");
    return 0;                    /* ← 启动 ota_0 */
}
```

**本仓库是反过来的一半**：有 factory、没有 otadata → 走上面那个分支。

## 10. 这个 SDK 的 OTA 真相

本仓库不用 OTA，但这部分知识留着——**将来换 2MB 或更大的模块时要用**。

> 对应的代码没有删，从 `esp-01S/` 移到了 `../ota-for-larger-flash/`
> （`ota.c` / `ota.h`）。那份目录里另有 README 写了移回去的步骤。
> 本节讲的是**它背后的机制**，代码移不移走都成立。

### ⚠ v3.4 没有自动回滚

证据一，otadata 的结构体（`esp_flash_data_types.h`）：

```c
typedef struct {
    uint32_t ota_seq;
    uint8_t  seq_label[24];
    uint32_t crc;          /* CRC32 of ota_seq field only */
} esp_ota_select_entry_t;
```

**只有 `ota_seq` + `crc`，没有状态位。**

证据二，`esp_ota_ops.h` 里公开的 API 一共这些：

```
esp_ota_begin / esp_ota_write / esp_ota_end
esp_ota_set_boot_partition / esp_ota_get_boot_partition
esp_ota_get_running_partition / esp_ota_get_next_update_partition
esp_ota_get_partition_description
```

**没有 `esp_ota_mark_app_valid_cancel_rollback()`。**

> ESP32 的自动回滚靠 otadata 里的**状态位**（`PENDING_VERIFY` / `VALID` / `INVALID`），
> bootloader 发现状态不对就切回另一块。ESP8266 这套机制**没有**。

### 后果

**新固件起不来 → 无限重启，不会自动切回旧的那块。只能靠串口救回来。**

### 怎么办：自己在应用层做

在 NVS 里存一个启动计数器：

```
每次启动   计数器 +1
连上服务器报到成功   → 计数器清零
启动 N 次都没报到成功 → esp_ota_set_boot_partition(另一块) → 重启
```

这就是"手动版回滚"。

> **上线前的底线**：每一版固件都先在桌面上验证过。
> 没有自动回滚的平台，这是唯一可靠的保险。

### 顺带：没有备用槽时，`esp_ota_get_next_update_partition()` 会怎样

返回 **NULL**，不会崩。`esp_ota_ops.c` 里的 `esp_ota_get_next_update_partition()`
先把 `default_ota` 置成 NULL，
循环一个都没匹配上就直接 `return default_ota;`。

调用方一定要判空：

```c
const esp_partition_t *next = esp_ota_get_next_update_partition(NULL);
if (next == NULL) {
    /* 在 1MB 的单槽表上必然走到这里：没有第二个 app 槽可写。
       移走的那份 ota.c 就是靠这个判空，决定"直接告诉对方用不了"。 */
}
```

## 11. 格式上的三个坑

改 `partitions_1mb.csv` 时，这三条都是真踩过的：

### 坑 1：必须纯 ASCII

`gen_esp32part.py` 按 ASCII 解码，**一个非 ASCII 字节就让所有构建目标失败**——包括注释里的。

而且它在 **cmake configure 阶段**就被读，不只是 build 阶段。

### 坑 2：最后一个逗号后面不能有东西

```
nvs, data, nvs, 0x9000, 0x6000,      ← 最后这列是 flags
                                       ← 这里写注释会被当成 flag
```

那一列是 `flags`，除了 `encrypted` 之外任何东西都报 `unknown flag`。
**注释要单独占一行、以 `#` 开头。**

### 坑 3：注释也不能有中文

和坑 1 是同一件事，但特别容易忘——因为"注释是人看的"这个直觉在这里不成立。

## 12. 怎么验证

改完分区表，**不要靠肉眼看**。三个命令，不需要板子：

> ⚠️ 在 mingw32 里 `$IDF_PATH` 是 `/home/Administrator/...` 这种 MSYS 路径，
> **Windows 版的 `python.exe` 读不懂**，会把它当成相对路径解析到别处去。
> 直接用 Windows 路径（`G:/github/...`）最省事。

### ① 语法检查和重叠检查

```bash
python $IDF_PATH/components/partition_table/gen_esp32part.py \
       partitions_1mb.csv build/_test.bin

python $IDF_PATH/components/partition_table/gen_esp32part.py \
       --verify build/_test.bin
```

第二条会把解析结果**倒着打印出来**，可以直接核对 Offset 和 Size：

```
nvs,data,nvs,0x9000,24K,
phy_init,data,phy,0xf000,4K,
app,app,factory,0x10000,960K,
```

### ② 纯 ASCII 检查

```bash
grep -n '[^ -~]' partitions_1mb.csv
```

**没有输出 = 纯 ASCII。** 这个字符类读作"**不在** `0x20`（空格）到 `0x7E`（`~`）之间"，
也就是所有非可打印字节：中文、BOM、以及制表符。

> **别写成 `[^ -~\t]`。** 括号表达式里**反斜杠是普通字符，不是转义**——
> `\t` 在里面表示"反斜杠"和"字母 t"这两个字符，不是制表符。
> 又因为这两个字符本来就落在 `0x20`–`0x7E` 里面，
> 整个表达式会**悄悄退化成 `[^ -~]`**。
> 结果碰巧是对的，但纯属巧合，读代码的人会被骗过去。
> 想真的放行制表符，得在括号里敲一个**真正的 Tab 字符**（旧版笔记就是那么写的）。

### ③ 构建系统会去哪烧固件

```bash
python $IDF_PATH/components/partition_table/parttool.py \
       --partition-table-file build/_test.bin \
       get_partition_info --partition-boot-default --info offset size
```

输出 `0x10000 0xf0000` —— 这就是 `flasher_args.json` 里 app 的烧录偏移。

> **注意**：`--partition-boot-default` 是**子命令的参数**，必须放在
> `get_partition_info` 后面。放前面会报 `unrecognized arguments`。
> `--info` 只接受 `offset` / `size`，多要字段会 `KeyError`。

### ④ 顺便看一眼构建系统会用什么 flash 大小

```bash
grep flash_size build/flasher_args.json
```

这个值会一路变成镜像头里的 `spi_size`，**也就是启动日志那行**（§2）。
改完 `sdkconfig` 记得回来看一眼，确认它真的变了。

## 13. 本仓库当前的表

`partitions_1mb.csv`：

```
# Name,   Type, SubType, Offset,   Size, Flags
nvs,       data, nvs,     0x9000,   0x6000,
phy_init,  data, phy,     0xf000,   0x1000,
app,       app,  factory, 0x10000,  0xF0000,
```

首尾相接自检：

```
0x9000  + 0x6000  = 0xF000     ✓
0xF000  + 0x1000  = 0x10000    ✓
0x10000 + 0xF0000 = 0x100000   ✓  正好 1MB
```

> **巧的是，这张表和 Espressif 给 1MB 芯片准备的默认表一字不差。**
> 打开 `components/partition_table/partitions_singleapp.csv`，就是这三行。
> 绕了一大圈，回到的正是官方默认布局。

### 相关配置

`sdkconfig`：

```
CONFIG_ESPTOOLPY_FLASHSIZE_1MB=y
CONFIG_SPI_FLASH_SIZE=0x100000
CONFIG_PARTITION_TABLE_CUSTOM=y
CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_1mb.csv"
CONFIG_PARTITION_TABLE_FILENAME="partitions_1mb.csv"
CONFIG_PARTITION_TABLE_OFFSET=0x8000
```

> **`CONFIG_SPI_FLASH_SIZE` 是关键的那一个。** 它决定了 §2 里所有那些
> "拿错误检查错误"的下游行为。它通常由 `CONFIG_ESPTOOLPY_FLASHSIZE_1MB`
> 带出来，但既然它能单独改坏，就值得单独确认一眼。

### 改动分区表之后

1. **重新 configure** —— 分区表是在 cmake *configure* 阶段读的。删掉 `build/` 重来最保险
2. **擦一次 flash**（`erase_flash`）—— 分区布局变了，旧布局的残留数据会留在新分区里

### 写 OTA 代码要不要改配置？不要

我在 `main/CMakeLists.txt` 里加 `REQUIRES app_update`，**实测下来不用**。

`tools/cmake/build.cmake` 里的 `__COMPONENT_REQUIRES_COMMON` 确实写着：

```cmake
set(requires_common newlib freertos heap log lwip)
```

`app_update` 不在这个列表里。但这只是**默认值**——`main` 这个组件是特殊的，
它自动拿到**所有**组件的头文件路径和库。

**证据一**（`build/compile_commands.json`）：`main.c` 的编译命令里有
**57 个**组件的 `-I` 路径，其中包括：

```
.../ESP8266_RTOS_SDK/components/app_update/include
.../ESP8266_RTOS_SDK/components/spi_flash/include
```

**证据二**（更直接，在你自己代码里）：`wifi_sta.c` 用了 `esp_event`、
`tcpip_adapter`、`nvs_flash`——**这三个都不在 `requires_common` 里**，
而 `main/CMakeLists.txt` 一行 `REQUIRES` 都没写，固件照样跑得好好的。

所以 `#include "esp_ota_ops.h"` 直接用，什么都不用改。

> **教训**：`requires_common` 是**默认值**，不是**全集**。
> 光看这一行会得出错误结论——我就是这么错的。
> 想知道某个组件能不能用，去看 `compile_commands.json` 里实际的 `-I` 列表，
> 或者干脆编译一次。

## 一页速查

```
分区表 = flash 的地图，放在固定位置 0x8000

⚠ 先量容量，再排表：
    esptool.py --port COM8 flash_id
    Device 后两位：14=1MB  15=2MB  16=4MB
    【不要】看启动日志的 SPI Flash Size —— 那是配置照镜子

地址布局（1MB）：
  0x00000 bootloader 32K  ┐
  0x08000 分区表      4K  ├ 禁区
  0x09000 nvs        24K
  0x0F000 phy_init    4K
  0x10000 app       960K  ← 唯一的固件槽
  0x100000 到头

找分区（两种规则不一样！）：
  代码      Type + SubType + 名字   （nvs_flash_init 要名字叫 "nvs"）
  bootloader 只看 SubType          （名字随便起）

三条规矩：
  1. 每行 offset + size == 下一行 offset
  2. 最后一行 == 0x100000
  3. 纯 ASCII，注释独立成行

超出末尾【不会报错】：
  1MB 芯片只解码 A0-A19
  0x108000 & 0xFFFFF = 0x008000   ← 回绕，擦回开头
  被擦掉的第一个东西就是分区表自己，然后是打印报错的代码

换算锚点：
  0x1000 = 4 KiB（一个扇区）
  0x10000 = 64 KiB
  0x100000 = 1 MiB
  0x200000 = 2 MiB

OTA：
  1MB 只有 960K 可用，双槽每块 480K（SDK 那张表更紧，448K）
  本仓库固件 485K（且这一版【没有】OTA）→ 放不下，不用
  换 WiFi 密码 ≠ 换固件，别为了改密码上 OTA
  ⚠ v3.4 没有自动回滚，失败会无限重启
```
