

# ESP8266 开发流程笔记

在 Windows 下使用 ESP8266_RTOS_SDK 开发 ESP-01S 流程。（建议先学会sdk裸开发作为保底手段，后面再使用vscode插件ESP8266-IDF简化开发操作）

## 1. 工具链与 SDK 准备

### 1.1 下载工具链压缩包

从乐鑫官方下载地址获取以下两个压缩包（Windows 32 位）：

| 压缩包 | 下载地址 |
| --- | --- |
| `xtensa-lx106-elf-gcc8_4_0-esp-2020r3-win32.zip` | <https://dl.espressif.com/dl/xtensa-lx106-elf-gcc8_4_0-esp-2020r3-win32.zip> |
| `esp32_win32_msys2_environment_and_toolchain-20181001.zip` | <https://dl.espressif.com/dl/esp32_win32_msys2_environment_and_toolchain-20181001.zip> |

分别解压到 `esp8266_toochain/` 目录下：

| 压缩包 | 解压后目录 | 作用 |
| --- | --- | --- |
| `xtensa-lx106-elf-gcc8_4_0-esp-2020r3-win32.zip` | `xtensa-lx106-elf/` | Xtensa 交叉编译器（`gcc`、`ld`、`objcopy` 等） |
| `esp32_win32_msys2_environment_and_toolchain-20181001.zip` | `msys32/` | MSYS2 环境，提供 `mingw32.exe` 终端 |

两个都是**解压即用**的绿色包，不需要安装，也不需要写注册表，删掉文件夹就等于卸载。

#### 这两个分别是什么？

**① `xtensa-lx106-elf` —— 干活的：交叉编译器**

ESP8266 芯片里的 CPU 是 **Xtensa** 架构，跟你的电脑（Intel/AMD 的 x86）**不是同一种语言**。你写的 C 代码，用电脑上普通的编译器编译出来的程序，ESP8266 根本跑不了。

所以需要一个"翻译官"：**它运行在你的 Windows 电脑上，产出的却是 ESP8266 能执行的机器码**。这种"在 A 平台上生成 B 平台代码"的编译器，就叫**交叉编译器**（cross compiler）。

它里面装着：

| 工具 | 用途 |
| --- | --- |
| `xtensa-lx106-elf-gcc` | 编译器，把 `.c` 翻译成 ESP8266 的机器码 |
| `xtensa-lx106-elf-ld` | 链接器，把编译出的一堆碎片拼成完整固件 |
| `xtensa-lx106-elf-objcopy` | 格式转换，生成能烧进 Flash 的 `.bin` 文件 |
| `xtensa-lx106-elf-objdump` | 反汇编，调试时用来查看机器码 |

名字是拼出来的，拆开读就懂了：

```text
xtensa - lx106 - elf - gcc8_4_0 - esp-2020r3 - win32
   ↑       ↑      ↑       ↑            ↑          ↑
 CPU架构  核心型号 文件格式 GCC版本   乐鑫发布版本  运行在Windows
```

ESP8266EX 的内核正是 Xtensa **L106**，所以叫 `lx106`。ESP32 用的是 L6，工具链名字是 `xtensa-esp32-elf`——看一眼名字就知道是给哪块芯片用的。

**② `msys32` —— 提供场地的：Linux 风格的终端环境**

ESP8266_RTOS_SDK 的构建系统是**照着 Linux 写的**：靠 `make` 驱动一堆 `.mk` 文件，脚本里到处是 `ls`、`cp`、`rm`、`sed` 这类 Linux 命令。Windows 自带的 cmd 和 PowerShell 都不认识它们，直接跑会寸步难行。

`msys32`（Minimal SYStem 2）相当于在 Windows 上开了个**"假装是 Linux"的小房间**，里面备齐了 bash 和那些 Linux 命令。`mingw32.exe` 就是这个房间的门——双击它，你就进到了一个长得像 Linux 的终端里。

> **名字里为什么带 `esp32`？** 这个 MSYS2 环境本身和芯片无关，只负责提供 shell 和基础命令。乐鑫当年把它打包给 ESP32 用，后来 ESP8266_RTOS_SDK 的 Windows 教程直接沿用了同一个包，所以名字没改。

**一句话总结分工**：`msys32` 负责把环境搭起来（让你能敲命令），`xtensa-lx106-elf` 负责把代码变成固件（让芯片能跑）。

完成后目录结构如下：

```text
esp8266_toochain/
├── msys32/                      ← esp32_win32_msys2_environment_and_toolchain-20181001.zip
│   └── home/Administrator/
│       └── esp/
│           ├── ESP8266_RTOS_SDK/
│           └── hello_world/
└── xtensa-lx106-elf/            ← xtensa-lx106-elf-gcc8_4_0-esp-2020r3-win32.zip
    └── bin/
```

> **版本配对**：`gcc8_4_0-esp-2020r3` 是 ESP8266_RTOS_SDK v3.4 对应的编译器版本，不要与其他版本的 SDK 混用。

### 1.2 获取 ESP8266_RTOS_SDK

使用 `esp8266_toochain/msys32/mingw32.exe` 打开终端，然后克隆 SDK（这里克隆不了就用cmd克隆，然后再用mingw32.exe进行其它操作）：

```bash
mkdir -p ~/esp
cd ~/esp
git clone --recursive https://github.com/espressif/ESP8266_RTOS_SDK.git
```

`--recursive` **不能省略**：SDK 依赖多个子模块（mbedtls、lwip 等），漏掉会导致后续编译缺文件。如果已经克隆但忘了加，可以补跑：

```bash
cd ~/esp/ESP8266_RTOS_SDK
git submodule update --init --recursive
```

mingw32 中的 `~` 对应 Windows 下的 `esp8266_toochain\msys32\home\Administrator`，因此 SDK 最终位于：

```text
..\esp8266_toochain\msys32\home\Administrator\esp\ESP8266_RTOS_SDK
```

> **不同步至代码仓库**：`esp8266_toochain` 整个目录已在 `.gitignore` 中排除——工具链体积大，且 SDK 本身有自己的 Git 仓库。

### 1.3 路径限制

ESP8266_RTOS_SDK 构建系统**不支持**在 SDK 或项目路径中使用空格，安装与克隆时请全程避开带空格的目录。（路径别带有中文）

### 1.4 安装 Python（32 位）

SDK 的构建脚本依赖 Python 3，且需要 **32 位**版本。

下载地址：<https://www.python.org/downloads/windows/>

在页面的 **Stable Releases** 表格中找到目标版本（如 Python 3.13.x），下载 **Windows installer (32-bit)** 一项——注意不要点成 64-bit，也不要下载 embeddable package（那是给嵌入用的，没有 pip）。

安装时保持默认的 **Install Now** 即可，安装路径一般是：

```text
C:\Users\Administrator\AppData\Local\Programs\Python\Python313-32
```

对应到 mingw32 中的写法（第 2 节要用的）：

```bash
/c/Users/Administrator/AppData/Local/Programs/Python/Python313-32
```

> **目录名怎么看位数**：32 位装的目录名结尾带 `-32`（`Python313-32`），64 位则不带后缀（`Python313`）。两者可以同时装在同一台机器上，互不干扰。
>
> **路径不一样的情况**：如果安装时选了 "Install for all users"，路径会变成 `C:\Program Files (x86)\Python313-32`，第 2 节的 `export PATH` 要跟着改。安装路径可以在安装向导第一屏的 "Customize installation" 里确认，装完后也能在终端用 `where python`（cmd）查看。

`AppData` 是隐藏目录，资源管理器里看不到属于正常现象，直接在地址栏粘贴上面的路径即可打开。

安装完成后验证：

```bash
which python      # 应指向 Python313-32 下的 python.exe
python -V         # 应输出 Python 3.13.x
```

## 2. 环境变量配置

`mingw32` **无法读取 Windows 系统环境变量**，因此每次进入mingw32.exe都需要手动设置。虽然 `IDF_PATH` 会和系统的 esp-idf 冲突，但冲突本身无所谓——根本原因是读不到。

```bash
# 添加环境变量：SDK 
export IDF_PATH=/home/Administrator/esp/ESP8266_RTOS_SDK

# 添加环境变量：Python（须确认路径下是 Python 3，且为 32 位，安装见 1.4 节）。
# :$PATH 不能省，$PATH 的意思就是"把path原来的内容抄过来"，因为path里面有很多其它的路径，不能丢掉。把$PATH放到末尾意味着，新添加的路径放到所有其它路径的最前面。 
export PATH="/c/Users/Administrator/AppData/Local/Programs/Python/Python313-32:$PATH"

# 添加环境变量：交叉编译工具链
export PATH="$PATH:/g/github/esp8266_toochain/xtensa-lx106-elf/bin"
```

```bash
python -m pip install --user -r $IDF_PATH/requirements.txt
```

ESP8266 SDK 专属依赖：

```bash
python -m pip install click pyelftools
```

### 3.2 处理 `pkg_resources` 缺失问题

从 **Python 3.12** 开始，官方彻底移除了内置的 `ensurepip` 和 `setuptools`。这意味着新装的 Python 3.13 是一个"纯净版"，连最基础的包管理工具都没有。而 ESP8266 RTOS SDK 的构建脚本依赖 `pkg_resources`（`setuptools` 的一部分）来检查环境，找不到就会直接罢工。

```bash
# 下载并运行 get-pip.py（需要联网）
curl https://bootstrap.pypa.io/get-pip.py -o /tmp/get-pip.py
/c/Users/Administrator/AppData/Local/Programs/Python/Python313-32/python.exe /tmp/get-pip.py
```

### 3.3 安装基础工具链（有坑）

最新版 `setuptools` (v71+) 已彻底删除 `pkg_resources`，而 ESP8266 SDK 的 Makefile 依赖这个旧模块。**装最新版等于白装。**

```bash
# ❌ 错误：会装上没有 pkg_resources 的新版
python -m pip install setuptools wheel

# ✅ 正确：锁定在 71 以下
python -m pip install "setuptools<71" wheel
```

### 5.2 编译并烧录

> 烧录前需先让 ESP-01S 进入**下载模式**（将io0接地）。

```bash
make -j10 #构建，ESP-01S 项目建议调用 4 线程，实测 10 线程也可行。
make ESPPORT=COM8 ESPBAUD=921600 flash #烧录成功率跟中间全链路有关，排除问题的优先级为，用手插紧线（尤其是杜邦线！接触不良时，高阻抗、时变噪声）->降波特率（本质上是增大时序容错窗口， 降低高频寄生参数的影响）->...   （先查连接，再测阻抗，最后才怀疑芯片）
```



[^]: 杜邦线接触不良被称作“万恶之源”，因为它会伪装成软件 Bug。按危害分级：🔴 **直接失效（易诊断）**——VCC/GND 接触电阻 >1Ω 时，WiFi 发射瞬间 300mA+ 的电流就会造成 >0.3V 压降、芯片欠压复位（“跑着跑着突然重启”“一连 WiFi 就死机”）；GPIO0 无法被拉低 → 卡在 `Connecting..._____`；TX/RX 松动 → 日志乱码或全无输出。🟠 **间歇性故障（极难诊断）**——SPI/I2C 偶发误码，让你花几天怀疑驱动代码、时序甚至芯片；ADC 读数跳变、PID 震荡；EN/RST 受干扰引入**无理由随机复位**，无法用代码逻辑复现。🟡 **隐性劣化**——信号完整性下降（高波特率烧录失败、WiFi 吞吐降低）；接触点发热；松动连接点成为“微型天线”恶化 EMC。⚫ **不可逆损伤**——电弧碳化排针与母头弹片；触摸松动线材引入 ESD 潜伤，芯片当时没坏但寿命大幅缩短。💡 **核心认知：接触不良是在系统中引入一个“时变、非线性、不可预测”的故障源。** 代码 Bug 是确定性的（可复现、可定位、可修复），接触不良是概率性的（受温度、湿度、振动、氧化影响）——无法被单元测试覆盖，无法被静态分析发现，只能靠物理层可靠性设计消除。



[^]: 接触不良时降波特率能提高烧录成功率，并非“修好”了连接，而是**降低了系统对物理层缺陷的敏感度**。四个机制：① **时序容错窗口变大**——UART 为异步通信，无时钟线同步。921600 下单个比特仅 **1.08μs**，一个 0.5μs 的瞬态开路/短路就占了半个比特周期；74880 下单比特 **13.3μs**，同样干扰占比不足 4%，接收端滤波器有时间忽略毛刺、在稳定区采样。② **高频寄生参数影响减弱**——松动接触点等效为不稳定的 RLC 网络，高频时寄生 LC 形成低通效应，边沿变缓、过冲振铃加剧直至逼近判决阈值；低频时能量集中在低端，波形接近理想方波，眼图张开度更大。③ **接触点非线性效应减小**——金属接触存在**收缩电阻**与**隧道效应**，阻值随电流大小和变化速率而变；高速翻转诱发微电弧与热电势噪声，低速时接触点有更长的“静止时间”，热平衡更稳定。④ **打断 esptool 的重传正反馈**——高波特率下误码 → 不断重传 → 总线持续高频活动 → 接触点发热氧化 → 误码率再升，形成**正反馈崩溃**；低波特率下单次传输长、空闲间隔占比大，接触点有机会“冷却”恢复。**本质：用时间冗余换取抗干扰能力。**

## 6. 波特率说明

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| `Default baud rate` | 115200 baud | 烧录 / 下载速度 |
| `'make monitor' baud rate` | 74880 bps | 串口调试 / 日志输出速度 |

### 为什么监视器波特率是 74880？

74880 是一个**非常特殊**的数字——它是 ESP8266 在 26MHz 晶振下的原生波特率（26000000 / 345 ≈ 75362，接近 74880）。

ESP8266 在刚上电、Bootloader 阶段打印的底层启动信息（Flash 电压、RF 校准、Reset 原因）**固定使用 74880 波特率**。

如果把这个值改成 115200，你将**看不到开机时的底层诊断信息，只能看到乱码**，直到应用程序初始化并重新配置 UART 为 115200 后，日志才会恢复正常。

> 只有当你确认不需要看底层启动日志，且希望应用层日志与电脑端终端默认波特率一致时，才考虑改为 115200。

这段日志是 ESP8266 的**"出生证明"和"体检报告"**，表明开发环境、硬件连接、烧录过程以及代码逻辑**全部完美通过**。

### 7.1 核心结论：系统启动成功

- **`Hello world!`**：最直接的信号。说明 `app_main()` 已被正确加载并执行，业务代码跑通了。
- **`rst cause:2`**：复位原因是 **2 (External System Reset)**。通常对应按下开发板 RST 按钮，或 USB-TTL 下载器在烧录完成后自动触发的复位。属于正常启动流程。
- **`boot mode:(3,4)`**：
  - `3`：GPIO0 为高电平（运行模式），GPIO2 为高电平 —— 芯片没有进入下载模式，而是正常启动。
  - `4`：SPI Flash 电压为 3.3V。

### 7.2 硬件与存储状态确认

- **`SPI Flash Size : 1MB`**：~~验证模块确实是 1MB 版本~~ —— **这一行什么都不验证。**

  > ⚠️ **本节原来写的是**：
  >
  > > 验证模块确实是 **2MB (16Mbit)** 版本。ESP-01S 有 1MB 和 2MB 两种常见版本。
  > > 若 menuconfig 里选错大小（比如选了 1MB），这里就会报错或启动失败。
  > > 当前日志说明**分区表配置与实际硬件完全匹配**。
  >
  > **这段话每一个字都是错的**，而且它直接导致了一次把芯片擦成砖的事故——
  > 过程见 [§8.6](#86-怎么确认-flash-到底多大)。留着它是为了记住这个坑长什么样。

  这一行是 **sdkconfig 绕了一圈之后打印回来的自己**，跟芯片真实容量毫无关系：

  ```text
  sdkconfig: CONFIG_ESPTOOLPY_FLASHSIZE_2MB=y
      ↓ 构建系统生成
  build/flasher_args.json:  "flash_size": "2MB"
      ↓ make flash 把它作为参数交给 esptool
  esptool --flash_size 2MB
      ↓ esptool 把这个值写进 .bin 的镜像头
  esp_image_header_t.spi_size = ESP_IMAGE_FLASH_SIZE_2MB
      ↓ bootloader 从 flash 里把镜像头读出来
  bootloader_init.c 里的 print_flash_info()   ESP_LOGI(TAG, "SPI Flash Size : %s", str)
  ```

  `spi_size` 只是镜像头里一个 **4 bit 的字段**（`esp_image_format.h`），
  它记录的是**烧录时告诉 esptool 的那个数**，不是芯片回答的任何东西。

  > **怎么正确判断？** 见 [§8.6](#86-怎么确认-flash-到底多大)——问芯片本身。

- **`SPI Speed : 40MHz` / `QIO Mode`**：Flash 工作在 40MHz 四线 IO 模式，是 ESP8266 的标准性能配置。若显示 26MHz 或 DIO 模式，可能意味着晶振频率不同或 Flash 芯片较老，但 **40MHz QIO 是最理想的状态**。

### 7.3 内存布局分析（进阶视角）

日志中的 `esp_image: segment` 揭示了固件在 Flash 和 RAM 中的分布：

| Segment | 类型 | 大小 | 说明 |
| --- | --- | --- | --- |
| 0 | `map` | ~117 KB | **应用程序代码**，存放在 Flash 中，CPU 通过映射直接执行（XIP） |
| 2 & 4 | `load` | ~1.3 KB + 20 KB | **静态数据、全局变量和中断向量表**，启动时从 Flash 复制到内部 SRAM（`0x3FFE8000` / `0x40100000`）才能被 CPU 快速访问 |

**分区表：**

| Label | 大小 | 用途 |
| --- | --- | --- |
| `nvs` | 24 KB | 键值存储。WiFi 驱动存射频数据，应用用命名空间 `app_cfg` 存 SSID/密码 |
| `phy_init` | 4 KB | 存储射频校准参数 |
| `factory` | 960 KB | 主程序分区 |

### 7.4 为什么波特率是 74880？

注意日志开头的 `ets Jan 8 2013...`：

- 这段信息由 ESP8266 的 **ROM Bootloader**（固化在芯片内部的只读存储器）打印。
- ROM Bootloader **固定使用 74880 波特率**输出，无法更改。
- 这就是 menuconfig 中把 monitor 波特率设为 74880 的原因：**只有这样才能看到完整的启动链路**。若设为 115200，这几行关键的硬件自检信息就会变成乱码。

## 8. 自定义分区表

默认用的是 SDK 里写死的分区表，想自己分配 Flash 空间，就要切到自定义模式。

### 8.1 开启方式

在 menuconfig 中：

```text
Partition Table  --->
    Partition Table (Custom partition table CSV)  --->
    (partitions_1mb.csv) Custom partition CSV file
```

- 第一项选 **Custom partition table CSV**（另外两个选项是 `Single factory app, no OTA` 和 `Factory app, two OTA definitions`）。
- 第二项填 csv 的文件名，这就是你自己的分区表。
- **这个文件名是相对于项目根目录解析的**，所以 csv 必须放在项目根目录下（Kconfig 原文：`This path is evaluated relative to the project root directory.`）。

### 8.2 两条铁律

这个 csv 的容错度极低，**违反任意一条，整个工程直接编译不了**：

| # | 规则 | 违反后果 |
| --- | --- | --- |
| 1 | 注释必须**单独开行**，以 `#` 开头 | 行末注释会被当成 Flags 列 → `unknown flag` |
| 2 | 文件必须**纯英文**（纯 ASCII），注释里也不能有中文 | 读取时解码失败 → `UnicodeDecodeError` |

### 8.3 为什么必须纯英文？

分区表是由 Python 脚本 `gen_esp32part.py` 解析的，而它打开文件的方式是：

```python
# parttool.py 里的 ParttoolTarget.__init__()
with open(partition_table_file, "r") as f:
    partition_table = gen.PartitionTable.from_csv(f.read())
```

注意是 `open(..., "r")` —— **没有指定 `encoding`**，于是 Python 会用**系统默认编码**（中文 Windows 上是 GBK），而不是 UTF-8：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0xaf in position 53: illegal multibyte sequence
```

csv 一旦存成 **UTF-8 且含中文**，这些 UTF-8 字节按 GBK 去解就会失败。某些环境下默认编码还会退化成 ASCII，报的是另一种：

```text
UnicodeDecodeError: 'ascii' codec can't decode byte 0xe8 in position 50: ordinal not in range(128)
```

> **写在注释里也救不了**：解码发生在 `f.read()` —— **读取整个文件的那一刻**，早于任何逐行处理，更早于 `#` 的判断。所以"我把中文放在注释行，应该会被跳过吧"是行不通的，实测一样报错。

### 8.4 为什么注释必须单独开行？

csv 按逗号切分后，每一列的含义是固定的，第 6 列（`fields[5]`）是 **Flags**：

```text
# Name,   Type, SubType, Offset,   Size, Flags
    ↑       ↑      ↑        ↑        ↑      ↑
 fields[0]  [1]    [2]      [3]      [4]    [5]
```

而 Flags 列只认一个值 `encrypted`：

```python
flags = fields[5].split(":")
for flag in flags:
    if flag in cls.FLAGS:          # FLAGS = {"encrypted": 0}
        setattr(res, flag, True)
    elif len(flag) > 0:
        raise InputError("CSV flag column contains unknown flag '%s'" % flag)
```

所以在字段行末尾写 `..., 0x1E0000,  <-- 注释` ，这个注释会被当作 Flags 列的内容：

```text
Error at line 4: CSV flag column contains unknown flag '<-- main app'
```

**这一条和中文无关** —— 就算注释是纯英文，只要写在字段行末尾就一样报错。

### 8.5 为什么这个坑特别难查

分区表是在 CMake 的 **configure 阶段**就被读取解析的，根本轮不到编译。所以 csv 里一个字节的错误，表现出来是**整个工程全线报错**：

```text
-- Configuring incomplete, errors occurred!
FAILED: build.ninja
ninja: error: rebuilding 'build.ninja': subcommand failed
```

这时候 build、clean、menuconfig、size **每一个** target 都会失败 —— 因为每个 target 都要先过 configure 这一关。遇到这种"什么都不能用了"的场面，**先回头检查分区表 csv**，不要急着怀疑工具链、环境变量或者代码。

### 8.6 怎么确认 flash 到底多大

**结论先说：别看启动日志，去问芯片本身。**

```bash
python $IDF_PATH/components/esptool_py/esptool/esptool.py --port COM8 flash_id
```

```text
Chip is ESP8266EX
MAC: 8c:aa:b5:0b:dd:62
Manufacturer: 68
Device: 4014
Detected flash size: 1MB        ← 芯片当场回答的那个数
```

`Device` 的后两位就是容量，查表：

| Device 后两位 | 容量 |
| --- | --- |
| `14` | 1 MB |
| `15` | 2 MB |
| `16` | 4 MB |
| `17` | 8 MB |
| `18` | 16 MB |

> 这是 esptool 发 **JEDEC RDID (`0x9F`)** 命令、芯片**实时答复**的。
> 下面整条链路里，**只有这一步真正问过芯片**。

#### 为什么启动日志靠不住

因为 SDK **从来没有探测过 flash 大小**。同一个 `CONFIG_SPI_FLASH_SIZE` 有两个去处：

```c
/* spi_flash.c 里给 g_rom_flashchip 赋值那段 —— 结构体初始化，chip_size 是第二个字段 */
esp_rom_spiflash_chip_t g_rom_flashchip = {
    0x1640ef,
    CONFIG_SPI_FLASH_SIZE,   /* ← chip_size：直接把配置抄过来 */
    64 * 1024,
    4 * 1024,
    256,
    0xffff
};
```

```c
/* spi_flash.c —— 名字叫"获取芯片大小" */
size_t spi_flash_get_chip_size()
{
    return g_rom_flashchip.chip_size;   /* ← 还是那个配置值 */
}
```

**函数名骗人。** `get_chip_size()` 不 get 任何东西，它只是把配置读出来。
（`port.c` 里的 `MBPortSetMode()` 里还有一份同样的赋值。）

#### 后果：擦除能绕过芯片的物理边界

```c
/* spi_flash.c 里的 spi_flash_erase_sector() —— 擦除前的边界检查 */
if (sec >= (g_rom_flashchip.chip_size / g_rom_flashchip.sector_size)) {
    return ESP_ERR_FLASH_OP_FAIL;
}
```

**边界和被检查的对象是同一个值。** 配置写错了，"检查"就变成**拿错误去证明错误合法**。

于是那次事故是这样发生的：

```text
配置写 2MB，实际是 1MB
ota_1 排在 0x108000，长 0xF8000
              ↓
1MB 芯片只解码 A0–A19，第 20 位被直接丢弃
              ↓
0x108000 & 0xFFFFF = 0x008000   ← 地址"回绕"，不是报错
              ↓
擦 149 个扇区，从 0x008000 一路往上擦
              ↓
分区表(0x8000)、nvs(0x9000)、otadata(0xD000)、phy_init(0xF000)
以及正在运行的固件的 95.2% —— 全部归零
```

> **为什么连一句报错都没有？**
> 因为负责报错的那段代码，自己也在被擦的范围内。
> 芯片先把打印日志的函数擦掉，再继续调用它——于是串口安静地死掉。
> 这不是"日志看不懂"，是**根本没有机会打印**。

#### 一张表记住

| 想知道什么 | ❌ 别问 | ✅ 该问 |
| --- | --- | --- |
| flash 多大 | 启动日志的 `SPI Flash Size` | `esptool.py flash_id` |
| 分区表对不对 | 启动日志的分区列表 | `gen_esp32part.py --verify`（用法见 [分区表笔记 §12](ESP8266分区表.md#12-怎么验证)） |
| 固件多大 | 猜 | `ls -l build/esp-01S.bin` |

> **一句话**：凡是"SDK 打印出来告诉你"的硬件参数，先想一想它是**问来的**还是**抄配置抄来的**。

### 8.7 本项目当前使用的分区表

1MB 的 ESP-01S，**单 app 槽，没有 OTA**。见根目录的 [`partitions_1mb.csv`](../partitions_1mb.csv)：

```text
# Name,   Type, SubType, Offset,   Size, Flags
nvs,       data, nvs,     0x9000,   0x6000,
phy_init,  data, phy,     0xf000,   0x1000,
app,       app,  factory, 0x10000,  0xF0000,
```

首尾相接自检：

```text
0x9000  + 0x6000  = 0xF000     ✓
0xF000  + 0x1000  = 0x10000    ✓
0x10000 + 0xF0000 = 0x100000   ✓  正好 1MB
```

> **巧的是，这张表和 Espressif 自己给 1MB 芯片准备的默认表一字不差。**
> 打开 `components/partition_table/partitions_singleapp.csv`，就是这三行。
> 绕了一大圈，回到的正是官方默认布局。

#### 为什么没有 OTA

**两个槽放不下。** 两种切法都试过了，都不够：

```text
   1MB 去掉 bootloader / 分区表 / nvs / phy_init → 960 KiB 留给 app
        │
        ├─ 双槽对半分 = 每块 480 KiB
        │     本仓库固件实测 496448 字节（≈485 KiB）  → 超出 4.8 KiB  ❌
        │
        └─ Espressif 自己给 1MB 准备的双槽表（更紧）：
           partitions_two_ota.1MB.csv，每槽 0x70000 = 448 KiB
                → 超出 36.8 KiB  ❌
```

**关键在那 496448 是"OTA 已经拆掉之后"的固件。** 也就是说，装不下这件事
**不用再把 OTA 自身的体积算进来就已经成立了** —— 把 `ota.c` 放回去只会更胖。

> **SDK 其实早就知道这件事** —— `partition_table/Kconfig.projbuild` 里的 `PARTITION_TABLE_FILENAME` 配置项：
>
> ```text
> default partitions_two_ota.csv      if PARTITION_TABLE_TWO_OTA && ... && !ESPTOOLPY_FLASHSIZE_1MB
> default partitions_two_ota.1MB.csv  if PARTITION_TABLE_TWO_OTA && ... &&  ESPTOOLPY_FLASHSIZE_1MB
> ```
>
> 只要 `FLASHSIZE` 选的是 1MB，再选双 OTA，SDK 会**自动换成小槽表**。
> 出事的那份配置是 **Custom partition table CSV** —— 手写的表绕过了这条保护。

> **代码层面已经把 OTA 摘干净了**：`main/ota.c` / `main/ota.h` 和 `升级` 命令
> 都从工程里移走了，详见 [§9.9](#99-为什么这个工程没有-ota)。

#### 没有 otadata 也能启动吗

能，而且更简单。没有 otadata 分区时，bootloader 直接选 `factory`：

```c
/* bootloader_utility.c 里的 bootloader_utility_load_partition_table() —— 按 SubType 认，不看名字 */
case PART_SUBTYPE_FACTORY: /* factory binary */
    bs->factory = partition->pos;
```

所以 CSV 里这一行 `app, app, factory, ...` 一定启动得起来，
**不需要任何 OTA 选择逻辑参与**。

#### 换 WiFi 热点要不要改分区表

不要。热点名/密码存在 `nvs` 里，走网络就能改（`main/cmd.c` 里的 `wifi <SSID>,<密码>` 命令）。

> ⚠ **但这条路要求"节点还连得上"。** 连不上时的兜底是有的 ——
> 30 次重连失败后自己开热点、出一个网页让人用手机重填（§10），
> 但那是**本地**手段：人得走到板子旁边。所以能远程的时候**永远优先远程**。
>
> 顺带说明：原来那个"手机往空气里广播密码"的 SmartConfig 已经整个拆掉，
> 理由和实测数据见 §9.7。现在的兜底是**网页**，不是它。

> **顺带澄清一个常见误解**：OTA 是"换固件"，改密码是"改配置"，两件不相干的事。
> 而且 OTA 本身要走网络——密码改错、连不上了，OTA 也够不着它。

烧录后，启动日志里会打印实际生效的分区表（格式见第 7 节），可以核对是否改对了 ——
注意**核对的是三行的 Offset/Size，不是 `SPI Flash Size` 那一行**（理由见 §8.6）。

## 9. 联网控制：TCP 命令与热点切换

前面几节把"能编译、能烧进去、能启动"这条链路走通了。这一节讲的是
它长成**一个能被远程控制的灯开关**之后的样子。

### 9.1 八个文件，各管一段

`main/` 里不是一个越来越大的 `main.c`，而是按**职责**切开的：

| 文件 | 管什么 | 不管什么 |
| --- | --- | --- |
| `main.c` | 把下面这些**按顺序接起来**、启动 | 任何业务逻辑 |
| `relay.c` | 继电器怎么动（GPIO0 拉高 / 拉低） | 什么时候**该**动 |
| `cmd.c` | 攒字节、认关键字、派发动作 | 回执**走哪条路发回去** |
| `link.c` | 当前走 TCP 还是 UDP；所有回执的出口 | 命令**是什么意思** |
| `wifi_sta.c` | 连热点、存凭据、断线重连 | 连上以后干什么 |
| `ap_prov.c` | 连不上时的**兜底**：开热点 + 出网页收新凭据（§10） | 凭据存哪儿、连上以后干什么 |
| `tcp_client.c` | 建连接、收发字节 | 这些字节**是什么意思** |
| `udp_client.c` | 不建连接、直接丢数据报 | 同上 |

`main.c` 短到只剩 `app_main()` 和一个打印芯片信息的小函数：
把上面这些模块按顺序叫起来，自己一行业务都不做。
继电器怎么动、命令怎么解析，全在各自的文件里。

数据的流向：

```text
   ESP32 主节点
   TCP Server
        │  ① 发 "开灯"
        ▼
   ┌──────────────┐
   │ tcp_client.c │  ② recv() 拿到【裸字节】，原样往上抛
   └──────┬───────┘     （它不知道"开灯"是什么东西）
          │  回调 cmd_on_tcp_rx()
          ▼
   ┌──────────────┐
   │    cmd.c     │  ③ 攒进缓冲区 → 找关键字 → 决定干什么
   └──────┬───────┘
          │  relay_on()
          ▼
   ┌──────────────┐
   │   relay.c    │  ④ gpio_set_level()
   └──────┬───────┘
          ▼
       GPIO0 ──→ 继电器
```

要回话的时候（比如回一句 `LED ON`），`cmd.c` 也**不直接碰 socket**，
而是调 `link.c` 的 `link_send()` —— 由它按当前链路决定走 TCP 还是 UDP。

**为什么要拆开？** 因为 `tcp_client.c` 里没有一行代码知道"灯"这个东西存在。
将来把继电器换成温度传感器，`tcp_client.c` 一行都不用改。

### 9.2 拓扑：主节点 ESP32 自己开热点

**路由器不参与这个系统。** 主节点 ESP32 开一个 SoftAP，从节点连上去，
再走 TCP 连 ESP32 上的服务器：

```text
   ┌────────────────────────────────┐
   │  ESP32 主节点                   │
   │                                │
   │  SoftAP      "ESP32-S3-host"   │  ① 开热点
   │  AP 的 IP    192.168.4.1       │     ← 固定，不是 DHCP 分的
   │  DHCP 服务   给从节点分地址      │  ② 给 ESP-01S 分一个 IP
   │  TCP Server  监听 :8086        │  ③ 等从节点连上来
   └───────────────┬────────────────┘
                   │
                   │  空中：2.4GHz，中间没有路由器
                   │
   ┌───────────────▼────────────────┐
   │  ESP-01S 从节点（本仓库）        │
   │  STA       连 "ESP32-S3-host"   │
   │  自己的 IP  DHCP 分的（会变，无所谓）
   │  TCP Client 连 192.168.4.1:8086 │
   └────────────────────────────────┘
```

#### 为什么这个拓扑省事：**需要被知道的地址是死的**

`192.168.4.1` 不是"约定俗成"，是**编译进 SDK 的常量** ——
`tcpip_adapter_init()` 里无条件赋值（`tcpip_adapter_lwip.c`）：

```c
IP4_ADDR(&esp_ip[TCPIP_ADAPTER_IF_AP].ip,      192, 168, 4, 1);
IP4_ADDR(&esp_ip[TCPIP_ADAPTER_IF_AP].gw,      192, 168, 4, 1);
IP4_ADDR(&esp_ip[TCPIP_ADAPTER_IF_AP].netmask, 255, 255, 255, 0);
```

所以 [`main/tcp_client.c`](../main/tcp_client.c) 顶部那行硬编码的地址**永远有效**：

```c
#define TCP_SERVER_IP    "192.168.4.1"
#define TCP_SERVER_PORT  8086
```

> ⚠ **注意这里的角色分工，它才是省事的关键：**
>
> | | 谁的地址 | 会变吗 | 需要被别人知道吗 |
> | --- | --- | --- | --- |
> | 主节点 ESP32 | `192.168.4.1` | **不会** | **需要** —— 从节点要主动连它 |
> | 从节点 ESP-01S | DHCP 分的 | 会 | **不需要** —— 它只主动连别人 |
>
> **会变的那个地址，恰好是没人需要知道的那个。**
> 这就是 SoftAP 方案比"两个都连路由器"便宜的全部原因 ——
> 后者两个地址都会变，而其中一个还必须被硬编码。

> ⚠ **一个我必须说清楚的边界**：上面那个 `192.168.4.1` 是我**在这台机器上
> 查证过的**，查的是 `ESP8266_RTOS_SDK` 里的 `tcpip_adapter_lwip.c`。
> **ESP32 跑的是 ESP-IDF，不是这个 SDK** —— 我这边没有 ESP-IDF 源码，没法核对。
> ESP-IDF 的 SoftAP 默认值历史上也是 `192.168.4.1`，但**请以 ESP32 那边
> 实际打印出来的 IP 为准**，别把我的话当保证。

#### 两边必须对上的四个值

主节点和从节点是**各自独立编译**的，编译器不会帮你核对。
下面每一项对不上，现象都是"连不上"，但原因完全不同：

| 值 | 从节点（本仓库） | 主节点（ESP32） | 对不上会怎样 |
| --- | --- | --- | --- |
| SSID | `WIFI_SSID_DEFAULT`（`wifi_sta.c`） | `ap.ssid` | `reason=201`，**扫不到** |
| 密码 | `WIFI_PASSWORD_DEFAULT` | `ap.password` | `reason=15` / `205`，**握手不过** |
| 加密方式 | `threshold.authmode = WPA2_PSK` | `ap.authmode` 也必须是 WPA2 | 见下面 ⚠ |
| 端口 | `TCP_SERVER_PORT` | 服务器 `listen()` 的端口 | WiFi 连上了，**但 TCP 连不上** |

⚠ **加密方式那一条最容易踩**，因为两边的"默认"不一样：

```text
   从节点这边：
       cfg.sta.threshold.authmode = WIFI_AUTH_WPA2_PSK;
       意思是"比 WPA2 弱的（WEP、WPA-TKIP）我都不连"

   主节点那边：ESP32 的 SoftAP 如果开成【开放式】（authmode = OPEN）
       → 从节点直接把它过滤掉，连尝试都不尝试
```

所以主节点的 SoftAP 也要选 **WPA2-PSK**，而且**密码不能少于 8 字节**
（WPA2 的下限，短了 ESP32 那边拒绝开 AP）。

> **为什么阈值设成 `WPA2_PSK` 而不是"接受任何加密"？**
> 因为不设等于 `WIFI_AUTH_OPEN` —— 那会去连**开放性热点**。
> 在一个有几十个热点的环境里，这是真实存在的风险，不是理论问题。

#### 主节点要做的三件事（不在本仓库）

本仓库里只有从节点。ESP32 那边要另写，最少三件事：

```text
   ① 开 SoftAP
        esp_wifi_set_mode(WIFI_MODE_AP);
        esp_wifi_set_config(ESP_IF_WIFI_AP, &ap_cfg);
            ap_cfg.ap.ssid      = "ESP32-S3-host"   ┐
            ap_cfg.ap.password  = "88888888"        ├ 必须和 wifi_sta.c 对上
            ap_cfg.ap.authmode  = WIFI_AUTH_WPA2_PSK┘

   ② 起 TCP Server
        socket() → bind(:8086) → listen() → accept()

   ③ 收发 + 解析
        命令表可以直接照抄本仓库 cmd.c 那几个关键字
```

> ⚠ **ESP32 是 ESP-IDF，API 名字和这里不完全一样。**
> 最明显的差别：ESP-IDF v4+ 用 `esp_netif` 取代了 `tcpip_adapter`，
> 函数名和 `ESP_IF_WIFI_*` 这些常量都可能换了写法。
> WiFi 配置结构体的**形状**是一样的，但别直接复制粘贴。

#### 连上以后长什么样

```text
========== WiFi 连接成功 ==========
  SSID     : ESP32-S3-host
  IP       : 192.168.4.x          ← 从节点自己，DHCP 分的
  子网掩码 : 255.255.255.0
  网关     : 192.168.4.1          ← 主节点，固定
===================================
```

> **要对上的是「网关」那一行** —— 它必须等于 `TCP_SERVER_IP`。
> 上面的 IP 只是个例子（DHCP 每次分的都可能不同）。
>
> **换成 SoftAP 之后，这个"对不上"的风险基本消失了** ——
> 因为网关现在是常量。真对不上只剩一种可能：**宏被改错了**。
> （对比一下：原来连 Windows 热点时，网关是随电脑和热点开关变的。）

连上之后 ESP 会先主动发一句 `hello from ESP-01S`，
用来一眼确认这条链路是**双向**通的。

#### 台面调试：想用网络调试助手怎么办

**换 SoftAP 之后有个副作用，得提前知道**：原来电脑既是热点又是服务器，
所以你可以开着网络调试助手，**直接对着继电器敲 `开灯`**。
现在服务器搬到 ESP32 上了，这条路就没了。

> **要在台面上调，就把凭据临时改回电脑** —— 两套值都留在文件里，注释掉一套：
>
> ```c
> /* 台面调试：电脑开热点 + 网络调试助手当服务器 */
> #define WIFI_SSID_DEFAULT       "DESKTOP-XXXXXXX 0000"
> #define WIFI_PASSWORD_DEFAULT   "88888888"
> #define TCP_SERVER_IP           "192.168.137.1"
>
> /* 正式：ESP32 主节点 */
> /* #define WIFI_SSID_DEFAULT     "ESP32-S3-host"  */
> /* #define WIFI_PASSWORD_DEFAULT "88888888"       */
> /* #define TCP_SERVER_IP         "192.168.4.1"    */
> ```
>
> ⚠ **台面调试只对"第一次烧录"有效。** 一旦 NVS 里存过凭据（§9.6 的三层优先级），
> 后面改 `wifi_sta.c` 顶部**不再生效** —— 它会继续用 NVS 里那套。
> 想让新默认值生效得先擦 NVS，见 §9.7 最后那一节。

### 9.3 命令表

| 发送 | 动作 | 收到的回复 |
| --- | --- | --- |
| `开灯` / `on` | GPIO0 拉高，继电器吸合 | `LED ON  (GPIO0 = HIGH)` |
| `关灯` / `off` | GPIO0 拉低，继电器释放 | `LED OFF (GPIO0 = LOW)` |
| `wifi <SSID>,<密码>` | 换热点并存进 NVS | `WIFI OK (reconnecting)` |

回复一律用**纯 ASCII** —— 这样不管调试助手设成 UTF-8 还是 GBK，都不会显示成乱码。

> ⚠ **`wifi` 命令必须勾上"发送新行"。**
> 因为它要等到**整行**才执行：TCP 是字节流，一次 `recv()` 可能只收到
> `wifi DESKTOP`，后面的密码还没来。硬猜的话会把半截 SSID 存进 NVS。
> 所以规矩是**以换行结尾**。其它命令没有这个要求。

### 9.4 坑一：TCP 是字节流，不是消息队列

你在网络调试助手里点一次"发送"，ESP 这边 `recv()` 收到的**可能是**：

```text
① 一次收到完整的 "开灯"          ← 最理想
② 分两次收到 "开" 和 "灯"        ← 被网络拆包了
③ 一次收到 "开灯关灯"            ← 你连点了两次，粘在一起了
```

**所以绝对不能用每次 `recv` 到的内容直接去比较。**
那样 ②③ 两种情况都会失败，而且现象是"**偶尔灵偶尔不灵**"——最难查的那一类。

正确做法是**攒**：收到的字节先堆进一个缓冲区，再在缓冲区里找关键字，
找到就把那一条抠掉，剩下的继续留着等下一批字节来拼。

```c
static char s_cmd_buf[CMD_BUF_SIZE + 1];   /* 64 字节，+1 留给结尾的 '\0' */
static int  s_cmd_len = 0;
```

> 代码里那个 `while (cmd_try_one()) { }` 空循环是有意的：
> **一次收到的字节里可能拼出好几条命令**（就是上面的 ③），
> 得一条一条处理干净，不能只处理一条就走。

### 9.5 坑二：中文命令的编码

`strstr()` 比的是**字节**，不是"字"。同样是"开灯"两个字：

| 命令 | UTF-8 | GBK |
| --- | --- | --- |
| 开灯 | `E5 BC 80 E7 81 AF`（6 字节） | `BF AA B5 C6`（4 字节） |
| 关灯 | `E5 85 B3 E7 81 AF` | `B9 D8 B5 C6` |

**谁说了算？**

- `.c` 文件里写的 `"开灯"` 是什么字节 → 由**这个文件存成什么编码**决定（本文件是 UTF-8，6 字节）
- 调试助手发出来的是什么字节 → 由**助手的编码设置**决定（中文 Windows 上大多默认 GBK，4 字节）

两边对不上，`strstr` 就永远找不到。现象是：

> **串口明明打印"收到 N 字节"，但继电器不动，也没有回复。**

解法有三层：

1. **命令表里两种编码都收** —— UTF-8 和 GBK 各一行
2. **关键字写成转义字节**，不让它跟着文件编码走：

   ```c
   #define KEY_KAI_UTF8   "\xE5\xBC\x80\xE7\x81\xAF"   /* 开灯 */
   #define KEY_KAI_GBK    "\xBF\xAA\xB5\xC6"           /* 开灯 */
   ```

   这样无论这个文件将来被谁存成什么编码，匹配到的都是同一串字节。
3. **能不用中文就别用** —— `on` / `off` 这些 ASCII 别名没有编码歧义，是最保险的路

串口还会把收到的字节按十六进制打出来，一眼就能对上是哪种编码：

```text
[cmd] 收到 4 字节: BF AA B5 C6         ← 4 字节 = GBK
[cmd] 收到 6 字节: E5 BC 80 E7 81 AF   ← 6 字节 = UTF-8
```

> **一个容易忽略的坑：关键字可能互相"包含"。**
> 代码里那张命令表以前有过一条 `"config"`（进配网模式，已拆掉），
> 它里面就**含**着 `"on"`（c-**on**-fig）——
> 如果"找到一条就执行"，那收到 `config` 会先去**开灯**。
> 所以代码是**扫完整张表**，再挑**位置最靠前**的那条：
> `config` 从下标 0 开始，`on` 从下标 1 开始 —— config 胜出。
>
> **现在表里已经没有互相包含的关键字了，但这条规矩留着** ——
> 它是正确的通用规则，而下一个加进来的关键字随时可能再踩同一个坑。
> 别把它简化成"找到第一条就返回"。

### 9.6 换热点：三层凭据

**热点名和密码不该焊死在固件里。** 焊死的后果是：主节点换个密码，
这个节点就连不上了，只能把板子拆下来插串口线重烧。

所以凭据按优先级存在三个地方：

```text
   ① NVS（命名空间 app_cfg）        ← 运行时改过就用这个，掉电不丢
        ↓ 没有
   ② main/wifi_sta.c 顶部的默认值    ← 编译进固件的"出厂默认值"
        ↓ 没有
   ③ 用 ②，并顺手写进 ①
```

第一次上电时 NVS 是空的，走 ③；之后不管用什么方式改过密码，
都以 NVS 为准，`wifi_sta.c` 顶部那两行就不再生效了。

> **NVS = Non-Volatile Storage**，芯片 flash 里划出来的一小块**键值存储**区
> （就是 §8.7 分区表里的 `nvs` 分区，24 KB）。
> 它跟文件系统不是一回事：没有目录、没有文件，只有 `(命名空间, 键) → 值` 的映射，
> 用起来像个小字典。用 `nvs_open` / `nvs_get_str` / `nvs_set_str` / `nvs_commit` 操作。

**改热点只有两种情形，按"节点还连不连得上"分：**

| 节点状态 | 怎么做 | 要人到现场吗 |
| --- | --- | --- |
| 还连得上 | 发 TCP 命令 `wifi <SSID>,<密码>` | 不用 |
| 已经连不上 | 等它转**配网模式**，手机连它的热点开网页重填（§10） | **要** |

> ⚠ **第一行是这个工程最重要的一条操作纪律。**
> 第二行虽然能救回来，但代价是**得跑到板子跟前**；所以顺序仍然是：
> **① 先发 TCP 命令 `wifi <新SSID>,<新密码>` ② 再改主节点。**
> 反过来做，这块板子就得靠人肉一趟。

> **为什么用逗号分隔，不用空格？** 因为 **SSID 里可以有空格** ——
> 比如热点叫 `My Home WiFi`，用空格当分隔符就会被劈成两半。
>
> ⚠ 这跟当前默认值无关。现在连的 `ESP32-S3-host` 没有空格，
> **但别因为"现在的名字没空格"就把分隔符改成空格** —— 那等于把这条命令悄悄写窄了。

> **⚠ 换了 SoftAP 之后，"改热点"这件事的含义变了。**
> 主节点是 ESP32，热点名是**你写在 ESP32 固件里的**。
> 所以现在的正确顺序是：
>
> ```text
>    ① 改 ESP32 那边（写 "ESP32-S3-host-2" 之类）—— 先别烧！
>    ② 先在从节点上发  wifi ESP32-S3-host-2,<密码> ← 从节点还在旧热点上，够得着
>    ③ 再烧 ESP32，让它改名
> ```
>
> **顺序反了就得跑一趟现场。** 从节点一旦连不上新的热点名，
> 它会自己开热点等人来救（§10）—— 不是死，但要有人拿着手机过去。

长度限制来自 802.11 协议：**SSID ≤ 32 字节，密码 ≤ 64 字节**。
超长会在写进 NVS **之前**就被拒绝 —— 因为截断后照样能存进去，但永远连不上，
那种"**命令说成功了、就是连不上**"的毛病最难查。

### 9.7 连不上了怎么查（以及为什么拆掉了 SmartConfig）

#### 先看串口：失败提示长什么样

连不上时**不会立刻转配网**，而是**先定期报数** —— 报数期间看串口还能救；
一直不成才由 §10 的配网模式接手。
[`main/wifi_sta.c`](../main/wifi_sta.c) 里那条管理任务每 30 秒吭一声：

```text
[wifi] 第 3 次失败，reason=201
[wifi] 还没连上 "ESP32-S3-host"：已失败 3 次，仍在重试
[wifi]   查这三样：SSID 拼写（空格和大小写都算）、密码、
[wifi]   热点是不是只在 5GHz 上（ESP8266 只认 2.4GHz）
```

> **它只报不修，也不数到 30 就撒手。** 重连本身**不需要定时器** ——
> `wifi_event_handler()` 一收到"断开"事件就直接调 `esp_wifi_connect()` 了，
> 那是一条事件驱动的快路径。管理任务负责两件事：**别让你对着安静的串口猜**，
> 以及**数够 `WIFI_RETRY_BEFORE_AP` 次后把配网模式叫起来**（§10）。
> 30 秒这个间隔由 `WIFI_DOWN_REPORT_MS` 控制。

#### 一条捷径：用 reason 码分流

每条 `第 N 次失败` 后面那个数就是 **802.11 的原因码**，
它比"连不上"三个字信息量大得多：

| reason | 含义 | 说明什么 |
| --- | --- | --- |
| `201` | 扫不到这个 SSID | 名字写错，**或者热点在 5GHz** |
| `15` / `205` | 看得见 AP，但握手不过 | 密码不对 |

> ⚠ **先分清它是"扫不到"还是"连不上"** —— 这两类的排查方向**正好相反**：
> `201` 去查**名字和频段**（见下面 2.4GHz 那一节），`15`/`205` 才去查**密码**。
> 拿着 `201` 反复改密码，是这里最容易白费的一类功夫。

#### 省电模式那句不是修复，别指望它

官方 example 在 `esp_wifi_init()` 之后紧跟着有一句：

```c
ESP_ERROR_CHECK(esp_wifi_set_ps(WIFI_PS_NONE));
```

但**在这个 SDK 上它是冗余的**。查 `esp_wifi.h` 里的 `esp_wifi_set_ps()`：

```text
  * @attention Default power save type is WIFI_PS_NONE.
```

默认本来就是不省电 —— 所以**这不是任何问题的修复**，别把它当排查方向。
本项目保留这一句，只是想把"射频全程开着"这个前提写死。

> ⚠ 顺带记一个**容易混的地方**：`WIFI_PS_MIN_MODEM` 那句
> "每个 DTIM 信标时醒一下"（`esp_wifi_types.h` 里的 `wifi_state_t`）描述的是**省电模式本身的行为**，
> 不是"这个 SDK 的默认状态"。默认是 `WIFI_PS_NONE`，射频全程开着。

**不过这个前提在将来会真的有用**：SDK 自带的 ESP-NOW 示例
（`examples/wifi/espnow/README.md`）里明确写了一句 ——
**如果接收方是 station 模式且连着一个 AP，必须关掉 modem sleep**。
也就是说哪天从节点改用 ESP-NOW 走点对点，省电模式开着就会**收不到包**。
现在把这一句写死，等于提前把那个坑守住。

#### 热点必须是 2.4GHz

**这是"连不上"里最容易被忽略、也最容易查错方向的一条**，因为它和"密码错"
在日志上长得很像 —— 都是连不上，但原因完全在物理层：

```text
   热点开在 5GHz
        │
        └─ ESP8266 射频只有 2.4GHz，物理上【扫不到】它
               │
               ▼
       reason = 201（扫不到这个 SSID）
               │
       看起来像"名字写错了"，其实是"这个频段它根本没长眼睛"
```

Windows 的移动热点是**可选频段**的（不同版本默认值不一样），
所以这条**别靠猜**，直接去热点设置里看，或者看手机连上后 WiFi 详情里显示的频段。

> **换成 SoftAP 拓扑之后，这一条基本不用管了** ——
> ESP32 的 SoftAP 本来就只有 2.4GHz，不可能开错频段。
> 留着它是因为**台面调试**（§9.2 最后那一节）会连回 Windows 热点，
> 那时候这条又成立了。

#### 另一个反向的坑：改了默认值不生效

```text
   NVS 里有旧凭据  →  改 wifi_sta.c 顶部的 WIFI_SSID_DEFAULT 不起作用
```

因为凭据是三层优先级（§9.6），**NVS 那一层先命中就不会往下走**。
所以日志上会出现"代码里写 4128，它还在找 4127"这种看似灵异的现象。

想让新默认值生效，得先把 nvs 分区擦掉。`make erase_flash` 是 SDK 自带的整片擦除目标
（`components/esptool_py/Makefile.projbuild`，实际就是调 `esptool.py erase_flash`），
**它擦的是整块 flash** —— 分区表、固件、凭据一起没，之后要重新烧一遍。

#### 为什么拆掉了 SmartConfig

**结论**：**SmartConfig 这条路不要再接回来。** 现在的兜底是网页配网（§10）——
它慢、要人到现场，但它**看得见**：连没连上、存没存住，串口上都写着一行。

当年试过的是 SmartConfig：手机 App 把 SSID 和密码**编码成一串特制的
802.11 广播包**，节点在空口上直接收。它的卖点是**不需要节点认识任何路由器**，
听起来正好治"密码改了、节点已经连不上"。拆掉它有两层理由。

**第一层：它的链路太长，任何一环不配合就死，而且没有反馈。**

```text
   手机 WiFi 驱动肯不肯把 App 的包当广播发出去
        │
        ▼
   路由器肯不肯把这串包原样转出去
        │
        ▼
   ESP 的混杂模式肯不肯把这些帧递到我们手上
        │
        ▼
   配网库肯不肯认出包里的协议版本
```

四环，**每一环都不在我们的控制范围内**；而任何一环断了，现象都**完全一样**：
串口上安安静静，什么都没发生。没有错误码，没有进度，
也没法区分"手机没发"和"收到了但没认出来"。

**第二层：我们实测过，量出来的数在物理上说不通。**

动手改配网库之前先量了一遍空口：把 ESP 钉死在手机所在的那个信道（ch11）上，
数了 60 秒。下面是探针的原始输出（节选）：

```text
[wifi]   60 秒：共 17088 帧（管理帧 2114 / 单播上行 5421 / ★广播上行 0）
[wifi] ----- 整个窗口累计 17090 帧 -----
[wifi] ----- 发送方 MAC（单播上行 5423 帧 / 广播上行 0 帧）-----
[wifi]   a4:a4:90:ff:45:5e  单播  5422 (ch 11)  ★广播     0 (ch)
[wifi]   d4:58:97:9c:96:cc  单播     1 (ch 11)  ★广播     0 (ch)
```

上面那个 `a4:a4:90:ff:45:5e` 就是那部手机：**60 秒里发了 5422 个单播帧，
广播帧一个都没有。**

这个结果**本身就不成立**：

- 60 秒里 2114 个管理帧，约合**每秒 35 个**，绝大多数是信标 ——
  说明这条信道上有好几个 AP 加一堆客户端，是个**忙信道**
- 忙信道上**不可能一个组播数据帧都没有** ——
  ARP、DHCP、mDNS、IPv6 邻居发现**全都是组播**
- 所以只剩两种可能：**要么驱动没把组播数据帧交上来，要么探针的过滤把它挡住了**

也就是说：**探针在"广播"这个维度上是瞎的**，它证明不了"手机没发"。
而当时已经没有更好的办法去区分这两种可能了。事后回头看，
至少有两个嫌疑（当时都没来得及处理）：

- `esp_wifi.h` 里的 `esp_wifi_set_promiscuous_filter()` 写着：默认的混杂模式过滤器
  **"过滤除 `WIFI_PKT_MISC` 之外的所有数据包"**
- 官方 sniffer 例子里那句 `esp_wifi_set_recv_data_frame_payload(true)`
  （`examples/wifi/sniffer/main/sniffer_main.c`）**在任何公共头文件里都没有**，
  是例子自己 `extern` 声明的 —— 注释说它的作用是"启用接收正确的数据帧载荷"

> **一个查不下去的问题，比一个确定的问题更该放弃。**
> 配网这条路每次失败都要人跑到设备跟前按手机，失败时又给不出任何线索 ——
> 与其继续猜，不如换一条**能看见**的链路。

**拆掉它的代价现在补上了，但补得不完全一样。** 补上的是 §10 的网页配网：
节点连不上会自己开热点，手机连上去填新的 —— 但它**要人到现场**。
所以 §9.6 那条顺序纪律没有被省掉：换主节点凭据仍然必须是
**① 先发 TCP 命令 `wifi <新SSID>,<新密码>` ② 再改主节点**。

**顺带记一个技巧**（这次没救成，但对任何闭源库都通用）：
`components/esp8266/lib/libsmartconfig.a` 是**预编译的闭源库**，
没有源码可读，但它的**调试字符串是明文躺在二进制里的** ——
用 `strings` 之类的手段就能捞出来。当年"协议类型不对会卡在找信道之前"
这个结论就是这么来的。库自己打的进度是 `SC version` / `sync_len` /
`TYPE: ..., ch:%d` 这几类。

> **那以后用什么？** 主节点（ESP32）和这个从节点**都是自己的设备**，
> 所以"配网"这一步**可以整个省掉** —— 凭据直接烧进去，或者走 TCP 推。
>
> **链路已经定了（2026-09-25）：ESP32 开 SoftAP，从节点 TCP 连过去，路由器不参与。**
> 理由和细节见 §9.2，这里只留结论：
>
> | 方案 | 好处 | 代价 |
> | --- | --- | --- |
> | **✅ ESP32 开 SoftAP + 现有 TCP** | 服务端地址 `192.168.4.1` 是**编译期常量**，硬编码不会失效；[`main/tcp_client.c`](../main/tcp_client.c) 的传输层一行不用动 | 从节点**永远挂在这个 AP 上**，不再上家里路由器 —— 要控制它就得先连 ESP32 的热点；ESP32 的射频被 AP 占住 |
> | ⏸ ESP-NOW（**暂缓，不是否决**） | 连 IP 都不需要，单包上限 250 字节（`esp_now.h` 里的 `ESP_NOW_MAX_DATA_LEN` 宏） | 两端必须**同信道**；STA 模式下要关 modem sleep |
>
> 先让 TCP 这条路跑稳，ESP-NOW 作为第二步 —— [`main/tcp_client.c`](../main/tcp_client.c)
> 是纯传输层（只暴露 `send` + `set_rx_handler`），换掉它只需要动 `link.c`
> 那一层，业务层（`cmd.c`）一行不用改 —— 当初把接口切成这样就是为了留这个口子。

### 9.8 顺带两个硬件坑

**① 开灯 = GPIO0 拉高，而 GPIO0 是启动模式选择脚**

```text
复位那一刻芯片重新采样 GPIO0：
   高  →  从 Flash 启动，程序正常运行
   低  →  进 UART 下载模式，【程序根本不跑】
```

而继电器"关灯"时，GPIO0 正好是**低**的。所以将来任何要加重启的地方，
都必须**先把 GPIO0 拉高**（调 `relay_on()`，它在 `relay.c` 里）——
否则重启后模块是死的，串口一片安静，
**看起来像把板子刷坏了，其实只是进错模式了**。

> 本工程现在没有任何地方会调 `esp_restart()`，所以这条是"**别引入**"的提醒，
> 而不是"要处理"的问题。原来唯一会重启的是 OTA（见 §9.9），它已经移出工程了。
>
> **§10 的配网模式也是按这条约束设计的**：它不重启，而是在运行中把射频从
> STA 切成 AP，填完再切回 STA —— 这不是图省事，是因为重启那一刻 GPIO0
> 正好被继电器拉低（§9.8 ①），一复位就进下载模式，救不回来。

> 注意复位采样那一刻，GPIO0 是**输入 / 高阻态**，芯片只是在"读"这根线，
> 它此刻输出什么无关紧要。让它被读成高的，是**上拉电阻** ——
> 而上拉电阻不是驱动器，只能提供几十 µA。
> 一旦外接电路（比如继电器模块的输入端）把这根线拉低，弱上拉就扛不住，
> 芯片每次复位都会掉进下载模式。
>
> **真正决定命运的是挂在这根线上的外部电路**，不是程序里写 0 还是 1。

**② 供电不够会伪装成"程序跑飞"**

WiFi 发射瞬间电流会冲到 **170~300 mA**，叠加上继电器线圈，
如果还是拿 USB 转串口板那个 3.3V 脚供电，很容易掉电复位（brownout）。

> **模块开始反复重启、串口刷乱码时，先怀疑供电。**
> 在 VCC-GND 之间并 **100~470µF 电解电容 + 0.1µF 瓷片电容**。
> 这类故障和"代码有 bug"的现象几乎一模一样，但**改代码永远改不好**。

### 9.9 为什么这个工程没有 OTA

**OTA（远程升级）在这块板子上做不了，所以代码已经从工程里移走了**，
连同它的命令一起。剩下的是这条推理 —— 它是 §8 分区表那笔账的直接结论。

> 那两个文件没有删，挪到了本工程**外面**保存：
> `../ota-for-larger-flash/`（跟 `esp-01S/` 同级，同一个 `project/` 目录下）。
> 将来换 2MB 的模组，把它们移回 `main/`、换一张双槽分区表就能用。
> 那边的 `README.md` 写了来龙去脉。

要 OTA，分区表里就得有**两块 app 槽**：跑在 A 槽，把新固件写进 B 槽，
写完改 otadata 让 bootloader 下次从 B 启动。关键在"写进**另一块**" ——
不能一边跑一边改自己，那等于边开车边换发动机。

而两块槽意味着**每块都要放得下整个固件**：

```text
1MB flash 去掉 bootloader / 分区表 / nvs / phy_init 之后，正好剩 960 KB（0xF0000）给 app
   │
   ├─ 单槽：960 KB 全给一块              ✅ 现固件 496448 字节（≈485 KiB），还剩 475 KiB
   │
   └─ 双槽：两块对半分 = 每块 480 KB     ❌ 485 KiB > 480 KB，超出 4.8 KiB
                                         （SDK 自带那张 1MB 双槽表更紧：每槽 448 KB → 超出 36.8 KiB）
```

> **SDK 自己也知道这件事。** `components/partition_table/Kconfig.projbuild` 里的 `PARTITION_TABLE_FILENAME` 配置项：
>
> ```text
> default partitions_two_ota.csv      if PARTITION_TABLE_TWO_OTA && ... && !ESPTOOLPY_FLASHSIZE_1MB
> default partitions_two_ota.1MB.csv  if PARTITION_TABLE_TWO_OTA && ... &&  ESPTOOLPY_FLASHSIZE_1MB
> ```
>
> 这边只要 `FLASHSIZE` 选 1MB、又开了双 OTA，SDK 会自动换成小槽表
> （每槽 448 KB）—— 但 448 KB 同样放不下。换成自定义 CSV 只是**绕过了这层保护**，
> 并没有解决问题。

**为什么不是"把固件改小点"？** 这个固件已经很小了 —— 真正占地方的是
SDK 自带的 WiFi 协议栈和 TCP/IP 栈，砍不掉。想留 OTA，起点是 2MB 的模组。

> **顺带说说那个容易搞混的地方**：OTA 是"换固件"，改密码是"改配置"，两件不相干的事。
> 而且 OTA 本身要走网络 —— 密码改错、连不上了，OTA 也够不着它。
> **少了 OTA，这个工程的应急能力本来也没少**：在 1MB 的板子上它根本装不下，
> 而且它救不了"已经失联"这种场面 —— 那种场面归 §10 的配网模式管。

> ⚠ **上面那个 496448 是 2026-09-29 的构建**（`build/esp-01S.bin`），
> 也就是**加完配网模式之后**的样子 —— 这份固件里没有 OTA。
> 所以"两个槽装不下"这件事，**不用再把 OTA 自己的体积算进来就已经成立**。
>
> 这个数以后还会变（固件只会变胖）。**数字别记，要量**：
> 链接完 `ls -l build/esp-01S.bin` 看实际大小。

## 10. 配网模式：连不上时怎么救回来

§9.7 拆掉了 SmartConfig，留下一个洞：**节点失联之后怎么办。**
这一节补的就是那个洞 —— 从今往后，连不上不再等于"拆下来重烧"。

### 10.1 什么时候会自己进配网模式

开机以后 `wifi_sta.c` 照常重连，失败就一直重试（就是 §9.7 那套定期报数）。
**连续失败 `WIFI_RETRY_BEFORE_AP` 次**（默认 30，写在 [`main/wifi_sta.h`](../main/wifi_sta.h)）
之后，它会把配网模式叫起来。串口上会多出这么几行：

```text
[wifi] 第 30 次失败，reason=201
[wifi] 已经失败 30 次了，转配网模式

[prov] ========== 进入配网模式 ==========
[prov] 热点  : ESP-01S-Setup-A4B2
[prov] 密码  : 12345678
[prov] 手机连上后打开 http://192.168.4.1/
[prov] ================================
```

> **为什么是 30 次，不是 3 次？** 因为"连不上"里最常见的一类是**临时的**：
> 主节点还没启动完、信号一时不好、板子刚上电时 AP 的信标还没出来。
> 次数定得太低，主节点每次开机慢一点，从节点就开一次热点空等 ——
> 而它一旦进了配网模式，**TCP 那条路就断了**，一直断到有人来处理为止。
>
> 30 是个**权衡值**，不是协议规定，改它就是改
> [`main/wifi_sta.h`](../main/wifi_sta.h) 里的 `WIFI_RETRY_BEFORE_AP` 一行。
>
> ⚠ **它不是"30 秒"，也不是"30 次开机"。** 是**一次开机之内**重连失败 30 次。
> 每次之间隔多久取决于失败的方式 —— 扫不到 SSID（`201`）很快，
> 握手超时（`15`/`205`）慢得多 —— 所以**别按秒估，看串口上那个计数**。

### 10.2 它做的事：把射频从 STA 切成 AP

ESP8266 只有一套射频，**同一时刻只能是 STA 或者 AP**（还有一个 STA+AP 的混合模式，
这里不用它，理由见 10.4）。所以整段流程是"关掉一头、开另一头、办完再换回来"：

```text
   STA 连不上，数到 30
        │
        ▼
   ① esp_wifi_stop()          ← 先停下来，别在半开状态下改模式
        │
        ▼
   ② set_mode(WIFI_MODE_AP)   ← 声明"现在我是热点"
        │
        ▼
   ③ set_config(ESP_IF_WIFI_AP) + esp_wifi_start()
        │                        热点开始发信标，DHCP 服务跟着起来
        │                        （IP 固定是 192.168.4.1，不是 DHCP 分的）
        ▼
   ④ httpd_start() + 注册两个路由：GET / 和 POST /save
        │
        ▼
   ⑤ 【阻塞在这里】等人拿手机来填 —— portMAX_DELAY，没人来就一直等
        │
        ▼
   ⑥ 收到提交：先回"保存成功"页面，再立事件位
        │
        ▼
   ⑦ 等 1.5 秒（让页面画出来）→ httpd_stop() → esp_wifi_stop()
        │
        ▼
   ⑧ set_mode(WIFI_MODE_STA)，把凭据交还给 wifi_sta.c
        │
        ▼
   ⑨ wifi_sta.c 存 NVS → 拉回 STA → 连新热点
```

**⑦ 和 ⑧ 的顺序不能动**：先停网页、再停热点。反过来的话，网页还活着的那一小会儿
它的网卡已经没了，那条 socket 会怎么结束就不好说了。

> **为什么等 1.5 秒？** 两个作用：① 让手机把"保存成功"那页画出来 ——
> 下面一停热点，连接就断了，页面会变成"打不开"；② 立事件位只保证
> POST 处理函数**写完了回执**，它还要再返回一步，服务端在它返回之前被拆掉的话，
> 收尾的动作会踩在一个正在退出的会话上。

### 10.3 手机上怎么操作

```text
   ① 手机 WiFi 列表里找 ESP-01S-Setup-XXXX（XXXX 是这块板 MAC 的后两字节）
        密码 12345678
        ↓
   ② 连上之后浏览器打开  http://192.168.4.1/
        ↓
   ③ 页面顶部会写"这块板子现在连不上 XXX" ← 就是它当前在死磕的那个名字
        填【新的】热点名和密码，点"保存并连接"
        ↓
   ④ 看到"保存成功"就完事了
        手机回到原来那个 WiFi 即可；板子的热点马上就没了
```

> ⚠ **第 ④ 步之后别急着判定成败。** 页面说"保存成功"只表示**收到了**，
> 不表示**连上了**。真正的结果在串口上：`[wifi] 配网结束，改用 "xxx" 重新连`。
>
> **填错了会怎样？** 不会卡死，但要**再等 30 次失败**才会重新开热点。
> 所以填的时候慢一点 —— 这 30 次是按分钟计的。

> **热点名里那四个十六进制数是干嘛的？** 同时开着两块板子时，手机列表里能分清
> 哪块是哪块。都叫 `ESP-01S-Setup` 的话，你只能靠信号强弱猜，
> **猜错就是把 A 板的密码填进 B 板的 NVS 里。**

### 10.4 为什么这次能行，SmartConfig 那次不行

两件事解决的是**同一个问题**（节点已经连不上，怎么把新凭据送进去），
区别只在**链路**：

| | SmartConfig（已拆） | 网页配网（现在这个） |
| --- | --- | --- |
| 手机要不要装 App | 要 | 不要，浏览器就行 |
| 走什么 | 特制的 802.11 广播包，从**空气里**过 | 普通 TCP，手机直连板子的热点 |
| 谁可能把链路弄断 | 手机驱动、路由器、混杂模式过滤、**闭源**配网库（四环都不归我们管） | 只有手机和板子这两端，**都是我们能碰的** |
| 失败了看得见吗 | **看不见** —— 串口一片安静，没有错误码，也分不出"没发"还是"没收到" | 看得见 —— 每一页、每一行都有对应的一句 `printf` |
| 要不要人到现场 | 不用 | **要** |

**用"要人到现场"换"看得见"，这笔交易是划算的。** §9.7 那段实测数据的结论是
"探针在广播这个维度上是瞎的"—— 一个查不下去的问题，比一个确定的问题更该放弃。
网页这条路慢、笨、要人跑一趟，但它**每一步都有回音**。

> **为什么不用 STA+AP 混合模式？** 那样就不用关 STA 了，听起来更省事。
> 但混合模式下两个接口各占一份协议栈资源，而这块板子的内存本来就紧
> （§9.9 那笔账）；更关键的是**热点得跟着"连不上"这个状态走** ——
> 混合模式是常开的，那等于把配网热点**一直挂在空气里**，
> 旁边的人任何时候都能连上来改你的凭据。
> 现在这样只在需要的那几分钟存在，完了就关，更干净。

### 10.5 几个"看着奇怪、其实有原因"的地方

| 现象 | 原因 |
| --- | --- |
| 热点名后面跟着 `-A4B2` | MAC 后两字节。见 10.3 最后那条 |
| 热点密码是 `12345678` 这种固定值 | 它是**编译进固件的常量**，谈不上保密；作用只是别让旁边的人顺手把你的节点配到他家热点上 |
| 密码框**不是**那种隐藏的圆点，是明文的 | 手机上没法核对，打错一个字符就要再等两分钟才知道。这个热点只在配网那几分钟存在，**看得见比藏着强** |
| 两个输入框都写了 `autocapitalize="off"` | iOS 默认把输入框首字母改成大写，而 **SSID 区分大小写**。不改的话用户明明填对了却永远连不上 —— 这是最难查的一类 |
| 一个汉字算 **3 字节** | 表单长度按**字节**校验（SSID ≤ 32、密码 ≤ 64，都是 802.11 的协议上限）。手机输入框的 `maxlength` 数的是**字符**，拦不住"11 个汉字"这种 33 字节的 SSID |
| 超长/空值**整条拒收**，不截断 | 截断出来的名字照样能存进 NVS，但永远连不上 —— 而页面已经说过"保存成功"了 |
| 最多只让 2 台设备连 | 手机有时先连一条、过一会儿才释放旧的，卡在 1 上会出现"明明没人连却说连满了"。硬上限是 4，留 2 够用 |
| 页面刷新几次之后还能开 | `lru_purge_enable = true`。默认是**关**的，槽位被手机占满后新连接会被直接拒掉，表现是"热点连上了、页面就是打不开"，刷新多少次都没用 |

> **表单里那个 `+` 和 `%XX` 是要还原的。** 浏览器提交表单时把空格写成 `+`、
> 其余"不安全"的字节写成百分号加两位十六进制 —— 一个汉字会变成三组。
> 而 SDK 的 `httpd_query_key_value()` **只管把字段切出来，不做还原**。
> 不还原的话，写进 NVS 的就是那串转义本身，然后**一直连不上，串口上看着 SSID 还是对的**。

### 10.6 它救不了什么

**配网兜底不等于"什么都能救"。** 它只治一件事：**凭据填错了**（或者换了密码没通知它）。

| 场面 | 配网救得了吗 |
| --- | --- |
| 新密码填错了 / 主节点改了名 | ✅ 这正是它治的 |
| 主节点根本没开机 | ❌ 填对了也连不上，热点会一次次再开 |
| 热点开在 5GHz | ❌ ESP8266 物理上扫不到（§9.7） |
| 板子离主节点太远 | ❌ 参数没错，信号不够 |
| 固件本身坏了 / 分区表被擦了 | ❌ 那是烧录的事，得插串口线 |

所以 §9.6 那条顺序纪律**没有被省掉**：
**① 先发 TCP 命令 `wifi <新SSID>,<新密码>` ② 再改主节点。**
配网是**救急**的，不是**省事**的。

### 10.7 想改的话改哪儿

| 想改什么 | 去哪儿 |
| --- | --- |
| 失败几次转配网 | [`main/wifi_sta.h`](../main/wifi_sta.h) 的 `WIFI_RETRY_BEFORE_AP` |
| 配网热点的名字前缀 | [`main/ap_prov.c`](../main/ap_prov.c) 的 `AP_SSID_PREFIX` |
| 配网热点的密码 | 同一个文件的 `AP_PASSWORD`（**不能少于 8 字节**，短了热点起不来） |
| 热点开在哪个信道 | 同一个文件的 `AP_CHANNEL`（`1`/`6`/`11` 三个互不重叠，挑一个） |
| 网页长什么样 | 同一个文件的 `PAGE_HEAD` / `PAGE_TAIL` |
| 请求头最多能有多长 | **不在 `ap_prov.c` 里**，在 `sdkconfig` 的 `CONFIG_HTTPD_MAX_REQ_HDR_LEN`。见 10.8 |


> **加一个文件的时候别忘两件事**：`main/CMakeLists.txt` 的 `SRCS` 里要加
> （`main/component.mk` 是自动扫描的，不用管）；确认它对 `wifi_sta.h` 的
> 依赖是**单向**的 —— `ap_prov.c` 只调了 `wifi_sta_get_ssid()` 这一个只读函数，
> 所以"收上来的凭据交给谁"这件事它一概不知道，靠 `main.c` 把回调接起来。
> 这一刀是故意切的：`wifi_sta.c` 反过来要是包含了 `ap_prov.h`，两个文件就绕成一个环了。

### 10.8 踩过的坑：请求头塞不下，网页报 431

**现象。** 手机连上热点、页面也能打开，但一按"保存"，页面回一句：

> Header fields are too long for server to interpret

串口上同时出现这么一串：

```text
W (193896) httpd_parse: parse_block: response uri/header too big
W (193900) httpd_txrx: httpd_resp_send_err: 431 Request Header Fields Too Large - Header fields are too long for server to interpret
W (193923) httpd_parse: parse_block: incomplete (0/128) with parser error = 16
W (193926) httpd_txrx: httpd_resp_send_err: 400 Bad Request - Server unable to understand request due to invalid syntax
```

**这三条不是三件事，是一条。** 下面的 400 和 `parser error = 16` 是同一个根因的**回声**：
431 之后服务端把这条连接上的解析**暂停**了（16 就是 `HPE_PAUSED`），解析器停住，
剩下的字节当然"不完整"，于是又补报一个 400。**别去追 400，追 431。**

**根因是编译期常量。** `esp_http_server` 解析请求行和请求头时，用的是一块**固定的**
scratch 缓冲区，大小等于 `HTTPD_MAX_REQ_HDR_LEN`（`esp_httpd_priv.h` 里的 `HTTPD_SCRATCH_BUF` 宏，缓冲区本体在
`struct httpd_req_aux` 里，`esp_httpd_priv.h`）。而

```c
/* esp_http_server.h */
#define HTTPD_MAX_REQ_HDR_LEN  CONFIG_HTTPD_MAX_REQ_HDR_LEN
```

它来自 Kconfig，**默认 512**（`components/esp_http_server/Kconfig`）。请求头一旦超过，
`parse_block()` 拿到一个 0 长度就记下 `response uri/header too big`
（`httpd_parse.c`，顺带一提这句是 SDK 自己的**笔误**，它说的是 *request*），
然后回一个 431。

> **为什么电脑上试好好的，手机一填就超？** 因为超的是**请求头**，不是表单内容。
> 电脑上用 `curl` 发，头就那几行；手机浏览器会自己带上 `User-Agent`、一串 `Cookie`、
> `Accept-*`、`Sec-Fetch-*`、`sec-ch-ua*`…… 加起来轻松越过 512 字节。
> **也就是说，这个坑在开发机上基本复现不了 —— 它只在真手机上出现。**
> 页面本身能打开，也说明不了任何问题：GET 的请求头比 POST 短得多。
>
> 顺带解释这串日志里在最上面的那两行 `E wifi: AES PN: ...`：那是 WiFi 驱动在报
> "这个加密包号我见过"，属于重传/重复包，**和 HTTP 一点关系都没有**，不用管。

**怎么改。** `sdkconfig` 里改 `CONFIG_HTTPD_MAX_REQ_HDR_LEN`：

```text
CONFIG_HTTPD_MAX_REQ_HDR_LEN=2048
```

本工程从默认的 512 调到了 2048。**改完必须重新编译重新烧** —— 它是编进代码里的常量，
不是运行时可调的：`httpd_config_t` 里**根本没有**这个字段，`ap_prov.c` 里调不了它。

代价是 `httpd_start()` 时多分配 1.5 KB（2048 − 512 = 1536）。**这笔账划算**：
`struct httpd_data` 是整个服务**一次性** `calloc` 出来的（`httpd_main.c` 里的 `httpd_create()`），
**不是每条连接一份**，而且配网一结束、`httpd_stop()` 一调就还回去了 ——
也就是说这 1.5 KB 只在配网那几分钟里占着。

> **为什么要一次加到 2048，不先试 1024？** 因为失败的代价不对称。
> 加多了只是多占 1 KB 堆，而且是暂时的；加少了，用户得**走到设备跟前、
> 掏手机、连热点、填完表单，然后吃一个看不懂的英文报错**——还得再走一遍。
> 一个配网兜底功能，最不该出的就是"兜底的时候自己坏了"。
> 想知道当时到底还剩多少堆，看配网启动横幅里那行 `剩余内存:` 就行了。

| 看着像坏了，其实不是 | 其实是 |
| --- | --- |
| 页面能打开，说明网络没问题 | GET 的头比 POST 短。**能打开页面 ≠ POST 能进去** |
| `400 Bad Request - invalid syntax` | 431 处理完之后的回声，不是独立的语法错误 |
| `parser error = 16` | 16 是 `HPE_PAUSED`，"解析已暂停"，同样是被 431 触发的 |
| `AES PN: ...` | WiFi 驱动的重复包提示，无关 |
| 电脑上复现不了 | 手机请求头天生比电脑长。这类问题**只能在真手机上验** |
