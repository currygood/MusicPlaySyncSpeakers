> 环境：ESP-01S（**1MB** flash）· ESP8266_RTOS_SDK v3.4（`v3.4-115-g858c7c2e`）· 手机 ESP-TOUCH App
>

>

> （见 `ESP8266开发流程.md` §9.7），所以第 2 节那些"怎么用"的坑现在**用不上了** ——

## 1. SmartConfig 是怎么工作的

**先记住一句话：它传的不是数据，是"长度"。**

普通的思路是"把 SSID 和密码打包发过去"。但节点这时候**根本没连上任何热点**，
手机也没法找到它 —— 没有 IP、没有连接、没有地址可寻。

SmartConfig 绕开了这个问题：

```text
   手机（已连上目标热点）
        │
        │  App 把 SSID + 密码切成一串比特
        │  每个比特不去改包的内容，而是去改【包的长度】
        │      bit 0 → 发一个 len = A 的包
        │      bit 1 → 发一个 len = B 的包
        ▼
   目标热点（这时候它只是个【搬运工】，不知道自己在搬什么）
        │
        │  这些包是 UDP 广播 → AP 照常转发到本信道
        ▼
   节点（未连接，但射频在【混杂模式】下听）
        │
        │  每收到一帧就量一下长度
        ▼
   攒够比特 → 拼出 SSID + 密码 → 存 NVS → 去连
```

**为什么必须是"长度"？**

因为节点没连上，所以：

- 它**没有 MAC 层地址**可以被寻址 → 包只能发**广播**
- 它**没有 IP**，也没走四次握手 → 没有加密、没有关联
- 所以它只能看到**最裸的 802.11 帧**，而裸帧里**唯一可自由变化的、又不需要解密就能读到的字段，就是长度**

> **这不是猜的。** 库自己在日志里打了一行 `sync_len: [60,643]` ——
> 一个**长度区间**。一个不需要读内容、只需要卡长度的协议，
> 正好就需要这么一个常量。这是旁证，不是文档引用。

**推论（很重要）**：既然信息在长度里，
那么**你用 `tcpdump` 抓包看内容、看协议号、看端口，全是白费** ——
包里根本没有你要的东西。这也解释了为什么这个方案**天生没法用常规抓包工具排查**。

## 2. v3.4 上的四个坑

### 坑 1：协议类型必须**另外**设置，而且必须在 `start()` 之前

v3.4 的 `smartconfig_start_config_t` **只有三个字段**，没有 type
（`esp_smartconfig.h`：`enable_log` / `esp_touch_v2_enable_crypt` / `esp_touch_v2_key`）。

类型只能靠**另一个函数**单独设：

```c
esp_smartconfig_set_type(SMARTCONFIG_TYPE);   /* ← 漏了这一句，就拿不到你想要的协议 */
esp_smartconfig_start(&sc_cfg);
```

**不调会怎样？** 库里有个默认值 **2 = `SC_TYPE_ESPTOUCH_AIRKISS`**（两个协议都听）。

| 值 | 枚举名 | 手机 App |
| --- | --- | --- |
| 0 | `SC_TYPE_ESPTOUCH` | 老版 ESP Touch |
| 1 | `SC_TYPE_AIRKISS` | 微信 AirKiss（国内那套） |
| 2 | `SC_TYPE_ESPTOUCH_AIRKISS` | **库的默认值**，两个都听 |
| 3 | `SC_TYPE_ESPTOUCH_V2` | 新版 App，走 ESP-TOUCH V2 |

**本项目实测日志**（手机那端确认用的就是 V1）：

```text
SC version: V3.0.0, TYPE: 0        ← TYPE 0 = ESPTOUCH V1，两边是对上的
```

**所以这条坑我们没踩。** 记下来是因为它特别容易踩 ——
而一旦踩了，现象是"永远卡在找信道之前"，跟信号不好长得一模一样。

### 坑 2：App 版本必须和协议匹配，V1/V2 的 App **互不兼容**

官方 README 原话：ESP-Touch V1 和 V2 的**手机 App 互不兼容**。
V1 用老版 `ESP Touch`，V2 用 `ESP Touch V2`。

**装错了永远收不到**，而且报错方式和"没收到信号"完全一样。

### 坑 3：热点必须是 2.4GHz

ESP8266 射频**只有 2.4GHz**。热点开在 5GHz 上，它物理上扫不到、也收不到。

Windows 的移动热点是**可选频段**的，不同版本默认值不一样 —— **别靠猜，去设置里看**。

> 本项目就踩过：一开始电脑连的是 5GHz 网络，手机和 ESP 都连电脑的热点，
> 抓了半天才发现得先换成 2.4GHz 路由器。

### 坑 4：**这条是致命的** —— 链路太长，而且全环静默失败

```text
   ① 手机 WiFi 驱动肯不肯把 App 的包当广播发出去
        │
        ▼
   ② 路由器肯不肯把这串包原样转出去
        │
        ▼
   ③ ESP 的混杂模式肯不肯把这些帧递到我们手上
        │
        ▼
   ④ 配网库肯不肯认出包里的协议版本
```

**四环，每一环都不在我们的控制范围内。** 而任何一环断了，
现象**完全一样**：

```text
   串口上安安静静，什么都没发生。
   没有错误码，没有进度，也没有办法区分"手机没发"和"收到了但没认出来"。
```

> **前三个坑都有明确的排查方向，第四个坑没有。**
> 这份笔记后面全是围绕第四个坑展开的。

但"能收包"和"能收到**手机发的长度包**"是两件不同的事。
后者就要靠空口探针了 —— 见下一节。

## 4. 探针自己的三个坑

**这一节是这份笔记最有用的部分。**

配合追踪"手机到底发没发"，我写了一段空口探针：混杂模式 + 扫全部 13 个信道 +
统计每个信道上见了多少帧、都是谁发的。

**然后连踩三个坑，而且每个坑都让探针给出一个"看起来很确定"的错误结论。**

### 坑 A：我自己的方向过滤器，把要抓的帧**精准地**滤掉了

**我做了什么**：想只统计"节点上行"的帧，于是加了一句
（思路：只有发往分配系统的帧才置 ToDS 位）：

```c
if (!to_ds || from_ds) return;      /* 只保留"上行单播"，其余全丢 */
```

**结果**：MAC 表从几十个**塌到 2 个**。

**为什么**：802.11 帧控制字节的 ToDS/FromDS 位，规则是：

```text
   单播、发给 AP（经分配系统转发）   →  ToDS = 1   ← 只有这一类
   广播 / 组播                       →  ToDS = 0, FromDS = 0
```

**STA 发出的广播帧是 ToDS=0 的。** 而 ESP-TOUCH 的包是 **UDP 广播** ——
**正好全部落在我这个过滤器的"丢掉"那一侧。**

> **教训**：过滤器是**你对协议的理解**的编码。
> 理解错了，过滤器不会报错 —— **它会安静地、系统性地帮你删掉你最爱看的证据。**
> 而且删得越干净，你越觉得"结果很明确"。

### 坑 B：探针跑的时候，自动重连把射频抢走了

**现象**（实测日志，一次扫描的累计 MAC 表）：

```text
[wifi]   d4:58:97:9c:96:cc     46 帧  信道: 2 3 4 5 6 7 8 10
[wifi]   5c:02:14:7c:af:e2    355 帧  信道: 5 6 7 8 9
```

**问题在哪**：`d4:58:97:9c:96:cc` 出现在了 **8 个信道**上。

而**一个 802.11 射频，同一瞬间只在一个信道上。**
一个设备不可能同时在 8 个信道上发帧。

**所以这些帧的『信道』标签是不可信的** —— 驱动正在切信道，
而 `rx_ctrl.channel` 是在**回调执行时**取的，不是收帧那一刻。

**为什么在切信道**：那时候配网还没开始（`s_smartconfig_on` 是 false），
所以 `wifi_event_handler()` 收到断开事件就调 `esp_wifi_connect()` ——
**SDK 每次连接尝试会扫全部 13 个信道**，正好和探针的扫描打架。

**修法**：探针期间把重连停掉（拉标志位 + `esp_wifi_disconnect()` + 等一拍）。

> **教训**：**探针和数据源在抢同一个硬件的时候，量出来的东西不能信。**
> 看到一个"物理上不可能"的值（一个设备在 8 个信道），
> 别去解释它，**先怀疑测量本身**。

### 坑 C：混杂模式默认**不给你完整的数据帧载荷**

改完前两个坑，仍然没有广播帧。回头翻 SDK，发现两条：

**第一条**（`esp_wifi.h` 里的 `esp_wifi_set_promiscuous_filter()`）：

```text
  * @note The default filter is to filter all packets except WIFI_PKT_MISC
```

⚠️ **这句话有歧义，而且和实测对不上。** 按字面读，"默认只放行 `WIFI_PKT_MISC`" ——
但我们明明收到了 2114 个管理帧和 5421 个数据帧。

两种可能：**要么探针自己设过过滤器**（覆盖了默认值），
**要么这句文档根本没描述 v3.4 的实际行为**。当时没来得及确认。

> **教训**：**别按文档假设过滤器放行了什么 —— 打计数器，看实际收到了什么。**
> 头文件里的 `@note` 是给人看的，不是给编译器的。

**第二条**（`examples/wifi/sniffer/main/sniffer_main.c` 里的 `sniffer_task()`）：

```c
#if CONFIG_FILTER_MASK_DATA_FRAME_PAYLOAD
    /*Enable to receive the correct data frame payload*/
    extern esp_err_t esp_wifi_set_recv_data_frame_payload(bool enable_recv);
    ESP_ERROR_CHECK(esp_wifi_set_recv_data_frame_payload(true));
#endif
```

**三个信号，每一个都值得停下来看：**

1. 注释是 **"Enable to receive the correct data frame payload"** ——
   言下之意：**默认收到的载荷是"不正确的"**
2. 这个函数是 **`extern` 就地声明的** —— 意思是它在**任何公共头文件里都不存在**，
   官方例子自己都不知道该 `#include` 什么
3. 它被一个 **Kconfig 开关**包着，默认**不开**

> **教训**：官方例子里的 `extern` 是一个**信号**。
> 正经 API 不会需要 `extern` 就地声明 —— 出现这种写法，
> 说明**这个函数没打算给你用**，或者**忘了导出**。
> 两种情况下用它都要先问一句"我是不是在走一条没人维护的路"。

### 小结：探针踩坑的通用形状

```text
   过滤器理解错了         → 证据被安静地删掉（坑 A）
   探针和数据源抢硬件     → 标签被打错（坑 B）
   按文档假设了默认行为   → 少了一整个维度（坑 C）
```

**三个坑的共同点：探针都没有报错。**
它高高兴兴地打印出一堆数字，每个数字看上去都像个结论。

> **所以量之前先量"探针自己"。**
> 本项目最后能确认探针是好的，靠的是一条**自洽性检验**：
> 把 ESP 钉死在 ch11 数 60 秒，每轮统计的数据帧数
> **恰好等于**手机那个 MAC 的累计增量 ——
> 也就是说 ch11 上 **100% 的上行流量都来自那一部手机**。
> 数字对得上，探针才可信。

## 5. 那个「0 广播帧」到底证明了什么

### 实测数据（把 ESP 钉死在 ch11，连续 60 秒）

```text
[wifi]   60 秒：共 17088 帧（管理帧 2114 / 单播上行 5421 / ★广播上行 0）
[wifi] ----- 整个窗口累计 17090 帧 -----
[wifi] ----- 发送方 MAC（单播上行 5423 帧 / 广播上行 0 帧）-----
[wifi]   a4:a4:90:ff:45:5e  单播  5422 (ch 11)  ★广播     0 (ch)
[wifi]   d4:58:97:9c:96:cc  单播     1 (ch 11)  ★广播     0 (ch)
```

`a4:a4:90:ff:45:5e` 就是那部手机（用户比对手机 WiFi 详情确认过）。

**结果：60 秒里它发了 5422 个单播帧，广播帧一个都没有。**

### 为什么这个结果**本身就不成立**

```text
   60 秒 2114 个管理帧 ≈ 每秒 35 个，绝大多数是信标
        ↓
   说明这条信道上有好几个 AP 加一堆客户端 —— 是个【忙信道】
        ↓
   忙信道上【不可能】一个组播数据帧都没有
        ↓
   因为 ARP、DHCP、mDNS、IPv6 邻居发现 —— 【全都是组播】
```

**一个忙信道，60 秒，零组播。这在物理上说不通。**

### 所以结论是什么

**结论不是"手机没发"，而是"这个探针在『广播』这个维度上是瞎的"。**

两种可能，当时已经无法区分：

```text
   ① 驱动根本没把组播数据帧交给我们的回调
   ② 探针自己的过滤器把它挡住了（坑 C 那两条嫌疑）
```

**而"我分不清这两种可能"就等于"这条路查不下去了"。**

> ⚠️ **这是本项目最该记住的一条判断**：
> 当测量给出一个**物理上不可能**的结果时，
> **不要花力气去解释它，要花力气去证明测量本身是好的。**
> 做不到，就该承认"测不出来"，而不是拿这个数字当结论往下推。

## 6. 为什么最后放弃了

### 直接原因：查不动

```text
   ✗ 手机到底发没发？        —— 探针在广播这个维度上是瞎的（§5）
   ✗ 路由器转没转？          —— 没法在手机上验证
   ✗ 驱动交没交？            —— 闭源库 + 预编译驱动，看不到
   ✓ 协议类型对不对？        —— 对上了（TYPE: 0）
   ✓ 频段对不对？            —— 2.4GHz，而且库扫到了目标 AP
   ✓ 密码对不对？            —— 根本没走到这一步
```

**已知的都对，剩下的全都看不见。**

### 根本原因：它的失败方式**不给任何反馈**

这是 SmartConfig 和"其他难查的 bug"的根本区别：

| | 普通的 bug | SmartConfig 收不到包 |
| --- | --- | --- |
| 现象 | 报错 / 崩溃 / 行为异常 | **串口安静** |
| 复现 | 跑一遍就有 | **要人跑到设备跟前按手机** |
| 二分 | 能砍掉一半代码再试 | **砍哪一半都一样安静** |
| 日志 | 有 | **只有"卡在找信道"一句** |

**每试一次都要人工参与，而每次的结果都不增加任何信息。**
这不是"难"，这是**没有收敛路径**。

> **一个查不下去的问题，比一个确定的问题更该放弃。**

### 代价（必须如实说）

拆掉它的**当天**，代价是这样的：

```text
   节点一旦失联  →  没有任何远程办法  →  只能拆下来重烧
```

因此操作纪律变成：

```text
   换主节点凭据的顺序必须是：
     ① 先发 TCP 命令  wifi <新SSID>,<新密码>
     ② 再改主节点
   反过来做，这块板子就只能重烧了。
```

> **这个代价是可以接受的，因为这是个控制灯的继电器节点。**
> 但**必须写下来** —— 见 `ESP8266开发流程.md` §9.6 和 §9.7。
> 不写下代价的架构决策，下次会以"意外"的形式回来。

#### 后来补上了 —— 但补的不是 SmartConfig

**失联之后有路可走了**：节点连续 30 次连不上就自己开热点、出一个网页，
人拿手机连上去重填（`ESP8266开发流程.md` §10）。

```text
   节点一旦失联  →  自己开热点 + 网页  →  人走过去重填
```

对照下面第 7 节那句 **"AP 配网 = 所有厂商的保底方案"** ——
绕了一大圈，最后落回的正是当初记下的那个结论。

> ⚠ **但纪律没有被省掉，只被减轻了。** 网页配网**要人到现场**，
> 而 TCP 命令不用。所以能远程的时候永远优先远程：
> **① 先发 TCP 命令 ② 再改主节点。**
>
> 区别只在于：顺序写反了，现在的后果是"跑一趟"，不是"拆下来重烧"。

## 7. 智能家居大厂是怎么做的

**先看一个关键事实：大厂基本不拿 SmartConfig 当主力方案**，最多当第二/第三备选。

### 为什么

因为大厂面对的问题和本项目**不一样**：

| | 大厂 | 本项目 |
| --- | --- | --- |
| 产品形态 | 卖给陌生人，设备在**别人家** | **两端都是自己的** |
| 出货量 | 几十万，不能出一次问题 | 一块板子 |
| 失败成本 | 退货 / 客诉 / 差评 | 跑一趟现场（曾经是"拆下来重烧"） |
| 现场有没有人 | **有**，用户就在旁边 | 有（自己） |

> **本项目最后用的就是这张表里的第一行：AP 配网。**
> 节点连不上 30 次后自己开热点、出网页（`ESP8266开发流程.md` §10）。
> 本项目还有一条大厂没有的便利 —— **两端都是自己的设备**，
> 所以平时根本不配网，凭据直接走 TCP 推；AP 配网只当**保底**。

### 大厂实际用的方案

| 方案 | 怎么工作 | 为什么用它 |
| --- | --- | --- |
| **AP 配网** | 设备自己开一个热点，手机连上去、开网页填密码 | **所有厂商的保底方案**。最土，但最可靠 —— 不依赖路由器、不依赖 App 的特殊行为，只需要用户会连 WiFi |
| **BLE 配网** | 手机通过蓝牙把凭据传给设备 | **现代主流**。有双向通道 → **能反馈、能重试、能报错**。⚠️ **ESP8266 没有蓝牙，物理上做不到** |
| **Zigbee / Thread** | 设备只和**网关**说话，根本不碰路由器 | 配网问题**整个消失** —— 从没要求设备知道 SSID |
| SmartConfig | 见 §1 | 用户不用切 WiFi，体验最顺 —— 但只当**次要**方案 |

### 关键洞察：大厂把三件事**分开**解决

```text
   配网（把凭据送进设备）
        ↓  这是 SmartConfig 在干的事
   入网（让设备加入网络、拿到地址）
        ↓
   控制（日常的开关指令）
        ↓  这是 TCP / ESP-NOW 在干的事
```

**大厂几乎总是用「网关 / 集线器」架构**，就是为了把这三个问题**解耦** ——
设备只跟网关说话，网关才去管路由器。

### 那本项目呢

**本项目可以把"配网"这一步整个删掉。**

理由：**两端都是自己的设备。**
SSID 和密码可以直接烧进固件，或者设备连上以后用 TCP 推一条命令过去。

```text
   大厂必须先解决配网，因为设备在别人家、它不知道别人家的 WiFi 密码。
   本项目不需要解决配网，因为写固件的人【就是】拉网线的人。
```

> **这是放弃 SmartConfig 的正当性来源。**
> 不是"SmartConfig 不好用"，而是**它解决的问题在本项目里根本不存在**。
> 一个为解决不存在的问题而引入的、又没有反馈的故障点 —— 删掉是净收益。

### 主节点链路：已经选了（2026-09-25）

主节点 ESP32、从节点 ESP-01S。**选了 ESP32 开 SoftAP + 现有 TCP。**

选的依据是**"哪个地址必须被知道"**，不是"哪个更先进"：

```text
   ESP32 主节点                          ESP-01S 从节点
   SoftAP "ESP32-S3-host"    ←── 连 ──   STA
   IP 192.168.4.1（【常量】）             IP 由 DHCP 分（会变，但没人需要知道）
   TCP Server :8086          ←── 连 ──   TCP Client
```

**关键的不对称**：

| | 地址 | 会变吗 | 需要被别人知道吗 |
| --- | --- | --- | --- |
| 主节点 ESP32 | `192.168.4.1` | **不会**（SDK 里的常量） | **需要** —— 从节点要主动连它 |
| 从节点 ESP-01S | DHCP 分的 | 会 | **不需要** —— 它只主动连别人 |

**会变的那个地址，恰好是没人需要知道的那个。** 这就是它便宜的全部原因。

| 方案 | 结论 |
| --- | --- |
| **ESP32 开 SoftAP + 现有 TCP** | **✅ 已选**（改动约 3 行） |
| ESP-NOW | ⏸ 以后可能要 —— 见下面的坑 |
| 两个都连路由器，ESP32 当 server | ❌ 落选：主节点地址变成 DHCP 分的，硬编码会随租约失效 |
| ESP-NOW + 从节点同时连路由器 | ❌ 落选：射频被钉在 AP 信道上，AP 一换信道就断 |

> **ESP-NOW 的坑提前记一笔**：`examples/wifi/espnow/README.md` 明确写着 ——
> **如果接收方是 station 模式且连着一个 AP，必须关掉 modem sleep。**
> 本项目代码里 `esp_wifi_set_ps(WIFI_PS_NONE)` 那一句已经在了，
> 而且它在 v3.4 上**本来就是默认值**（`esp_wifi.h` 里的 `esp_wifi_set_ps()`）——
> 所以那句现在是冗余的，**但留着它对 ESP-NOW 是必需的**。

> ⚠ **落选不等于没用。** 哪天要扩展到多个节点、或者要让手机/电脑
> 也能直接够着从节点，就得回头选"都连路由器"那条路 ——
> 那时候要补的是**地址发现**（静态 IP / DHCP 保留 / mDNS，
> 本 SDK 里有 `components/mdns` 可直接用）。

## 8. 顺带：闭源库怎么查

`components/esp8266/lib/libsmartconfig.a` 是**预编译的闭源库**，没有源码。
**但它的调试字符串是明文躺在二进制里的。**

```bash
strings libsmartconfig.a | grep -i -E "sync_len|TYPE|SC version"
```

捞出来的东西能拼出这张表：

```text
   库打印的                       落在哪个 .o            说明
   ────────────────────────────   ────────────────────   ───────────────────────
   SC version: %s, TYPE: %d       sc_sniffer.o           本次用的协议
   ch %d rs %d ssid %s ...        sc_sniffer.o           扫描结果，每个 AP 一行
   sync_len: [%d,%d]              sc_sniffer.o           库内部的同步检测
   TYPE: ESPTOUCH, ch:%d          sc_esptouch.o          ← 按 ESPTOUCH 锁定信道
   TYPE: ESPTOUCH_V2, ch: %d      sc_esptouch_v2.o       ← 按 V2 锁定信道
   TYPE: AIRKISS, ch:%d           sc_airkiss.o           ← 按 AirKiss 锁定信道
```

> **这张表是"从二进制里读出来的"，不是"从文档里查到的"。**
> 后面三行的 `ch:%d` 和事件 `SC_EVENT_FOUND_CHANNEL` 语义对得很齐，
> 但**库的字符串顺序不等于严格的调用顺序** —— 当排查线索用，别当规范。

**这招对任何闭源 `.a` 都通用。** 判断依据：

```text
   ✗ 看不到源码          → 以为没法查
   ✓ 但能看到【字符串】  → 能知道它【会打印什么】
   ✓ 拿到打印内容        → 就知道它【走到哪一步】了
```

**代价**：`strings` 只能给你"它有哪些状态"，给不了"它为什么停在这"。
所以这招能定位**卡在哪**，**不能**解释**为什么卡** ——
这次就是卡在 `ch-N` 循环上，然后就到头了。

## 9. 一页速查

```text
SmartConfig 原理：
  传的不是数据，是【包的长度】
  手机改长度 → AP 当搬运工 → 节点混杂模式听长度
  ⚠ 所以抓包看内容 = 白费，包里没有你要的东西

v3.4 四个坑（现在用不上了，但记着它的形状）：
  1. 类型要【另外】设，且必须在 start() 之前；默认是 2（两个协议都听）
  2. App 版本和协议必须匹配 —— V1/V2 的 App 互不兼容
  3. 热点必须 2.4GHz（ESP8266 射频只有 2.4GHz）
  4. ★ 四环链路全都不受控，且【全环静默失败】← 致命的那条

排查的顺序：
  先看库自己的日志（它会打 SC version / ch rs ssid / sync_len）
  只有 ch-N 在反复跳  →  卡在【锁信道】，后面的流程全没走
  ⚠ 日志到这就没了 —— 再往下就要空口探针

★ 探针自己的三个坑（最有价值，换项目照样踩）：
  A. 过滤器是【你的协议理解】的编码
     我加了 if (!to_ds || from_ds) return; 想只留上行
     结果 STA 发的广播帧是 ToDS=0 → ESP-TOUCH 的包被【精准删光】
     MAC 表从几十个塌到 2 个，而探针一声不响
  B. 探针和数据源抢同一个射频时，量出来的不能信
     一个设备出现在 8 个信道上（2 3 4 5 6 7 8 10）—— 物理上不可能
     原因：wifi_event_handler 在 esp_wifi_connect()，SDK 每次扫全 13 信道
  C. 别按文档假设默认行为
     esp_wifi.h 里的 esp_wifi_set_promiscuous_filter() 说"默认只放行 WIFI_PKT_MISC"，和实测【对不上】
     sniffer_main.c 里的 sniffer_task() 里 esp_wifi_set_recv_data_frame_payload()
     是 extern 就地声明的 —— 公共头文件里【根本不存在】
     ⚠ 官方例子里出现 extern，说明这条路没人维护
  → 三个坑的共同点：【探针都不会报错】，它高高兴兴打印一堆像结论的数字

★★ 最重要的判断：
  测量给出【物理上不可能】的结果时，不要解释它，
  要证明【测量本身是好的】。做不到就承认"测不出来"。

  本例：60 秒 / 17090 帧 / 2114 个管理帧（≈35 信标/秒，忙信道）/
        单播上行 5421 / ★广播上行 0
        ARP、DHCP、mDNS、IPv6-ND 全是组播 → 忙信道不可能零组播
        ⇒ 不是"手机没发"，是"探针在广播这个维度上是瞎的"

放弃的理由：
  已知的全对（协议 TYPE: 0 / 2.4GHz / 库扫到了 AP），剩下的全看不见
  每试一次都要人跑到设备跟前按手机，而结果【不增加任何信息】
  ⇒ 不是"难"，是【没有收敛路径】
  一个查不下去的问题，比一个确定的问题更该放弃

代价（必须写下来）：
  拆掉当天：节点一旦失联 → 没有任何远程办法 → 只能拆下来重烧
  后来补上：节点一旦失联 → 自己开热点 + 网页 → 人走过去重填
  所以：① 先发 TCP 命令 wifi <新SSID>,<新密码>  ② 再改主节点
        （配网要人到现场，能远程就永远优先远程）

大厂怎么做：
  配网 / 入网 / 控制 是【三个独立问题】，大厂用网关架构把它们解耦
  AP 配网 = 所有厂商的保底方案
  BLE 配网 = 现代主流（有双向通道 → 能反馈）⚠ ESP8266 没蓝牙，做不到
  Zigbee/Thread = 设备只跟网关说话，配网问题整个消失
  SmartConfig = 永远只是次要方案，从不单独用

  ★ 本项目【可以把配网整个删掉】：两端都是自己的设备
    → 不是"SmartConfig 不好用"，是它解决的问题在这里【不存在】
```
