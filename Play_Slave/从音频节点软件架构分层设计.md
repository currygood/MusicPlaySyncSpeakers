# 从音频节点软件架构分层设计

> 适用工程：`Play_Slave`（ESP32-S3-N16R8，16MB Flash + 8MB OPI PSRAM）
> 通信协议：UDP 音频协议 v2（单播，端口 5680）
> 最后更新：2026-10-23

## 0. 文档定位

本文描述**当前代码实际运行**的从节点架构。

`docs/02-设计/从音频节点软件架构分层设计.md` 描述的是早期方案（组播 239.0.0.1:5678 + 控制 5679 + PING/PONG 时钟同步），该方案已经在 MVP 重构中被替换，**两份文档冲突时以本文和代码为准**。

当前方案与旧方案的核心差别：

| 项目 | 旧方案（已废弃） | 当前方案（v2） |
| --- | --- | --- |
| 音频承载 | 组播 239.0.0.1:5678 | **单播 UDP 到从节点 5680** |
| 时钟同步 | 从节点发 PING，主节点回 PONG | **单向估计**：用每帧的 `t_play_us` 与本地收包时刻求最小单程延迟 |
| 从节点上行流量 | PING 包 | **无**（从节点不发任何网络包） |

| 控制通道 | 组播 5679（多种命令） | 组播 5679（当前只处理音量） |

历史背景与问题定位过程见 `docs/04-测试/从节点无法播放的问题解决.md`。

## 1. 设计目标与原则

### 1.1 设计目标

从节点的职责只有一件事：**在正确的时间，把主节点发来的 PCM 数据送到功放**。

“正确的时间”指与主节点本地播放对齐。主节点是声学基准，从节点可以比主节点晚一个固定的最小网络延迟（局域网通常 1~3ms），但不能忽早忽晚，否则同一房间会听到回声。

硬件与业务范围：从节点只保留 Wi-Fi + I2S 功放输出，业务路径不包含经典蓝牙、LCD、SD 卡、麦克风。`debug.c` 里的 SD 裸扇区测试和蜂鸣自检只是调试入口，默认不参与启动流程。

### 1.2 设计原则

#### （1）时间戳驱动，而不是“收到就播”

UDP 到达时刻受网络抖动影响，直接写 I2S 会让出声时刻随机漂移。每一帧都带主节点给出的 `t_play_us`，从节点先把帧放进抖动缓冲，再按时间戳换算成本地时刻后播放。

#### （2）从节点保持单向、零回包

时钟偏移用“最小单程延迟”单向估计，从节点不需要向主节点发 PING，主节点也不需要维护 PONG 处理逻辑。好处：

- 从节点没有上行流量，不占用 Wi-Fi 发送机会；
- 主节点不需要为每个从节点维护未决 PING 表；
- 旧架构中发送通道因组播回环且无人读取而耗尽 lwIP pbuf 的问题，也随数据面改单播、发送通道关闭回环而消失（详见 §3.4.1）。

代价是偏移里含一个常量偏差 `L_min`（最小单程延迟），局域网 1~3ms，人耳不可闻。

#### （3）数据面单播，控制面组播

- 音频：点对点单播，有明确的目的地址，不依赖 AP 的组播转发策略；
- 控制：组播 239.0.0.1:5679，一次下发所有从节点。

#### （4）分层单向依赖

上层可以调用下层，下层不反向依赖上层；业务模块之间只允许通过明确声明的接口协作（如 `ctl_rx → amplifier`）。`main` 是唯一的装配层，负责初始化顺序和参数注入。

#### （5）大缓冲放 PSRAM，内部 RAM 留给 Wi-Fi / DMA

从节点的抖动缓冲、音量工作缓冲、任务工作缓冲都优先分配在 PSRAM。内部 DRAM 主要留给中断、Wi-Fi/lwIP、FreeRTOS 栈和 I2S DMA。

#### （6）异常必须可恢复、可观测

丢包、断流、缓冲过深、时钟漂移都在播放任务内部闭环处理，并通过周期日志输出计数器和缓冲水位。网络恢复后不需要重启。

#### （7）MVP 边界明确

`MusicPlay`、`ota_manager` 当前是空桩，保留目录和构建入口；没有实现的功能不强行接入主链路。

## 3. 各层详细设计

### 3.1 BSP 层

#### 3.1.1 i2s_driver

**职责**：把 ESP32-S3 的 I2S 外设封装成句柄化的“物理总线”，只负责配置、收发、切换采样率，不包含任何业务逻辑。

**设计约定**：

1. 引脚、采样率、位宽、槽位模式全部由调用方通过 `i2s_pin_cfg_t` / `i2s_bus_cfg_t` 传入，驱动本身不写死板级参数；
2. 一个句柄绑定一个 I2S 控制器端口、一个方向（TX 或 RX）；
3. **驱动内部没有锁**，多任务串行化由上层负责（当前由 `amplifier` 的写锁承担）；
4. `i2s_bus_phy_set_sample_rate()` 内部是 `disable → reconfig → enable`，会清空 DMA 中尚未播放的数据，调用方必须清楚这个代价。当前音频路径**不调用**它。

**接口**：

```c
esp_err_t i2s_bus_phy_create(i2s_port_t port, bool is_tx,
                             const i2s_pin_cfg_t *pins,
                             const i2s_bus_cfg_t *cfg,
                             i2s_bus_handle_t *out);
esp_err_t i2s_bus_phy_write(i2s_bus_handle_t h, const uint8_t *data,
                            size_t len, size_t *written, uint32_t timeout);
esp_err_t i2s_bus_phy_read(...);
esp_err_t i2s_bus_phy_flush(i2s_bus_handle_t h);
esp_err_t i2s_bus_phy_set_sample_rate(i2s_bus_handle_t h, uint32_t sample_rate);
esp_err_t i2s_bus_phy_destroy(i2s_bus_handle_t h);
void      i2s_bus_phy_debug_dma(i2s_bus_handle_t h);
```

当前板卡只使用 `I2S_NUM_1` TX：BCLK=GPIO8、WS=GPIO9、DOUT=GPIO10。RX 接口保留给后续麦克风使用。

#### 3.1.2 gpio_driver

**职责**：对 `gpio_set_level` / `gpio_get_level` 等 IDF 接口做薄封装，统一初始化方向和上下拉，供 `StartAndStop`、`StatusLed` 使用。

```c
esp_err_t Gpio_Init(gpio_num_t gpio, gpio_mode_t mode);
esp_err_t Gpio_Set_Level(gpio_num_t gpio, uint32_t level);
int       Gpio_Get_Level(gpio_num_t gpio);
esp_err_t Gpio_Toggle(gpio_num_t gpio);
/* 中断注册接口保留，当前业务未使用 */
```

有效电平由调用方解释：`StartAndStop` 认为按键低电平为按下，`StatusLed` 认为高电平点亮。

### 3.2 中间件层

#### 3.2.1 udp_audio（数据面核心）

##### 3.2.1.1 模块职责

`udp_audio` 是从节点唯一的声音来源，负责：

1. 监听单播 UDP 端口 5680；
2. 校验帧头、识别新流、过滤迟到/重复包；
3. 按 `seq` 写入环形抖动缓冲；
4. 用帧头时间戳估计并冻结本地时钟偏移；
5. 完成 preroll 后按目标时刻写 I2S；
6. 丢包时做 PLC，缓冲过深时跳帧，晶振漂移时做 sample slip；
7. 周期输出统计日志。

它**不负责**：音量控制（`ctl_rx` → `amplifier`）、播放状态 UI（`StatusLed` 未联动）、本地曲库（`MusicPlay` 为空桩）。

##### 3.2.1.2 线格式（协议 v2）

小端字节序，固定 20 字节头 + PCM：

| 偏移 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | `uint16` | `magic` | 固定 `0xAA55` |
| 2 | `uint8` | `version` | 固定 `2`，版本不符直接丢弃 |
| 3 | `uint8` | `flags` | bit0 = 本次流的首帧（`UDIO_FLAG_STREAM_START`） |
| 4 | `uint16` | `stream_id` | 一次流唯一标识，发送端重启会变 |
| 6 | `uint16` | `seq` | 包序号，0~65535 回绕 |
| 8 | `uint64` | `t_play_us` | 该帧的基准播放时刻（**发送端时钟**，µs） |
| 16 | `uint16` | `payload_len` | PCM 字节数（不含头） |
| 18 | `uint16` | `lead_ms` | 发送端提前量 D（ms），当前为 200 |
| 20 | `int16[]` | `pcm` | 44100Hz / 单声道 / 16bit 小端 |

`t_play_us` 放在偏移 8，保证 8 字节对齐，接收端可以直接按 `uint64_t` 读取（结构体声明为 `packed`）。

固定参数：

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `UDIO_SAMPLE_RATE` | 44100 | 全链路采样率 |
| `UDIO_CHANNELS` | 1 | 单声道 |
| `UDIO_BITS` | 16 | 位深 |
| `UDIO_MARGIN_US` | 60000 | 接收端抖动余量 / 主节点本地播放余量 |
| `UDIO_DEFAULT_PORT` | 5680 | 从节点监听端口 |

发送端当前每 15ms 发一帧（661/662 采样交替），PC 测试脚本默认 10ms 一帧（441 采样）。接收端按 `payload_len` 自适应，不依赖固定帧长。

##### 3.2.1.3 两个任务与共享状态

| 任务 | 优先级 | 栈 | 核心 | 阻塞点 | 职责 |
| --- | --- | --- | --- | --- | --- |
| `udp_audio_rx` | 11 | 4096 | 不绑定 | `recvfrom` 200ms 超时 | 收包、校验、落槽、更新偏移窗口 |
| `udp_audio_play` | 10 | 5120 | 不绑定 | `Amplifier_Play_Buffer(..., UINT32_MAX)` | preroll、对齐、PLC、sample slip、写 I2S |

两个任务通过一把互斥锁 `s_lock` 保护环形槽位和所有跨任务字段。**铁律：持锁期间绝不调用 `Amplifier_Play_Buffer()`**——I2S 写可能阻塞十几毫秒，持锁会把接收任务一起卡住。

接收任务的处理顺序：

```text
recvfrom
  → 长度 / magic / version / 采样数校验（bad_pkts）
  → 识别新流（stream_id 变化，或首帧标志 + 真停顿/seq 倒退）
      → 清空全部槽位、重置偏移窗口、s_playing=false
  → 已播过的包（seq 落后于读游标）→ late_pkts，丢弃
  → 槽位已有同一 seq → dup_pkts，丢弃
  → 拷贝 PCM、最后写 valid=1
  → 更新 s_first_seq / s_write_seq / s_last_t_play_us / s_last_rx_us
  → ua_offset_update_locked(d = now − t_play_us)
```

`valid` 最后写，保证播放任务不会读到半成品槽位。

##### 3.2.1.4 时钟偏移的单向估计

设：

- 主节点时钟为 `M`，从节点时钟为 `S`，两者差 `Δ = S − M`；
- 第 i 帧在主节点时刻 `t_tx` 发出，`t_play = t_tx + D`（`D = lead_ms = 200ms`）；
- 单程网络延迟为 `L(i)`，从节点在 `S_rx = t_tx + L(i) + Δ` 收到。

定义：

```text
d(i)   = S_rx(i) − t_play(i)
       = (t_tx + L(i) + Δ) − (t_tx + D)
       = Δ + L(i) − D
```

取最近 64 个包的最小值：

```text
d_min = Δ − D + L_min
```

于是：

```text
offset = d_min + lead_ms × 1000 + UDIO_MARGIN_US
       = Δ + L_min + 60ms
```

从节点在本地时刻 `t_play + offset` 出声。换算回主节点时间轴：

```text
从节点出声时刻（主节点时钟）
  = (t_play + Δ + L_min + 60ms) − Δ
  = t_play + L_min + 60ms
```

主节点本地在 `t_play + 60ms` 出声，所以从节点只比主节点晚 `L_min`（局域网 1~3ms），听不出先后。

**为什么用最小值**：排队延迟、Wi-Fi 重传、AP 省电都会让 `L(i)` 变大，只有最小值最接近真实传播延迟。窗口取 64 个包，在 100 包/秒时约 640ms。

**为什么偏移在 preroll 时冻结**：偏移一变，所有未播帧的目标时刻一起平移，相当于一次播放跳变。稳态下不再改偏移，晶振差交给 sample slip 慢慢补（§3.2.1.6）。

**为什么不需要 PING/PONG**：`d_min` 里已经包含“从机时钟 − 主机时钟”的固定部分。发送端把 `D` 通过 `lead_ms` 告诉接收端，接收端加回去即可。代价是残差 `L_min`（下行最小单程延迟）；本方案甚至不需要上行路径。

##### 3.2.1.5 抖动缓冲与启动流程

**槽位结构**：

```c
#define UA_SLOTS        64      /* 必须是 2 的幂 */
#define UA_MAX_SAMPLES  1024

typedef struct {
    uint64_t t_play_us;
    uint16_t seq;
    uint16_t nsamples;
    uint8_t  valid;
    int16_t  pcm[UA_MAX_SAMPLES];
} ua_slot_t;                     /* ≈ 2064B/槽 */
```

- 按 `seq % 64` 定位，天然处理乱序；
- 64 槽 × 2064B ≈ **132KB**，分配在 PSRAM；
- 10ms 帧可缓冲约 640ms，15ms 帧约 960ms，远大于“过深”阈值 450ms；
- 单帧上限 1024 采样，兼容主节点 661/662 和 PC 脚本 441。

**preroll 条件**（满足其一）：

1. 正常启动：有效槽位 ≥ 8，偏移窗口 ≥ 10 个样本，且缓冲时间深度 ≥ `lead_ms × 3/4`（当前 150ms）；
2. 发送端停顿兜底：已有数据，窗口 ≥ 5 个样本，且 100ms 没有新包。

正常启动要等深度达到 150ms，是因为发送端只提前 200ms 发；按“包数 ≥ 20”之类的固定阈值在 15ms 帧下永远凑不齐。

**启动动作**：

1. 找缓冲区里最早的有效 `seq`；
2. 计算并冻结 `offset = d_min + lead_ms×1000 + 60000`；
3. 计算 `start_at = 该帧 t_play + offset`；
4. 等到 `start_at`：剩余 > 20ms 时每 10ms 睡一次，最后 20ms 忙等（保证对齐精度）；
5. 写第一帧，并对前 128 个采样做淡入，压掉 DMA 从静音切到音频时的直流台阶。

首帧之后不再逐帧等待 `t_play + offset`：`Amplifier_Play_Buffer()` 的阻塞返回时刻就是 DMA 有空位的时刻，播放任务跟着 DMA 的节奏走；长期偏差由 sample slip 修正。因此启动时的 `start_at` 对齐精度决定了整场的相位，之后靠从机晶振和 slip 维持。

##### 3.2.1.6 稳态播放、异常处理与漂移补偿

**播放循环**：

```text
取 read_seq 对应槽位
  ├─ 命中：拷贝 PCM，更新“跑道”观测值
  ├─ 缺失且距上次收包 > 500ms：清空槽位，回到 preroll
  ├─ 缺失：PLC 重复上一帧（×3/4 衰减）；没有上一帧则补 441 采样静音
  ├─ 缓冲深度 > 450ms：跳到“最新 − 150ms”附近的有效 seq，重置漂移基准
  ├─ 本次开播第一帧：128 采样淡入
  ├─ 计算 sample slip
  └─ Amplifier_Play_Buffer(..., UINT32_MAX)   ← 阻塞写，构成从机时钟节拍
```

**关键计数器与阈值**：

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `UA_UNDERRUN_RESET_US` | 500ms | 超过这么久没有新包，判定断流，清盘重新 preroll |
| `UA_LEVEL_MAX_US` | 450ms | 缓冲过深阈值，超过就跳帧 |
| `UA_LEVEL_TARGET_US` | 150ms | 跳帧后希望保留的深度 |
| `UA_PREROLL_PKTS` | 8 | preroll 最少有效帧数 |
| `UA_OFFSET_WIN` | 64 | 偏移估计窗口 |
| `UA_SLIP_DEADBAND_US` | 4ms | 漂移死区 |
| `UA_SLIP_MIN_GAP_US` | 20ms | 两次 slip 的最小间隔 |
| `UA_SLIP_WARMUP` | 200 帧 | 开播后测漂移基准的预热帧数 |
| `UA_SPLICE_TAP` | 8 | slip 拼接处的平滑点数 |
| `UA_FADE_IN_SAMPLES` | 128 | 首帧淡入点数 |

**PLC（丢包隐藏）**：把上一帧原地乘 3/4 后重复写入。连续丢包会连续衰减，直到下一帧有效数据覆盖 `last_good`。比直接补零听感柔和，也不会让缓冲时间轴停住——`read_seq` 照常 +1。

**跳帧**：`level = 最新收到的 t_play − 当前播放帧的 t_play`。超过 450ms 说明从节点已经落后太多（例如 Wi-Fi 长时间拥塞后突然恢复），继续播会让延迟越积越大。此时在“最新帧往前 150ms”的窗口里找一个有效 seq，直接把读游标跳过去。

**sample slip（漂移补偿）**：

两块板子的晶振差几十 ppm，播放头会缓慢脱离发送端的时刻表。观测量选“抖动缓冲的跑道”：

```text
level = 最近收到的 t_play − 正在播放帧的 t_play
```

- 从机晶振慢 → DMA 消耗慢 → 跑道变长；
- 从机晶振快 → 跑道变短。

为什么不用“写入时刻 − 时刻表”：写入时刻由 I2S DMA 的排空节奏决定，而 DMA 和 `esp_timer` 共用同一个从机晶振。每写一帧，本地时间前进的微秒数正好等于 `t_play` 前进的微秒数，差值恒为 −DMA 深度，晶振差完全看不见。

控制逻辑：

1. 每帧更新跑道的 EMA（`shift = 5`，约 0.3~0.5s 时间常数）；
2. 开播 200 帧后，把当前 EMA 定为基准 `obs_ref`（避开 DMA 刚填充时的瞬态）；
3. `obs_avg > obs_ref + 4ms`：丢一个样本（输出 `n−1`），播放时间轴加快；
4. `obs_avg < obs_ref − 4ms`：插一个样本（输出 `n+1`），播放时间轴放慢；
5. 两次 slip 至少间隔 20ms。

**输出样本数必须真的变化**。I2S DMA 按从机晶振消耗样本；写 `n−1` 个，下一帧就提前 1/44100 秒进入 DMA，时间轴才真正前进。早期版本“丢了一个样本又把长度补齐到 n”，时间轴没变，跑道会一直偏，slip 会以最大速率反复触发。

**拼接平滑**：

- 丢样本时，用上一个输出样本对 `src[1]` 之后的前 8 个点做线性过渡；
- 插样本时，插入值取 `(prev_last + src[0]) / 2`，把台阶分摊到两侧。

**补偿能力**：一个样本 = 22.7µs，最小间隔 20ms，最大约 **1134ppm**。常见晶振偏差 ±20~50ppm，余量充足；典型情况下每 0.4~1 秒才补一个样本。

**为什么不再调 I2S 采样率**：`i2s_bus_phy_set_sample_rate()` 会 `disable → reconfig → enable`，把 DMA 里最多 46ms 的音频全部丢掉，并制造一次时钟空窗。sample slip 只改一帧的样本数，听感上几乎无痕。

##### 3.2.1.9 日志与观测

稳定运行时每 5 秒输出一行：

```text
I (20000) UDP_AUDIO: rx=1000 lost=0 late=0 bad=0 dup=0 slip=0 level=250ms dev=0ms offset=123456ms
```

| 字段 | 含义 | 健康值 |
| --- | --- | --- |
| `rx` | 累计收包数 | 持续增长 |
| `lost` | 用 PLC 补过的帧数 | 0 或极少 |
| `late` | 读游标之后才到的包 | 0 或极少 |

`level` 不是“音频延迟”，而是“最新收到的帧与正在播放的帧之间的时间跨度”，约等于 `D + margin` 减去网络与 DMA 的少量占用。

#### 3.2.2 amplifier

**职责**：封装 NS4168 D 类功放，向上提供“写 PCM”和“设音量”两个能力。NS4168 没有硬件音量寄存器，音量只能通过衰减 PCM 实现。

**硬件与 I2S 配置**：

| 项目 | 值 |
| --- | --- |
| 控制器 | `I2S_NUM_1`，TX |
| BCLK / WS / DOUT | GPIO8 / GPIO9 / GPIO10 |
| 采样率 | 44100Hz |
| 位宽 | 16bit |
| 槽位模式 | MONO，`slot_mask = LEFT / RIGHT`（硬件把单声道复制到两个时隙） |
| DMA | 8 个描述符 × 256 帧 ≈ 46ms |
| `tx_auto_clear` | true（DMA 欠载时自动补零，避免旧数据重复） |

**并发模型**：模块内部持有 `Amp_WriteMutex`，`Amplifier_Play_Buffer()` 在锁内完成“音量缩放 + 一次 I2S 写”。同一时刻只允许一路音源写 I2S；当前只有 `udp_audio_play` 一个生产者。

**软件音量**：

```c
gain = ((uint32_t)vol * vol * 32768) / 10000u;   /* (vol/100)² */
out  = (int16_t)(((int32_t)in * gain) >> 15);
```

- 平方曲线更接近人耳等响感知；
- 100% 时完全直通，不做任何拷贝；
- 0% 时直接 `memset` 静音；
- 工作缓冲 8KB，优先 PSRAM，失败回退内部 RAM；分配失败时保持直通（有声音比没声音好）。

**板级校准**：`AMPLIFIER_GAIN_TRIM_PERCENT` 是线性幅度百分比，只能衰减。2026-10-23 确认主从响度差异来自扬声器本身，两块板都恢复为 100（不校准）；宏保留，换喇叭/腔体后可将偏响的一块调到 70/50/35。

**API**：

```c

esp_err_t Amplifier_Deinit(void);
esp_err_t Amplifier_Play_Buffer(const uint8_t *buffer, size_t size,
                                size_t *bytes_written, uint32_t timeout);
esp_err_t Amplifier_Set_Volume(uint8_t volume);   /* 0~100，超限截断 */
uint8_t   Amplifier_Get_Volume(void);
esp_err_t Amplifier_Set_Sample_Rate(uint32_t sample_rate);  /* 当前链路不用 */
```

`Amplifier_Set_Sample_Rate()` 与 `Play_Buffer()` 共用同一把写锁，但当前 `udp_audio` 不做采样率调整，保留接口仅供调试。

#### 3.2.3 ctl_rx

**职责**：接收主节点通过组播下发的控制命令，当前只处理音量。

**通道**：`239.0.0.1:5679`，由 `wifi_manager` 创建并持有 socket，`rx_enable = true`，FIFO 1024B。

**帧格式**（与主节点 `sync_ctrl_basic_t` 一致）：

```c
typedef struct __attribute__((packed)) {
    uint16_t magic;   /* 0xAA55 */
    uint8_t  cmd;     /* 0x05 = VOLUME */
    uint8_t  param;   /* 0~100 */
} ctl_basic_t;        /* 4 字节 */
```

**处理逻辑**：

1. 从 FIFO 阻塞取包（超时 1000ms，超时继续等）；
2. 长度不足 4 字节、magic 不符、cmd 不是 `0x05` 的包直接忽略（主节点的 START/HEARTBEAT/PING/PONG 扩展帧都会落到这里）；
3. `param > 100` 时截断到 100；
4. 与上一次音量相同则不重复设置、不重复打日志；
5. 调 `Amplifier_Set_Volume()`，下一次 `Play_Buffer()` 生效。

**任务**：`ctl_rx`，优先级 5，栈 3072，不绑定核心。

**必须持续读 FIFO**：`ctl_rx` 是这条通道唯一的消费者。如果长期不读，FIFO 会写满，新的控制包在 `wifi_manager` 里被丢弃（`rx_dropped++`）。

旧架构更严重的教训在发送侧：`rx_enable = false` 的通道不参与 RX 任务轮询，若又开着组播回环，自己发出的包会留在 socket 接收队列里无人消费，逐渐占满 lwIP pbuf，最终 `sendto` 返回 `ENOMEM`，控制包全丢。`wifi_manager.c` 的注释记录了这个坑；当前发送通道已关闭回环。

**边界**：音量变化不写 NVS。主节点是音量权威，从节点只跟随；重启后先用自己的 NVS 音量，等主节点下一次下发再对齐。

**组播通道 API**：

```c
typedef struct {
    const char *group;        /* 例如 239.0.0.1 */
    uint16_t    port;         /* 例如 5679 */
    bool        rx_enable;    /* 需要接收才建 RX 任务和 FIFO */
    uint32_t    rx_fifo_bytes;
} wifi_mcast_cfg_t;

                                  const wifi_mcast_cfg_t *cfg,
                                  wifi_mcast_handle_t *out);
esp_err_t wifi_manager_mcast_send(...);
esp_err_t wifi_manager_mcast_recv(...);   /* 从 FIFO 阻塞取 */

```

**RX 任务设计**：

| 项目 | 值 |
| --- | --- |
| 任务名 | `wifi_mcast_rx` |
| 优先级 | 6 |
| 栈 | 4096 |
| 核心 | **Core 0（绑定）** |
| 最多监听通道 | 8 |
| 等待方式 | `poll(fds, nfds, 100ms)` |
| 收包方式 | 非阻塞 `recvfrom` 循环，包进 `xRingbuffer` FIFO |
| 收包缓冲 | 4KB，优先 PSRAM |

**关键修复：纯发送通道关闭组播回环。** `wifi_mcast_socket_create()` 对所有通道都会 `IP_ADD_MEMBERSHIP` + `bind`（组播 socket 的常规做法），但 `rx_enable = false` 时把 `IP_MULTICAST_LOOP` 设为 0。早期实现里回环是开的，而发送通道不参与 RX 任务轮询：自己发出的包被回环进本 socket 的接收队列，没人消费，lwIP pbuf 被逐渐占满，最终 `sendto` 返回 `ENOMEM`，主节点的 PONG 发不出去，时钟永远锁不上。接收通道（从节点的 `ctl_rx`）保留回环，并且必须由上层持续读 FIFO。

**为什么用 `poll()` 而不是短延时轮询**：本工程 `CONFIG_FREERTOS_HZ = 100`，1 tick = 10ms。早期代码用 `vTaskDelay(pdMS_TO_TICKS(2))`，`pdMS_TO_TICKS(2)` 等于 0，`vTaskDelay(0)` 只让出同优先级任务，prio 6 的 RX 任务会把 Core 0 的 IDLE0 饿死，5 秒后触发 Task WDT。`poll()` 在没数据时真正挂起任务，有数据立即唤醒，既修了看门狗，又降低了收包延迟。

**从节点如何使用它**：只有 `ctl_rx` 使用 `wifi_manager` 的组播通道。音频数据面直接用 lwIP socket，原因见 §3.2.1：单播不需要加组，音频需要独立的 64KB 接收缓冲和零额外 FIFO 拷贝，两条链路互不拖累。

**职责**：PMOS 自锁供电的开关机控制。

| 项目 | 值 |
| --- | --- |
| 电源按键 | GPIO4（宏 `POWER_BTN_GPIO`），低电平按下 |

| 扫描周期 | 20ms（FreeRTOS 软件定时器） |
| 上电忽略期 | 2 秒 |
| 长按关机 | 3 秒 |

**行为**：

- `SystemStart()`：把 GPIO5 拉高，锁住电源；
- `StartAndStop_Init()`：配置按键输入，创建并启动 20ms 周期软件定时器；
- 定时器回调每 20ms 采样一次，连续按下计数达到 `3000/20 = 150` 次后调用 `SystemStop()`，把 GPIO5 拉低，系统断电；

**实现说明**：没有独立任务，回调运行在 FreeRTOS 定时器服务任务上下文，只做 GPIO 读写，不阻塞。

**已知文档问题**：`StartAndStop.c` 文件头和函数注释里仍写着 GPIO14/GPIO36（旧板卡），实际行为由头文件宏 GPIO5/GPIO4 决定，以宏为准。

## 4. 关键数据流

### 4.1 音频数据面：主节点 → 从节点 → 喇叭

```text
主节点                                    从节点
  │
  ├─ 采集/解码得到一帧 PCM
  ├─ t_play = t_tx + D(200ms)
  ├─ 单播 UDP → 从节点:5680 ──────────────► recvfrom()
  │                                           ├─ 校验 magic/version/长度
  │                                           ├─ seq % 64 落槽
  │                                           ├─ d = now − t_play → 64 窗口
  │                                           └─ 更新 last_t_play / last_rx
  │
  │                                       播放任务（preroll）
  │                                           ├─ 有效帧 ≥ 8、窗口 ≥ 10、深度 ≥ 150ms
  │                                           ├─ offset = d_min + 200ms + 60ms
  │                                           ├─ start_at = 最老帧 t_play + offset
  │                                           └─ 睡/忙等到 start_at
  │
  │                                       播放任务（稳态）
  │                                           ├─ 取 read_seq 槽位
  │                                           ├─ 缺失 → PLC / 断流重来
  │                                           ├─ 过深 → 跳到 150ms
  │                                           ├─ 漂移 → slip ±1 样本
  │                                           └─ Amplifier_Play_Buffer()
  │                                                 └─ I2S1 → NS4168 → 喇叭
```

**时刻对齐关系**：

- 主节点本地在 `t_play + 60ms` 出声；
- 从节点在本地时刻 `t_play + offset` 出声，换算回主节点时钟是 `t_play + L_min + 60ms`；
- 两者相差 `L_min`（局域网 1~3ms），听感上同步。

### 4.2 控制面：音量跟随

```text
主节点 LCD / 蓝牙音量变化
  → sync_protocol 发 4 字节基础帧到 239.0.0.1:5679
  → 从节点 wifi_mcast_rx_task（Core 0）收包
  → xRingbuffer FIFO
  → ctl_rx_task 取包、校验 magic + cmd
  → Amplifier_Set_Volume(param)
  → 下一次 Amplifier_Play_Buffer() 生效
```

音量变化只影响后续帧，不会重采样已经写入 DMA 的数据。

### 4.3 播放状态机

```text
                 首包 / 新 stream_id
   WAIT_STREAM ─────────────────────► PREROLL
        ▲                                │
        │                                │ 有效≥8、窗口≥10、深度≥3/4·D
        │                                │ 或发送端停顿且已有数据
        │                                ▼
        │                          对齐等待 start_at
        │                                │
        │                                ▼
        │                           PLAYING ── level>450ms ──► 跳到 150ms
        │                                │                    （仍在 PLAYING）
        │                                │
        └──── 500ms 无新包，清空槽位 ◄───┘
                     （重新 PREROLL）
```

严格来说代码里只有 `s_playing` 一个布尔量，上图的“状态”是行为上的划分：

- `s_playing = false`：播放任务每 20ms 尝试一次 `ua_try_start()`；
- `s_playing = true`：进入逐帧播放循环；
- 断流 500ms 把 `s_playing` 置回 false，但保留 `stream_id` 和偏移窗口，因此新包到达后可以直接重新 preroll，不必等 `stream_id` 变化。

## 5. 同步误差与恢复策略

### 5.1 误差来源

| 来源 | 量级 | 处理方式 |
| --- | --- | --- |
| 最小单程网络延迟 `L_min` | 1~3ms（局域网） | 单向估计的固有残差，接受 |
| 偏移窗口量化 | 窗口内最小时延的抖动，约 1ms 内 | 64 包窗口 + 取最小值 |
| DMA / 阻塞写抖动 | 一帧以内 | 阻塞写让 DMA 自己定节拍，不叠加软件定时误差 |
| 晶振漂移 | 几十 ppm | sample slip，死区 4ms |
| slip 量化 | 1 样本 = 22.7µs | 拼接平滑，听感不可闻 |
| 主节点本地播放余量 | 60ms 固定 | 两端使用相同数值的余量（60000µs），互相抵消 |

### 5.2 异常与恢复动作

| 现象 | 判定 | 动作 | 影响 |
| --- | --- | --- | --- |
| 单包丢失 | 槽位缺失 | PLC 重复上一帧 ×3/4，`read_seq+1` | 听感轻微，时间轴不停 |
| 连续丢包 | 连续槽位缺失 | 连续 PLC，逐次衰减 | 声音渐弱，不爆音 |
| 断流 < 500ms | 无新包但未超时 | 继续 PLC | 网络短暂抖动可扛 |
| 断流 ≥ 500ms | `now − last_rx > 500ms` | 清空槽位，`s_playing=false`，重新 preroll | 静音后自动恢复 |
| 缓冲过深 > 450ms | `level > 450ms` | 跳到“最新 − 150ms”附近 | 丢一段音频，延迟回落 |
| 发送端换流 | `stream_id` 变化 | 清空槽位、重置偏移窗口、重新 preroll | 短暂静音 |
| 发送端重启但 stream_id 不变 | 首帧标志 + 100ms 停顿 / seq 倒退 > 64 | 同上 | 短暂静音 |
| 迟到包 | `seq` 落后读游标 | 丢弃，`late++` | 无 |
| 重复包 | 槽位已有同 seq | 丢弃，`dup++` | 无 |
| 非法包 | magic/version/长度错误 | 丢弃，`bad++` | 无 |
| Wi-Fi 断开 | `recvfrom` 超时 | 继续等，socket 保持绑定 | Wi-Fi 恢复后自动续播 |

### 5.3 现场排查顺序

按“物理层 → 网络层 → 时钟 → 音频”逐层排查：

1. **功放响不响**：临时打开 `Debug_BeepTest()` 或 `APP_BOOT_BEEP`，绕开网络；
2. **Wi-Fi 连上没有**：看 `wifi connected: ip=... rssi=...`；
3. **有没有收到包**：看 `first packet from ...` 和 `rx=` 是否增长；
4. **时钟估计是否合理**：看 `stream ... start`、`playing: ... offset=...`，`offset` 数值本身无意义，关键是能稳定进入 `playing`；
5. **缓冲是否健康**：`level` 应在 200~300ms，`dev` 在 ±4ms 内，`lost/late/bad` 接近 0；
6. **是否有声音**：若 `rx` 增长但无声，查 `volume` 是否为 0、功放供电、I2S 接线。

## 6. FreeRTOS 任务设计

### 6.1 任务表

| 任务 | 优先级 | 栈（字节） | 核心 | 创建者 | 主要阻塞点 |
| --- | --- | --- | --- | --- | --- |
| `udp_audio_rx` | 11 | 4096 | 不绑定 | `udp_audio_start()` | `recvfrom`，200ms 超时 |
| `udp_audio_play` | 10 | 5120 | 不绑定 | `udp_audio_start()` | `Amplifier_Play_Buffer(..., UINT32_MAX)` |
| `wifi_mcast_rx` | 6 | 4096 | **Core 0** | `wifi_manager_create()` | `poll(..., 100ms)` |
| `ctl_rx` | 5 | 3072 | 不绑定 | `ctl_rx_start()` | `wifi_manager_mcast_recv(..., 1000ms)` |
| `app_main` | IDF 默认 | IDF 默认 | 不绑定 | 启动 | 初始化完成后每 10s 延时 |
| FreeRTOS Timer | IDF 默认 | IDF 默认 | — | 系统 | `PowerBtnTimer` 20ms 周期回调 |
| Wi-Fi / lwIP / event loop | IDF 默认 | IDF 默认 | IDF 决定 | 系统 | 协议栈内部 |

### 6.2 优先级设计理由

- **`udp_audio_rx` (11) 高于 `udp_audio_play` (10)**：收包任务必须及时把 socket 里的数据搬进槽位，否则 `SO_RCVBUF` 溢出、包被协议栈丢掉；播放任务在 I2S 写上是阻塞的，不会长期占 CPU。
- **`udp_audio_play` (10) 高于 `ctl_rx` (5)**：音量解析可以等，音频帧不能等。
- **`ctl_rx` (5) 低于 `wifi_mcast_rx` (6)**：FIFO 的生产者优先，避免控制 FIFO 堆积。
- 音频两个任务**不绑定核心**：ESP32-S3 双核由调度器平衡；当前负载很轻（44.1kHz 单声道 + 一次/帧的缩放），没有绑定必要。若后续加入 SD 解码/OTA 等重负载，可把 `udp_audio_play` 固定到 Core 1，避免和 Wi-Fi 抢 Core 0。

### 6.3 tick 与延时

`CONFIG_FREERTOS_HZ = 100`，1 tick = 10ms。这意味着：

- `pdMS_TO_TICKS(1..9)` 都等于 0，`vTaskDelay(0)` 不会让任务真正睡眠；
- 所有小于 10ms 的等待必须用 `esp_timer_get_time()` 忙等（当前 preroll 的最后 20ms 就是这么做的）；
- 周期任务的最小可靠延时是 10ms。

旧代码里 `vTaskDelay(pdMS_TO_TICKS(2))` 导致的 IDLE0 饿死/看门狗问题，根因就在这条（详见 §3.4.1）。

## 7. 内存与缓冲预算

### 7.1 主要占用

| 项目 | 大小（约） | 位置 | 说明 |
| --- | --- | --- | --- |
| 抖动缓冲 | 132KB | PSRAM | 64 槽 × 2064B |
| 播放任务工作缓冲 | 6KB | PSRAM | `frame` / `slip_buf` / `last_good` |
| 功放音量缓冲 | 8KB | PSRAM | 最大 2048 帧 × 2B |
| 接收任务收包缓冲 | 4KB | 内部 RAM | `malloc` |
| 组播 RX 收包缓冲 | 4KB | PSRAM | `wifi_manager` 每实例一块 |
| 任务栈 | 约 17KB | 内部 RAM | rx + play + ctl + mcast |
| I2S DMA | 4KB | 内部 DMA | 8 × 256 帧 × 2B |
| socket 接收缓冲 | 64KB（请求值） | lwIP | 实际由 lwIP 配置约束 |
| Wi-Fi 静态 RX 缓冲 | 16 个 | PSRAM/内部 | `CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM=16` |
| Wi-Fi 动态 RX 缓冲 | 32 个 | PSRAM/内部 | `CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM=32` |

### 7.2 分配策略

- `CONFIG_SPIRAM_USE_MALLOC=y`：`heap_caps_malloc(MALLOC_CAP_SPIRAM)` 可用；
- `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=4096`：小于 4KB 的分配优先走内部 RAM，避免小对象碎片化 PSRAM；
- `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y`：Wi-Fi/lwIP 的大缓冲可以落 PSRAM，缓解内部 DRAM 压力；
- 所有大缓冲都“优先 PSRAM，失败回退内部 RAM”，并在失败时打印告警，不直接崩溃。

## 10. 当前实现状态与已知限制

### 10.1 模块状态

| 模块 | 状态 | 说明 |
| --- | --- | --- |
| `udp_audio` | ✅ 已实现 | 当前唯一的音频路径 |
| `amplifier` | ✅ 已实现 | I2S1 + 软件音量 + 板级校准宏 |
| `ctl_rx` | ✅ 已实现 | 只处理音量 |
| `wifi_manager` | ✅ 已实现 | STA + 组播控制通道 |
| `node_role` | ✅ 已实现 | NVS 参数 |
| `StartAndStop` | ✅ 已实现 | GPIO4 按键 / GPIO5 电源保持 |
| `StatusLed` | ⚠️ 部分实现 | 驱动可用，但未随播放状态联动 |
| `MusicPlay` | ⛔ 空桩 | 无本地曲库/解码 |
| `ota_manager` | ⛔ 空桩 | 无 OTA 流程 |

### 10.2 已知限制

1. **自动发现是"公告式"的，不依赖静态 IP**。`ctl_rx` 每 3 秒向 `239.0.0.1:5679` 发一条 `ANNOUNCE`（MAC/IP/音频端口/音量/RSSI/设备名），主节点按 MAC 维护运行时从机表并自动更新单播目标；静态 IP 表只在"还没收到过任何公告"时作为兜底。限制：公告依赖 AP 转发客户端组播，开了客户端隔离/严格 IGMP snooping 的网络可能收不到；配对令牌是编译期常量，还不支持 UI 配对。
2. **没有丢包重传**。UDP 丢包只靠 PLC 隐藏；连续丢包会听出衰减。协议没有 NACK/重传，也没有 FEC。
3. **上行信息很少**。从节点只上报身份、音量、RSSI；主节点仍不知道从节点的缓冲深度、丢包/欠载计数和播放状态，深度排查要看从节点串口。
4. **音量不持久化**。`ctl_rx` 收到主节点音量只改内存，不写 NVS；从节点重启后先用自己的 NVS 音量，等主节点下一次下发才对齐。
5. **只验证了单从机**。协议和缓冲支持多从机（每台从机独立收单播），但没有多从机实测数据。
6. **控制命令只有音量**。暂停/继续/切歌等基础帧 `ctl_rx` 会忽略；从节点也没有本地播放能力来响应切歌。
7. **`StatusLed` 未联动**。`udp_audio` 没有对外暴露播放状态，LED 目前只初始化。
8. **`StartAndStop` 注释过期**。源码注释里的 GPIO14/GPIO36 是旧板卡，实际使用 GPIO5/GPIO4。
9. **偏移估计的残差是最小下行单程延迟**。若 AP 对下行做了额外缓冲/整形，`L_min` 会变大，主从相对延迟随之变大；家用局域网通常没问题。
10. **sample slip 补偿上限约 1134ppm**。超出这个范围的晶振（极少见）或极端温度漂移无法完全跟上。
11. **没有配网流程**。从节点没有触摸屏/按键配网 UI，Wi-Fi 凭据来自 NVS 或编译期默认值；换网络需要重新烧录、改宏，或通过串口/其他方式写入 NVS。

### 10.3 后续演进方向

- 公告里补充播放/缓冲健康状态，主节点 LCD 可显示每台从机的欠载计数；
- 控制命令扩展（PAUSE/RESUME/NEXT/PREV），配合 `MusicPlay` 的本地播放；
- `udp_audio` 暴露状态查询接口，驱动 `StatusLed`；
- 多从机同步测试与主节点发送队列优化；
- OTA 流程落地（分区已就绪）。
