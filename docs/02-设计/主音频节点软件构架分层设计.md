# 主音频节点软件架构分层设计

> **节点型号**：ESP32-WROVER-E-N8R8
> **文档范围**：仅描述**音频主节点**的软件架构；从节点固件另行设计。
> **核心原则**：App 层不直接调用 ESP-IDF 蓝牙 API；所有音频源 PCM 统一进入 `sync_protocol` 调度；`audio_decoder` 仅用于 SD 卡 MP3/WAV 解码；主节点本地播放也延迟 `D`，与从节点同步。

------

## 1. 设计原则

**分层解耦**：BSP → 中间件 → 应用层，单向依赖。

------

## 2. 分层架构总览

```reStructuredText
┌─────────────────────────────────────────────────────────────┐
│                        应用层 (App)                         │
│  MusicPlay  │  CallPhone  │  UI  │  LightControl  │ PlayMode │
└──────────────┬──────────────────────────────────────────────┘
               │ 调用中间件 API / 接收事件
┌──────────────▼──────────────────────────────────────────────┐
│                      中间件层 (middlewares)                  │
│  LCD_Touch  │  sd_card  │  audio_decoder  │  bt_audio       │
│  microphone │ amplifier │  audio_bus      │  sync_protocol  │
└──────────────┬──────────────────────────────────────────────┘
               │ 调用 BSP 驱动
┌──────────────▼──────────────────────────────────────────────┐
│                         BSP 层 (bsp)                        │
│   gpio_driver  │  i2c_driver  │  i2s_driver  │  spi_driver  │
└──────────────┬──────────────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────────────┐
│                     硬件 (ESP32-WROVER-E)                   │
│  GPIO / I2C / I2S / SPI / 蓝牙 / WiFi / SD / LCD / 触摸     │
└─────────────────────────────────────────────────────────────┘

横切服务：mysystem（ota_manager / wifi_manager / node_role / StartAndStop）
```

#### 3.2.3 `audio_decoder`

- **实现状态**：未实现；本小节为规划中的正式对外接口（规划头文件 `components/middlewares/audio_decoder/audio_decoder.h`）。
- **架构位置**：只负责解码 SD 卡 `/sdcard/music` 下 MP3/WAV 文件为 16-bit PCM，解码任务在模块内部创建，通过 `on_pcm` 回调把 PCM 交给 `MusicPlay`（仅注册回调）统一喂给 `sync_protocol`。
- **解码库方案**：MP3 使用离线单头文件库 `minimp3`（CC0-1.0），随模块一起维护在 `third_party/minimp3/`；WAV 由模块内部解析，不依赖外部组件。
- **设计约束**：
  - 播放/暂停/上下曲归 `MusicPlay`，模块内部只提供解码与输出回调。
  - 当前不做 `seek()` 回拉；但保留 `get_position_ms()` 给 UI 显示进度。
  - 音量不做在本模块，由 `amplifier`/上层控制。
- **对外接口**：

```c
/* 句柄 */
typedef struct audio_decoder_s *audio_decoder_handle_t;

/* 音频格式 */
typedef enum {
    AUDIO_DECODER_FMT_MP3 = 0,
    AUDIO_DECODER_FMT_WAV,
} audio_decoder_format_t;

/* 文件参数 */
typedef struct {
    audio_decoder_format_t format;
    uint32_t               sample_rate;
    uint8_t                channels;
    uint32_t               duration_ms;
    uint32_t               bitrate_bps;
} audio_decoder_info_t;

/* PCM 输出回调：解码任务上下文调用，直接进 sync_protocol */
typedef void (*audio_decoder_pcm_cb_t)(const int16_t *pcm,
                                       size_t samples,
                                       uint32_t sample_rate,
                                       uint8_t channels,
                                       void *user_ctx);

/* 播放/编解码事件回调 */
typedef enum {
    AUDIO_DECODER_EVT_READY,   /* 文件头解析完成，可读取参数 */
    AUDIO_DECODER_EVT_EOF,     /* 解码到文件尾，MusicPlay 切下一首 */
    AUDIO_DECODER_EVT_ERROR,   /* 文件损坏/解码失败 */
} audio_decoder_event_id_t;

typedef void (*audio_decoder_event_cb_t)(audio_decoder_event_id_t event,
                                         const audio_decoder_info_t *info,
                                         void *user_ctx);

/* 打开文件时的配置 */
typedef struct {
    audio_decoder_pcm_cb_t   on_pcm;
    void                   *pcm_ctx;
    audio_decoder_event_cb_t on_event;
    void                   *event_ctx;
} audio_decoder_cfg_t;

/* 生命周期 */
esp_err_t audio_decoder_init(void);
esp_err_t audio_decoder_deinit(void);

/* 打开并解码 SD 卡文件（如 "/sdcard/music/a.mp3"） */
audio_decoder_handle_t audio_decoder_open(const char *path,
                                          const audio_decoder_cfg_t *cfg);

esp_err_t audio_decoder_close(audio_decoder_handle_t dec);

/* 播放/暂停/停止（内部解码任务驱动 on_pcm 回调） */
esp_err_t audio_decoder_play(audio_decoder_handle_t dec);
esp_err_t audio_decoder_pause(audio_decoder_handle_t dec);
esp_err_t audio_decoder_stop(audio_decoder_handle_t dec);

/* 查询文件参数 / 当前进度（UI） */
esp_err_t audio_decoder_get_info(audio_decoder_handle_t dec,
                                 audio_decoder_info_t *info);
esp_err_t audio_decoder_get_position_ms(audio_decoder_handle_t dec,
                                        uint32_t *position_ms);
```

- **对外接口补充**：`audio_decoder_pcm_cb_t` 为对外同步回调的唯一出口，由 `MusicPlay` 注册并将回调指向 `sync_protocol_master_push_pcm()`；不提供 `seek()`。

#### 3.2.4 `bt_audio`

- **实现状态**：未实现；本节能定义正式版对外接口（规划头文件 `components/middlewares/bt_audio/bt_audio.h`）。
- **架构位置**：封装经典蓝牙协议栈，提供 A2DP Sink、HFP(HF) 语音助手与 AVRCP 控制。
- **设计约定**：
  - PCM 下行（A2DP 音乐 + HFP 语音应答）统一通过 `on_pcm` 回调交给 `sync_protocol`，不经过 App 层。
  - UI 控制统一走 `bt_audio_send_ctrl_cmd()`；手机 AVRCP 状态统一通过 `on_event` 回调交给 UI。
  - 蓝牙协议栈回调内不直接调用外部回调；`bt_audio` 内部先入 FIFO，再在自身任务上下文触发 `on_event` / `on_pcm`。
- **对外接口**：

#### 3.2.7 `audio_bus`

- **实现状态**：已实现（`audio_bus.h` / `audio_bus.c`）。
- **职责**：对 I2S TX/RX 做软件仲裁。TX 多写者互斥，RX 内部读取任务向每个读者私有 FIFO 广播。
- **依赖**：`i2s_driver`。
- **对外接口**：


#### 3.2.8 `sync_protocol`

- **实现状态**：未实现；`components/middlewares/sync_protocol` 目录当前没有头文件和源文件。
- **架构位置**：汇聚 `bt_audio`（A2DP/语音应答）与 `audio_decoder`（SD 卡）的 PCM，打时间戳后经 `wifi_manager` 组播通道发到从节点、并按 `t_play_master = t_tx + D` 交给 `audio_bus` 本地播放；本模块不持有 UDP socket，组播由 `wifi_manager` 统管。

#### 3.3.2 `CallPhone`

- **实现状态**：未实现；本小节为已定稿的对外接口（规划头文件 `components/App/CallPhone/call_phone.h`）。
- **职责**：

## 4. 关键数据流

### 一、手机音乐下行（A2DP）——主链路

```
手机 → A2DP(SBC) 
  ↓ [蓝牙空中，协议栈接管]
ESP-IDF 蓝牙协议栈（SBC 自动解码成 16bit PCM）
  ↓ [协议栈回调，中断/协议栈上下文]
bt_audio 模块
  ↓ [内部 FIFO + 自身任务]
on_pcm 回调 → sync_protocol → 组播(从节点) + 本地延迟 D → amp → audio_bus → i2s_driver → 喇叭
```

逐节点职责：

- bt_audio

  ：封装蓝牙协议栈的"壳"。只做三件事：

  - 收：协议栈回调里不直接调外部回调，先把 PCM 放进 `a2dp_fifo_bytes` 的 FIFO，再由 bt_audio 自身任务取出、按需触发 `on_pcm`（避免在蓝牙回调上下文做重活）；
  - 发：收集手机的 AVRCP 状态/歌曲信息/音量变化，向外发 `on_event`；
  - 控：`bt_audio_send_ctrl_cmd()` 把 UI 命令转 AVRCP 发回手机。
  - **不干**：不解码（esp-id 做）、不决定谁播放、不合并音源。

1. **App 接线层**（app_main 初始化处）：`bt_audio_cfg.ona_pcm` 被接到转发函数，把回调转调 `sync_protocol_master_push_pcm()`。**注意：只做"接线"，不做任何格式判断**——源是 A2DP 还是 HFP 由 `source` 枚举区分，决定走哪个 stream。

2. **sync_protocol**：汇聚 + 同步。它不关心音源是谁（蓝牙/SD/HFP），只认 

   ```
   stream_id + sample_rate + channels
   ```

   。收到 PCM →

   - 打上主节点时间戳 `t_tx` → 立即打包经 `wifi_manager` 音频通道发组播（从节点）；
   - 同时把同一包放进本地**延迟队列**，等到 `t_play_master = t_tx + D` 才经 `amplifier` 往 `audio_bus` 写，保证主从同拍。
   - **不：** 不持有 socket（wifi_manager 管）、不写 I2S 之外的东西、不做格式转换。

3. **audio_bus（TX）**：I2S 输出仲裁层。多写者互斥（实际经上层 `amplifier` 写入，`sync_protocol` 不直接写它），它负责把 PCM 写到对应 I2S 端口的 DMA buffer。

4. **amplifier**：`audio_bus` 的 TX 上层，NS4168 输出链路 + 软件音量。NS4168 无硬件音量接口，音量只是软件侧保存/应用（写 PCM 时乘以系数）；PCM 最终经 `audio_bus` 落到 I2S。

5. **i2s_driver**：BSP 层，真正把 PCM 转 DMA/I²S 信号给功放。

------

### 二、SD 卡本地播放

```
SD 卡文件 → sd_card(FATFS 读) → audio_decoder 解码任务
  → on_pcm 回调 → sync_protocol_master_push_pcm()（同一条链路）
  → 组播 + 本地延迟 D → amplifier → audio_bus → i2s_driver → 喇叭
```

职责分工（重点：**audio_decoder 极端摆烂**）：

- **audio_decoder**：只做两件事。①对 MP3/WAV 流式解码；②把解码出的 PCM 通过 `on_pcm` 回调丢出去。它**没有 play/pause 决策权**——`audio_decoder_play/pause/stop` 只是内部解码任务的启停，真正的"接下来放哪首、单曲循环还是顺序"由 **MusicPlay** 决定。

- MusicPlay

  ：播放状态机的主人。它接收 UI/蓝牙/解码三类事件，统一进内部事件队列串行处理：

  - 当上游（audio_decoder）来消息时：`AUDIO_DECODER_EVT_EOF` 由它决定下一首（顺序→自动切下一条；循环→重播当前曲），然后调用 `audio_decoder_play(下一个文件)`；
  - 广播同步命令 `sync_protocol_master_broadcast_cmd(SYNC_CMD_NEXT)`，让从节点也切曲。

- **同一个 push_pcm() 汇聚点**：本地与蓝牙都是直接 `push_pcm`，sync_protocol 不管来源。

------

### 三、HFP 语音应答下行（手机→喇叭）

```
手机(助语应答) → HFP SCO → esp-idf → bt_audio(HFP FIFO)
 → on_pcm(BT_AUDIO_PCM_SOURCE_HFP_DOWNLINK) → sync_protocol_master_push_pcm() → 本地播放
```

**职责要点**：

- bt_audio 内部分了两个 FIFO（`a2dp_fifo_bytes` / `hfp_fifo_bytes`），并靠 `source` 枚举区分 A2DP 和 HFP 下行，两个流进入不同 stream_id；
- **CallPhone 不做下行**：它不管手机应答的放音，只负责上行；
- HFP 下行也走 sync_protocol，不落在 App 层。

------

### 四、麦克风上行（本地唤醒词 → 手机语音助手）

```
INMP441 → i2s_driver(RX)
  → audio_bus(RX 读取任务 + 每 reader 私有 FIFO 广播)
  → microphone（audio_bus 上层：Microphone_Read_Pcm16 封装读取）
  → CallPhone（esp-sr 唤醒检测）
  → esp-sr 唤醒检测（你好小智，wn9s_nihaoxiaozhi）
  → 命中 → bt_audio_hfp_start_voice() → SCO 打开等待
  → 循环 bt_audio_hfp_send_pcm(mic pcm)
  → ESP-IDF HFP → 手机
```

逐节点职责与边界：

- **audio_bus（RX）**：不定"谁读"，把 I2S 进来的数据**同时复制到每个注册 reader 各自私有 FIFO**。所以 CallPhone 注册 reader 拿话筒，未来别的模块也可以注册多读者。

- **总线归属**：RX 总线由 microphone 模块私有创建并持有，`Microphone_GetBus()` 仅供装配层借出句柄给 CallPhone 注册 reader，不转让所有权；总线销毁统一由 `Microphone_Deinit()` 负责。

- CallPhone：只做两件事——①话筒 PCM 喂 esp-sr 做唤醒词检测；②检测命中后建 HFP 链路 + 把话筒 PCM 上行发送。

  - **明确不发事件**：不向 UI/灯控/MusicPlay 发任何通知；需要状态就 `call_phone_get_state()` 查询；
- **esp-sr 只在主节点引入**，从节点不编译；
  - **上行不进 sync_protocol、不广播**（从节点也不出声音）。

- **bt_audio 只把自己的 HFP 能力原子接口借给 CallPhone**（start_voice / send_pcm / wait_audio_open），HFP 链路建立与 SCO 管理实际在 bt_audio。

------

### 五、UI 资源加载（图片/字体：SD 卡 → 屏幕）

```
SD 卡图片/字体文件（/sdcard/ui/…，PNG/JPG/字体等）
  → sd_card（FATFS / SPI，挂载点 /sdcard）
  → LVGL 文件系统适配（lv_fs / fopen 读取文件）
  → UI_Task（LVGL 渲染线程）按需解码 → LCD_Touch 显示（ILI9341）
```

1. **依赖**：UI 依赖 `sd_card`（图片/字体资源存放在 SD 卡，不烧录进固件），经 `/sdcard` 挂载点读取；
2. **不进音频链路**：图片/字体加载是低频应用数据，只进 LVGL 图像缓存，不经过 `audio_bus`、`sync_protocol`；
3. **容错**：`SD_Card_Is_Mounted()` 为假（SD 未插/损坏）时，UI 用内置占位图标与配色，界面照常可用；SD 恢复后按需重新加载；
4. **初始化顺序**：`SD_Card_Init()` 挂载成功后才允许 UI 从 SD 卡加载资源。

### 六、控制 / 命令流（不流经音频 LINE）

#### 6.1 PlayChoice vs MusicPlay（你最关心的边界，单独一栏）

|                 | **PlayMode（App）**                                          | **MusicPlay（App）**                                         |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 职责            | **只做「源选择」决策**：蓝牙/本地                            | **只做「播放」执行**：播放/暂停/上下曲/音量/列表/状态机      |
| 持有 API 的关系 | **完全解耦**：不持有、不直接调用 MusicPlay                   | 两者唯一的“触点”是 `on_switch` 回调                          |
| 如何换源        | 自己轮询 `bt_audio_get_a2dp_info()` 判断连接状态 → 决策 → 回调 `on_switch(source)` | 收到回调 → `music_play_switch_source(source)` 执行源切换（启动新流/停旧流） |
| 自动规则        | 蓝牙优先级最高：连接→BT;断开→LOCAL（SD 继续放）              | 不在乎源规则，只响应指令                                     |
| 给 UI           | `play_mode_event_cb on_event`(EVT_CHANGED)                   | `music_play_event_cb`（播放状态/曲目/音量快照）              |
| 谁有最终话语权  | 只输出"期望源"                                               | 状态的最终刷新以接收到的 `bt_audio`/解码事件为准             |

一句话结论：**「切什么源」是 PlayMode 的决策，「怎么切、切完之后怎么播」是 MusicPlay 的领地。** 中间用回调松耦合，（不被 MusicPlay 引用 PlayMode 的循环依赖）。

#### 6.2 UI 控制手机（AVRCP）

```
UI 触摸 → music_play_command()（统一命令口）→ MusicPlay 状态机
   ├─ BT：→ bt_audio_send_ctrl_cmd(PLAY/PAUSE/NEXT/PREV/VOL) → AVRCP → 手机
   │      → 手机回流 BT_AUDIO_EVT_PLAY_STATE_CHANGED → 状态机采信/刷新
   └─ 同时：→ sync_protocol_master_broadcast_cmd(SYNC_CMD_*) → 从节点
```

边界：**UI 不得直接调 bt_audio**；必须经由 MusicPlay（文档边界：App 层依赖中间件完成硬件操作；蓝牙控制最终只能经过 bt_audio 的 API，但 UI 只能到 MusicPlay 这一层）。

- 手机与 UI "同时按键" 的处理：**指令都是"期望"**，进入 MusicPlay 事件队列串行执行，最终状态以 bt_audio 回流事件为准（本地源则以解码器状态为准）。
- MusicPlay 再把它需要静音的同步命令（播放/暂停/上下曲/音量/重置）广播给从节点。

### 七、系统服务流（不经过音频区域到）

#### 7.1 灯控

```
UI 点击 → light_control_send(cmd, light) → JSON 组包
   → wifi_manager_mcast_send(239.0.0.2:8889)（rx=true 已开）
   → ESP8266 → ack JSON → wifi_manager_mcast_recv(FIFO) → LightControl 解析
   → light_control on_event(ACK/ERROR) → UI 软件刷新图标

   ─── 周期状态上报（灯控每 30s 上行）───
   ESP8266 → status JSON → wifi_manager_mcast_recv(FIFO) → LightControl 解析
   → light_control on_event(STATUS) → UI 软件刷新图标
```

边界：LightControl **不持有 socket**，socket 全在 wifi_manager；它是纯粹的"协议编解码 + 状态解析"模块，灯状态以 `ack`/`status` 上报实际值为准，不再做下发推断。

#### 7.2 WiFi / 配对 / 状态

```
UI 触摸配网：给 node_role_set(ssid, password)   → NVS 持久化（唯一入口）
            → wifi_manager_set_sta(...) → 发起连接
后续查询：UI 图标 → wifi_manager_get_state()/is_connected()（轮询，不绑事件）
```

- node_role 是唯一 NVS 写者；wifi_manager 只拿 NVS 凭据，不自己写。

#### 7.3 OTA

```
app 就绪 → OTA_Update_Init(NULL) ← 内部按 cfg→node_role 配置（ota_server_url）→默认宏兜底
 → OTA_Update_Start() 后台 或 CheckAndUpgrade() 阻塞
 → HTTP 直连服务器（不经组播/wifi socket）
 → 下载写入备用分区 → 校验 SHA256 → 切换重启
 → 过程经 on_event 回调（进度/失败）给 main / UI
```

- OTA 只依赖 `wifi_manager_is_connected()` 判断网络，不占用 `sync_protocol` 与 `audion 路由`。

#### 7.4 从节点（广播侧）

```
接收：从节点 wifi_manager RX → 从节点 sync_protocol(裁剪版) → 延迟队列
 → t_play_local = t_tx + D + clock_offset → 从节点 audio_bus → i2s → 喇叭
```

- 主节点 role：唯一发流，从节点只跟随。主/从角色由 node_role 存 NVS 决定。

| ------------------- | ------------------------------------------------------- | ------------------------------------------------------- |
| bt_audio            | 封装蓝牙栈；A2DP/HFP/AVRCP；FIFO 输出 PCM= 事件         | 不决定播放、不解码、不跨网络、App 不得碰 ESP-IDF BT API |

| The rest（ESP-IDF） | SBC 解码、I2S DMA、网络栈                               | ——                                                      |

## 5. 同步播放架构说明

同步播放的本质：**主节点发一个包时，约定这个包在未来的 t_tx + D 时刻播放；主节点自己也要等到这个时刻才播。**

- `sync_protocol` 是所有音源 PCM 的汇聚点。

- 主节点本地播放不是立即的，而是延迟 `D`（默认 200ms）。

- 从节点通过 PING/PONG 估计 `clock_offset` 和 `net_delay`，然后计算：

  ```text
t_play_local = t_tx + D + clock_offset
  ```
  
- 这样主从都在主节点时间轴的 `t_tx + D` 时刻播放。

**与 audio_bus 的关系**：

- 同步模式下，`sync_protocol` 是 I2S TX 的唯一 PCM 数据源（经 `amplifier` 写入 `audio_bus` 落 I2S）。
- HFP 通话的麦克风上行不经 `audio_bus` TX：`CallPhone` 从 `audio_bus` RX 读麦克风 PCM，经 `bt_audio_hfp_send_pcm()` 上行到手机；语音应答下行（HFP_DOWNLINK）仍由 `sync_protocol` 汇聚、经 `amplifier` 写入 I2S。

## 6. FreeRTOS 任务设计（主节点）

> **任务视图说明**：任务表为**实现视图**——App 层任务与 middlewares / mysystem 模块内部自建的常驻任务全部登记（见“所属”列），优先级、栈、核绑定全局统一仲裁；模块内部任务由模块自身 `create/start` 创建，App 层不感知创建细节。

> **核分配原则**：Core 0 (PRO_CPU) 承担协议与系统核心——Wi-Fi、蓝牙协议栈、TCP/IP 栈（lwIP）以及高精度定时器等系统关键任务默认固定在其上运行，负载已经很高，**不适合再放置高优先级、计算密集型的应用任务**，否则可能因抢占/饿死协议栈而导致系统不稳定；Core 1 (APP_CPU) 是应用与实时核心，**所有对实时性、流畅度要求高的任务都放在 Core 1**，与网络/蓝牙协议栈解耦，保证执行确定性。

| 任务名                 | 所属                        | 优先级 | 栈大小  | 核         | 功能                                                         |
| :--------------------- | :-------------------------- | :----- | :------ | :--------- | :----------------------------------------------------------- |
| `UI_Task`              | App: UI                     | 12     | 13312   | **Core 1** | LVGL 界面交互与显示；图片/字体资源从 `/sdcard/` 按需加载     |
| `SyncTx_Task`          | middlewares:sync_protocol   | 11     | 8192    | **Core 0** | 打时间戳、UDP 组播发送                                       |
| `OTA_Task`             | mysystem: `ota_manager`      | 11     | 8192    | **Core 0** | 动态创建，执行 OTA 升级（网络下载）                          |
| `SyncLocalPlay_Task`   | middlewares: `sync_protocol` | 10     | 10240   | **Core 1** | 本地延迟队列取 PCM，按 `t_play_master` 写 I2S                        |
| `audio_decoder` 解码任务 | middlewares: `audio_decoder` | 10     | 8192    | **Core 1** | SD 卡 MP3/WAV 流式解码→ `on_pcm`→`push_pcm()`；解码任务在模块内部 |
| `CallPhone_Task`       | App: CallPhone              | 8      | 8192    | **Core 1** | 唤醒词检测（esp-sr）、HFP 麦克风上行转发                      |
| `MusicPlay_Task`       | App: MusicPlay               | 9      | 4096    | **Core 1** | SD 选曲/播放控制/状态机（原 LocalPlay_Task；不承载解码，解码在 audio_decoder 内部） |
| `PlayMode_Task`        | App: PlayMode                | 7      | 4096    | **Core 0** | 轮询 A2DP 状态，自动/手动切换播放源（蓝牙→本地）               |
| `bt_audio_task`        | middlewares: `bt_audio`      | 6      | 8192    | **Core 1** | 蓝牙事件 FIFO 出队，触发 `on_event`/`on_pcm`（协议栈回调不入用户回调） |
| `audio_bus_rx_Task`    | middlewares: `audio_bus`     | 6      | 4096    | **Core 1** | 启用 RX（麦克风）时创建：I2S 接收→各 reader 私有 FIFO 广播    |
| `wifi_mcast_rx_Task`   | mysystem: `wifi_manager`    | 6      | 4096    | **Core 0** | 组播收包→FIFO（rx 启用的通道，如灯控通道 ack/status）         |
| `SmartHome_Task`       | App: LightControl            | 5      | 4096    | **Core 0** | 处理 UI 灯控指令 UDP 组播发送；解析 ack / 30s status 上报并触发事件回调 |
| `LCD_Touch_Task`       | middlewares: LCD_Touch       | 5      | 4096    | **Core 1** | 触摸 IC（FT6336G）扫描，由模块内部创建                           |

**核分配理由**（按“网络/协议侧→Core 0，实时/应用侧→Core 1”）：
- **网络/协议侧（Core 0）**：`SyncTx_Task`（UDP 组播依赖 lwIP）、`OTA_Task`（网络下载）、`PlayMode_Task`（轮询蓝牙协议栈状态）、`SmartHome_Task`、`wifi_mcast_rx_Task`（组播收包）放 Core 0，与 lwIP/蓝牙同核，减少跨核开销；
- **实时音频侧（Core 1）**：`SyncLocalPlay_Task`（写 I2S）、`audio_decoder` 解码任务、`bt_audio_task`（PCM 出队回调）、`CallPhone_Task`（esp-sr 计算密集）放 Core 1，隔离网络抖动；
- **交互与应用（Core 1）**：`UI_Task`/`LCD_Touch_Task`（LVGL 与触摸）、`MusicPlay_Task`（控制编排）放 Core 1，避免界面卡顿；
- **任务归属变化说明**：原“`AudioSource_Task`”（逻辑上汇总蓝牙/SD 音频源）**不再作为独立任务**——A2DP PCM 由 `bt_audio_task` 出队回调、SD 解码由 `audio_decoder` 解码任务产出，二者均在中间件内部直接回调 `sync_protocol`；原“`LocalPlay_Task`”更名为 `MusicPlay_Task`，只做选曲/控制/模式状态机（优先级保留，栈从 12288 降至 4096，因为数据解码已移至 `audio_decoder`）。

> **实现约定**：所有任务统一用 `xTaskCreatePinnedToCore()` 创建，按上表绑定核（`Core 0`=0，`Core 1`=1）；模块内部任务由各模块 `create/start` 自建；`OTA_Task` 动态创建时同样按表绑定。

> 任务间通信：中控之间用事件组/命令队列传递状态与控制；PCM 数据经 `audio_decoder`/`bt_cb` 的文件级回调进入 `sync_protocol`，再经各 FIFO/Jitter Buffer 传递，不走核间消息队列。
