# 主音频节点软件架构分层设计

> **节点型号**：ESP32-WROVER-E-N16R8
> **文档范围**：仅描述**音频主节点**的软件架构；从节点固件另行设计。
> **核心原则**：App 层不直接调用 ESP-IDF 蓝牙 API；所有音频源 PCM 统一进入 `sync_protocol` 调度；`audio_decoder` 仅用于 SD 卡 MP3 解码；主节点本地播放也延迟 `D`，与从节点同步。

------

## 1. 设计原则

**分层解耦**：BSP → 中间件 → 应用层，单向依赖。

------

## 2. 分层架构总览

> BSP 层只关心“如何操作硬件”，不包含音频业务、文件系统或应用策略。

**总线仲裁（优先级准入 + 会话预算）**：

- 设备在 `Spi_DeviceConfig_t` 声明优先级（`SPI_PRIO_LOW/NORMAL/HIGH`）：
  LCD 刷屏 = HIGH，SD 卡数据流 = NORMAL（格式化等后台操作可用 LOW）；
- 会话式设备（SD 卡）在长等待循环与多扇区读写边界调用
  `Spi_Device_Session_Yield_If_Needed()`：有更高优先级设备在等、或本段连续
  占用超过会话预算（默认 10ms）时主动让出，让 LCD 插入一笔事务后立即续回；
  让出期间 CS 保持低电平，SD 命令序列不中断；
- `Spi_Get_Stats()` / `Spi_Dump_Stats()` 输出每设备的持有/等待/让出统计，
  用于验证“UI 最长事务等待”与 SD 吞吐的平衡（板级调参依据）。

#### 3.2.3 `audio_decoder`

- **实现状态**：已实现（`components/middlewares/audio_decoder/audio_decoder.h` / `audio_decoder.c`）。
- **架构位置**：只负责解码 SD 卡 `/sdcard/music` 下 MP3 文件为 16-bit PCM，解码任务在模块内部创建，通过 `on_pcm` 回调把 PCM 交给 `MusicPlay`（仅注册回调）统一喂给 `sync_protocol`。
- **解码库方案**：MP3 使用离线单头文件库 `minimp3`（CC0-1.0），随模块一起维护在 `third_party/minimp3/`；当前仅支持 MP3，WAV 等其他格式暂不支持。
- **设计约束**：
  - 播放/暂停/上下曲归 `MusicPlay`，模块内部只提供解码与输出回调。
  - 当前不做 `seek()` 回拉；但保留 `get_position_ms()` 给 UI 显示进度。
  - 音量不做在本模块，由 `amplifier`/上层控制。
- **对外接口**：

```c
/* 句柄 */
typedef struct audio_decoder_s *audio_decoder_handle_t;

/* 音频格式 */
typedef enum {
    AUDIO_DECODER_FMT_MP3 = 0,
} audio_decoder_format_t;

/* 文件参数 */
typedef struct {
    audio_decoder_format_t format;
    uint32_t               sample_rate;
    uint8_t                channels;
    uint32_t               duration_ms;
    uint32_t               bitrate_bps;
} audio_decoder_info_t;

/* PCM 输出回调：解码任务上下文调用，直接进 sync_protocol */
typedef void (*audio_decoder_pcm_cb_t)(const int16_t *pcm,
                                       size_t samples,
                                       uint32_t sample_rate,
                                       uint8_t channels,
                                       void *user_ctx);

/* 播放/编解码事件回调 */
typedef enum {
    AUDIO_DECODER_EVT_READY,   /* 文件头解析完成，可读取参数 */
    AUDIO_DECODER_EVT_EOF,     /* 解码到文件尾，MusicPlay 切下一首 */
    AUDIO_DECODER_EVT_ERROR,   /* 文件损坏/解码失败 */
} audio_decoder_event_id_t;

typedef void (*audio_decoder_event_cb_t)(audio_decoder_event_id_t event,
                                         const audio_decoder_info_t *info,
                                         void *user_ctx);

/* 打开文件时的配置 */
typedef struct {
    audio_decoder_pcm_cb_t   on_pcm;
    void                   *pcm_ctx;
    audio_decoder_event_cb_t on_event;
    void                   *event_ctx;
} audio_decoder_cfg_t;

/* 生命周期 */
esp_err_t audio_decoder_init(void);
esp_err_t audio_decoder_deinit(void);

/* 打开并解码 SD 卡文件（如 "/sdcard/music/a.mp3"） */
audio_decoder_handle_t audio_decoder_open(const char *path,
                                          const audio_decoder_cfg_t *cfg);

esp_err_t audio_decoder_close(audio_decoder_handle_t dec);

/* 播放/暂停/停止（内部解码任务驱动 on_pcm 回调） */
esp_err_t audio_decoder_play(audio_decoder_handle_t dec);
esp_err_t audio_decoder_pause(audio_decoder_handle_t dec);
esp_err_t audio_decoder_stop(audio_decoder_handle_t dec);

/* 查询文件参数 / 当前进度（UI） */
esp_err_t audio_decoder_get_info(audio_decoder_handle_t dec,
                                 audio_decoder_info_t *info);
esp_err_t audio_decoder_get_position_ms(audio_decoder_handle_t dec,
                                        uint32_t *position_ms);
```

- **对外接口补充**：`audio_decoder_pcm_cb_t` 为对外同步回调的唯一出口，由 `MusicPlay` 注册并将回调指向 `sync_protocol_master_push_pcm()`；不提供 `seek()`。

#### 3.2.4 `bt_audio`

- **实现状态**：已实现（`components/middlewares/bt_audio/bt_audio.h` / `bt_audio.c`）。
- **架构位置**：封装经典蓝牙协议栈，提供 A2DP Sink 与 AVRCP 控制；HFP(HF) 代码保留但当前无调用者，不会建立连接。
- **设计约定**：
  - PCM 下行（A2DP 音乐；HFP 语音应答通道保留但无调用者）统一通过 `on_pcm` 回调交给 `sync_protocol`，不经过 App 层。
  - UI 控制统一走 `bt_audio_send_ctrl_cmd()`；手机 AVRCP 状态统一通过 `on_event` 回调交给 UI。
  - 蓝牙协议栈回调内不直接调用外部回调；`bt_audio` 内部先入 FIFO，再在自身任务上下文触发 `on_event` / `on_pcm`。

#### 3.2.8 `sync_protocol`

- **实现状态**：已实现（`components/middlewares/sync_protocol/sync_protocol.h` / `sync_protocol.c`）。
- **架构位置**：汇聚 `bt_audio`（A2DP）与 `audio_decoder`（SD 卡）的 PCM，打时间戳后经 `wifi_manager` 音频通道逐台单播到从节点（UDP 5680）、并按 `t_play_us + 60ms` 经 `Amplifier_Play_Buffer()` 本地播放；本模块不持有 UDP socket，通道由 `wifi_manager` 统管。
- **源无关设计**：`sync_protocol` 不感知蓝牙/SD 等业务概念，只认 `stream_id + sample_rate + channels`。当前播放源由 App 层 `MusicPlay` 维护，换源时由 `MusicPlay` 重新调 `sync_protocol_master_start()` 并传入新 `stream_id`。
- **关键公式**：包头 `t_play_us = t_tx + D`（D 默认 200ms，NVS 可调）；主节点出声 `t_play_us + 60ms`（`SYNC_RX_MARGIN_US`）；从节点 `offset = d_min + lead_ms×1000 + 60ms`、出声 `t_play_us + offset`。

#### 3.3.1 `MusicPlay`

- **实现状态**：已实现（`components/App/MusicPlay/`）；原 `PlayMode`（3.3.4）已并入本模块。
- **职责**：
  - 播放源、播放状态、音量、播放模式的唯一状态主人；
  - 蓝牙源驱动 `bt_audio`，本地源驱动 `audio_decoder`，同步控制走 `sync_protocol_master_broadcast_cmd()`；

#### 3.3.3 `LightControl`

- **实现状态**：已实现（`components/App/LightControl/light_control.h` / `light_control.c`）。
- **职责**：
  - 封装灯控 JSON 协议，提供 on/off 开关**单个区域灯**的 App 接口（不支持全屋广播）；灯控节点是 ESP8266 独立工程，硬件为继电器，只能开/关、不能调亮度，当前只有一盏灯（`bedroom`）；
  - 数据包经 `wifi_manager` 灯控组播通道发送（默认 239.0.0.2:8889），不自行持有 socket；报文统一带 `version` 字段（当前 1）；
  - 解析灯控上行三类消息：即时回执 `{"cmd":"ack","light":"<name>","ok":<bool>,"version":1}`、周期状态上报 `{"cmd":"status","light":"<name>","ok":<bool>,"version":1}`（灯控每 30s 发送一次）、版本不兼容回告 `verr`，统一通过 `on_event` 回调通知 UI 刷新灯状态图标；

  - 周期上报的周期（30s）由灯控端约定，本模块只负责解析与超时判定：超过 `state_timeout_ms` 未收到该灯上行，发 `LIGHT_EVT_ERROR` 并把该灯状态回落 `UNKNOWN`。

## 4. 关键数据流

### 一、手机音乐下行（A2DP）——主链路

```
手机 → A2DP(SBC) 
  ↓ [蓝牙空中，协议栈接管]
ESP-IDF 蓝牙协议栈（SBC 自动解码成 16bit PCM）
  ↓ [协议栈回调，中断/协议栈上下文]
bt_audio 模块
  ↓ [内部 FIFO + 自身任务]
on_pcm 回调 → sync_protocol → 单播(逐台从节点，UDP 5680) + 本地延迟 → amplifier → i2s_driver → 喇叭
```

逐节点职责：

- bt_audio

  ：封装蓝牙协议栈的"壳"。只做三件事：

  - 收：协议栈回调里不直接调外部回调，先把 PCM 放进 `a2dp_fifo_bytes` 的 FIFO，再由 bt_audio 自身任务取出、按需触发 `on_pcm`（避免在蓝牙回调上下文做重活）；
  - 发：收集手机的 AVRCP 状态/歌曲信息/音量变化，向外发 `on_event`；
  - 控：`bt_audio_send_ctrl_cmd()` 把 UI 命令转 AVRCP 发回手机。
  - **不干**：不解码（esp-id 做）、不决定谁播放、不合并音源。

1. **App 接线层**（app_main 初始化处）：`bt_audio_cfg.on_pcm` 被接到转发函数，把回调转调 `sync_protocol_master_push_pcm()`。**注意：只做"接线"，不做任何格式判断**——源是 A2DP 还是 HFP 由 `source` 枚举区分，决定走哪个 stream。

2. **sync_protocol**：汇聚 + 同步。它不关心音源是谁（蓝牙/SD/HFP），只认 

   ```
   stream_id + sample_rate + channels
   ```

   。收到 PCM →

   - 打上基准播放时刻 `t_play_us = t_tx + D` → 立即打包经 `wifi_manager` 音频通道逐台单播（从节点 UDP 5680）；
   - 同时把同一包放进本地**延迟队列**，等到 `t_play_us + 60ms`（`SYNC_RX_MARGIN_US`，与从节点同一公式）才经 `Amplifier_Play_Buffer()` 写 I2S，保证主从同拍。
   - **不：** 不持有 socket（wifi_manager 管）、不写 I2S 之外的东西、不做格式转换。

3. **amplifier（TX）**：持有 I2S TX 句柄，内部写锁保证同一时刻只允许一路写入，把 PCM 写到对应 I2S 端口的 DMA buffer（原 audio_bus 的 TX 职责并入本模块）。

4. **amplifier**：NS4168 输出链路 + 软件音量。NS4168 无硬件音量接口，音量只在软件侧保存/应用（写 PCM 时乘以系数）；PCM 经 `Amplifier_Play_Buffer()` 在内部写锁下落到 I2S。

5. **i2s_driver**：BSP 层，真正把 PCM 转 DMA/I²S 信号给功放。

------

### 二、SD 卡本地播放

```
SD 卡文件 → sd_card(FATFS 读) → audio_decoder 解码任务
  → on_pcm 回调 → sync_protocol_master_push_pcm()（同一条链路）
    → 单播 + 本地延迟 → amplifier → i2s_driver → 喇叭
```

职责分工（重点：**audio_decoder 极端摆烂**）：

- **audio_decoder**：只做两件事。①对 MP3 流式解码；②把解码出的 PCM 通过 `on_pcm` 回调丢出去。它**没有 play/pause 决策权**——`audio_decoder_play/pause/stop` 只是内部解码任务的启停，真正的"接下来放哪首、单曲循环还是顺序"由 **MusicPlay** 决定。

- MusicPlay

  ：播放状态机的主人。它接收 UI/蓝牙/解码三类事件，统一进内部事件队列串行处理：

  - 当上游（audio_decoder）来消息时：`AUDIO_DECODER_EVT_EOF` 由它决定下一首（顺序→自动切下一条；循环→重播当前曲），然后调用 `audio_decoder_play(下一个文件)`；
  - 广播同步命令 `sync_protocol_master_broadcast_cmd(SYNC_CMD_NEXT)`，让从节点也切曲。

- **同一个 push_pcm() 汇聚点**：本地与蓝牙都是直接 `push_pcm`，sync_protocol 不管来源。

> **启动顺序**：SD 卡挂载、蓝牙建链、列表扫描都在 UI 之前完成（UI 页面要用列表与播放状态），
> 但**第一首不在那时起播**；等 UI 首帧刷完、App 调 `music_play_set_autoplay(true)` 放行后才 open/解码，
> 因此开机观感是「屏幕先亮，音乐随后响」。

### 五、UI 资源加载（图片：Flash storage → 屏幕；字体：编译进固件）

```
UI 图片：spiffs_create_partition_image 生成的 storage 分区镜像（storage/ui_img/ 3 张 PNG，随固件烧录）
  → esp_vfs_spiffs_register 挂载 /storage
  → LVGL 文件系统盘符 'F'（VFS stdio 适配）
  → UI_Task（LVGL 渲染线程）按需解码 → LCD_Touch 显示（ILI9341）

字体/图标：lv_font_conv 生成 C 数组（ui_font_cn_16 / ui_icons_16 / ui_icons_24）编译进 app 固件，
           运行时直接引用 const lv_font_t，无文件系统 IO。
```

1. **依赖**：UI 依赖 Flash `storage`（spiffs）分区读取 3 张 PNG 图片；字体/图标编译进固件，二者都不依赖 `sd_card`；
2. **不进音频链路**：图片/字体加载是低频应用数据，只进 LVGL 图像缓存，不经过音频中间件与 `sync_protocol`；
3. **容错**：`storage` 分区未挂载（镜像未烧录/损坏）时，UI 图片用内置字形/占位色块降级，字体/图标不受影响，界面照常可用；
4. **初始化顺序**：`ui_hw_bringup()` 内 `esp_vfs_spiffs_register()` 挂载 `/storage` 成功后才允许加载图片（失败置降级标志，不阻塞 UI）。

### 六、控制 / 命令流（不流经音频 LINE）

#### 6.1 源选择 vs 播放执行（同一模块内的两条职责）

|                 | **源选择（MusicPlay 内部策略）**                             | **播放执行（MusicPlay 状态机）**                             |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 职责            | 决定「切什么源」：蓝牙/本地                                  | 执行「怎么切、切完怎么播」：播放/暂停/上下曲/音量/列表       |
| 如何换源        | 内部轮询 `bt_audio_get_a2dp_info()` 判断连接状态 → 自动规则  | 收到切换请求 → 停旧流/起新流（同一个 `MusicPlay_Task` 串行） |
| 自动规则        | 蓝牙优先级最高：连接→BT；断开→LOCAL（SD 继续放）            | 不在乎源规则，只执行切换                                     |
| 手动入口        | `music_play_set_source()`（UI）；自动规则下次轮询校正        | —                                                            |
| 给 UI           | `music_event_cb_t` 的 `MUSIC_EVT_SOURCE_CHANGED`             | `music_event_cb_t`（播放状态/曲目/音量快照）                 |
| 谁有最终话语权  | 输出"期望源"                                                 | 状态的最终刷新以接收到的 `bt_audio`/解码事件为准             |

一句话结论：**源选择（自动/手动）与播放执行都在 MusicPlay 内，由同一个 `MusicPlay_Task` 串行处理；「切什么源」按蓝牙优先自动规则，「怎么切、切完之后怎么播」由状态机执行。** 原独立 `PlayMode` 模块已并入，消除了两份 source 状态不一致的问题。

#### 6.2 UI 控制手机（AVRCP）

```
UI 触摸 → music_play_command()（统一命令口）→ MusicPlay 状态机
   ├─ BT：→ bt_audio_send_ctrl_cmd(PLAY/PAUSE/NEXT/PREV/VOL) → AVRCP → 手机
   │      → 手机回流 BT_AUDIO_EVT_PLAY_STATE_CHANGED → 状态机采信/刷新
   └─ 同时：→ sync_protocol_master_broadcast_cmd(SYNC_CMD_*) → 从节点
```

边界：**UI 不得直接调 bt_audio**；必须经由 MusicPlay（文档边界：App 层依赖中间件完成硬件操作；蓝牙控制最终只能经过 bt_audio 的 API，但 UI 只能到 MusicPlay 这一层）。

- 手机与 UI "同时按键" 的处理：**指令都是"期望"**，进入 MusicPlay 事件队列串行执行，最终状态以 bt_audio 回流事件为准（本地源则以解码器状态为准）。
- MusicPlay 再把它需要静音的同步命令（播放/暂停/上下曲/音量/重置）广播给从节点。

### 七、系统服务流（不经过音频区域到）

#### 7.1 灯控

```
UI 点击 → light_control_send(cmd, light) → JSON 组包
   → wifi_manager_mcast_send(239.0.0.2:8889)（rx=true 已开）
   → ESP8266 → ack JSON → wifi_manager_mcast_recv(FIFO) → LightControl 解析
   → light_control on_event(ACK/ERROR) → UI 软件刷新图标

   ─── 周期状态上报（灯控每 30s 上行）───
   ESP8266 → status JSON → wifi_manager_mcast_recv(FIFO) → LightControl 解析
   → light_control on_event(STATUS) → UI 软件刷新图标
```

边界：LightControl **不持有 socket**，socket 全在 wifi_manager；它是纯粹的"协议编解码 + 状态解析"模块，灯状态以 `ack`/`status` 上报实际值为准，不再做下发推断。

#### 7.2 WiFi / 配对 / 状态

```
开机：wifi_manager_start() → 从 node_role 读 SSID/密码 → 发起连接（当前无配网 UI）
后续查询：UI 图标 → wifi_manager_get_state()/is_connected()（轮询，不绑事件）
```

- node_role 是唯一 NVS 写者；wifi_manager 只拿 NVS 凭据，不自己写。

#### 7.3 OTA

```
app 就绪 → OTA_Update_Init(NULL) ← 内部按 cfg→node_role 配置（ota_server_url）→默认宏兜底
 → OTA_Update_Start() 后台 或 CheckAndUpgrade() 阻塞
 → HTTP 直连服务器（不经组播/wifi socket）
 → 下载写入备用分区 → 校验 SHA256 → 切换重启
 → 过程经 on_event 回调（进度/失败）给 main / UI
```

- OTA 只依赖 `wifi_manager_is_connected()` 判断网络，不占用 `sync_protocol` 与 `audion 路由`。

#### 7.4 从节点（广播侧）

```
接收：从节点 wifi_manager RX（UDP 5680 单播）→ 从节点 sync_protocol(裁剪版) → 延迟队列
 → offset = d_min + lead_ms×1000 + 60ms → t_play_local = t_play_us + offset → 从节点 amplifier → i2s → 喇叭
```

- 主节点 role：唯一发流，从节点只跟随。主/从角色由 node_role 存 NVS 决定。

## 5. 同步播放架构说明

同步播放的本质：**主节点发一个包时，约定这个包在未来的 t_tx + D 时刻播放；主节点自己也要等到这个时刻才播。**

- `sync_protocol` 是所有音源 PCM 的汇聚点。

- 主节点本地播放不是立即的，而是延迟 `D` 再加 60ms 抖动余量（`SYNC_RX_MARGIN_US`；`D` 默认 200ms）。

- 从节点用"最小单程延迟"单向估计时钟偏移（PING/PONG 保留，但不参与音频同步），然后计算：

  ```text
d(i)   = 本地收到时刻 − t_play_us（接收窗口内取最小值 d_min）
offset = d_min + lead_ms×1000 + 60ms
t_play_local = t_play_us + offset
  ```

- 这样主从都在同一基准时刻出声（双方加相同的 60ms 余量），音频同步不需要从节点回包。

- 长期漂移用丢/插单个样点（sample slip）补偿，不改 I2S 采样率。

**音频链路的关系**：

- 同步模式下，`sync_protocol` 是 I2S TX 的唯一 PCM 数据源（经 `Amplifier_Play_Buffer()` 落 I2S）。
- 麦克风上行链路已整体下线：`microphone`（INMP441）与 `CallPhone`（esp-sr 唤醒）已移入 `legacy_disabled`，不经 `amplifier` TX；`bt_audio` 内的 HFP 代码保留但无调用者，不会建立 SCO。

## 6. FreeRTOS 任务设计（主节点）

> **任务视图说明**：任务表为**实现视图**——App 层任务与 middlewares / msystem 模块内部自建的常驻任务全部登记（见“所属”列），优先级、栈、核绑定全局统一仲裁；模块内部任务由模块自身 `create/start` 创建，App 层不感知创建细节。

> **核分配原则**：Core 0 (PRO_CPU) 承担协议与系统核心——Wi-Fi、蓝牙协议栈、TCP/IP 栈（lwIP）以及高精度定时器等系统关键任务默认固定在其上运行；Core 1 (APP_CPU) 是实时音频核心，**写 I2S、解码、蓝牙 PCM 出队这些有硬时限的任务放 Core 1**，与网络/蓝牙协议栈解耦，保证执行确定性。
>
> UI 是例外：LVGL 刷一整屏（320×240×2B @10MHz SPI）要连续占用所在核约 123ms，若放 Core 1 会直接造成 I2S 欠载，所以 `UI_Task`/`Touch_Task` 放 Core 0，并把优先级压到 10（低于 `SyncTx_Task` 的 11），让同核的发包节拍优先。

| 任务名                 | 所属                        | 优先级 | 栈大小  | 核         | 功能                                                         |
| :--------------------- | :-------------------------- | :----- | :------ | :--------- | :----------------------------------------------------------- |
| `SyncLocalPlay_Task`   | middlewares: `sync_protocol` | 12     | 4096    | **Core 1** | 本地延迟队列取 PCM，按 `t_play_us + 60ms` 写 I2S；喂 I2S 的消费端，优先级最高 |
| `SyncTx_Task`          | middlewares: `sync_protocol` | 11     | 4096    | **Core 0** | 打时间戳、UDP 逐台单播发送                                   |
| `bt_audio_task`        | middlewares: `bt_audio`      | 11     | 4096    | **Core 1** | 蓝牙事件 FIFO 出队，触发 `on_event`/`on_pcm`（协议栈回调不入用户回调） |
| `UI_Task`              | App: UI                     | 10     | 32768   | **Core 0** | LVGL 界面交互与显示；图片从 Flash `/storage` 按需加载            |
| `audio_decoder` 解码任务 | middlewares: `audio_decoder` | 10    | 4096    | **Core 1** | SD 卡 MP3 流式解码→ `on_pcm`→`push_pcm()`；解码任务在模块内部 |
| `MusicPlay_Task`       | App: MusicPlay               | 9      | 4096    | **Core 1** | SD 选曲/播放控制/状态机 + 自动源选择（原 PlayMode，轮询 A2DP）；不承载解码（在 audio_decoder 内部） |
| `wifi_mcast_rx`        | msystem: `wifi_manager`      | 6      | 6144    | **Core 0** | 组播收包→FIFO（rx 启用的通道，如灯控通道 ack/status）         |
| `SmartHome_Task`       | App: LightControl            | 5      | 4096    | **Core 0** | 处理 UI 灯控指令 UDP 组播发送；解析 ack / 30s status 上报并触发事件回调 |
| `ota_update` / `ota_sync` | msystem: `ota_manager`    | 5      | 12288   | **Core 0** | 动态创建，执行固件下载/升级，完成后自销毁                    |
| `Touch_Task`           | middlewares: LCD_Touch       | 3      | 2048    | **Core 0** | 触摸 IC（FT6336G）扫描，由模块内部创建                           |
| `app_hb`               | App: `app_main` 心跳         | 2      | 3072    | **Core 0** | 卡死定位心跳，不参与启动时序，创建失败仅少一份诊断            |

**核分配理由**（按“网络/协议侧→Core 0，实时/应用侧→Core 1”）：
- **网络/协议侧（Core 0）**：`SyncTx_Task`（UDP 单播依赖 lwIP）、`ota_update`/`ota_sync`（网络下载）、`SmartHome_Task`、`wifi_mcast_rx`（组播收包）、`app_hb`（心跳）放 Core 0，与 lwIP/蓝牙同核，减少跨核开销；
- **实时音频侧（Core 1）**：`SyncLocalPlay_Task`（写 I2S）、`audio_decoder` 解码任务、`bt_audio_task`（PCM 出队回调）、`MusicPlay_Task`（播放状态机）放 Core 1，与网络协议栈分核，隔离网络抖动；
- **交互（Core 0）**：`UI_Task` / `Touch_Task` 放 Core 0。LVGL 刷一整屏（320×240×2B @10MHz SPI）约 123ms，会连续占住所在核；若与 `SyncLocalPlay_Task` 同核，会直接造成 I2S 欠载。代价是会推后同核的 `SyncTx_Task`，所以 `UI_Task` 优先级定在 10（低于 `SyncTx_Task` 的 11），让发包节拍优先；
- **任务归属变化说明**：原“`AudioSource_Task`”（逻辑上汇总蓝牙/SD 音频源）**不再作为独立任务**——A2DP PCM 由 `bt_audio_task` 出队回调、SD 解码由 `audio_decoder` 解码任务产出，二者均在中间件内部直接回调 `sync_protocol`；原“`LocalPlay_Task`”更名为 `MusicPlay_Task`，只做选曲/控制/模式状态机；启动期另有一次性引导任务（`mp_boot`、`lc_boot`）和 UI 引导任务，跑完即退出，不登记为常驻任务。

> **实现约定**：所有任务统一用 `xTaskCreatePinnedToCore()` 创建，按上表绑定核（`Core 0`=0，`Core 1`=1）；模块内部任务由各模块 `create/start` 自建；`ota_update` / `ota_sync` 动态创建时同样按表绑定。

> 任务间通信：中控之间用事件组/命令队列传递状态与控制；PCM 数据经 `audio_decoder`/`bt_cb` 的文件级回调进入 `sync_protocol`，再经各 FIFO/Jitter Buffer 传递，不走核间消息队列。
