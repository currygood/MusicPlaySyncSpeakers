# 从音频节点软件架构分层设计

> **节点型号**：量产目标与主节点相同，为 ESP32-WROVER-E-N16R8；开发阶段暂用 ESP32-S3 开发板（如 ESP32-S3-N16R8）替代，`Play_Slave/sdkconfig` 里的 `CONFIG_IDF_TARGET="esp32s3"` 即为此开发态。
> **文档范围**：仅描述**音频从节点**的软件架构；主节点（ESP32-WROVER-E）固件另行设计。
> **核心原则**：从节点仅工作于**同步模式**，接收主节点 UDP **单播** PCM，按包头 `t_play_us` 对齐出声、用丢/插单个样点补偿晶振漂移，实现与主节点几乎无感知的同步播放。从节点**无经典蓝牙、无触摸屏、无 SD 卡、无麦克风**，仅保留 I2S 功放输出。

------

## 1. 节点概述

从节点是低成本同步播放终端，硬件上仅使用：

- ESP32-WROVER-E-N16R8（量产目标，16MB Flash + 8MB PSRAM）；开发阶段改用现成的 ESP32-S3 开发板（如 ESP32-S3-N16R8，同为 16MB Flash + 8MB PSRAM）
- NS4168 I2S 功放 + 4Ω 3W 喇叭
- 状态灯（GPIO15）
- 电源

从节点**不包含**：

- 经典蓝牙：固件不含 A2DP，不接蓝牙音频（开发阶段的 ESP32-S3 本身也不支持 BR/EDR）
- 触摸屏 / LCD
- SD 卡
- 麦克风
- 灯控相关硬件

从节点软件职责：

1. 连接同一 WiFi 路由器；音频在 UDP `5680` 上 `bind(INADDR_ANY)` 单向接收（**不加入任何组播组、不做 `IP_ADD_MEMBERSHIP`**）。
2. 接收主节点**单播**发来的 PCM 音频帧（20 字节包头 + PCM，44.1kHz/16bit/单声道，默认 15ms 一帧、661/662 样点交替）。
3. 用 `d(i) = 本地收到时刻 − t_play_us` 的窗口最小值单向估计时钟偏移（从节点不回包，不需要 PING/PONG）。
4. 按 `seq` 将 PCM 帧放入环形抖动槽位（吸收乱序与抖动）。
5. 在本地时间 `t_play_us + offset`（`offset = d_min + lead_ms×1000 + 60ms`）时刻，通过 I2S 输出至功放。
6. 以抖动缓冲水位为观测量，用丢/插单个样点（sample slip）补偿晶振漂移，**不改 I2S 采样率**。
7. 处理异常：丢包、网络中断、主节点重启等。
8. OTA 升级：**未实现**（仅分区表预留 `ota_0` / `ota_1` 槽位）。

------

## 2. 设计原则

1. **极简分层**：仅保留必要模块，降低 Flash / RAM 占用与 BOM 成本。
2. **同步优先**：所有音频数据流围绕 `udp_audio` 设计，无本地音源（原 `sync_protocol` 已从从节点工程删除）。
3. **无蓝牙依赖**：不编译任何经典蓝牙 / A2DP / HFP 组件。
4. **无文件系统**：不挂载 SD 卡，不使用 FATFS，不包含 `audio_decoder`。
6. **I2S 唯一写者**：从节点只有 `udp_audio` 向 I2S TX 写数据，无需复杂仲裁。

### 4.2 中间件层（middlewares）

#### 4.2.1 amplifier

- **职责**：NS4168 I2S 功放驱动，将 PCM 输出至喇叭。
- **依赖**：`i2s_driver`（I2S TX 由 amplifier 内部持有）
- **对外接口**：

```c
/* ======================== 功放音频配置 =========================================== */

/** 音频采样率（Hz）：44.1kHz，与主节点全链路统一 */
#define AMPLIFIER_SAMPLE_RATE  44100

/** 音频位深度：16-bit，每个采样点 2 字节 */
#define AMPLIFIER_BIT_DEPTH    16

/** 音频通道数：1（单声道），语音播放不需要立体声 */
#define AMPLIFIER_CHANNEL_NUM  1

/* ======================== API 函数 =============================================== */

/**
 * @brief 初始化功放模块
 *
 * 初始化 I2S TX（I2S_NUM_1）接口，准备音频输出到 NS4168 功放芯片。
 * NS4168 是一款 5W 单声道 D 类功放芯片，通过 I2S 接口接收 PCM 音频数据。
 *
 * 注意：初始化后需要调用 Amplifier_Play_Buffer() 才能播放音频。
 *
 * @return ESP_OK  初始化成功
 *         ESP_FAIL I2S 接口初始化失败
 */
esp_err_t Amplifier_Init(void);

/**
 * @brief 反初始化功放模块
 *
 * 关闭 I2S TX 接口，释放 DMA 缓冲区等资源。
 *
 * @return ESP_OK 反初始化成功
 */
esp_err_t Amplifier_Deinit(void);

/**
 * @brief 通过功放播放 PCM 音频缓冲区
 *
 * 将 PCM 16-bit 单声道音频数据通过 I2S 总线发送到 NS4168 功放芯片，
 * 驱动扬声器发声。
 *
 * @param buffer        指向 PCM 音频数据的指针（16-bit 单声道，小端字节序）
 * @param size          缓冲区大小（字节）
 * @param bytes_written 输出参数，返回实际写入的字节数（可为 NULL）
 * @param timeout       超时时间（FreeRTOS tick 数），若 I2S DMA 缓冲区满则等待
 *
 * @return ESP_OK             播放成功
 *         ESP_ERR_INVALID_ARG buffer 为 NULL 或 size 为 0
 *         ESP_FAIL            I2S 写入失败
 */
esp_err_t Amplifier_Play_Buffer(const uint8_t *buffer, size_t size, size_t *bytes_written, uint32_t timeout);
```

- **备注**：从节点仅此一个音频输出设备。

#### 4.2.3 udp_audio（从节点音频接收与同步，取代原 sync_protocol）
- **实现状态**：已实现（`components/middlewares/udp_audio/udp_audio.h` / `udp_audio.c`）；从节点工程已删除 `sync_protocol`，该名字只在主节点保留（单播发送端）。
- **架构位置**：从节点唯一的音频汇入点——只负责**接收**主节点**单播**发来的 PCM 并按 `t_play_us` 对准出声，**不产生也不转发任何音源**：
  
  - 音频通道：UDP **5680 单播**（RX），`bind(INADDR_ANY)`，**不加入组播组、不做 `IP_ADD_MEMBERSHIP`**；包头 20 字节 `magic(u16,0xAA55) | version(u8,=2) | flags(u8,bit0=流首帧) | stream_id(u16) | seq(u16) | t_play_us(u64) | payload_len(u16) | lead_ms(u16)`，后接 44.1kHz/16bit/单声道 PCM（默认 15ms 一帧，661/662 样点交替）；
  - 控制通道（音量 / 公告）由 `ctl_rx` 单独处理（组播 `239.0.0.1:5679`，见 4.4 的 wifi_manager），本模块不持有它；
  - 本模块自建 5680 单播 socket（`ua_open_socket()`），不经 `wifi_manager_mcast_open()`；
  - 音频同步**不需要从节点回包**：`PING(0x20)` / `PONG(0x21)` 帧仍保留在控制通道定义里，但已不参与音频同步。
- **源无关（纯接收端）**：从节点没有蓝牙/SD/HFP，不感知音源业务，只认 `stream_id + 44.1kHz/16bit/单声道`（全链路固定采样率，见 4.2.1 amplifier）。
- **同步算法**：

  ```text
  时钟估计（单向，不需要 PING/PONG）
    d(i)   = 本地收到第 i 帧的时刻 − 该帧 t_play_us
    d_min  = 最近 64 帧窗口内 d(i) 的最小值
    offset = d_min + lead_ms × 1000 + UDIO_MARGIN_US(60000)
    出声时刻 = t_play_us + offset

  漂移补偿（sample slip，不改 I2S 采样率）
    观测量 = 抖动缓冲"跑道"（最近收到的 t_play − 正在播放帧的 t_play）
    开播 200 帧后把跑道均值定为基准
      跑道比基准长 4ms 以上 → 丢 1 个样点（加快）
      跑道比基准短 4ms 以上 → 插 1 个样点（放慢）
      最小间隔 20ms，拼接点做 8 点线性过渡
  ```

- **对外接口**：

```c
/* ======================== 线格式（与主节点逐字节一致） ============================ */
#define UDIO_MAGIC                  (0xAA55)
#define UDIO_VERSION                (2)
#define UDIO_DEFAULT_PORT           (5680)
#define UDIO_SAMPLE_RATE            (44100)
#define UDIO_CHANNELS               (1)
#define UDIO_BITS                   (16)

/** flags 位定义：bit0 = 本次流的首帧 */
#define UDIO_FLAG_STREAM_START      (0x01)

/** 帧头（packed，20 字节），`t_play_us` 落在 8 字节边界上 */
typedef struct __attribute__((packed)) {
    uint16_t magic;         /* 固定 UDIO_MAGIC */
    uint8_t  version;       /* 固定 UDIO_VERSION */
    uint8_t  flags;         /* UDIO_FLAG_* */
    uint16_t stream_id;     /* 一次音频流唯一标识 */
    uint16_t seq;           /* 包序号，0~65535 回绕 */
    uint64_t t_play_us;     /* 基准播放时刻（发送端时钟，µs） */
    uint16_t payload_len;   /* PCM 字节数（不含头） */
    uint16_t lead_ms;       /* 发送端提前量 D（ms） */
} udio_hdr_t;

/** 接收端抖动余量（µs）：抖动缓冲深度，主节点本地播放也加同一值 */
#define UDIO_MARGIN_US              (60000)

/* ======================== 对外接口 =============================================== */
esp_err_t udp_audio_start(uint16_t port);   /* 0 = UDIO_DEFAULT_PORT(5680)；内部起接收、播放两个任务 */
void      udp_audio_stop(void);             /* 停止接收任务并关闭 socket（调试用，正常流程不调用） */
```

- **收包链路**：`ua_rx_task` 在 5680 上 `recvfrom` → 校验 `magic` / `version` → 按 `seq % 64` 落环形槽位（重复包丢弃，已播过的迟到包丢弃）→ 更新 `d(i)` 窗口；`flags` 首帧或 `stream_id` 变化视为新流，清盘重新 preroll。
- **出声链路**：`ua_play_task` 攒够 preroll（有效帧 ≥ 8 且缓冲深度 ≥ `lead_ms` 的 3/4）后冻结 `offset`，等到 `t_play_us + offset` 起播，经 `Amplifier_Play_Buffer()`（amplifier 内部写锁）直接写 I2S，从节点 I2S 唯一写者；首帧做 128 点淡入，缺帧用上一帧 3/4 衰减的 PLC 补，断流 > 500ms 清盘重新 preroll，缓冲深于 450ms 跳到 150ms 位置。
- **无心跳链路**：从节点不收心跳、不做速率微调、也不回 PING；漂移完全由上面的 sample slip 补偿，丢包/欠载规则见第 6 章。
- **构件裁剪**：从节点为独立工程，`app_main` 直接串起 `StartAndStop / node_role / StatusLed / wifi_manager / amplifier / ctl_rx / udp_audio`；不存在 `CONFIG_NODE_ROLE_SLAVE` 这类角色裁剪宏，主节点的 `sync_protocol_master_*` 系列 API 不出现在从节点。

## 5. 关键数据流

### 5.1 同步播放数据流

```reStructuredText
主节点 UDP 单播 → 从节点 5680
        │
        ▼
从节点 WiFi 接收（不加入组播组）
        │
        ▼
udp_audio
        │
        ├── 解析包头：stream_id, flags, seq, t_play_us, payload_len, lead_ms
        ├── 计算 offset = d_min + lead_ms×1000 + 60ms
        ├── 按 seq 放入抖动缓冲环形槽位
        │
        ▼
udp_audio 播放任务
        │
        ├── 等到 t_play_us + offset
        ├── 从槽位取 PCM
        ├── 缺帧时用上一帧 PLC（3/4 衰减）补
        │
        ▼
Amplifier_Play_Buffer()
        │
        ▼
I2S → 喇叭
```

### 5.2 时钟同步数据流

音频同步不使用 PING/PONG：`PING(0x20)` / `PONG(0x21)` 帧仍保留在控制通道定义里，但已不参与音频同步，从节点也不回包。时钟偏移由单向观测得到：

```reStructuredText
主节点单播音频帧（带 t_play_us）
        │
        ▼
从节点收到：d(i) = 本地收到时刻 − t_play_us
        │
        ▼
窗口（64 帧）内取最小值 d_min
        │
        ▼
offset = d_min + lead_ms×1000 + 60ms
        │
        ▼
出声时刻 = t_play_us + offset
```

主节点本地也按 `t_play_us + 60ms` 出声，所以两端残差只有最小单程延迟（局域网通常 1~3ms）。

### 5.3 漂移校正数据流

从节点不收心跳、不做速率微调，也不改 I2S 采样率；漂移由抖动缓冲水位间接观测，再用丢/插单样点补偿：

```reStructuredText
从节点每个播放帧
  ├── 跑道 = 最近收到的 t_play − 正在播放帧的 t_play
  ├── 开播 200 帧后把跑道均值定为基准
  ├── 跑道比基准长 > 4ms → 丢 1 个样点（加快播放头）
  ├── 跑道比基准短 > 4ms → 插 1 个样点（放慢播放头）
  └── 两次 slip 间隔 ≥ 20ms，拼接点做 8 点线性过渡
```

## 6. 同步机制（从节点核心算法）

### 6.1 启动同步

1. 从节点连接 WiFi（**不加入音频组播组**）。

2. 在 UDP `5680` 上 `bind(INADDR_ANY)`，等待主节点单播音频帧。

3. 每收到一帧记录 `d(i) = now − t_play_us`，维护最近 64 帧窗口内的最小值 `d_min`。

4. 攒够 preroll（有效帧 ≥ 8 且缓冲深度 ≥ `lead_ms` 的 3/4）后冻结换算偏移：

   ```text
offset = d_min + lead_ms × 1000 + 60000
   t_play_local = t_play_us + offset
   ```
   
5. 等到 `t_play_local` 到达时起播（首帧 128 点淡入，避免直流台阶）。

6. 已播过的 `seq` 直接丢弃，迟到包不覆盖槽位。

7. 缓冲深于 450ms 时跳到约 150ms 的位置，避免延迟无限累积。

### 6.2 持续校正

- 从节点不回包、不收心跳；播放过程中**不重算 offset**（重算等于改出声时刻，会产生阶跃）。

- 观测量是抖动缓冲"跑道"：`跑道 = 最近收到的 t_play − 正在播放帧的 t_play`。从机晶振慢 → DMA 消耗慢 → 跑道变长。

- 开播 200 帧后把跑道均值定为基准，之后只看它相对基准的变化量。

- 调整策略：

  | 条件                     | 动作                                         |
| :----------------------- | :------------------------------------------- |
  | `跑道 − 基准 > +4ms`     | 丢 1 个样点（加快播放头）                    |
| `跑道 − 基准 < −4ms`     | 插 1 个样点（放慢播放头）                    |
  | 其余                     | 保持                                         |
  
- 两次 slip 间隔 ≥ 20ms，拼接点做 8 点线性过渡；**不改 I2S 采样率**（`disable → reconfig → enable` 会清空 DMA 中未播的音频）。

### 6.3 异常处理

| 异常场景             | 处理策略                                                     |
| :------------------- | :----------------------------------------------------------- |
| 丢包（Seq 不连续）   | 用上一帧 3/4 衰减后的 PLC 补一帧，`seq` 照常前进              |
| Jitter Buffer 欠载   | 同上（没有上一帧可参考时补 10ms 静音）；断流 > 500ms 清盘重新 preroll |
| 网络中断 > 500ms     | 持续写静音（避免 DMA 放空出嗡嗡声），断流超时后清盘重新 preroll；不涉及组播重新加入 |
| 主节点重启 / 切换    | 检测到 `stream_id` 变化或首帧标志，清空缓冲重新 preroll        |
| 从节点启动晚于主节点 | 按最小单程延迟对齐，落后的帧直接丢弃 / 跳帧，从可播位置开始   |
| 主节点暂停 / 恢复    | 从节点不解析 PAUSE / PLAY（`ctl_rx` 只认音量帧）；主节点停发后按"欠载 / 断流"处理，恢复发流后重新 preroll |
| 主节点切歌           | 靠 `stream_id` / 首帧标志识别新流并清盘，不解析 `NEXT` / `PREV` |

## 7. FreeRTOS 任务设计（从节点）

> **任务视图说明**：任务表为**实现视图**——与主节点一致，App 层任务与 mysystem / middlewares 模块内部自建的常驻任务全部登记（见“所属”列），优先级、栈、核绑定全局统一仲裁；模块内部任务由模块自身 `create/start` 创建，App 层不感知创建细节。从节点无蓝牙（`bt_audio`）、无 SD 解码（`audio_decoder`）、无 UI/麦克风等模块，因此表中只登记同步链路、控制通道与网络三类任务。

> **核分配原则（设计目标；当前 `udp_audio` / `ctl_rx` 的任务尚未绑定核）**：Core 0 (PRO_CPU) 承担协议与系统核心——Wi-Fi、TCP/IP 栈（lwIP）以及高精度定时器等系统关键任务默认固定在其上运行，负载较高，**不适合再放置高优先级、计算密集型的应用任务**；Core 1 (APP_CPU) 是应用与实时核心，**对实时性、流畅度要求高的任务（I2S 音频输出）都放在 Core 1**，与网络协议栈解耦，保证执行确定性。

| 任务名                 | 所属                         | 优先级 | 栈大小  | 核         | 功能                                                         |
| :--------------------- | :--------------------------- | :----- | :------ | :--------- | :----------------------------------------------------------- |
| `udp_audio_rx`         | middlewares: `udp_audio`     | 11     | 4096    | 未绑定（`xTaskCreate`） | 在 5680 单播 socket 上 `recvfrom` → 校验 magic/version → 按 `seq` 落环形槽位 → 更新 `d(i)` 偏移窗口 |
| `udp_audio_play`       | middlewares: `udp_audio`     | 10     | 5120    | 未绑定（`xTaskCreate`） | 攒够 preroll 后等 `t_play_us + offset`，取 PCM 经 `Amplifier_Play_Buffer()` 落 I2S；缺帧 PLC / 断流重新 preroll / sample slip |
| `ctl_rx`               | middlewares: `ctl_rx`        | 5      | 3072    | 未绑定（`xTaskCreate`） | 控制组播 5679：取 4 字节音量帧调 `Amplifier_Set_Volume()`；每 3s 发一条 ANNOUNCE |
| `wifi_mcast_rx_Task`   | mysystem: `wifi_manager`     | 6      | 4096    | **Core 0** | 组播收包写入通道 FIFO（`rx_enable` 的通道各创建一个，从节点当前只有控制通道） |

> WiFi 连接 / 断线重连由 esp_event 默认事件循环处理，**没有独立的 `WiFi_Manager_Task`**；`OTA_Task` 也不存在——`ota_manager` 目前是空壳，OTA 尚未实现。

**核分配理由**：
- `udp_audio_rx`：从单播 socket 收包，依赖 lwIP 栈侧数据；只解包入队，出声对齐不在这里。当前用 `xTaskCreate()` 创建，未绑定核。
- `udp_audio_play`：写 I2S 是实时音频输出，按上表设计目标应放 Core 1 以减小抖动；当前同样用 `xTaskCreate()`，未绑定核。
- `ctl_rx`：读控制组播 FIFO 并周期发公告，负载很轻；同样未绑定核。
- `wifi_mcast_rx_Task`（Core 0）：组播收包依赖 lwIP 栈，用 `xTaskCreatePinnedToCore()` 固定在 Core 0，优先级 6，与主节点一致。
- **不建独立任务说明**：`StatusLed`（GPIO 状态指示）**不建独立任务**——`StatusLed_Init()` 在 `app_main` 里调用一次，`StatusLed_On()/Off()` 原定由 `MusicPlay` 按播放状态调用，但 `MusicPlay` 尚未实现，当前两个接口没有任何调用者。

> 实现约定：`wifi_manager` 的组播收包任务用 `xTaskCreatePinnedToCore()` 绑定 Core 0；`udp_audio`、`ctl_rx` 的任务当前用 `xTaskCreate()` 创建（未绑定核）；模块内部任务由各模块 `create/start` 接口自建。

> 任务间通信：事件组通知同步状态切换，消息队列 / 环形缓冲区（FIFO / Jitter Buffer）传输 PCM 数据块。
