# 主节点 LCD「已连接从机」显示设计

> 日期：2026-10-23 ｜ 涉及工程：Play_Master（UI + 发现表）、Play_Slave（ANNOUNCE）
>
> 需求：主节点发现从节点后，在 LCD 设置页里显示已连接从机。
>
> 本文先总结量产多房间/多音箱产品的通行做法，再给出本项目的落地规格。
> 代码已经按本文实现，协议与参数以源码为准。

---

## 1. 先看量产产品怎么做

### 1.1 Sonos

- **System / Rooms 列表是设备管理的主入口**，不是藏在"网络设置"里。列表按房间展示，房间下可以再分组（group），组内可单独调每台音箱的音量。
- 每个房间的 **Room Settings** 里有：名称、网络连接方式（Wi-Fi/有线、是否禁用 Wi-Fi）、麦克风开关、立体声配对、低音/环绕、EQ、音量上限。
- **Identify（识别）**：在设置里点音箱图标，音箱闪 LED，帮助用户确认"我点的是哪一台"。
- 当前 App 用 **System 页**承载"所有房间 + 当前状态"；离线设备通常表现为不可用/灰显或从列表中消失，而不是弹一个错误框。

对本项目的启示：**列表要按设备逐条展示，名称是最重要的身份；网络细节放在次级信息里**。

### 1.2 WiiM Home

- **Devices 页**列出局域网内所有 WiiM 设备，顶部是当前播放设备；每个设备卡片右上角有 **分组（link）图标**，勾选其他设备即可组多房间。
- 分组在列表里显示为 **"主设备名 + N"**（如 `WiiM Sound-824E+2`），组内可调总音量或单台音量。
- **Add Device** 支持手动输入 IP，作为自动发现失败时的兜底。
- 每台设备有独立的 **Settings（齿轮）**：网络、待机、设备名等。

对本项目的启示：**自动发现 + 手动兜底要并存；分组/多设备状态用一行摘要表达**。

### 1.3 Denon HEOS

- **Rooms 标签页**自动出现已连网的 HEOS 产品；新设备通过 **Settings → Add Device / My Devices** 加入。
- **My Devices → 某台设备**里可以：改名、查看无线信号质量、在"有线/Wi-Fi"之间切换、进入高级网络设置。
- 换路由器/租约变化后会出现 **stale / duplicate / unavailable** 条目，官方排障步骤包括给音箱断电 30 秒、重启路由器、强制关闭 App；确认不要的设备可以删除。

对本项目的启示：**离线设备要保留并标记，不要立刻删掉；设备名和"最近一次在线"是排障关键**。

### 1.4 Yamaha MusicCast

- 屏幕左上角的房间名点开后是 **全部 MusicCast 设备列表**，可以切房间、控制设备、添加新设备。
- 多房间用 **Link（链条）图标**把房间串起来；每个房间可以有自己的输入源。
- 官方 FAQ 没有文档化"在线/离线"小圆点，发现失败时更多是"设备不出现"或连接失败。

对本项目的启示：**小屏设备上，"当前设备 + 设备列表"可以合并成一个可滚动页**，不必为列表再开一级页面。

### 1.5 Google Home / Apple 家庭类 App

- Google Home 的设备卡片在离线时**灰显**；点卡片进设置可以重启设备、重新配网。2025-2026 年的一次后端故障就是"设备明明能用却全部灰显"，说明 **灰显是用户理解离线的主要视觉语言**。
- 这类 App 的共同点是：**在线状态是持续轮询/推送出来的，不是用户点"刷新"才更新**；离线不会把设备从家里删除，只会改变状态。

### 1.6 共性提炼

| 做法 | 量产产品中的表现 | 本项目是否采用 |
| --- | --- | --- |
| 设备/房间列表是独立的一等信息 | Sonos System、WiiM Devices、HEOS Rooms | 采用：设置页里的独立分区 |
| 每行 = 名称 + 状态 + 次级信息 | 名称/房间 + 在线/播放 + IP/信号/音量 | 采用：名称 + IP + RSSI |
| 在线状态点 + 离线灰显 | Google Home、HEOS | 采用：绿点/灰点 + 灰字 |
| 离线设备保留一段时间 | HEOS 的 unavailable 条目 | 采用：保留到重启，表满时顶掉最久离线项 |
| 在线优先排序 | Sonos/WiiM 列表把可用设备放前面 | 采用：在线在前、离线在后 |
| 自动发现 + 手动 IP 兜底 | WiiM Add Device by IP | 采用：ANNOUNCE 自动发现；静态 IP 表兜底 |
| 设备名默认由硬件生成、可改 | Sonos/HEOS 改名 | 部分：默认 `从机-XXXX`，改名留到后续 |
| 识别设备（闪灯/响一声） | Sonos Identify | 未做：从节点 `StatusLed` 还没联动 |
| 分组/立体声配对 | Sonos/WiiM/MusicCast | 未做：当前是"主机 + N 从机"的单一组 |
| 状态持续刷新，不需手动刷新 | 全部 | 采用：UI 1s 轮询 |

## 2. 本项目的信息模型

### 2.1 三种"连接"不要混

| 概念 | 含义 | 数据来源 |
| --- | --- | --- |
| **已发现（known）** | 收到过该 MAC 的公告 | 主节点发现表 |
| **在线（online）** | 最近 10s 内收到过公告 | 发现表 + 超时扫描 |
| **正在同步播放（playing）** | 主节点当前处于 `SYNC_STATE_PLAYING` | `sync_protocol_master_get_status()` |

UI 上分别表达为：

- 没有任何条目 → `正在扫描从机...`（若还配着静态目标，追加「已配置 N 个」）
- 有条目但都不在线 → `已发现 N 个 · 暂时无连接`
- 有在线条目 → `已连接 N/M · 同步播放中`（`M` 是发现表里的总数）
- 每行状态点：绿色 = 在线，灰色 = 离线；离线行附带 `失联 Ns`

### 2.2 设备身份

- **MAC 是唯一身份**，IP 只是当前地址。DHCP 换 IP 后，同一 MAC 的公告会覆盖旧 IP，主节点自动把单播目标切到新地址。
- **设备名**默认 `从机-XXXX`（MAC 末两字节），放在 16 字节定长字段里。后续要做改名，只需在 `node_role_cfg_t` 加字段并让公告带上。
- **配对令牌** `SYNC_ANNOUNCE_TOKEN = 0x53594E43`（"SYNC"）是编译期常量，防止同局域网里别人家的同款从节点被自动拉进播放组。它不是加密，只做"同一套设备"的粗筛。

### 2.3 生命周期

```text
从节点上电 → 连上 WiFi → ctl_rx 任务启动
    │
    ├─ 每 3s 向 239.0.0.1:5679 发 ANNOUNCE
    │
主节点 SyncTx_Task 每轮循环读控制通道
    ├─ 收到合法公告 → 按 MAC upsert → 标记 online → 重建单播目标
    ├─ 每 1s 扫描：超过 10s 没公告 → 标记 offline → 重建单播目标
    └─ 离线条目保留在表里（灰显），表满时被新设备顶掉
```

**单播目标切换规则**：

- 收到第一份合法公告之前：沿用编译期/运行时配置的静态 IP 表（兼容旧固件，也方便没上电从机时本机先播）。
- 收到公告之后：发现表成为唯一权威，只给 **online** 的从机单播；全部离线就只本机播放，下一份公告到达后自动恢复。
- 这样既解决了 DHCP 换 IP，也不会对已经拔电的从机持续发无效单播。

## 3. LCD 界面规格

### 3.1 屏幕与分页布局

- LCD 320×240，状态栏 24px、Tab 栏 40px、内容区 176px。
- 设置页已从纵向滚动改为 **固定 4 页翻页**（右上角 `← 2/4 →`，点击区域外扩 6px）：
  第 1 页 播放源+网络、第 2 页 同步播放、第 3 页 固件（原“语音助手”分区随语音唤醒下线删除）、第 4 页 关于。
- 「同步播放」独占第 2 页：顶部一行摘要 + 最多 8 行设备。行距取 `ui_font_cn_16`
  的 `line_height = 19`，23 + 8×19 = 175，正好占满 176px 内容区，因此这一页不放分区标题。

### 3.2 线框

```text
┌──────────────────────────────────────────┐  ← 设置页第 2 页（共 4 页）
│ 已连接 1/2 · 同步播放中      ← 2/4 →     │  摘要（1s 刷新）
│ ● 从机-A1B2  192.168.31.45  -52 dBm      │  在线：绿点 + 主文字色
│ ○ 从机-C3D4  192.168.31.77  失联 12s     │  离线：灰点 + 灰字
│                                          │
│   （最多 8 行，未使用的行隐藏）            │
└──────────────────────────────────────────┘
```

### 3.3 文案与颜色

| 场景 | 摘要 | 颜色 |
| --- | --- | --- |
| 同步模块未初始化 | `同步服务未启动` | `UI_COLOR_DISABLED` |
| 没收到过公告、无静态目标 | `正在扫描从机...` | `UI_COLOR_TEXT_SUB` |
| 没收到过公告、有静态目标 | `正在扫描从机...（已配置 N 个）` | `UI_COLOR_TEXT_SUB` |
| 有条目但全离线 | `已发现 N 个 · 暂时无连接` | `UI_COLOR_TEXT_SUB` |
| 至少一台在线 | `已连接 N/M · {状态}` | `UI_COLOR_OK` |

`{状态}` 直接复用同步状态机的文案：`待机 / 准备中 / 同步播放中 / 已暂停 / 已停止 / 错误`。

行文本：

- 在线：`{name}  {ip}  {rssi} dBm`
- 离线：`{name}  {ip}  失联 {seconds}s`（秒数封顶 999，避免撑破行宽）

> **文案受字库限制**：中文用 `ui_font_cn_16`，由 `--symbols` 白名单生成，字库外的字会渲染成空白。
> 最初的「搜索 / 台 / 离线」里 **搜、索、台、离** 都不在字库，所以最终改用
> 「扫描」「个」「失联」。改文案前先查 `ui_font_cn_16.c` 头部 Opts 里的 `--symbols` 列表，
> 或重新生成字体时把新字加进去。

### 3.4 为什么固定 8 行、不做动态增删

设置页里的控件全部是**绝对定位**的，翻页要求每一页的高度和位置在构建时就固定下来：

- 启动时一次性创建 4 个页面容器，每页的控件也一次性建好；
- 从机列表固定 8 行（`SYNC_MAX_SLAVES`）的状态点 + 文本；
- 每秒只改文本、颜色和 `hidden` 标志，翻页只改页面容器的 `hidden`；
- 好处：无堆碎片、无布局抖动、翻页零延迟；代价：从机少于 8 台时第 2 页底部留白。

> 如果以后从机上限改成 16 台，一行 19px 就放不下了：建议把从机列表拆成独立子页并让它自己翻页，或换更小的行内字体。

### 3.5 刷新策略

- 复用现有 `settings_timer_cb`，周期 1s，运行在 UI_Task / LVGL 上下文。
- 每次调用：
  1. `sync_protocol_master_get_status()` 取全局状态；
  2. `sync_protocol_master_get_slaves()` 取发现表快照；
  3. 在线优先排序后刷新 8 行。
- 1s 与公告周期 3s、离线超时 10s 匹配：最坏情况离线状态最多晚 1s 上屏。

## 4. 发现协议（ANNOUNCE）

复用现有控制组播 `239.0.0.1:5679`，不新增 socket、不改音频数据面。

### 4.1 帧格式

```text
Magic(0xAA55,2) | Type(0x30,1) | Len(36,1) | Payload(36)
```

载荷 `sync_announce_payload_t`（主从逐字节一致，packed）：

| 偏移 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0 | `ver` | u8 | 当前 1，版本不符丢弃 |
| 1 | `mac[6]` | u8[6] | STA MAC，设备身份 |
| 7 | `ip[4]` | u8[4] | 当前 IPv4（网络字节序） |
| 11 | `audio_port` | u16 | 音频接收端口，当前 5680 |
| 13 | `volume` | u8 | 当前音量 0~100 |
| 14 | `rssi` | i8 | 从节点侧 RSSI（dBm） |
| 15 | `flags` | u8 | 保留，当前 0 |
| 16 | `token` | u32 | `0x53594E43` 配对令牌 |
| 20 | `name[16]` | char[16] | UTF-8 设备名，不足补 0 |

固定 40 字节整包，远小于主节点 256 字节控制接收缓冲。

### 4.2 为什么把 IP 放在载荷里

主节点现有的 `wifi_manager_mcast_recv()` 为了兼容旧调用，**没有返回 `recvfrom` 的源地址**。与其改公共 API（影响灯控等其他通道），不如让从节点自己把 IP 带上——从节点本来就能通过 `wifi_manager_get_ip()` 拿到当前地址。代价是 4 字节载荷，收益是零侵入。

### 4.3 时序参数

| 参数 | 值 | 位置 |
| --- | --- | --- |
| 公告周期 | 3s | `ctl_rx.c: CTL_ANNOUNCE_MS` |
| 接收轮询超时 | 1s | `ctl_rx.c: CTL_POLL_MS` |
| 离线判定 | 10s（连续丢 3 包） | `sync_protocol.h: SYNC_SLAVE_OFFLINE_TIMEOUT_MS` |
| 表容量 | 8 | `SYNC_MAX_SLAVES` |
| UI 刷新 | 1s | `scr_settings.c: settings_timer_cb` |

## 5. 代码落点

### 5.1 从节点（Play_Slave）

| 文件 | 改动 |
| --- | --- |
| `components/middlewares/ctl_rx/ctl_rx.c` | 新增 `ctl_send_announce()`；任务循环每 3s 发一次；保存 `wifi_manager` 句柄用于查 IP/RSSI |

公告走 `ctl_rx` 已有的控制通道句柄（`rx_enable=true` 的 5679 socket）。从节点会收到自己的回环公告，但 `ctl_rx` 只认 4 字节音量帧，直接忽略。

### 5.2 主节点（Play_Master）

| 文件 | 改动 |
| --- | --- |
| `components/middlewares/sync_protocol/sync_protocol.h` | 新增 `SYNC_MSG_ANNOUNCE`、`sync_announce_payload_t`、`sync_slave_info_t`、`sync_protocol_master_get_slaves()`；状态快照加 `slave_targets` / `slaves_online` |
| `components/middlewares/sync_protocol/sync_protocol.c` | 发现表 `slaves[8]`；`sync_announce_handle()` 按 MAC upsert；`sync_slaves_sweep()` 1s 扫描离线；`sync_rebuild_targets_locked()` 用在线表重建单播目标；`sync_protocol_master_get_slaves()` 提供 UI 快照 |
| `components/App/UI/scr_settings.c` | 设置页改为 4 页固定布局（右上角箭头翻页）；第 2 页为摘要 + 8 行设备列表；1s 定时器刷新 |

### 5.3 兼容性

- 音频数据面（单播 5680、20 字节头）**一行未改**。
- 旧从节点固件不发公告：主节点保持静态 IP 表，行为与之前一致。
- 新从节点 + 旧主节点：主节点把 0x30 扩展帧当未知类型忽略，不影响音量。
- **令牌必须主从一致**；只改一边会导致发现静默失败（没有报错），这是最容易踩的坑。

## 6. 验证

### 6.1 串口

从节点：`ctl_rx` 当前只在发送失败时打 D 级日志（`CTL_RX: announce send failed`），成功后不打印；要确认公告是否发出，看主节点侧日志或抓包。

主节点：

```text
SYNC: slave online: 从机-A1B2 ip=192.168.31.45 rssi=-52 vol=15 (targets=1)
SYNC: slave lost: 从机-A1B2 (192.168.31.45)
```

### 6.2 LCD

1. 上电 → 设置页翻到第 2 页（右上角显示 `2/4`），摘要显示 `正在扫描从机...`（若配了静态 IP，括号里显示 `已配置 N 个`）；
2. 从节点连上 WiFi 后 3s 内出现绿点行，摘要变 `已连接 1/1 · 待机`；
3. 主节点开始播放 → 摘要变 `已连接 1/1 · 同步播放中`；
4. 从节点断电 → 10~11s 后绿点变灰点，行尾显示 `失联 Ns`；
5. 从节点重新上电（可以换一个 DHCP 地址）→ 行的 IP 自动更新，点变绿，音频恢复；
6. 两台从节点 → 两行，在线在前；摘要 `已连接 2/2`。

### 6.3 边界

- 表满 8 台后再来新设备：若存在离线条目，顶掉最久没消息的那条；全部在线则忽略并打 WARN。
- 令牌不匹配：主节点完全静默忽略，LCD 一直显示"正在扫描从机..."。
- AP 开启客户端隔离：公告和音量组播都收不到（同一根因），需要关隔离或改用主节点 SoftAP 方案。

## 7. 已知限制与后续

1. **列表是只读的**。量产 App 里的改名、识别（闪灯）、删除、分组都没有做；当前固件没有触摸行交互，先保证"看得见、状态准"。
2. **从节点不报播放状态**。每行的"播放中"是主节点的全局状态，不是每台从机独立上报；多从机时无法区分"某台没出声"。
3. **不持久化设备名/白名单**。发现表在 RAM，重启后靠公告重建；配对令牌是编译期常量。
4. **公告依赖组播转发**。部分路由器默认开启客户端隔离或严格 IGMP snooping，会让公告和音量一起失效。后续可加广播兜底，或采用"主节点 SoftAP + 从节点接入"的零配置形态。
5. **识别功能**：等 `StatusLed` 与播放状态联动后，可在行上做"点一下闪灯"，对齐 Sonos 的 Identify。
