## UDP组播的json完整格式：

```json
{
  "cmd": "on",
  "light": "bedroom",
  "version": 1
}
```

1. cmd为开关命令，继电器只能做到开关灯，所以cmd命令只有：`on` `off`   两个命令
2. light为哪里的灯，目前测试只有一个  `bedroom`
3. 而且调不了亮度，所以没有brightness
4. version 为灯控 JSON 协议版本（整数，当前为 1）。主控下发的所有报文都携带；
   灯控节点（ESP8266）上行 ack/status 也应回带同一字段



## 状态上报（30s 周期）

灯控节点每 **30 秒**向音频主控发送一次当前开关状态，供主控 UI 刷新/显示状态图标，并用于掉线或异常后状态对账：

```json
{
  "cmd": "status",
  "light": "bedroom",
  "ok": true,
  "version": 1
}
```

- `cmd`：固定 `status`
- `light`：房间名，与开关命令一致（如 `bedroom`）
- `ok`：当前实际开关状态，`true` = 开，`false` = 关
- `version`：协议版本，与开关命令一致（当前 1）

发送方为灯控节点，走与开关命令同一条 UDP 组播链路；周期固定 30 秒，不受开关命令影响。执行开关命令后的即时回复仍用原来的 `ack`，两者并存。

### 版本协商（OTA 只升了一台时的行为）

两端在**解析/执行任何指令之前**先校验 `version`：

| 收到报文的 version | 处理方式 |
| :--- | :--- |
| == 本端支持版本（1） | 正常执行/上报 |
| < 本端支持版本 | 兼容处理（旧版本字段语义未变） |
| 缺省（对端旧固件） | 按 v1 兼容处理 |
| > 本端支持版本 | **明确判定不兼容**：丢弃报文、不执行任何指令，并回一条下方格式的报文 |

不兼容回告（收到不认识的新版本时，任一端都应回发）：

```json
{
  "cmd": "verr",
  "light": "-",
  "version": 1
}
```

主控收到 `verr`（或解析到高于本端的 version）后，在灯控页显示“版本不兼容”，
提示用户对齐两端固件，而不是把语义跑偏的指令照常执行。
