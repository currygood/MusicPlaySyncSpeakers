> 说明：音频主节点具备完整功能；出于成本考虑，从节点使用现有的 ESP32-S3 开发板（如 ESP32-S3-N16R8），放弃“无主节点时切换为蓝牙模式、让手机连接播放音频”的功能。从节点不再需要 esp-sr 的 ASR 语音唤醒与 5 分钟超时切换逻辑，仅工作于同步模式：主节点启动并发送组播音频后，从节点直接接收并同步播放。
>
> 手机热点大概率不能作为“路由器”来进行测试UDP组播

# ESP32 双设备无线音频同步与智能家居联动系统 系统设计说明书

> 本文档整理自《项目文档.md》，仅保留与**系统设计**直接相关的内容（系统概述与架构、硬件平台、软件架构、分区与OTA、任务设计、同步协议、同步算法、网络联动、功能设计、关键配置、性能指标）。测试方案、硬件模块详解与引脚接线表、简历描述等不属于系统设计范畴的内容已移除，相关专题由对应文档（测试计划、硬件设计说明、引脚分配表等）承接。

> **项目定位**：基于 ESP32 的双设备无线音频同步系统，支持蓝牙音乐接收、本地 SD 卡解码播放，以及 **WiFi 组播音频同步分发**，实现两台音箱无感知同步播放，为低成本全屋智能音频系统提供可扩展的解决方案。

------

## 📖 项目概述

1. 本项目设计并实现了一套集**双设备无线音频同步**与**全屋智能家居联动**于一体的综合系统。系统包含三个核心节点：

   - **音频主节点（Master）**：ESP32-WROVER-E-N8R8，负责蓝牙 A2DP 音频接收、SD 卡本地解码、UDP 组播分发，以及通过 UI 界面发起灯控指令。
   - **音频从节点（Slave）**：ESP32-S3 开发板（如 ESP32-S3-N16R8），接收 UDP 组播音频数据，通过时间戳同步与动态速率校正算法实现无感知同步播放（纯组播同步收听，不参与蓝牙播放）。
   - **灯控节点（Light Controller）**：**ESP8266**，同时支持**局域网 UDP 组播接收**（来自音频主节点 UI 屏幕控制）和**巴法云 MQTT 接入**（来自米家 App / 小爱同学语音控制），驱动**白色可调亮度 LED 灯**实现全屋灯光控制。

   ### 核心创新

   1. **高精度音频同步**：主节点将 PCM 数据通过 UDP 组播分发至从节点，结合路由器 **IGMP Snooping（组播侦听）** 机制实现音频数据的精准投递，避免局域网泛洪。从节点通过时间戳同步与动态速率校正，实现误差 < ±15ms 的无感知同步。
   2. 双通道灯控闭环：
      - **本地 UI 控制链路**：ESP32 主节点 UI 界面 → UDP 组播（`239.0.0.2:8889`）→ ESP8266 灯控节点（局域网低延迟，不依赖公网）
      - **云端语音控制链路**：ESP32 主节点通过 HFP 唤醒手机语音助手 → 米家云 → 巴法云 MQTT → ESP8266 灯控节点（接入米家生态，支持小爱同学语音控制）
   3. **WiFi 多路复用**：ESP32-WROVER-E-N8R8 的 WiFi 协议栈（lwIP）同时承载高实时性的 UDP 音频组播（`239.0.0.1:5678`）、UDP 灯控组播（`239.0.0.2:8889`），与 ESP8266 灯控节点深度联动。

### 音频总线（audio_bus）职责说明

系统物理上只有一个功放、一个麦克风，但多个上层音源/消费方（蓝牙 A2DP、本地 SD 播放、组播同步播放、语音通话等）都要使用它们，为避免“输出乱序、互相抢占”：

| 方向         | 行为       | 说明                                             |
| ------------ | ---------- | ------------------------------------------------ |
| TX（功放）   | 多写者互斥 | 同一时刻只允许一路音源占用总线，按块原子写入     |
| RX（麦克风） | 多读者广播 | 每个读者独立 FIFO，互不阻塞，均可获取完整数据    |

- `bsp/i2s_driver` 只提供“物理通道”（参数化 TX/RX 句柄，不再写死引脚/采样率）；
- `audio_bus`（middlewares）负责**单机内多路音源争用同一硬件**的同步仲裁；
- `amplifier` / `microphone` 作为外设注册进总线（TX 写者 / RX 读者），上层 App 通过模块 API 或总线句柄访问；
- 主节点同时启用 TX + RX；从节点仅有 TX（功放）。

> 说明：`audio_bus` 解决“单机内多音源争用硬件”的同步；`sync_protocol` 解决“主从两机时间对齐”的同步，两者职责不同。

## 💾 音频主节点-分区表（双备份 OTA，主节点 8MB Flash）

> **注**：分区表按主节点 8MB Flash 设计；从节点为 ESP32-S3-N16R8（16MB Flash），固件不含蓝牙 / LVGL / SD 卡组件，可采用相同双备份 OTA 布局并放大 ota_0/ota_1 分区（如各 6MB）。

由于 UI 资源全部迁移至 SD 卡，Flash 分区专为 OTA 升级设计，无需 SPIFFS 分区。8MB Flash 总容量为 **8,388,608 字节**。

```csv
# Name,      Type, SubType,   Offset,    Size,      Flags
nvs,         data, nvs,       0x9000,    24K,
phy_init,    data, phy,       0xf000,    4K,
otadata,     data, ota,       0x10000,   8K,
ota_0,       app,  ota_0,     0x20000,   0x280000,  # 2.5MB
ota_1,       app,  ota_1,     0x2A0000,  0x280000,  # 2.5MB
storage,     data, spiffs,    0x520000,  0x2C0000,  # 2.75MB（预留）
```

### 空间占用分析

| 分区                  | 起始地址     | 结束地址     | 大小       | 说明                                    |
| :-------------------- | :----------- | :----------- | :--------- | :-------------------------------------- |
| Bootloader + 表头     | 0x0000       | 0x9000       | 36KB       | 系统保留                                |
| NVS                   | 0x9000       | 0xF000       | 24KB       | 存储蓝牙配对信息、WiFi 配置、节点角色等 |
| PHY Init              | 0xF000       | 0x10000      | 4KB        | 射频校准数据                            |
| **otadata**           | **0x10000**  | **0x12000**  | **8KB**    | **OTA 启动选择标志**                    |
| **ota_0（固件区 A）** | **0x20000**  | **0x2A0000** | **2.5MB**  | 当前运行固件 / 升级目标区 1             |
| **ota_1（固件区 B）** | **0x2A0000** | **0x520000** | **2.5MB**  | 当前运行固件 / 升级目标区 2             |
| **storage（预留）**   | **0x520000** | **0x7E0000** | **2.75MB** | 预留用于设备证书、调试日志或未来扩展    |
| 未分配                | 0x7E0000     | 0x800000     | ~128KB     | Flash 末端保留                          |

## 🌐 双设备同步协议设计

### 音频数据包格式（自定义轻量级 RTP）

采用 UDP 组播（IP 组播地址 `239.0.0.1`，端口 `5678`），每个音频包携带约 **15ms** 的 PCM 数据：

```reStructuredText
+----------------+----------------+----------------+----------------+
|  Magic (0xAA55) |  Seq (16bit)   |  Timestamp (32bit) |  Data Len (16) |
+----------------+----------------+----------------+----------------+
|  Audio Data (PCM, 16bit, 44.1kHz, 单声道)  最大 1323 字节   |
+-----------------------------------------------------------------+
```

| 字段       | 大小   | 说明                                                 |
| :--------- | :----- | :--------------------------------------------------- |
| Magic      | 2 字节 | 包起始标志 `0xAA55`，用于同步和过滤干扰              |
| Seq        | 2 字节 | 序列号，递增（0~65535 循环），从节点用于检测丢包     |
| Timestamp  | 4 字节 | 主节点发送时的微秒级时间戳（`esp_timer_get_time()`） |
| Data Len   | 2 字节 | 实际 PCM 数据长度（字节），最大 1323 字节            |
| Audio Data | 变长   | PCM 数据（16bit, 44.1kHz, 单声道），约 15ms 时长     |

> **包大小计算**：15ms × 44.1kHz × 2 字节 = 1323 字节，加上 10 字节头部，共约 1333 字节，UDP 包远小于 MTU 1500 字节，避免 IP 分片。

### 控制命令包（端口 5679）

控制命令使用独立端口（5679），同样通过组播发送，格式如下：

```reStructuredText
+----------------+----------------+----------------+
|  Magic (0xAA55) |  Cmd (8bit)    |  Param (8bit)  |
+----------------+----------------+----------------+
```

| 命令码 | 含义       | Param                   |
| :----- | :--------- | :---------------------- |
| 0x01   | PLAY       | 0                       |
| 0x02   | PAUSE      | 0                       |
| 0x03   | NEXT       | 0                       |
| 0x04   | PREV       | 0                       |
| 0x05   | VOLUME     | 0~100                   |
| 0x06   | SYNC_RESET | 0（强制从节点重新同步） |

## 🕒 同步机制详解（核心算法）

### 第一阶段：启动同步（初始对齐）

从节点加入组播组后，**不立即播放**，而是先完成初始对齐：

1. 从节点开始接收数据，存入环形缓冲区（Jitter Buffer）。
2. 收到**第一个音频包**时，记录本地接收时间 `t_local_recv`，取出主节点时间戳 `t_master_send`。
3. 通过发送 10 个探测包计算平均网络延迟 `net_delay`（或固定假设为 20ms）。
4. 设定**目标播放时间**：`t_play_target = t_master_send + net_delay + 200ms`（200ms 缓冲用于抗网络抖动）。
5. 从节点持续接收数据，直到 Jitter Buffer 中缓存达到 **200ms** 的音频数据。
6. 在 `t_play_target` 时刻**精确启动 I2S DMA**，开始播放。

**关键代码示意**：

```c
// 从节点收到第一个包时
uint64_t t_master_send = pkg->timestamp;
uint64_t t_local_recv = esp_timer_get_time();
uint64_t estimated_net_delay = 20000; // 20ms
uint64_t play_target_time = t_master_send + estimated_net_delay + 200000; // +200ms

// 配置 I2S 并在精确时刻启动 DMA
esp_timer_create_args_t timer_args = {
    .callback = i2s_start_callback,
    .name = "sync_start"
};
esp_timer_handle_t timer;
esp_timer_create(&timer_args, &timer);
esp_timer_start_once(timer, play_target_time - esp_timer_get_time());
```

### 第二阶段：持续同步校正（防时钟漂移）

两个设备使用不同晶振，长期播放会产生时钟漂移（如 50ppm 误差，1 分钟漂移 3ms，10 分钟漂移 30ms）。

**校正策略**：

1. **主节点**每隔 **1 秒**发送一个 `SYNC_HEARTBEAT` 包（通过控制通道），包含当前播放位置时间戳。
2. **从节点**收到心跳后，比较自己的播放进度与主节点的预期进度：
   - 若从节点**落后 > 10ms**，轻微**加快**播放速率（提高 I2S 采样率）。
   - 若从节点**领先 > 10ms**，轻微**减慢**播放速率（降低 I2S 采样率）。
3. 每次调整步长 < 1ms，避免产生可听噪声。

```c
// 加快播放：采样率从 44100 提高到 44150
i2s_set_clk(I2S_NUM_0, 44150, I2S_BITS_PER_SAMPLE_16BIT, I2S_CHANNEL_MONO);

// 减慢播放：采样率从 44100 降低到 44050
i2s_set_clk(I2S_NUM_0, 44050, I2S_BITS_PER_SAMPLE_16BIT, I2S_CHANNEL_MONO);
```

### 第三阶段：异常处理

| 异常场景               | 处理策略                                                |
| :--------------------- | :------------------------------------------------------ |
| **丢包**（Seq 不连续） | 静音填充（写入 0 值），避免 I2S 欠载产生爆音            |
| **网络中断 > 500ms**   | 自动进入静音模式，UI 显示“同步断开”，尝试重新加入组播组 |
| **主节点重启/切换**    | 检测到 SSRC 变化，自动重新执行同步流程                  |

| 项目                      | 配置                                                         |
| ------------------------- | ------------------------------------------------------------ |
| WiFi 模式                 | 所有节点（音频主/从、ESP8266）均连接 **同一路由器**（Station 模式） |

### ESP32 与 ESP8266 通信协议（UDP 组播）

**数据格式（JSON）**：

```json
{
  "cmd": "on",
  "light": "bedroom",
}
```

| 字段  | 说明                             |
| ----- | -------------------------------- |
| cmd   | 指令：`on` / `off`               |
| light | 目标灯：`bedroom` / `livingroom` |

**ESP32 端代码示意（UI 点击灯控按钮）**：

```c
// ESP32 主节点：UI 界面点击开灯按钮后，通过 UDP 组播发送指令
void ui_bedroom_light_on_click(void) {
    const char* cmd_json = "{\"cmd\":\"on\",\"light\":\"bedroom\"}";
    
    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    struct sockaddr_in multicast_addr = {
        .sin_family = AF_INET,
        .sin_port = htons(8889),
        .sin_addr.s_addr = inet_addr("239.0.0.2")  // 灯控组播地址
    };
    
    sendto(sock, cmd_json, strlen(cmd_json), 0, 
           (struct sockaddr*)&multicast_addr, sizeof(multicast_addr));
    close(sock);
}
```

**ESP8266 端代码示意（UDP 组播接收）**：

```c
// ESP8266 灯控节点：加入灯控组播组并接收指令
void udp_multicast_receiver_task(void *pvParameters) {
    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    struct sockaddr_in server_addr = {
        .sin_family = AF_INET,
        .sin_port = htons(8889),
        .sin_addr.s_addr = INADDR_ANY
    };
    bind(sock, (struct sockaddr*)&server_addr, sizeof(server_addr));
    
    // 加入灯控组播组（触发 IGMP Join）
    struct ip_mreq imreq;
    imreq.imr_multiaddr.s_addr = inet_addr("239.0.0.2");
    imreq.imr_interface.s_addr = IPADDR_ANY;
    setsockopt(sock, IPPROTO_IP, IP_ADD_MEMBERSHIP, &imreq, sizeof(struct ip_mreq));
    
    char buf[256];
    while(1) {
        int len = recv(sock, buf, sizeof(buf), 0);
        if (len > 0) {
            buf[len] = '\0';
            // 解析 JSON 并控制 LED
            parse_and_control_led(buf);
        }
    }
}
```

## 🔄 OTA 升级流程

### 音频节点（ESP32）

采用双备份 OTA 分区（ota_0 / ota_1），支持远程升级与异常回滚。

### 灯控节点（ESP8266）

ESP8266 采用单分区 OTA（4MB Flash），通过 HTTP 下载新固件并写入备用区域，重启后自动切换。

## ✨ 功能详细说明

### 1. 蓝牙音频接收（仅主节点）

- 主节点作为 A2DP Sink 连接手机，接收 SBC 音频流。
- 将 PCM 数据同时送入本机播放队列和组播发送队列。

### 2. 双设备同步播放（核心创新）

- **组播分发**：主节点使用 UDP 组播将音频数据发往 `239.0.0.1:5678`。
- **从节点接收**：从节点加入该组播组，接收数据并执行同步播放。
- **同步误差**：实测 < ±15ms（稳定 WiFi 环境下），人耳无感知。
- **容错处理**：从节点若超过 500ms 未收到组播包，自动静音并尝试重连。

### 3. 本地音乐播放（SD 卡）

- 仅主节点可播放 SD 卡 `/music` 目录下的 MP3/WAV 文件（从节点无 SD 卡）。
- 从节点仅作为同步播放终端，不提供独立的本地 / 蓝牙播放源。

### 4. LVGL 图形界面（资源从 SD 卡加载）

- 主节点 UI 显示当前播放源（蓝牙/组播/本地）、歌曲信息、进度条、控制按钮。
- 从节点无触摸屏 / UI，仅通过状态提示；主节点 UI 显示同步状态（已同步/同步中/断开）及当前延迟。
- 主/从固件因芯片不同分开编译，角色由刷写固件决定。

### 5. HFP 语音助手（仅主节点）

- 通过 INMP441 麦克风采集语音，经 HFP 协议传输至手机，唤醒小爱/Siri。

### 6. AVRCP 控制（双向同步）

- 手机端控制（播放/暂停/切歌）通过 AVRCP 同步至主节点，主节点通过组播控制命令同步至从节点。

### 7. UI 屏幕灯控（UDP 组播，本地低延迟）

音频主节点通过 LVGL UI 界面提供灯光控制入口，与 ESP8266 智能灯控节点深度联动：

- **通信机制**：`SmartHome_Task` 在局域网内通过 **UDP 组播（239.0.0.2:8889）** 向 ESP8266 发送 JSON 格式的控制指令。
- **执行端**：ESP8266 的 `UDP_Multicast_Rx_Task` 加入灯控组播组，接收指令后调用 `LED_Control_Set_Light()` 驱动  LED 模块，通过软件 PWM 实现卧室灯/客厅灯的调亮度。
- 优势：
  - **局域网低延迟**：UI 点击到灯光响应 < 50ms
  - **不依赖公网**：即使家里断网，UI 仍可控制灯光
  - **多节点扩展**：未来增加 ESP8266 灯控节点，只需加入同一组播组即可
- **并发保障**：灯控组播（`239.0.0.2:8889`）与音频组播（`239.0.0.1:5678`）使用不同的组播地址和端口，在 lwIP 协议栈中通过不同的 Socket 独立运行，互不阻塞。

### 8. 语音助手灯控（HFP + 巴法云 MQTT，云端生态）

音频主节点通过 HFP 协议唤醒手机语音助手，实现云端语音控制灯光：

- 控制链路：
  1. 用户长按 ESP32 主节点的物理按键，触发 HFP 通话
  2. 通过 INMP441 麦克风采集语音，经 HFP 传输至手机
  3. 手机语音助手（小爱/Siri）识别语音指令（如"打开卧室灯"）
  4. 语音助手通过米家云 → 巴法云 MQTT → ESP8266 控制灯光
- **执行端**：ESP8266 的 `BemFa_MQTT_Task` 订阅巴法云主题（`bedroom002` / `livingroom002`），接收米家下发的灯控指令并执行。
- 优势：
  - **接入米家生态**：支持米家 App 和小爱同学语音控制
  - **云端远程控制**：即使不在家，也可通过手机 App 控制灯光
  - **状态同步**：ESP8266 每 30 秒向巴法云上报当前灯光状态，米家 App 显示与实际一致

### 9. 双通道灯控的统一执行

ESP8266 灯控节点同时处理来自两个通道的指令：

| 控制来源          | 通信方式                     | 延迟      | 适用场景                     |
| ----------------- | ---------------------------- | --------- | ---------------------------- |
| **ESP32 UI 屏幕** | UDP 组播（`239.0.0.2:8889`） | < 50ms    | 本地快速控制，不依赖公网     |
| **手机语音助手**  | 巴法云 MQTT                  | 200~500ms | 语音控制、远程控制、米家联动 |

**指令融合**：两个通道的指令最终都调用同一个 `LED_Control_Set_Light()` 函数，状态天然一致，互不冲突。无论通过哪种方式控制，灯光状态都会同步更新，并通过巴法云上报至米家 App。
