# ESP32 双设备无线音频同步与智能家居联动系统 系统设计说明书

> 本文档整理自《项目文档.md》，仅保留与**系统设计**直接相关的内容（系统概述与架构、硬件平台、软件架构、分区与OTA、任务设计、同步协议、同步算法、网络联动、功能设计、关键配置、性能指标）。测试方案、硬件模块详解与引脚接线表、简历描述等不属于系统设计范畴的内容已移除，相关专题由对应文档（测试计划、硬件设计说明、引脚分配表等）承接。

> **项目定位**：基于 ESP32 的双设备无线音频同步系统，支持蓝牙音乐接收、本地 SD 卡解码播放，以及 **WiFi 单播音频同步分发**，实现两台音箱无感知同步播放，为低成本全屋智能音频系统提供可扩展的解决方案。

------

## 📖 项目概述

1. 本项目设计并实现了一套集**双设备无线音频同步**与**全屋智能家居联动**于一体的综合系统。系统包含三个核心节点：

   - **音频主节点（Master）**：ESP32-WROVER-E-N16R8，负责蓝牙 A2DP 音频接收、SD 卡本地解码、UDP 单播分发，以及通过 UI 界面发起灯控指令。
   - **音频从节点（Slave）**：目标硬件同为 ESP32-WROVER-E-N16R8（开发阶段用 ESP32-S3 开发板，如 ESP32-S3-N16R8），接收 UDP 单播音频数据，按包头 `t_play_us` 对齐出声时刻、用丢/插单个样点补偿长期漂移，实现无感知同步播放（纯同步收听，不参与蓝牙播放）。
   - **灯控节点（Light Controller）**：**ESP8266**，同时支持**局域网 UDP 组播接收**（来自音频主节点 UI 屏幕控制）和**巴法云 MQTT 接入**（来自米家 App / 小爱同学语音控制），驱动**单路继电器灯**（只有开/关，不支持调光），并**每 30s 向主节点组播回传一次开关状态**。

   ### 核心创新

   1. **高精度音频同步**：主节点把同一份 PCM 数据通过 UDP **逐台单播**发到从节点（每帧带 `t_play_us` 基准播放时刻），从节点按该时刻对齐出声，长期漂移用丢/插单个样点补偿；主从残差只剩两端最小单程延迟之差（局域网 1~3ms）。
   2. 双通道灯控闭环：
      - **本地 UI 控制链路**：ESP32 主节点 UI 界面 → UDP 组播（`239.0.0.2:8889`）→ ESP8266 灯控节点（局域网低延迟，不依赖公网）；ESP8266 每 30s 经该组播通道回传一次开关状态，主节点侧解析后刷新灯控图标
      - **云端语音控制链路（已下线）**：原设计为 ESP32 主节点通过 HFP 唤醒手机语音助手 → 米家云 → 巴法云 MQTT → ESP8266 灯控节点；HFP 语音链路已整链路移除（`CallPhone` 与 `microphone` 在 `Play_Master/legacy_disabled`），主节点不再建立通话连接，现仅剩 ESP8266 侧的巴法云 MQTT 接入
   3. **WiFi 多路复用**：ESP32-WROVER-E-N16R8 的 WiFi 协议栈（lwIP）同时承载高实时性的 UDP 音频单播（发往各从节点 `:5680`）、UDP 控制组播（`239.0.0.1:5679`）、UDP 灯控组播（`239.0.0.2:8889`），与 ESP8266 灯控节点深度联动。

### 核心功能一览

| 功能模块                         | 说明                                                         |
| -------------------------------- | ------------------------------------------------------------ |
| 蓝牙音频接收（A2DP Sink）        | 主节点接收手机/平板蓝牙音频流                                |
| 双设备音频同步（WiFi 单播）      | 主节点通过 UDP 逐台单播分发 PCM 数据（每包带 `t_play_us`），主从残差 1~3ms |
| **UI 屏幕灯控（UDP 组播）**      | **主节点 UI 界面通过 UDP 组播控制 ESP8266 灯光，局域网低延迟；ESP8266 每 30s 回传一次开关状态** |
| **米家智能家居接入**             | **ESP8266 通过巴法云 MQTT 接入米家生态，支持小爱同学语音控制** |
| 本地音乐播放（SD 卡）            | 仅主节点可独立播放 SD 卡 `/sdcard/music` 下的 MP3 文件（不支持 WAV；从节点无 SD 卡）|
| 播放控制（AVRCP）                | 全局控制（播放/暂停/切歌/音量），同步至从节点                |
| LVGL 触摸屏界面                  | 只有主音频节点配备 2.8 寸触摸屏，显示播放状态及**灯控入口**  |
| 双备份 OTA 升级                  | 主节点支持 WiFi 远程升级，具备失败自动回滚能力（从节点 OTA 未接线）|
| 节点角色配置                     | 主/从节点目标硬件同为 ESP32-WROVER-E-N16R8（开发阶段从节点用 ESP32-S3），固件分开编译，NVS 存储各自参数|

> - 目标硬件主/从同为 ESP32-WROVER-E-N16R8（开发阶段从节点用 ESP32-S3 开发板验证），固件分开编译，通过 NVS 保存各节点运行参数。

## 🌐 双设备同步协议设计

### 音频数据包格式（自定义轻量级 RTP）

主节点把同一份 PCM **逐台单播**到各从节点的 UDP `5680`（不组播），每个音频包携带约 **15ms** 的 PCM 数据（661 个样点），包头 20 字节：

```reStructuredText
┌───────┬─────────┬───────┬───────────┬─────┬───────────┬─────────────┬─────────┐
│ magic │ version │ flags │ stream_id │ seq │ t_play_us │ payload_len │ lead_ms │
│  2B   │   1B    │  1B   │    2B     │ 2B  │    8B     │     2B      │   2B    │
├───────┼─────────┼───────┼───────────┼─────┼───────────┼─────────────┼─────────┤
│      PCM payload（16bit / 44.1kHz / 单声道，默认 661 样点 = 1322 字节）       │
└───────────────────────────────────────────────────────────────────────────────┘
```

| 字段       | 大小   | 说明                                                 |
| :--------- | :----- | :--------------------------------------------------- |
| Magic      | 2 字节 | 包起始标志 `0xAA55`，用于同步和过滤干扰              |
| Version    | 1 字节 | 协议版本，当前 `2`；接收端丢弃版本不符的包           |
| Flags      | 1 字节 | `bit0 = 1` 表示本次流的首帧                          |
| Stream ID  | 2 字节 | 一次音频流的唯一标识（主节点重启 / 切歌时变化）      |
| Seq        | 2 字节 | 序列号，递增（0~65535 循环），从节点用于检测丢包     |
| t_play_us  | 8 字节 | 该帧的基准播放时刻（主节点 `esp_timer` 微秒），不是发送时刻 |
| Payload Len| 2 字节 | 实际 PCM 数据长度（字节）                            |
| Lead ms    | 2 字节 | 提前量 D（ms），默认 200，从节点换算时钟偏移要用      |
| Audio Data | 变长   | PCM 数据（16bit, 44.1kHz, 单声道），约 15ms 时长     |

> **包大小计算**：15ms × 44.1kHz × 2 字节 ≈ 1323 字节（默认 661 样点取整），加上 20 字节头部，共约 1343 字节，UDP 包远小于 MTU 1500 字节，避免 IP 分片。
>
> **时刻定义**：`t_play_us = 发送时刻 + D`；主节点本地出声时刻 = `t_play_us + 60ms`（`SYNC_RX_MARGIN_US`），与从节点用同一公式，故主从同拍。

### 控制命令包（端口 5679）

控制命令使用独立端口（5679），同样通过组播发送，格式如下：

```reStructuredText
+----------------+----------------+----------------+
|  Magic (0xAA55) |  Cmd (8bit)    |  Param (8bit)  |
+----------------+----------------+----------------+
```

| 命令码 | 含义       | Param                   |
| :----- | :--------- | :---------------------- |
| 0x01   | PLAY       | 0                       |
| 0x02   | PAUSE      | 0                       |
| 0x03   | NEXT       | 0                       |
| 0x04   | PREV       | 0                       |
| 0x05   | VOLUME     | 0~100                   |
| 0x06   | RESET      | 0（复位）               |

> **扩展帧**（同一控制通道 `239.0.0.1:5679`，靠 type 与 cmd 区分）：`magic + type + len + data`，type 取值 `0x12` SYNC_START、`0x13` SYNC_HEARTBEAT、`0x20` PING、`0x21` PONG、`0x30` ANNOUNCE。PING/PONG 帧格式仍保留，但已不参与音频同步。
>
> **从节点当前只处理 VOLUME 帧**（音量跟随主节点），其余命令与扩展帧一律忽略。从节点每 3s 组播一帧 ANNOUNCE（ver、mac、ip、audio_port、volume、rssi、flags、token、name），主节点按 MAC upsert 维护从机表，10s 收不到判离线，上限 8 台（`SYNC_MAX_SLAVES`）；收到第一份合法公告后，发现表成为单播目标的唯一权威，此前沿用静态 IP 表。

## 🕒 同步机制详解（核心算法）

### 第一阶段：启动同步（初始对齐）

从节点**不立即出声**，而是先收一段数据单向估计时钟偏移（全程不需要回包）：

1. 从节点在 `5680` 上接收单播音频，按 `seq` 存入抖动缓冲区（Jitter Buffer）。
2. 每收到一帧记 `d(i) = 本地收到该帧的时刻 − 该帧的 t_play_us`。
3. 取统计窗口内 `d(i)` 的最小值 `d_min`（最小单程延迟最有代表性）。
4. 换算时钟偏移：`offset = d_min + lead_ms × 1000 + 60ms`。
5. 之后**出声时刻 = t_play_us + offset**；主节点本地按 `t_play_us + 60ms` 出声，与从节点同一常数，因此主从同拍。

**关键代码示意**：

```c
// 从节点：最小单程延迟 → 时钟偏移 → 本地出声时刻
int64_t d = (int64_t)t_recv_us - (int64_t)pkt->t_play_us;
if (d < s_d_min) {
    s_d_min = d;                                  // 统计窗口内取最小
}

int64_t offset        = s_d_min + (int64_t)pkt->lead_ms * 1000 + UDIO_MARGIN_US;
int64_t t_play_local  = (int64_t)pkt->t_play_us + offset;
```

### 第二阶段：持续同步校正（防时钟漂移）

两个设备使用不同晶振，长期播放会产生时钟漂移（如 50ppm 误差，1 分钟漂移 3ms，10 分钟漂移 30ms）。

偏移量在开播时冻结，让误差自然累积，再用 **sample slip** 拉回：落后就丢一个样点、领先就插一个样点，**不改 I2S 采样率**。

**校正策略**：

1. 播放任务按 `t_play_us + offset` 对齐每一帧的出声时刻。
2. 实际出声时刻与目标偏差超出死区时，丢/插**单个样点**（拼接处做几个样点的平滑），把时间轴拉回一格。
3. 单次只补一个样点（≈22.7µs），避免产生可听噪声。

```c
// 从节点：丢/插一个样点，I2S 采样率保持不变
size_t n_out = ua_write_frame(pcm, n, slip, dst);   // slip > 0 丢一个、< 0 插一个、0 原样
Amplifier_Play_Buffer((const uint8_t *)dst, n_out * sizeof(int16_t), NULL, amp_timeout);
```

### 第三阶段：异常处理

| 异常场景               | 处理策略                                                |
| :--------------------- | :------------------------------------------------------ |
| **丢包**（Seq 不连续） | 静音填充（写入 0 值），避免 I2S 欠载产生爆音            |
| **网络中断 > 500ms**   | 自动进入静音模式，UI 显示“同步断开”，随 WiFi 重连重建单播接收 |
| **主节点重启/切换**    | 检测到 `stream_id` 变化，重新估计 `d_min` 与 offset      |

### ESP32 与 ESP8266 通信协议（UDP 组播）

**数据格式（JSON）**：

```json
{
  "cmd": "on",
  "light": "bedroom",
  "version": 1
}
```

| 字段  | 说明                             |
| ----- | -------------------------------- |
| cmd   | 指令：`on` / `off`               |
| light | 目标灯：当前只有 `bedroom`（一盏灯） |
| version | 协议版本，当前 `1`；对端高于本端版本时回 `verr` |

**ESP32 端代码示意（UI 点击灯控按钮）**：

```c
// ESP32 主节点：UI 界面点击开灯按钮后，通过 UDP 组播发送指令
void ui_bedroom_light_on_click(void) {
    const char* cmd_json = "{\"cmd\":\"on\",\"light\":\"bedroom\",\"version\":1}";
    
    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    struct sockaddr_in multicast_addr = {
        .sin_family = AF_INET,
        .sin_port = htons(8889),
        .sin_addr.s_addr = inet_addr("239.0.0.2")  // 灯控组播地址
    };
    
    sendto(sock, cmd_json, strlen(cmd_json), 0, 
           (struct sockaddr*)&multicast_addr, sizeof(multicast_addr));
    close(sock);
}
```

**ESP8266 端代码示意（UDP 组播接收）**：

```c
// ESP8266 灯控节点：加入灯控组播组并接收指令
void udp_multicast_receiver_task(void *pvParameters) {
    int sock = socket(AF_INET, SOCK_DGRAM, 0);
    struct sockaddr_in server_addr = {
        .sin_family = AF_INET,
        .sin_port = htons(8889),
        .sin_addr.s_addr = INADDR_ANY
    };
    bind(sock, (struct sockaddr*)&server_addr, sizeof(server_addr));
    
    // 加入灯控组播组（触发 IGMP Join）
    struct ip_mreq imreq;
    imreq.imr_multiaddr.s_addr = inet_addr("239.0.0.2");
    imreq.imr_interface.s_addr = IPADDR_ANY;
    setsockopt(sock, IPPROTO_IP, IP_ADD_MEMBERSHIP, &imreq, sizeof(struct ip_mreq));
    
    char buf[256];
    while(1) {
        int len = recv(sock, buf, sizeof(buf), 0);
        if (len > 0) {
            buf[len] = '\0';
            // 解析 JSON 并控制 LED
            parse_and_control_led(buf);
        }
    }
}
```

## 🔄 OTA 升级流程

### 音频节点（ESP32）

主节点采用双备份 OTA 分区（ota_0 / ota_1 各 4MB），支持远程升级、UI 触发与失败自动回滚。从节点分区表虽有 ota 槽位，但 `ota_manager` 目前是空壳，OTA 尚未接线。

### 灯控节点（ESP8266）

## ✨ 功能详细说明

### 1. 蓝牙音频接收（仅主节点）

- 主节点作为 A2DP Sink 连接手机，接收 SBC 音频流。
- 将 PCM 数据同时送入本机播放队列和单播发送队列。

### 2. 双设备同步播放（核心创新）

- **单播分发**：主节点把同一份 PCM 逐台单播到从节点（UDP `:5680`），每帧带 `t_play_us`。
- **从节点接收**：从节点按 `t_play_us + offset` 对齐出声，offset 由最小单程延迟单向估计。
- **同步残差**：两端最小单程延迟之差（局域网 1~3ms），人耳听不出先后。
- **容错处理**：从节点若超过 500ms 未收到音频包，自动静音并随 WiFi 重连恢复接收。

### 3. 本地音乐播放（SD 卡）

- 仅主节点可播放 SD 卡 `/sdcard/music` 目录下的 MP3 文件（minimp3 解码，不支持 WAV；从节点无 SD 卡）。
- 从节点仅作为同步播放终端，不提供独立的本地 / 蓝牙播放源。

### 4. LVGL 图形界面（图片在 Flash storage 分区，字体编译进固件）

- 主节点 UI 显示当前播放源（蓝牙/本地）、歌曲信息、进度条、控制按钮。
- 从节点无触摸屏 / UI；主节点的设置页第 2 页显示「已连接 N/M」从机列表（绿/灰状态点、IP、RSSI、失联秒数）。
- 目标硬件主/从同款，开发阶段从节点用 ESP32-S3，固件分开编译，角色由刷写固件决定。

### 5. AVRCP 控制（双向同步）

- 手机端控制（播放/暂停/切歌）通过 AVRCP 同步至主节点，主节点通过组播控制命令同步至从节点。

### 6. UI 屏幕灯控（UDP 组播，本地低延迟）

音频主节点通过 LVGL UI 界面提供灯光控制入口，与 ESP8266 智能灯控节点深度联动：

- **通信机制**：`SmartHome_Task` 在局域网内通过 **UDP 组播（239.0.0.2:8889）** 向 ESP8266 发送 JSON 格式的控制指令（`cmd` 只有 `on` / `off`，`light` 当前只有 `bedroom`，另带 `version`）。
- **执行端**：ESP8266 的 `UDP_Multicast_Rx_Task` 加入灯控组播组，接收指令后调用 `LED_Control_Set_Light()` 驱动**单路继电器**——只有开 / 关，不能调亮度；收到后回 ack，并每 30s 主动上报一次 status。
- 优势：
  - **局域网低延迟**：UI 点击到灯光响应 < 50ms
  - **不依赖公网**：即使家里断网，UI 仍可控制灯光
  - **多节点扩展**：未来增加 ESP8266 灯控节点，只需加入同一组播组即可
- **并发保障**：灯控组播（`239.0.0.2:8889`）与音频单播（从节点 `:5680`）、控制组播（`239.0.0.1:5679`）分别使用不同的地址 / 端口，在 lwIP 协议栈中通过不同的 Socket 独立运行，互不阻塞。

### 7. 云端灯控（巴法云 MQTT，当前不经主节点触发）

原设计由音频主节点通过 HFP 协议唤醒手机语音助手来触发云端灯控；HFP 语音链路（esp-sr 唤醒词、INMP441 麦克风、CallPhone）已整链路下线，主节点不再建立通话连接。现在这条链路只剩 ESP8266 侧的巴法云 MQTT 接入：

- 控制链路：米家 App / 小爱同学 → 米家云 → 巴法云 MQTT → ESP8266 控制灯光
- **执行端**：ESP8266 的 `BemFa_MQTT_Task` 订阅巴法云主题，接收米家下发的灯控指令并执行。
- 优势：
  - **接入米家生态**：支持米家 App 和小爱同学语音控制
  - **云端远程控制**：即使不在家，也可通过手机 App 控制灯光
  - **状态同步**：ESP8266 每 30 秒向巴法云上报当前灯光状态，米家 App 显示与实际一致

### 8. 双通道灯控的统一执行

ESP8266 灯控节点同时处理来自两个通道的指令：

| 控制来源          | 通信方式                     | 延迟      | 适用场景                     |
| ----------------- | ---------------------------- | --------- | ---------------------------- |
| **ESP32 UI 屏幕** | UDP 组播（`239.0.0.2:8889`） | < 50ms    | 本地快速控制，不依赖公网     |
| **手机语音助手**  | 巴法云 MQTT                  | 200~500ms | 语音控制、远程控制、米家联动 |

**指令融合**：两个通道的指令最终都调用同一个 `LED_Control_Set_Light()` 函数，状态天然一致，互不冲突。无论通过哪种方式控制，灯光状态都会同步更新，并通过巴法云上报至米家 App。
