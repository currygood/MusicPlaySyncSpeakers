# 主节点任务与内存分配说明

> 适用对象：主音频节点（`Play_Master`，ESP32-WROVER-E + 4MB PSRAM）。
> 本文是**实现视图**：任务参数、缓冲大小全部取自当前代码与当前构建产物
> （`build/Play_Master.elf`、`build/Play_Master.map`、`idf.py size`），
> 与《主音频节点软件构架分层设计.md》§6 的设计视图存在若干差异，见第 9 节。

**核心结论**：内部 RAM 是最稀缺资源，**只有任务栈、DMA 缓冲、ISR/定时器回调缓冲必须留在内部 RAM**；
其余音频/网络数据缓冲、模块句柄、队列/信号量一律放 PSRAM（4MB 富余）。

---

## 2. 启动引导任务（boot，临时）

`main/app_main.c` 在 `app_main()` 里**最先**创建 `UI_Task`（栈最大，趁内部堆还完整时
占住这块连续内存，随后阻塞等各模块就绪），再**严格串行**创建 3 个引导任务：每个任务
完成对应模块的 `create()`、置位就绪事件后 `vTaskDelete(NULL)` 退出，`app_main` 再建下一个
（中间 `vTaskDelay(50ms)` 让 IDLE 回收栈）。

| 任务名 | 入口函数 | 优先级 | 栈(B) | 核 | 依赖 / 职责 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `mp_boot` | `App_MusicPlay_Task` | **11** | 4096 | 1 | 建 MusicPlay（内部建蓝牙）→ 置 `APP_EVT_MUSIC_READY` |
| `cp_boot` | `App_CallPhone_Task` | **10** | 4096 | 1 | 等蓝牙 ready → 建 CallPhone |
| `lc_boot` | `App_LightControl_Task` | **9** | 3072 | 0 | 等 WiFi ready → 建 LightControl |
宏定义：`APP_MUSIC_TASK_PRIO = 11`、`APP_CALL_TASK_PRIO = 10`、`APP_LIGHT_TASK_PRIO = 9`、
`APP_MUSIC_TASK_STACK = 4096`、`APP_CALL_TASK_STACK = 4096`、`APP_LIGHT_TASK_STACK = 3072`、
`APP_UI_TASK_STACK = 10240`、`APP_UI_TASK_PRIO = 12`（`main/app_main.c:84-100`）。
另有一个 `APP_BOOT_TASK_PRIO = 10` 宏，当前未被引用（仅作注释性说明）。

> **boot 优先级为何提到 9~11**（`app_main.c:84-88`）：boot 任务必须高于解码(10)/同步(11)，
> 否则解码节流在"恰好追平"时余量 <1ms、不再 `vTaskDelay`（连续不让步），prio 5 的 boot
> 任务会被饿死——实测表现为 CallPhone 60s 内既不就绪也不失败，UI 只能陪等满 60s 超时才出屏。

> 4 个任务统一经 `App_Boot_Task_Create()` 创建：失败会打印内部堆余量并置对应
> FAILED 位，依赖方不再空等超时；`app_main()` 收尾改为 `return`，让 IDF 主任务自删、
> 回收约 4KB 内部栈。

> **为什么串行**：引导栈同样必须落内部 DRAM，4 个 boot 栈并存会直接把内部 RAM 吃光；
> 串行 + 逐个回收，是启动期内部 RAM 峰值最小化的关键约束。

## 4. 内存放置红线（必须内部 RAM）

1. **所有任务栈**（含引导栈）——PSRAM 栈会触发断言；
2. **DMA 缓冲与描述符**（I2S RX/TX、LCD SPI flush、SD/SPI 传输）；
3. **ISR / `esp_timer` 回调**里访问的缓冲（回调要求代码与数据都在内部 RAM）；
4. **cache 一致性 / 极低延迟**数据（如 `sync_master_s` 这类被高频读写的模块单例）。

除此之外的音频/网络数据缓冲、模块句柄、队列与信号量，**一律 PSRAM 优先、内部 RAM 回退**。

## 6. 内部 RAM 缓冲清单

| 缓冲 / 对象 | 大小(B) | 位置 | 说明 |
| :--- | ---: | :--- | :--- |
| 麦克风 I2S RX DMA | 4×256×8 = 8192 | `microphone.c` | `dma_desc_num=4`，`dma_frame_num=256`，32bit×2slot |
| 功放 I2S TX DMA | 4×512×4 = 8192 | `amplifier.c` | `dma_desc_num=4`，`dma_frame_num=512`，2slot×16bit |
| LVGL flush 缓冲 | 320×8×2 = 5120 | `ui_disp.c` | `MALLOC_CAP_DMA` + `MALLOC_CAP_INTERNAL`，失败逐半降行（最小 4 行） |
| SPI 收发静态缓冲 | 3 × 64 = 192 | `bsp/spi_driver/spi_driver.c` | `s_rx_dummy`/`s_rx_bounce`/`s_tx_bounce`，4 字节对齐（RX DMA 硬性要求） |
| SPI2 DMA 描述符 | 2 × 2 × 12 = 48 | IDF `spicommon_dma_desc_alloc` | 总线初始化时按 `max_transfer_sz` 预分配，TX/RX 各一份 |
| SPI 设备事务队列 | LCD 2×12×2 + SD 1×12×2 = 72 | IDF `spi_bus_add_device` | `xQueueCreate(queue_size, sizeof(spi_trans_priv_t))`，trans/ret 各一条；LCD 深度已由 7 收到 2 |
| `s_master`（`sync_master_s`） | 232 | `sync_protocol.c` | 模块单例静态变量（高频读写） |

> **SPI 总线约束**：`max_transfer_sz` 只按最大单笔传输设置（LCD 局部刷屏 320×8×2），
> 不要按整屏设置——它决定 IDF 在总线初始化时预分配的 DMA 描述符数量。
>
> 另外 ESP32 的 SPI DMA **只认内部 RAM**，且 RX 还要求缓冲起始地址 4 字节对齐
> （TX 无对齐要求，长度也不必对齐）。只要不满足，IDF 就会为**每一笔事务**从内部 DMA 堆
> 申请一份私有 bounce 缓冲；内部 RAM 耗尽时该分配失败，而驱动的错误清理路径会解引用
> 空指针直接 panic（`spi_common.c` 分配失败时不回写出参 → `spi_master.c`
> `setup_priv_desc` → `uninstall_priv_desc` 对 NULL 复制）。
>
> 这条约束在本项目里**真的会踩到**：FATFS 的扇区缓冲在 PSRAM
> （`CONFIG_FATFS_ALLOC_PREFER_EXTRAM=y`），ESP32 的 SPI DMA 到不了 PSRAM，所以每次
> SD 扇区读写都会申请一份 512B 内部缓冲。`bsp/spi_driver` 已改为自己做中转：DMA 可达
> （RX 另需 4 字节对齐）的缓冲直传，否则分块经静态对齐缓冲搬运。调用方不必关心 DMA
> 约束，也不会再有每笔事务的堆分配；代价是非直传传输被拆成 64B 一笔（SD 读一个扇区
> = 8 笔），带宽仍远高于音频需求。

## 7. 内部 RAM 用量实测

`idf.py size`（当前构建）：

| 段 | 大小(B) | 备注 |
| :--- | ---: | :--- |
| DRAM `.data` | 32395 | 已初始化数据 |
| DRAM `.bss` | 65288 | 未初始化数据 |
| **DRAM 合计** | **97683** | `dram0_0_seg` 段长 124580，段内余 26897 |
| IRAM | 115487 | 段长 131072，余 15585 |

链接期内部堆区间：`_heap_start = 0x3FFD7030` → `_heap_end = 0x40000000`，约 **164KB**
（含 `0x3FFE0000`–`0x40000000` 的 128KB 块）。

运行期用 `main/app_main.c` 的 `App_Log_Heap()` 在启动各节点打印三组余量：
`int`（`MALLOC_CAP_INTERNAL|MALLOC_CAP_8BIT`）、`dma`（`MALLOC_CAP_DMA|MALLOC_CAP_INTERNAL`）、
`psram`。其中 **`dma` 一栏最关键**：SPI 等外设驱动的收发缓冲只能落在这一区，
它见底就意味着任何一笔"驱动私有 bounce 缓冲"的分配都会失败（见第 6 节 SPI 总线约束）。

DRAM 静态占用最大的符号（`nm`，当前 ELF）：`a2dp_sink_local_param` 9680、
`sigmoid_table_5_8` 5680、`bta_hf_client_cb` 4372、`port_IntStack` 4192、
`g_cnxMgr` 3944、`bta_hf_client_co_cb` 3752、`s_io_buf`/`vflash_mem` 各 2048、`btm_cb` 1880、
`a2dp_source_local_param` 1752、`rfc_cb` 1700、`avdt_cb` 1696、`l2cb` 1392。

> 运行期：WiFi + 蓝牙协议栈启动后会再吃掉几十 KB 内部堆，
> 启动到 `bt_audio` 完成时内部堆仅剩个位数 KB（见《主音频节点开发过程.md》十三A 启动曲线）。
> 这正是"任务栈必须精打细算、大缓冲一律 PSRAM"的根本原因。
>
> 另一个关键约束是**分配顺序**：LVGL 的 widget/style 都是几百字节的小块
> `malloc`，当前 `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=0`，普通 `malloc` 优先落 PSRAM。
> 所以 `ui_init()` 只做硬件/LVGL 移植并创建 `UI_Task`，主题与页面构建移到
> `ui_task` 里执行——任务栈先占住，LVGL 的小对象不足时自动落 PSRAM 兜底。

设计文档 §6 未登记 `app_main` 的引导任务（`mp_boot`/`cp_boot`/`lc_boot`）与最先创建的
`UI_Task`，也把 `bt_audio_task`、`LCD_Touch_Task` 画成了固定绑核，实际实现见第 1、2 节。

## 10. 关键经验：大任务栈必须"先占位"

内部 RAM 紧张时，堆会被 WiFi/BT/I2S DMA/各任务栈逐步切碎：实测 `lc_boot` 之后
`free=12775` 但 `largest=6400`，到 `ui_init` 时只剩 `largest=4096` —— 这时再想建
13312B 的 `UI_Task` 必然失败（free 看起来够、最大连续块不够）。

所以**最大的那个任务栈要在启动最初分配**：`app_main()` 先建 `UI_Task`(10240B)，
它立刻阻塞等各模块就绪，等其它任务把堆切碎时这块内存已经握在手里。
`ui_run()` 打印的 `hwm_words`（栈高水位，×4 得字节数）用于复核栈是否给大了。

同理，`ui_init()` 不再内部建任务：调用方（UI 任务）在 `ui_init()` 成功后调用
`ui_run()` 进入渲染循环，避免"建任务"与"建页面"两个阶段互相挤占内部 RAM。

## 11. 维护约定

- 新增任务：先定"能不能不占任务栈"，再定栈大小；栈必须内部 RAM，且要计入第 8 节预算。
- 新增大缓冲：默认 `MALLOC_CAP_SPIRAM`，仅在第 4 节红线内才用内部 RAM。
- 队列/信号量：用 `xQueueCreateWithCaps` / `xSemaphoreCreateXxxWithCaps(MALLOC_CAP_SPIRAM)`。
- 改动后复测：`idf.py size` 看 DRAM 余量，运行期看 `heap_caps_get_free_size` +
  `heap_caps_get_largest_free_block`（`largest` 更能解释"为什么 free 够也建不出栈"）。
