### 问题2：蓝牙控制器使能失败（ESP_ERR_INVALID_ARG）

现象：`esp_bt_controller_enable(ESP_BT_MODE_BTDM)` 返回 `0x102 (ESP_ERR_INVALID_ARG)` 后 `abort()` 重启（bt_test.c:137）。

原因：sdkconfig 中经典蓝牙（Classic BT / BTDM 双模）没有正确使能，控制器按 BLE-only 方式编译，请求 BTDM 模式被协议栈拒绝。

解决：在 `idf.py menuconfig` 中开启蓝牙并按双模编译：
- `Component config → Bluetooth → Bluetooth → Bluetooth controller → Bluetooth mode` 选择 `Dual mode (BTDM)`；
- 确认 `CONFIG_BT_ENABLED`、`CONFIG_BT_CLASSIC_ENABLED`、`CONFIG_BTDM_CTRL_MODE_BTDM` 生效，并打开 A2DP / AVRCP / HFP Client 相关编译选项。

改完 sdkconfig 后控制器正常启动，手机可成功配对连接。

### 问题3：AVRCP 控制命令一直返回 ESP_ERR_INVALID_STATE

现象：调用 `bt_audio` 的 play/pause/prev/next 等控制命令连续报错，日志伴随：
```
W (...) BT_BTC: A2DP Enable without AVRC
W (...) BT_BTC: AVRC Controller is expected to be initialized in advance of A2DP !!
W (...) BT_BTC: AVRC Target is expected to be initialized in advance of A2DP !!
```

原因：初始化顺序错误。ESP-IDF 要求 AVRC（AVRCP Controller）必须在 A2DP **之前**初始化，否则 A2DP 启用了也没有控制通道，对外命令一律 `ESP_ERR_INVALID_STATE`。

解决：`bt_audio_start()` 流程中先 `esp_avrc_ctrl_init()` 建立 AVRC 控制通道，再初始化 A2DP Sink 与 GAP 可发现/可连接模式；之后 play / pause / prev / next / toggle 均返回 `ESP_OK`。

### 问题4：手机拒绝 AVRCP 绝对音量，滑块不同步

现象：`bt_audio_set_volume()` 返回 `ESP_OK`，但日志出现：
```
W (BT_BTC): handle_rc_metamsg_rsp: code 10 error 0x0
```
手机音量条不变化、本机也无反应；`get_track_info` 同时返回 `ESP_ERR_NOT_FOUND`（正在播放时无元数据属于正常，与音量问题无关）。

原因：大部分安卓手机默认未开启“蓝牙绝对音量”（Absolute Volume），AVRCP `SetAbsoluteVolume` 被手机以 `code 10`（REJECT）拒绝，volume 通道没有建立。

处理：
- 本机音量加减（`BT_AUDIO_CMD_VOLUME_UP/DOWN`）改为发送 AVRCP 透传按键 `ESP_AVRC_PT_CMD_VOL_UP / VOL_DOWN`，不依赖绝对音量通道；
- `bt_audio_set_volume()` 保留 `SetAbsoluteVolume`，用于开启了“蓝牙绝对音量”的手机同步滑块；
- 本机扬声器音量由 amplifier 模块的软件音量实现（见问题5），手机拒绝绝对音量不影响本地音量。

### 问题5：调音量功放没有声音变化

现象：`AMPLIFIER: Volume set to xxx%` 正常打印，声音大小完全不变。

原因：`Amplifier_Set_Volume()` 旧实现只保存了音量变量并打印日志，实际 PCM 没有做任何衰减；NS4168 是固定增益的 D 类功放，没有硬件增益寄存器，只能靠软件缩放 PCM。

解决（在 amplifier 模块实现）：
- 新增一块软件音量工作缓冲（优先 PSRAM，内部 RAM 不足时回退）；
- 按平方曲线 `gain = (vol/100)²` 对 16-bit PCM 定点缩放，音量 100% 直通、0% 静音；
- 把 `BT_AUDIO_EVT_VOLUME_CHANGED` 事件接入 `Amplifier_Set_Volume()`，蓝牙音量变化实时生效；
- 测试结果：100→70→40→10→60→85 各档能听到明显的音量台阶，暂停/上一首/下一首也正常。

### 问题6：HFP+SCO 测试时内部内存不足

现象：开启 HFP 后出现 `BT_OSI: osi_alarm_new failed to create timer, err 0x101` 断言重启；手机允许蓝牙唤醒（HFP + SCO + 语音识别）后因 RAM 不够重启；`SCO xmit Q overflow, pkt dropped`。

原因：经典蓝牙双链路（A2DP + HFP/SCO）叠加后内部 RAM（IRAM）紧张，协议栈定时器/队列分配失败。

处理方向：控制任务栈与 FIFO 大小，大的 PCM 缓冲尽量放 PSARM；后续开发 CallPhone 时再做评估（这次问题1同场景，一并放到 CallPhone 完成后验证）。

### 经验（非问题）：

- 初始化顺序：**必须先初始化麦克风（I2S RX），再初始化功放（I2S TX）**，颠倒会导致设备不可用（历史经验，已固化到初始化流程）。
- 蓝牙调通顺序建议：先 A2DP 出声音，再 AVRCP 控制，再音量，最后 HFP。

### 问题1：唤醒词检测不到（AFE Ringbuffer 一直为空）

现象：

```
W (12410) AFE: Ringbuffer of AFE is empty, Please use feed() to write data
（每 200ms 一条持续刷屏；对麦克风说“你好小智”无任何反应）
```

根因：CallPhone 的 LISTENING 流程在一次文件恢复事故中丢失了两个关键调用——`CallPhone_Resample_16_16()`（44.1k 单声道 → 16k 的 `feed_buf` 从未被填充）和 `afe_if->feed()`（AFE 环缓冲永远收不到输入，内部 200ms 超时告警）。

处理：恢复“重采样填满 `feed_buf` 一帧”的步骤；在 `fetch()` 前成对调用 `afe_if->feed(afe_data, feed_buf)`（feed/fetch 必须成对，参考 ESP_AI 工程 ASR.c 写成）。

验证：`Ringbuffer empty` 刷屏消失，流程进入唤醒检测阶段。

### 问题2：唤醒仍无反应（feed 数据整帧恒定）

现象：

```
mic: lanes avg0=44 avg1=60 (use lane 0), feed16k avg=640 peak=640
mic: lanes avg0=64 avg1=51 (use lane 0), feed16k avg=0   peak=0
```

`avg == peak` 且数值全部为 4 的倍数（增益×4 后）；说话时也大量出现 avg=0；唤醒永不触发。

根因：重采样游标 `rs_pos` 是跨帧累计的绝对游标，但输入缓冲区每帧只存放最新的 `in_need`（约 1412）个单声道样本。第 2 帧起 `idx = rs_pos >> 16 >= in_need`，越界被钳位成“取窗口最后一个样本”——整帧输出等同一个常数（≈静音）。

处理：每帧重采样后把游标折回帧内窗口 `rs_pos -= (in_need << 16)`，负值则归 0（同时吸收每帧约 0.2 采样的韵律抖动）。

定位方法：临时在日志间隔打印 `mono[0..3]` / `feed[0..3]` / `pos`，观察“mono 有语音变化但 feed 整帧恒定”即可锁定重采样级。

验证：feed 出现不同采样值、说话时 avg 抬升且 avg != peak，唤醒可稳定触发（本次“你好小智”验证通过）。

### 问题3：手机听不到麦克风上行语音（第三阶段遗留问题的真正根因）

现象（唤醒成功、SCO 打开后约 4.8s）：

```
[I (48390) bt_audio: HFP SCO open (mSBC, 16000 Hz, frame=0 B)
I (48394) CallPhone: HFP SCO open, mic uplink started
W (53131) BT_HCI: hcif disc complete: hdl 0x180, rsn 0x13 dev_find 1
W (53132) bt_audio: HFP voice recognition DISABLED
W (53134) bt_audio: HFP SCO closed
```

根因：`bt_audio.c` 的 `bt_hfp_data_send_cb()`（协议栈每 7.5ms 回调要一帧）上行重采样 44.1k→16k 时，模块级游标 `hfp_rs_pos` 同样只累计在窗口内——第 2 次回调起，idx 越界钳位到“窗口最后一个样本”，手机收到的实际是恒定电平 ≈ 静音 → 语音识别听不到语音，超时自动关闭 SCO。

处理：在 send 回调重采样完成后做 `hfp_rs_pos -= (in_need << 16)`、负值归 0（与问题2同样修复方法）。

验证：手机语音助手能听到提问并正常回答，SCO 不再自动关闭；第三阶段“麦克风数据无法给到手机”遗留问题正式关闭。

### 问题4：读取 MIC FIFO“不足一帧直接丢弃”（drop≈32/间隔）

现象：统计每 32 次完整帧约有 32 次因 `got < pair_need` 提前返回，麦克风数据有规律丢失。

处理：改为循环分段补读，直到凑齐一整帧（`while (got < pair_need)` 内继续 `read_pcm16`）。

验证：drops 归 0，链路无额外丢帧。

### 第四阶段经验小结：

- esp-sr 的 AFE：`feed()` 与 `fetch()` 必须成对调用；`feed` 输入为 16k 单声道 int16，每帧长度 = `get_feed_chunksize()`（本工程 512）；
- 16.16 定点线性插值重采样：凡“每次喂一个新窗口”的用法，游标必须按窗口折回/复位，否则输出整帧恒定（静音）；
- 节奏：LISTENING 实际每帧 wall 约 43ms（读 32ms + AFE 处理约 11ms），状态机按 SCO 事件驱动；
- 唤醒词“你好小智”对应模型 wn9s_niaoxiaozhi（sdkconfig 配置），唤醒通道链路：mic 44.1k → 左声道 → 44.1→16k → ×4 增益 → AFE feed → 唤醒；
- 上行分层职责不变：CallPhone 只负责 44.1k 单声道 PCM 上行，44.1k→mSBC 16k 降采样在 bt_audio 内部完成。


## 第五阶段：audio_decoder从sd卡读取mp3音频播放

### 简述

middlewares 层 `audio_decoder` 模块完成（minimp3 基础接口 `mp3dec_t + mp3dec_decode_frame`，
自建 8KB 窗缓冲滑动读 SD 卡），MP3 解码 -> PCM 回调直接经 `Amplifier_Play_Buffer` 播放
（测试阶段不经 sync_protocol），测试曲目播放、EOF 均正常。

### 遇到的问题与解决

1. 中文文件名打不开 / 小卡读不到
   - 现象：`fopen` 失败、日志里中文名字乱码；换成英文名能开，但有些文件 `fread` 读 0 字节、`fseek/tell` 返回 `ESP_FAIL`。
   - 解决：测试文件名先用 ASCII；SD 卡（121MB 小卡）重新格式化时格式选 **FAT（FAT16），不要选 FAT32**；格式化/换卡后读写正常。

2. 播放瞬间“自动断电”（USB 串口消失 / WDT 复位）
   - 现象：`audio_decoder_play()` 返回后立刻复位（`rst:0x8`，`TG1WDT_SYS_RESET`）；SD-only、BtA2dp 均正常，只有 decode 播放触发。
   - 排查：先用示波器测 3.3V 电源波形（复位瞬间无跌落），排除硬件供电；随后把目标锁定在 audio_decoder。
   - 根因一：首版用 `mp3dec_ex` 流式接口，内部约 128KB 缓冲落入 PSRAM，解码热循环触发 cache-livelock -> WDT 复位；改用基础接口 `mp3dec_decode_frame()` 解决。
   - 根因二：minimp3 单帧解码约需 20KB 栈（scratch 15.5KB + PCM 4.6KB），而首帧探测最初在 `app_main` 默认 3584B 栈上跑，栈溢出复位；把首帧探测移到 32KB 解码任务内（信号量同步）后解决。

3. 结论：全部为软件问题（栈溢出 + 大缓冲入 PSRAM），非硬件供电问题；详细排查笔记见 `note/audio_decoder模块开发遇到的问题.md`。


## 第六阶段：wifi_manager和node_role系统服务

### 简述

- mysystem 层新增 `wifi_manager` 与 `node_role` 两个系统服务：
  - `wifi_manager`：STA 连接、断线自动重连、IP 事件回调，并统一持有 UDP 组播 socket（音频/灯控通道复用）；重连后自动重建组播并重新加入；
  - `node_role`：NVS 持久化唯一入口（命名空间 `node_role`、Key `cfg` 单 blob，整体带 `version` 头），保存 WiFi 凭据、音量、播放模式、采样率、同步延迟、组播地址、OTA 地址；业务模块经 `node_role_get()/set()` 整体读写；
- 凭据链路：测试时先 `node_role_set()` 整份写入（含默认 SSID `HW666` 等），`wifi_manager` 启动经 `node_role_get()` 读取，不再硬编码。

### 遇到的问题与解决

1. esp-idf 6.0.1 对 `wifi_sta_config_t` 的 API 变化（`ssid_len` 已移除，SSID 以 `\0` 结尾）导致 `request for member ...` 类错误：按 6.0.1 实际定义修正，并使用 `strlcpy`/`snprintf` 限长拷贝；
2. 自定义事件类型与 `wifi_event_t` 命名冲突：按文档重命名为 `wifi_mgr_event_t` 后编译通过；
3. `snprintf` 截断告警（`-Werror=format-truncation`）：日志/信息拼接按字段最大长度（IP 15+1、SSID 32、密码 64）分配缓冲并限长格式化，消除告警；
4. 事件回调中强转 `event_data` 自建结构导致的成员访问错误（`request for member ...`）：改为按事件分别从 `esp_netif`/`wifi_ap_record` 等官方结构取字段；
5. 首次验证未连接（`disconnected, reason=2`、`wait ip timeout`）：修复后第二次验证成功——热点环境/SSID 密码需与 `node_role` 持久化值一致；
6. VSCode IntelliSense 报 `CONFIG_LOG_MAXIMUM_LEVEL` 未定义：系 IDE 未随 `idf.py` 重建索引，非编译错误。

### 验证

- 组播自环：`wifi_manager` 打开组播通道（默认组/端口），10 帧 `send→recv` 全部一致（`WIFI_TEST seq=0..9 cnt=10`），链路收发正常；
- 状态：`connected, ip=192.168.4.30 (first=1, changed=1)`、`rssi=-47`，重连与 stop/destroy 日志正常；
- NVS：`node_role_set()` 写入后 `node_role_get()` 全字段回读一致；默认参数（含 SSID/密码）在校验时从 NVS 驱动 WiFi 连接。

## 第九阶段：snyc_protocol同步播放实现

### 简述

middlewares 层实现 `sync_protocol` 模块（`components/middlewares/sync_protocol/`），本阶段只做**主节点侧**：

- PCM 汇聚 → 按 15ms 一帧分包（每帧 661/662 个 mono 采样交替，平均 44.1kHz）→ 打 64bit 微秒时间戳（`esp_timer_get_time()`，避免 32bit 约 71 分钟回绕）→ 经 wifi_manager 音频组播通道（239.0.0.1:5678，只发）发往从节点；
- 同一帧同时入本地延迟队列，`SyncLocalPlay_Task` 按 `t_play = t_tx + D`（D=200ms）出队，单声道→立体声（L/R 相同）后经 `Amplifier_Play_Buffer()` 直接写 I2S——主从节点按同一时刻写 amplifier，即"同拍播放"（第九阶段讨论定案，不注册 audio_bus writer）；
- 控制通道 239.0.0.1:5679：基础命令帧（Magic+Cmd+Param 4B）广播 PLAY/PAUSE/NEXT/PREV/VOLUME/RESET；时间同步扩展帧 PING(0x20)/PONG(0x21)/SYNC_START(0x12)/SYNC_HEARTBEAT(0x13)，0x10/0x11 预留——本阶段主节点实现收 PING 自动回 PONG、首帧后发一次 SYNC_START、每秒 Heartbeat、从节点在线判定（30s 未收到 PING 视为离线）；
- 两条任务（分层设计任务表）：`SyncTx_Task`（prio 11 / 栈 8192 / Core 0）帧化发送 + 控制收发；`SyncLocalPlay_Task`（prio 10 / 栈 10240 / Core 1）本地延迟播放；缓冲全部 PSRAM 优先（入口环默认 24KB、延迟队列 16 包）；
- 测试策略（见 `docs/04-测试/同步算法测试.md`）：从节点未实现，本阶段用"单机自环"——wifi_manager 组播开启 `IP_MULTICAST_LOOP` + `SO_REUSEADDR`，同一端口可绑定多个 socket 各收一份，测试用例再自开"嗅探"收 socket，验证 发→收 闭环；
- 测试入口：`app_main` 单开 `Sync_Protocol_Test()` 任务（16KB 栈，独立于 3.5KB 的 main 栈），喂 1kHz 正弦 PCM，最后应能听到本地功放出声。

### 遇到的问题与解决

1. **控制通道收包超时语义**：`wifi_manager_mcast_recv` 超时 0 是永久阻塞（`portMAX_DELAY`），TX 任务一旦没包就挂死。改为内部统一用 1ms 超时轮询。
2. **退出崩溃 `Guru Meditation ... uxListRemove`**：`deinit` 对已经自删的内部任务句柄再 `vTaskDelete` → TaskList 双重删除。修复：`deinit_pending` 标志 + 两个内部任务自退前清空句柄 + `deinit` 轮询等待（最长 1s），不再手动删除任务。
3. **自环收包“被撕成两半”（`[A][6][A][7]`、`[B] PLAY`、`[C] PING` 校验失败）**：RX FIFO 用 `RINGBUF_TYPE_BYTEBUF`，`xBufferReceive` 跨环回绕会把一个 UDP 包拆成两段返回（后半段当独立包，magic/len 全错）。修复：wifi_manager.c 一处 `RINGBUF_TYPE_NOSPLIT`（UDP 包整体原子出队）。经确认属 `msystem` 层改动。
4. **喂入速率不足（满不了 D、本地无声音）**：测试每 10ms 现算 441 个 sinf + `vTaskDelay(10ms)`，平均速率实际 < 44.1kHz，入口环被掏空。修复：喂入任务按 `esp_timer` 实际流逝补推（欠账累计），平均严格 44.1kHz。
5. **pause→resume 卡死在 PREPARING**：`sync_play_task` 在 `PREPARING` 状态也照常出队播放，D 缓冲永远攒不满 → 永不转 `PLAYING`。修复：PREPARING 阶段只攒不出队（攒满约 14 帧、210ms≥D 才出队切换 PLAYING）。
6. **玄学崩溃（`xQueueSemaphoreTake (pxQueue->uxItemSize == 0)`）**：两次出现在 `node_role_set()` 的 `cfg saved` 打印，均发生在 sync_protocol 尚未初始化之前，且崩溃位置随固件布局漂移（另一次表现为退出时任务链表 panic），特征像"存量模块越界写坏内存、受害对象随机"。排查：`addr2line` 对齐崩溃行；临时开 `CONFIG_HEAP_POISONING_COMPREHENSIVE` 复测通过；按约定随后还原 `sdkconfig`。结论：非本模块代码路径，未定位肇事者，后续复测未再出现，若再发按同手段定位。

### 验证（单机自环）

- `[A]` 音频自环 20 包：seq 连续、`len=1322/1324` 交替、帧间隔≈15ms（实测 15031µs/17850µs）、载荷非 0 —— 通过；
- `[B]` 控制命令 PLAY/PAUSE/NEXT/VOLUME(60) 四条 `loopback OK` —— 通过；
- `[C]` PONG：实测 `t1=5737075 t2=5739721 t3=5739724`，`t3-t2=3µs`、往返 ≈2.6ms —— 通过；
- `[D]` 暂停/恢复：PAUSE 后 `tx_pkts` 不再增长，恢复后 D 重新灌满转 PLAYING 出声；修复前 `fail=1`（卡 PREPARING），修复后复测 `fail=0`；
- 本地功放可听到 1kHz 正弦；退出 `SyncTx_Task exit / SyncLocalPlay_Task exit / deinit ok`，无崩溃。

### 经验

- 单机自环靠"同端口多 socket + `SO_REUSEADDR`"即可覆盖 发→收 闭环，无需第二台设备；
- 环缓冲注意原子性：BYTEBUF 会拆包，UDP 整包入出必须 `RINGBUF_TYPE_NOSPLIT`；
- "用真实时钟量喂入速率"而不是按代码逻辑判断——固定 `vTaskDelay` + 逐帧计算会让实际喂入低于标称，D 缓冲永远是空的；
- 玄学内存崩溃优先 `addr2line` 对齐崩溃行 + heap 消毒复测，不要上来猜代码；而且受害对象会随固件布局漂移，崩溃位置不同不代表根因不同；
- PREPARING 的"攒缓冲"与"出队播放"必须分离。

### 后续（从节点阶段再做）

- 时钟偏移估计（PING/PONG 的 `t2/t3` 已就位）与晶振漂移校正、从节点回 PPT 播放对齐；
- 命令 0x10/0x11（SYNC_PREPARE/SYNC_READY）按协议预留，从机阶段补充。

## 第十一阶段：MusicPlay

### 简述

App 层新增 `components/App/MusicPlay/`（`music_play.c/h`），实现《主音频节点软件架构分层设计》3.3.1 的 MusicPlay 模块：

- 播放状态唯一主人：源选择（自动/手动，BT/LOCAL）、播放/暂停/上下曲、音量、播放模式；UI 命令、bt_audio 事件、audio_decoder 事件统一进同一命令队列，由内部 `MusicPlay_Task`（prio 9 / 栈 4096 / Core 1）串行处理；
- 本地源：扫描 `/sdcard/music/*.mp3` → `audio_decoder_open/play` → 解码 PCM 经 `on_pcm` 回调直送 `sync_protocol_master_push_pcm()`；READY 后 `sync_protocol_master_start(stream_id=2, 44100, 2)`；
- 蓝牙源：控制命令经 `bt_audio_send_ctrl_cmd()`，状态以 bt_audio 回流事件为准；A2DP PCM 由 bt_audio 的 `on_pcm` 直连 sync_protocol（不经 MusicPlay）；蓝牙播放位置由新增的 `bt_audio_get_position_ms()` 提供（AVRCP `PLAY_POS_CHANGED` 主动注册通知，1s 间隔）；
- 音量三元同步：`Amplifier_Set_Volume` + `sync_protocol_master_broadcast_cmd(SYNC_CMD_VOLUME)` + （蓝牙源）`bt_audio_set_volume`，并持久化到 `node_role`；播放模式同样读写 `node_role`；
- `sync_protocol` 的 init/deinit 由 MusicPlay 的 create/destroy 负责，两条组播通道由 App 层经 `wifi_manager_mcast_open()` 传入；同步延迟 D 取 `cfg.sync_delay_ms`，未填则读 `node_role.sync_delay_ms`；
- 测试入口：`app_main.c` 新增 `MusicPlay_Test()`，用 `xTaskCreatePinnedToCore` 起独立任务（栈 4096）——`main_task` 只有 3584B，装不下测试流程。

### 问题1：内部 RAM 不足导致各模块连环创建失败（本阶段最大的坑）

现象：`E MusicPlay: create: queue/sem create failed`、`E bt_audio: task create failed`、`E SYNC_PROTOCOL: SyncTx_Task / SyncLocalPlay_Task create failed`、`E AUDIO_DECODER: open: task create failed` 依次出现；极端时 `E bt_audio: task create failed: internal free=7155 largest=4608`。

根因：ESP32 内部 DRAM 在 WiFi + BT + SD + 功放全开后极度紧张，而 PSRAM 还有 ~4.1MB 富余——问题是"大缓冲全落在内部 RAM"。量化（关掉 HFP AG 后的启动曲线）：`after wifi connect int free=99099` → `after controller enable 80863`（BT 控制器约 -13KB）→ `after bluedroid enable 64383`（Bluedroid 约 -16.5KB）→ `before task create 63675`，这 64KB 还要放 I2S DMA 描述符、SD/SPI 驱动、LVGL 缓冲和各模块任务栈。

解决（按收益排序）：

1. **大缓冲一律 PSRAM**：`heap_caps_malloc(n, MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT)`，失败再回退 `MALLOC_CAP_8BIT`。本阶段搬迁：minimp3 帧 scratch（约 15.5KB，原先在任务栈上）、解码输入窗 `in_buf` 8KB、sync 入口环 24KB / 组包缓冲 `tx_pkt` / 延迟队列、功放音量衰减缓冲 8KB、bt_audio 事件队列与 PCM/HFP FIFO；
2. **任务栈能降就降**（栈必须落内部 DRAM）：解码 32768→8192、`SyncTx_Task` 8192→4096、`SyncLocalPlay_Task` 10240→6144、`MusicPlay_Task` 4096（设计稿 12288，数据解码已移到 audio_decoder）；
3. **WiFi/LWIP 也走 PSRAM**：`CONFIG_SPIRAM_USE_MALLOC=y` + `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=4096` + `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y` + `CONFIG_WIFI_LWIP_ALLOCATION_FROM_SPIRAM_FIRST=y`（启动日志出现 `wifi_init: WiFi/LWIP prefer SPIRAM`）；
4. **砍功能省内部 RAM**：关 `CONFIG_BT_HFP_AG_ENABLE`（本项目只做 HFP HF 端，AG 是手机侧角色，白占约 16KB）；
5. **各模块 create/start 失败必须回滚**并返回 `ESP_ERR_NO_MEM`（本阶段补了 `sync_protocol` init 回滚、`bt_audio` task 创建失败回滚 FIFO/队列），否则 RAM 不够时是"半死模块 + 玄学崩溃"。

红线：PSRAM 不能放 `mp3dec_ex` 的 128KB 内部缓冲（第五阶段 cache-livelock 复位的根因），所以 minimp3 只用基础接口，并本地给 `minimp3.h` 加了 `mp3dec_decode_frame_scratch()`，把约 15.5KB 的 `mp3dec_scratch_t` 从任务栈提到调用方分配的 PSRAM。

### 问题2：链接期 IRAM 溢出

现象：`Play_Master.elf section '.iram0.text' will not fit in region 'iram0_0_seg'`，`region 'iram0_0_seg' overflowed by 13180 bytes`。
解决：关 `CONFIG_ESP_WIFI_IRAM_OPT` / `CONFIG_ESP_WIFI_RX_IRAM_OPT`（WiFi 代码从 IRAM 挪回 flash，牺牲一点吞吐换 IRAM）。注意是 **IRAM**，不是 DRAM。

### 问题3：`osi_alarm_new` 失败 → `hash_map_set` 断言崩溃

现象：连接手机瞬间 `E BT_OSI: osi_alarm_new failed to create timer, err 0x101`，随后 `assert failed: hash_map_set hash_map.c:129 (data != NULL)`，调用栈 `bta_hf_client_send_at_brsf → bta_sys_start_timer`。
根因：BT 协议栈定时器对象池耗尽，`bta_sys_start_timer` 拿不到 alarm；HFP SLC 建链 + AVRCP 注册通知这类突发负载最容易触发。
解决：`CONFIG_BT_ALARM_MAX_NUM=50`。

### 问题4：`-Werror=format-truncation` 编译失败（3 处）

现象：`music_play.c:643/649/929` 报 `'%s' directive output may be truncated writing up to 255 bytes into a region of size 64/114`。
根因：用 `snprintf` 拼"标题 - 歌手"、拼 SD 卡完整路径时，源字段（AVRCP 元数据 / 文件名最长 255B）比目标缓冲长，GCC 静态分析报必然截断。
解决：改手工 `memcpy` + 显式限长（按目标缓冲 room 截断），不再用 `snprintf` 拼接。

### 问题5：本地曲"只出一帧就哑"

现象：`AUDIO_DECODER: diag: frames=1 pos=26/364721ms` 后位置不再前进，功放只响一帧；日志显示同一次 select 里 open 了两遍（`8076 open → 8081 closed → 8131 open`，随后两个 `READY`、两次 `TRACK_CHANGED + PLAY_STATE_CHANGED`）。
根因：`MUSIC_MSG_SELECT_TRACK` 在非本地源时先调 `Music_Switch_Source_Msg()`（切源内部按 `view.track_index` 起播一次），返回后又调 `Music_Start_Local_Track()` 再起一次 → 同一文件 open 两遍 → 两个 READY → 对同一解码器调用两次 `audio_decoder_play()`，解码任务把多出来的 PLAY 当成打断命令退出解码循环。
解决：切源前先把 `view.track_index` / `view.track` 落好，由切源自己完成起播（`music_play.c:1062-1084`）。修复后单次 open、位置正常推进（`frames=39 pos=1018 → frames=77 pos=2011 → ...`）。

### 问题6：`mcast sendto failed ret=-1 errno=12`

现象：音频组播开始后刷屏 `W wifi_manager: mcast sendto failed ret=-1 errno=12`（ENOMEM）。
根因：①STA 默认省电（`WIFI_PS_MIN_MODEM`），驱动把包攒到 DTIM 窗口才发，突发时 socket 队列打满返回 ENOMEM；②`IP_MULTICAST_LOOP` 默认开，主节点把自己发的音频包再收一份（第九阶段单机自环需要，现在从节点才是接收方），白占 RX 队列。
解决：`wifi_manager_start()` 加 `esp_wifi_set_ps(WIFI_PS_NONE)`（主节点做低延迟同步不该省电，即收即发，启动日志确认 `wifi:Set ps type: 0`）；`wifi_mcast_socket_create()` 增加 `rx_enable` 形参，纯发送的音频通道（5678）关组播回环，控制通道（5679，要收 PING）保留。

### 问题7：`SYNC_START` 竞态（stop 后补发旧流）

现象：`SYNC_START sent: stream=2 t0=10350887` 出现在 `SYNC_PROTOCOL: stop` 之前——stop 已复位本流，发送任务仍补发一条属于旧流的 SYNC_START。主节点听不出来（`master_start` 会再清延迟队列），但从节点会跟着旧 t0 抖。
根因：`SyncTx_Task` 在锁外读 `active`，`sync_reset_stream()` 清零 `start_sent` 后任务又走了"首帧补发 SYNC_START"的分支。
解决：`sync_protocol.c` 增加流代号 `stream_gen`（`sync_reset_stream()` 自增），`SyncTx_Task` 循环顶部快照，发送前后用 `sync_stream_valid_locked(gen)`（须持 `s_lock`）校验 `started && (state == PLAYING || PREPARING) && stream_gen == gen`，失效即丢帧；音频组播发送仍在锁外（避免 20ms 阻塞占锁饿死播放任务），但发送后再次锁内校验，`start_sent` / `tx_seq++` / `frame_target` 等提交全部移到锁内，与 stop 串行。

### 问题8：SD 卡"播 1-2s 停、重播、彻底停"（非 bug）

现象：本地曲播 1~2s 后停，随后重播前面一小段，再停，最终彻底停。
结论：这是测试脚本 `MusicPlay_Test()` 的固定流程（select → NEXT → PAUSE → RESUME → set_mode → 音量 → 切 BT 源）依次执行，日志 `after NEXT` / `after PAUSE` / `after RESUME` 一一对应，链路本身正常；真正的问题只有问题5的"open 两遍"。另外播放中"停顿"的一段是切源前 `SYNC_PROTOCOL: stop` 停流。

### 验证

- 本地源：`MusicPlay: open track[0]` → `READY: 44100Hz/2ch dur=364721ms` → `SYNC_PROTOCOL: start: stream=2 44100Hz 2ch` → `state -> PLAYING (D=200 ms buffered)`，解码位置持续推进（`pos=1018 → 2011 → 3004 → 3840ms`）；
- 蓝牙源：手机连上后 `HFP SLC connected / A2DP connected / AVRCP connected / A2DP stream started` → `SYNC_PROTOCOL: start: stream=1` → `PLAYING`，`PLAY_STATE_CHANGED` / `TRACK_INFO` 事件正常回流；
- 音量：`AMPLIFIER: volume set: 50%` + `SYNC_PROTOCOL: broadcast cmd 0x05 param 50` + `VOLUME_CHANGED` 事件 + `node_role: cfg saved`；
- 稳定性：内部 RAM 打点不再出现 `task create failed`；`mcast sendto failed` 在关省电 + 关回环后不再刷屏；SD 卡播放曲目不再"只出一帧"。

### 经验

- 本项目最稀缺的是**内部 DRAM**（不是 PSRAM）：加缓冲前先问"多大 / 能不能放 PSRAM / 能不能不占任务栈"；
- 内存问题先打点（`heap_caps_get_free_size` + `heap_caps_get_largest_free_block`），`largest` 比 `free` 更能解释"为什么 7KB free 也建不出 4KB 栈"；
- 各模块 create/start 失败必须回滚，否则 RAM 不足时表现为"半死不活的模块 + 玄学崩溃"；
- 编解码/协议栈的突发定时器/对象池是隐藏地雷（`BT_ALARM_MAX_NUM`），报错点和崩溃点常不在同一处；
- PSRAM 不能乱放：`mp3dec_ex` 的 128KB 缓冲落 PSRAM 会 cache-livelock 复位（第五阶段教训）；
- 测试代码不要放 `main_task`（栈只有 3584B），一律单独起任务。

## 十二阶段：PlayMode 并入 MusicPlay

### 简述

原设计把"播放源选择（蓝牙/本地）"拆成独立 `PlayMode` 模块（分层设计 3.3.4），与 MusicPlay 用 `on_switch` 回调解耦。实现前评估判定该拆分冗余，决定**取消独立 PlayMode，并入 MusicPlay**：

- MusicPlay 本就是"播放源/播放状态/音量/播放模式"的唯一状态主人，独立 PlayMode 还得另存一份 source 与之同步，属多余的数据流转；
- MusicPlay 的 `MUSIC_MSG_SELECT_TRACK` 在非本地源时会自行切到本地源，独立模块下会出现两份 source 不一致（UI 显示与实际播放不符）；
- `MusicPlay_Task` 已带 50ms 周期 tick，且已在调 `bt_audio_get_a2dp_info()`，并入几乎零额外成本（不新增任务/队列/栈）。

### 实现

- 接口统一为 `music_play_` 前缀：`music_play_switch_source()` 更名 `music_play_set_source()`（与 `set_mode`/`set_volume` 一致）；新增 `music_play_get_source()`；`music_play_cfg_t` 新增 `source_poll_ms`（轮询间隔，0=默认 1000ms）；
- 自动源选择：`MusicPlay_Task` 内新增 `Music_Poll_Source()`（每 tick 调用、按 `source_poll_ms` 限频），读 `bt_audio_get_a2dp_info()`——A2DP 连接→`MUSIC_SOURCE_BT`，断开→`MUSIC_SOURCE_LOCAL`，仅在源变化时切换；create 后首次轮询即判定，故开机未连蓝牙自动落本地源；
- 手动切源：`music_play_set_source()` 参数非法发 `MUSIC_EVT_ERROR` 并返回 `ESP_ERR_INVALID_ARG`；合法则入队由状态机串行执行，蓝牙优先自动规则会在下一次轮询校正手动选择；轮询失败同样发 `MUSIC_EVT_ERROR`；
- 事件：源变化统一走已有的 `MUSIC_EVT_SOURCE_CHANGED`（手动/自动同一条），不再有 `PLAY_MODE_EVT_CHANGED`；
- 文档同步：分层设计（§3.3/§3.3.1/§3.3.4/§6.1/§6 任务表/§八）、系统设计说明书、nvs存储、UI界面设计、项目文档 均已按"并入"更新；空目录 `components/App/PlayMode/` 已删除。
