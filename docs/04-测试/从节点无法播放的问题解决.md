# 从节点无法播放主节点音频的问题解决

> 日期：2026-10-23
> 涉及工程：Play_Master（ESP32 主节点）、Play_Slave（ESP32-S3 N16R8 从节点）
> 对应提交：`6a19f05` 实现从节点接收并播放主节点发送的音频数据
> 设计细节：《Play_Slave/MVP 通信架构 - UDP 音频接收.md》

## 一、现象

- 从节点能连上 WiFi，但主节点播放音乐时从节点不出声，旧同步状态机一直走不到播放态。
- 期间还出现过一次“串口一切正常、就是没声音”，最后查明是功放模块的独立供电没接。
- 链路打通后又陆续暴露：从节点越播越提前、起播/滑码爆音、LCD 音量只控制主节点。

## 二、结论先行

| 问题 | 根因 | 处理 |
| --- | --- | --- |
| 从节点不出声（旧链路） | 音频走组播 + PING/PONG 锁时钟；控制包发不出去导致时钟永远锁不上；组播本身在 WiFi 上不可靠 | 数据面重写为**单播 UDP 5680 + 播放时刻戳（协议 v2）**，从节点不再回包 |
| 控制包 `sendto` 返回 ENOMEM | 纯发送的组播 socket 也加组、绑端口，但 RX 任务不读，收进来的包占住 lwIP pbuf | 只有 `rx_enable=true` 的通道才加组/绑定 |
| 从节点越播越提前 | sample slip 的丢弃分支把输出长度又补回 `n`，时间轴没有真正变化，漂移校正等于没做 | 丢样本输出 `n-1`、插样本输出 `n+1` |
| 起播/滑码“咔哒”声 | 拼接处样本硬跳变；首帧 DMA 从静音切音频有直流台阶 | 8 点线性过渡 + 首帧 128 点淡入 |
| 实测仍有爆音 | 杜邦线接触不良 | 换线；软件三处修正保留（漂移校正本身是必需的） |
| LCD 音量只控制主节点 | 从节点没有加入控制组播 5679 | 新增 `ctl_rx` 模块跟随音量（已实现） |

## 三、为什么旧链路播不出来

### 3.1 旧链路的组成

旧方案的数据面是组播：

- 音频：`239.0.0.1:5678`，主节点每 15ms 组播一帧（约 1.3KB）；
- 控制/时钟：`239.0.0.1:5679`，从节点每秒发 PING，主节点回 PONG，用 RTT 估时钟偏移；
- 从节点要完成“锁时钟 + 收到 SYNC_START + 缓冲够深”才进入播放。

### 3.2 直接原因：控制包发不出去，时钟永远锁不上

排查中发现 `wifi_manager` 的一个结构性缺陷（修改后已在代码注释里记录，
见 `Play_Master/components/msystem/wifi_manager/wifi_manager.c:441`）：

- 旧代码对**所有**组播通道都执行 `IP_ADD_MEMBERSHIP` + `bind`，包括 `rx_enable=false`
  的纯发送通道；
- 但 `wifi_mcast_rx_task` 对 `rx_enable=false` 的通道直接 `continue`，永远不读 socket；
- 这些通道上收到的包会一直留在 socket 接收队列里占着 lwIP 的 pbuf。pbuf 池被耗尽后，
  `sendto` 返回 `ENOMEM`，控制通道的 PONG 也就发不出去；
- 从节点收不到 PONG → 时钟偏移估计不收敛 → 状态机停在等锁，始终不出声。

修复方式：只有需要接收的通道才加组、绑端口；纯发送通道不加入组播组，源端口由协议栈
临时分配，`sendto` 照常工作。

即使修掉这个 pbuf 问题，组播在 WiFi 上的物理特性仍然不适合这条数据面：组播帧没有 ACK、
没有重传、强制使用基本速率，还会被 AP 按 DTIM 缓存。15ms 一帧的音频流一旦丢包就是
可听见的断点，而 PING/PONG 又依赖同一条不可靠的控制链路。因此**没有继续修旧同步机，
而是把数据面整体重写**。旧从节点的 `sync_protocol`（1727 行）随后被删除，只保留主节点
工程的同名模块作为 v2 单播发送端。

### 3.3 硬件层的干扰

排查时先做了 `APP_BOOT_BEEP` 自检（`Play_Slave/main/app_main.c:50`）：它绕开网络，直接
调 `Amplifier_Play_Buffer()` 放一声蜂鸣。

- 响 → 功放、I2S、喇叭、供电都正常，问题在收包/同步这一侧；
- 不响 → 先查功放供电和接线。2026-10-18 就是靠它确认了功放独立供电没接
  （NS4168 的 UVLO 欠压保护是静默的，不报任何错，日志看起来一切正常）。

这条经验后来复用到了爆音问题：软件三处修正做完仍有爆音，最后发现是杜邦线接触不良。

## 四、新数据面：单播 + 播放时刻戳（协议 v2）

### 4.1 线格式

音频包从“组播发给所有人”改为“逐台单播到从节点的 5680 端口”。包头 20 字节：

| 偏移 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0 | `magic` | u16 | 固定 `0xAA55` |
| 2 | `version` | u8 | 固定 2，版本不符直接丢弃 |
| 3 | `flags` | u8 | bit0 = 本次流的首帧 |
| 4 | `stream_id` | u16 | 一次流唯一标识，变化即清缓冲 |
| 6 | `seq` | u16 | 包序号，0~65535 回绕 |
| 8 | `t_play_us` | u64 | **该帧的基准播放时刻**（发送端时钟，µs） |
| 16 | `payload_len` | u16 | PCM 字节数 |
| 18 | `lead_ms` | u16 | 发送端提前量 D（默认 200ms） |
| 20 | `pcm[]` | i16[] | 44100Hz / 单声道 / 16bit 小端 |

与 v1 最大的差别：时间戳从“发送时刻”改成“**基准播放时刻**”。接收端不需要再做
“发送时刻 + D”的换算，直接按 `t_play_us` 出声。

### 4.2 为什么不需要 PING/PONG

设从节点收到第 i 帧的本地时刻为 `now`：

```text
d(i)   = now − t_play_us
       = (从机时钟 − 主机时钟) − D + 单程网络延迟

d_min  = 最近 64 个 d(i) 中的最小值
offset = d_min + lead_ms × 1000 + 60ms
出声时刻 = t_play_us + offset
```

`d_min` 对应“最小单程延迟”的那一包，固定部分就是两个时钟的差。发送端把 D 通过
`lead_ms` 告诉我们，再加 60ms 抖动余量，两端就在同一时刻出声。残差只有最小单程延迟
`L_min`（局域网 1~3ms），听不出来。

好处：

- 从节点**不需要向主节点发任何回包**，主节点也不用处理 PING；
- 不受控制通道丢包影响，链路状态只取决于音频包本身；
- 多台从节点各自估计各自的 offset，互不影响。

### 4.3 主节点的修改

#### （1）`wifi_manager`

- 纯发送通道不再 `IP_ADD_MEMBERSHIP` / `bind`（修复 pbuf 耗尽）；
- 新增 `wifi_manager_unicast_send(ch, ip, port, data, len, timeout_ms)`
  （`Play_Master/components/msystem/wifi_manager/wifi_manager.c:1366`）。

#### （2）`sync_protocol`

- 组包时算 `t_play = t_tx + D`，同时写进包头和本地延迟队列：

```c
hdr->version     = SYNC_PROTO_VERSION;
hdr->flags       = (seq == 0) ? SYNC_AUDIO_FLAG_STREAM_START : 0;
hdr->t_play_us   = (uint64_t)t_play;
hdr->lead_ms     = (uint16_t)s_master.cfg_delay_ms;
```

- 逐台从机单播，`timeout` 传 0（只尝试一次）。帧周期只有 15ms，某台从机离线时
  不能为它反复重试而拖住整条流；丢的帧由从机 PLC 补：

```c
for (uint8_t i = 0; i < slave_count; i++)
    wifi_manager_unicast_send(audio_chan, slave_ips[i],
                              SYNC_UNICAST_PORT_AUDIO, pkt, pkt_len, 0);
```

- 从机地址是编译期默认表 `SYNC_DEFAULT_SLAVE_IPS`（当前为 `192.168.31.45`，
  `sync_protocol.c:87`），运行时可用 `sync_protocol_master_set_slaves()` 覆盖；
  收到 ANNOUNCE 后单播目标改由发现表按在线从机重建，默认表只作兜底；
  空列表时音频只在本机播放。
- **主节点本地播放也必须加同样的 60ms 余量**，否则会比从节点早出声 60ms，
  同一间屋子能听出回声：

```c
int64_t play_at = (int64_t)ent.t_play_us + SYNC_RX_MARGIN_US;  /* 60000us */
```

- 本地延迟队列容量从 16 帧提高到 24 帧，装下 `D + margin`。

#### （3）`main/app_main.c`

音频通道从“组播 5678 只发”改为“单播 5680 只发”：

```c
mc.group     = SYNC_PROTOCOL_MCAST_GROUP;
mc.port      = SYNC_UNICAST_PORT_AUDIO;   /* 5680 */
mc.rx_enable = false;
wifi_manager_mcast_open(s_app.wifi, &mc, &s_app.audio_chan);
```

控制组播 5679 保持不变（音量等命令仍走它，但已不参与音频同步）。

### 4.4 从节点的修改

旧 `sync_protocol` 整体删除，新增 `components/middlewares/udp_audio/`，职责只有两个任务：

```text
ua_rx_task    recvfrom → 校验 magic/version → 按 seq 落进环形槽位
                    │
                    ▼（槽位 + 互斥锁）
ua_play_task  取下一帧 → 按 t_play_us 换算本地时刻 → 阻塞写 I2S
              └─ 丢包补 PLC、漂移补 sample slip
```

#### （1）接收任务（优先级 11）

- 绑定 `INADDR_ANY:5680`，64KB socket 接收缓冲；
- 校验包头、长度；`stream_id` 变化或收到带 `STREAM_START` 标志的新流时整盘清零；
- 已播过的迟到包丢弃；重复包丢弃；
- 每包更新一次 `d(i)` 窗口，窗口长度 64，取最小值得到 `d_min`。

#### （2）抖动缓冲

- 64 个槽位（2 的幂，`seq % 64` 定位），每槽最多 1024 采样，放 PSRAM，约 132KB；
- 槽位先填数据、最后置 `valid`，避免播放任务读到半成品；
- 10ms 一包时可存 640ms，远大于“缓冲过深”阈值 450ms。

#### （3）启动流程（preroll）

攒够 8 帧、`d` 窗口至少有 10 个样本、缓冲时间深度达到 `lead × 3/4` 才开始：

```c
offset_us = d_min + lead_ms * 1000 + UDIO_MARGIN_US;   /* 60ms */
start_at  = 最老帧的 t_play_us + offset_us;
```

然后冻结 `offset_us`，忙等到 `start_at` 再写第一帧。**偏移冻结后不再修改** —— 改偏移
等于改出声时刻，会产生阶跃；晶振漂移交给 sample slip 慢慢补。

#### （4）丢包与断流

- 缺帧：把上一帧乘 3/4 重复播放（PLC），比补零柔和；
- 超过 500ms 没有新包：清空缓冲、重新 preroll，恢复后自动重新对齐；
- 缓冲深度超过 450ms：跳到约 150ms 的位置，防止延迟无限累积。

#### （5）漂移补偿：sample slip

两块板子的晶振差几十 ppm，播放头会缓慢脱离发送端的时刻表。控制量是抖动缓冲的
“跑道” = 最近收到的 `t_play` − 正在播放帧的 `t_play`：

- 从机晶振慢 → DMA 消耗慢 → 跑道变长 → **丢一个样本**（输出 `n-1`）；
- 从机晶振快 → 跑道变短 → **插一个样本**（输出 `n+1`）；
- 死区 4ms，两次 slip 至少间隔 20ms；
- 开播 200 帧后把跑道 EMA 定为基准，不依赖 DMA 深度的先验值。

关键点：输出样本数必须真的变化。I2S DMA 按从机晶振消耗样本，写 `n-1` 个样本，下一帧
就提前 1/44100 秒被写入，时间轴才前进一个样本。**早期版本丢了样本又把长度补回 `n`，
时间轴一点没变**，漂移校正等于空转，跑道持续偏离，这就是“从节点越播越提前”的根因。

#### （6）拼接平滑与淡入

- 丢/插样本会在波形上留下台阶（相邻样本差可达上千 LSB），用前一个输出样本对拼接点
  做 8 点线性过渡，摊成约 0.2ms 的缓变；
- 每次开播的第一帧做 128 点淡入，压掉 DMA 从静音切到音频时的直流台阶（“啪”声）。

#### （7）装配顺序

`app_main` 不再打开任何组播通道，功放必须先于接收任务初始化：

```c
Amplifier_Init();
Amplifier_Set_Volume(nr.volume);
udp_audio_start(UDIO_DEFAULT_PORT);   /* 5680 */
```

## 五、关键参数

| 参数 | 值 | 位置 | 作用 |
| --- | --- | --- | --- |
| 提前量 D | 200ms | `sync_protocol.c` / `udio_hdr.lead_ms` | 数据提前送到从机 |
| 抖动余量 | 60ms | `SYNC_RX_MARGIN_US` / `UDIO_MARGIN_US` | 主从两端都必须加，保证同拍 |
| 帧长 | 15ms（661/662 采样交替） | 主节点 `SYNC_CFG_DEFAULT_FRAME_MS` | 平均正好 44.1kHz |
| 抖动缓冲 | 64 槽 ≈ 640ms @10ms 包 | `UA_SLOTS` | 吸收乱序与抖动 |
| preroll | ≥8 帧且深度 ≥ 3/4×D | `UA_PREROLL_PKTS` | 攒够再开播，避免一开播就欠载 |
| slip 死区 | 4ms | `UA_SLIP_DEADBAND_US` | 小于它的偏差听不出来 |
| slip 最小间隔 | 20ms | `UA_SLIP_MIN_GAP_US` | 防止连续 slip 变成爆音 |
| 漂移基准 | 开播后 200 帧 | `UA_SLIP_WARMUP` | 避开 DMA 灌满前的瞬态 |
| 断流重置 | 500ms | `UA_UNDERRUN_RESET_US` | 重新 preroll |
| 缓冲过深 | >450ms 跳到 150ms | `UA_LEVEL_MAX_US` | 防止延迟累积 |

## 六、验证

### 6.1 正常串口序列

```text
I (5582) UDP_AUDIO: listening on UDP 5680 (unicast, proto v2, margin=60ms)
I (5582) MAIN: audio ready: 发送到 udp://192.168.31.45:5680 (proto v2)
I (14662) UDP_AUDIO: first packet from 192.168.31.106:57022
I (14662) UDP_AUDIO: stream 48659 start (lead=200ms)
I (14822) UDP_AUDIO: playing: seq=0 nsamples=441 offset=-587980972ms
I (14912) UDP_AUDIO: first frame: seq=0 n=441 write=0ms level=250ms
I (14912) UDP_AUDIO: rx=26 lost=0 late=0 bad=0 dup=0 slip=0 level=250ms dev=0ms offset=-587980972ms
I (16862) UDP_AUDIO: drift reference: level=216ms
...
I (xxxxx) UDP_AUDIO: rx=3533 lost=0 late=0 bad=0 dup=0 slip=0 level=218ms dev=1ms
```

- `offset` 绝对值很大是正常的：它是发送端 `esp_timer` 与从节点开机时间的差，
  只有变化量有意义；
- `level` 从首帧的 250ms 落到 216~218ms，是 DMA 被灌满（约 46ms）的过程；
- `dev` 长期在 ±4ms 死区内、`slip` 不动作，说明两端节拍一致；
- `lost/late/bad/dup` 应保持 0 或偶发。

### 6.2 先用 PC 工具验证从节点

不依赖主节点，先用 `Play_Slave/tools/udp_audio_sender.py` 把链路单独打通：

```bash
python udp_audio_sender.py --host 192.168.31.45 --tone          # 正弦，验链路
python udp_audio_sender.py --host 192.168.31.45 --file song.wav # 放歌
python udp_audio_sender.py --host 192.168.31.45 --file song.wav --master
        # 完全模拟主节点节奏：15ms 一帧、661/662 采样交替
python udp_audio_sender.py --host 192.168.31.45 --tone --loop \
        --drop-pct 2 --jitter-ms 15                              # 验 PLC 和抖动缓冲
```

`--tone` 能响说明从节点接收、缓冲、I2S、功放整条路径都通，再去查主节点一侧。
不要和主节点同时往同一台从机发 —— 两个 stream_id 会让从机反复清缓冲。

### 6.3 端到端判据

- 主从放同一首歌，人耳听不出重影/回声；
- 从节点串口 `dev` 稳定在死区内，`slip` 只是偶发（正常晶振差约 2 个/秒）；
- LCD 调音量，从节点日志出现 `volume -> N (from master)`；
- 连续播放观察期内不出现周期性空洞或越来越超前。

## 八、遗留问题

1. **从机地址**：已由手动配置改为自动发现——编译期默认表 `SYNC_DEFAULT_SLAVE_IPS`
   只在收到第一批 ANNOUNCE 前作过渡；从节点每 3s 发一次 ANNOUNCE（0x30），
   主节点按 MAC upsert、10s 判离线，上限 8 台（`SYNC_MAX_SLAVES`）。
2. **控制命令只接了音量**：`ctl_rx` 在 5679 上跟随主节点音量；暂停/切歌未接，
   切歌表现为 `stream_id` 变化 → 清缓冲重来。
3. **从节点音量不写 NVS**：重启后回到默认值，要等主节点下一次调音量才跟上。
4. **没有重传**：丢一包就是一个 PLC 帧，`lead_ms` 的 200ms 窗口内其实还有机会补，
   后续可加 NACK。
5. **多从机未实测**：协议按 8 台设计，每台独立估计 offset，但没有多台并发验证。

## 九、经验

- **先分层，再改代码**：功放自检（绕开网络）→ 收包计数 → `playing`/`offset` → 音质。
  把“没声音”拆成“功放不响 / 收不到包 / 收得到但不对齐 / 对齐了但难听”，每次只查一层。
- **组播不适合这条数据面**：WiFi 组播无 ACK、无重传、基本速率、DTIM 缓存，
  控制包和音频包还会互相拖累。改成单播后，链路状态立刻可控。
- **接收端要按“播放时刻”出声，而不是“收到就播”**：后者把网络抖动直接变成主从时间差。
- **漂移校正必须真的改变输出样本数**：丢/插样本却保持长度不变，是一个很隐蔽的空操作，
  现象就是“越播越超前”，日志上 `slip` 还在涨，容易被误导。
- **软件改完仍有爆音时，回头查线**：杜邦线接触不良会伪装成软件 bug。
