## 二、主节点同步播放时很小声的原因

先把关键前提钉死：**主节点本地播放和发给从节点的是同一份 PCM**——`ent.pcm` 和 `pkt` 载荷都是从 `s_master.frame_buf` 各拷一份（`sync_protocol.c:568`、`611`），音量也是同一个 `(vol/100)²` 公式；从节点还额外有 `AMPLIFIER_GAIN_TRIM_PERCENT = 50`（-6dB，`Play_Slave/.../amplifier.h:72`）。所以**数字链路和音量本身不可能让主节点比从节点小**。

真正的差别只可能来自“**同步模式额外做的事**”，而代码里正好有一处结构性缺陷：

```
sync_tx_task 每帧的执行顺序（sync_protocol.c）：
  ① 组包
  ② 对每台从机 wifi_manager_unicast_send(...)        ← 第 632 行
  ③ 再把这一帧 sync_delay_push(&ent) 进本地延迟队列   ← 第 652 行
```

也就是说：**主节点的本地播放“粮食”要等单播发完才入队**。而从节点在线时，主节点每 15ms 真的要发一个约 1.3KB 的 WiFi 单播包（还和蓝牙 A2DP 共用 2.4G 射频），WiFi TX 队列满/共存切时隙时 `sendto` 那段会拖几十毫秒，`sync_tx_task` 的 15ms 节拍就被拉长。

后果是两边**不对称**的：

|        | 主节点                                                       | 从节点                                                       |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 缓冲   | 本地延迟队列默认 24 槽，稳态约 17/24，只剩 **~7 帧（约 105ms）**余量 | 抖动缓冲 24 槽 + 自己的时钟换算，余量更大                    |
| 欠载时 | **写静音帧**：`memset` 全 0 后 `Amplifier_Play_Buffer(2800B)`，而且紧接着还 `vTaskDelay(15ms)`（`sync_protocol.c:720-724`、`735-739`）——一次欠载实际会变成约 **50% 静音** | **PLC**：重复上一帧 × 0.75（`udp_audio.c` 的 `ua_write_plc`），听感连续且响 |

所以现象完全对得上：**只有主节点播放 → 没有单播发送 → TX 节拍稳 → 队列不断粮 → 很响；加上从节点同步 → 每帧多出 WiFi 单播 → TX 被拖慢 → 本地队列抽干 → 主节点补静音 → 听起来“很小声”；从节点靠缓冲+PLC 顶着 → “正常而且很大声”。**

> 顺带排除一个次要可能（5 分钟能核对）：从节点只在收到**音量变化事件**时才跟随主节点音量。主节点重启后如果没重新下发，从节点会保持自己 NVS 里的值，两边 volume 可能不一致。看主节点日志 `created (vol=N ...)` 和从节点日志 `volume -> N (from master)` 是否相同即可。但这不是本 bug 的根因——你说“只有主节点播放时是响的”，这就排除了音量和功放。

## 三、几套方案（按改动量从小到大，你挑）

**方案 A：最小改动（先试这个，10 分钟）**

- 把 `sync_tx_task` 里 **sync_delay_push(&ent) 提到单播发送之前**（本地先入队，网络再发；`ent` 是独立拷贝，先入队完全安全）。
- `SYNC_CFG_DEFAULT_DELAY_PKTS` 24 → 48，并把 PREPARING→PLAYING 的灌入深度从 `cnt*frame_ms >= D` 改成 `>= D + MARGIN + 2帧`（现在少灌了 60ms）。
- 效果：网络抖动不再直接饿死本地播放；改动小、风险低。

**方案 B：彻底解耦（推荐长期）**

- 主节点本地播放不再依赖 TX 任务的队列：在 `push_pcm` 时**同时写一份本地播放环**（或用独立本地生产者任务），`sync_tx_task` 只负责网络发送。
- 代价：多一份 PSRAM 缓冲（很便宜）；收益：**主节点作为声学基准，永远不会被从节点/网络拖累**。这才是“主节点响声不能被同步链路影响”的正确架构。

**方案 C：音质兜底（配合 A/B 一起做最好）**

- 本地欠载时**不要写静音**，改成和从节点一样的 PLC（重复上一帧 ×0.75）；
- 静音/PLC 分支**去掉额外的 vTaskDelay(15)**，严格保持 15ms 帧节拍——现在“写 15.8ms 静音 + 再睡 15ms”会把一次欠载放大成约 50% 静音。

**方案 D：降低单播对 TX 的干扰**

- 音频帧 15ms → 30ms（每包 1322 采样），**发送次数直接减半**，WiFi 发送开销和共存冲突同步减半；
- 或把采样率降到 32k/22.05k（带宽约减半）；
- 或主节点用 SD 音源时避免同时跑 BT A2DP（共存压力最大来源）。
- 代价：改协议帧长/采样率要主从同步改；收益是网络侧更稳。

**方案 E：音量侧核对（只在你发现两边 volume 不一致时做）**

- `SYNC_START` 里携带音量、或从节点上线后主动请求一次音量，保证重启后也一致；
- 主节点打开 `AMPLIFIER_DEBUG_LOGS`（现在是 `false`），能看到每次 `Amplifier_Play_Buffer` 是否超时、是否触发 DMA flush；顺手用 `Debug_BeepTest` 单独验一次功放。

## 直接回答：**当前这套实现不能“查找设备”**

现在的代码里，主节点发音频用的是：

```
// Play_Master/.../sync_protocol.c:81
static const char *const SYNC_DEFAULT_SLAVE_IPS[] = {
    "192.168.31.45",          // ← 编译期写死
};
```

- 主节点**只知道这个写死的 IP**（或运行时由 `sync_protocol_master_set_slaves()` 传进来的 IP 列表）；
- 从节点**从来不上报自己是谁/在哪**：`ctl_rx` 只监听 5679 上的 VOLUME；
- 主节点的 `wifi_manager_mcast_recv()` 在 `recvfrom(..., NULL, NULL)` 里**丢掉了发送方地址**（`wifi_manager.c:582`），所以主节点连“谁给我发了包”都不知道；
- 没有 mDNS、没有 DHCP hostname、没有 announce/握手。

所以你的担心是对的：**DHCP 一般会按 MAC 尽量续租同一个地址，但路由器重启、租约过期、换路由器、长时间断电后，从节点换 IP 是会发生的事。一旦换了，主节点还在往旧 IP 单播，从节点就永远收不到。**

好消息是：**改成“可发现”不需要动音频数据面**，只需要把“从节点 IP 表”从写死改成运行时发现。下面给你几套方案。

## 方案对比

| 方案                               | 做法                                                         | 优点                                                         | 缺点/风险                                                    | 工作量                   |
| ---------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------ |
| **A. 从节点 UDP 公告（推荐）**     | 复用现有 239.0.0.1:5679 控制通道，从节点周期性发 `ANNOUNCE`（MAC + 当前 IP + 端口 + 版本），主节点收到后更新目标表 | 不加组件、不加 socket；复用已验证的组播通道；容忍 DHCP 换 IP；可扩展到多从机 | 依赖 AP 允许客户端间组播；要做配对/白名单，否则同网段任何同固件设备都能收到你的音频 | 150~250 行               |
| **B. 主节点主动探测 + 从节点应答** | 主节点发 `DISCOVER`（组播/广播），从节点单播回 `ANNOUNCE`    | 空闲时几乎无流量；主节点启动时发现更快                       | 从节点要能发单播（现有 `wifi_manager` 没有 `unicast_send`，要补十几行）；主节点要拿到源 IP（现在 `recvfrom` 丢了） | 比 A 稍多                |
| **C. mDNS**                        | 从节点注册 `_syncspk._udp.local`（TXT：MAC/端口/版本），主节点 browse 得到 IP | 标准协议、手机/电脑也能发现；天然解决 DHCP 换 IP             | 要加 `mdns` 组件（Flash/RAM 开销）；组播 DNS 在部分路由器/IGMP snooping 下会被挡；查询有 1~2s 延迟 | 中等                     |
| **D. DHCP hostname + 静态租约**    | 从节点设置 hostname `syncspk-XXXX`，路由器按 MAC 做静态绑定  | 改动最小（几行 `esp_netif_set_hostname`）；地址永远不变      | **需要用户进路由器配置**，正是你想避免的                     | 最小                     |
| **E. 主节点自己开 AP（APSTA）**    | 主节点开 SoftAP + DHCP 服务，从节点连主节点的 AP；主节点甚至可按 MAC 给固定地址 | 对用户零配置；IP 完全可控；不受家里路由器组播策略影响        | 主节点射频要同时扛 AP+STA+BT 共存，带宽/距离下降；从节点上不了外网（一般无所谓） | 最大，但最适合消费级产品 |

## 推荐：方案 A（复用现有控制通道）

全部改动都在控制面，音频单播链路一行不用改：

1. **协议**：在 `sync_protocol.h` 里加两个扩展类型（扩展现有 `sync_ctrl_ext_t` 就行）：

   ```
   SYNC_MSG_ANNOUNCE = 0x30   // slave → master
   payload: { u8 ver, u8 mac[6], u8 ip[4], u16 audio_port,
              u8 volume, u8 flags, u32 group_token }
   ```

   主节点也可以加一个 `SYNC_MSG_DISCOVER = 0x32`（组播），从节点收到后立即回一帧 announce，这样主节点开机 1 秒内就能发现，不用等周期公告。

2. **从节点**：

   - WiFi 拿到 IP 后（`wifi_manager` 的 GOT_IP 事件）立刻发一次，之后每 3~5 秒发一次；
   - 用现有 `ctl_rx` 的通道直接 `wifi_manager_mcast_send()`（这个通道 `rx_enable=true`，socket 已绑定并加组，sendto 可直接用，**不需要新 socket**）；
   - 自己会收到自己的回环副本，用 MAC 过滤掉即可；
   - 顺便把 `volume` 也带上去，主节点重启后可以立即把音量对齐（顺手解决上次说的“两边音量可能不一致”）。

3. **主节点**：

   - 在 `sync_handle_control_rx()` 里加 `case SYNC_MSG_ANNOUNCE`；

   - 维护一张运行时表：

     ```
     typedef struct {
         uint8_t  mac[6];
         char     ip[16];
         uint16_t port;
         uint8_t  volume;
         uint32_t last_seen_ms;
         bool     paired;
     } slave_entry_t;   // SYNC_MAX_SLAVES = 8
     ```

   - 收到就 upsert（按 MAC 更新 IP），30 秒没收到就标记离线；

   - 表变化时调用现有的 `sync_protocol_master_set_slaves()`（它只替换列表、不重置流，`sync_set_slaves_locked()` 里没有 reset，可以运行中热更新）；

   - 把已配对的 MAC 存 NVS，只接受白名单内的设备（避免别人家的同款音箱收到你的音频）。

4. **配对/安全**（别省）：

   - 主节点 UI 加一个“配网/配对”模式（比如 60 秒内接受新设备），或两边都写同一个 `group_token`（NVS 里的 4~8 位配对码）；
   - 否则同一局域网里任何一台跑这套固件的从节点都会收到音频——是隐私问题。

5. **中途加入**：从节点在主节点播放中途上线时，最好主节点周期性重发一次 `SYNC_START`（或音频头里的 `STREAM_START` 每 1 秒置一次），让新加入的从节点能立刻开始；否则它的 `ua_try_start` 要靠缓冲深度自己判断（现在代码里已经有这个逻辑，但重发 start 更稳）。

**为什么推荐 A：** 你们现在**控制面本来就在用组播 5679**（音量命令已经验证能通），把它扩展成“公告 + 音量”是最省事的；不动音频单播、不动时钟估算，风险最小。

## 如果担心路由器挡组播

先做 A 时加一个降级：从节点 announce 同时尝试

- 组播 `239.0.0.1:5679`（首选），
- 广播 `255.255.255.255:5679`（socket 需要 `SO_BROADCAST`），

哪个通用哪个。如果两个都被挡（有些路由器开了“客户端隔离”），那就只剩 **方案 E（主节点自己开 AP）** 能彻底解决——这也是消费级产品最稳的形态：用户不用懂 IP，从节点开机连主节点即可，主节点还能按 MAC 固定分配地址。

## 一句话建议

- **比赛/演示阶段**：先上 **A（UDP 公告 + MAC 白名单）**，代码量小、能扛 DHCP 换 IP；
- **要做成用户能直接用的产品**：最终选 **E（主节点 SoftAP + A 公告）**，对用户零配置；
- **mDNS（C）** 可以以后作为加分项加上（手机 App 也能发现设备），但不要作为唯一发现手段。
