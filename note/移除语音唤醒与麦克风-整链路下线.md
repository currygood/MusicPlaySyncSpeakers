# 移除语音唤醒 / 麦克风整条链路（2026-10-25）

> 决策：主节点不再做语音唤醒与通话上行。`CallPhone`（esp-sr 唤醒词）+ `microphone`
> （INMP441 采集）两个模块移出构建，源码留档在 `Play_Master/legacy_disabled/`。
> 恢复清单见该目录的 `README.md`。

## 1. 为什么是"砍掉"而不是再调一轮参数

第 4 次 panic 的调用链（`up=2848s`，播放第 1~2 首）：

```text
IDLE0（被中断）→ _xt_lowint1 → shared_intr_isr
   → i2c_master_isr_handler_default      (i2c_master.c:861)
   → xQueueGiveFromISR                   (queue.c:1385)
   → vPortEnterCritical → xPortEnterCriticalTimeout (port.c:489)
   → spinlock_acquire                    (spinlock.h:142)  ← PC 停在这里
```

`xPortEnterCriticalTimeout` 先 `portSET_INTERRUPT_MASK_FROM_ISR()`（屏蔽 level 1~3，
**包括喂狗用的 tick**），再去抢 `xQueue->mux`：`timeout` 传的是 `portMUX_NO_TIMEOUT`
（寄存器 A2=`0xFFFFFFFF`），抢不到就原地无限重试。ISR 里屏蔽中断 + 死等 = tick 停 =
`Interrupt wdt timeout on CPU0`。

前 3 轮的处置都只是把**触发概率**压低，没有动"为什么触摸 I2C 会一路走到硬件超时 +
FSM reset + 深层中断嵌套"这个根：`i2c f=2848 r=1 last=ESP_ERR_INVALID_RESPONSE`，
FT6336G 的读失败率约 3%，每次失败都由驱动做一次 `clear_bus` 复位。

而让这一切有机会叠在一起的是算力：wn9s 常驻监听时单帧推理 ≈ 一帧音频时长，
Core1 占用 ~78%，`IDLE1` 长期贴地；`afe_fetch()` 是**阻塞**的（`portMAX_DELAY`），
一旦 AFE 卡住整个 Core1 就跟着停（实测 `proc=3387945us`）。Core0 侧则被
classic BT 中断 + coex 反复仲裁占住，I2C ISR 迟迟跑不到 → 硬件超时率上升。

**结论**：语音唤醒是这台"同步播放音箱"的锦上添花功能，却持续把系统推到
时序悬崖边。第 2、3 轮的处置已经把它的价值压到"播放时被暂停、只有暂停时能唤醒"，
再往下调只剩"彻底关掉"这一种，于是直接关掉。

## 3. 烧录后怎么判断"真的好了"

按以下顺序看串口（`[hb]` 每 ~10s 一行，`[btpcm]` 每 3s 一行）：

1. **启动日志**应完全不再出现 `[CallPhone]`、`afe`、`esp-sr`、`wakenet` 字样；
   `[heap] after amp` 的内部 DRAM 余量应比之前多（少了一条 AFE 流水线 + 麦克风 FIFO）。
2. `[hb]` 行尾只到 `i2c f= r= last=`，**没有** `cp st=` 字段 —— 确认跑的是新固件。
3. 播放中 `[btpcm]` 的 `un=`（underrun）与 `gap=` 应明显小于之前的 173 / 77~117ms；
   `A2DP starved` 警告应基本消失。
4. `i2c f=` 的增长速度是关键判据：
   - 若从 ~4 次/秒降到接近 0 或极慢 → 说明之前的总线失败确实由 CPU 挤占间接造成；
   - 若仍然稳定增长（每秒数次）→ 触摸硬件/电路本身有问题，见下节。
5. 连续播放 10 首以上、`up=` 超过 3000s 不再 panic，即可认为语音链路这条因已拔除。

## 4. 还没解决的两件事（与语音无关，但会咬人）

1. **触摸 I2C 约 3% NACK**：`ESP_ERR_INVALID_RESPONSE` 是硬件超时，说明从机没在
   超时窗口内响应。候选原因按可能性排序：
   - FT6336G 的 SDA/SCL 上拉偏弱（模块板载 10k + 长排线容性）；
   - 触摸 INT/RST 与 LCD 共用 SPI 的时序干扰；
   - 事务超时 10ms 对 400kHz 下的个别重载周期偏紧。
   可试：提高上拉（4.7k）、把 `I2C_MASTER_TIMEOUT` 放到 20~30ms、或读失败时不再
   `clear_bus` 而是直接跳过本次（少一次 FSM reset 就少一次深层 ISR 嵌套）。
2. **`LCD_Touch.c` 的重试逻辑失败后不归零**：连续 N 次失败后进入长退避，却没有在
   读成功后复位计数，触摸会"越用越迟钝"。这是纯逻辑 bug，与崩溃无关，建议单独修。

## 5. 若要再给 I2C 上一层保险（可选，未做）

- `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` 0 → 4096：让小对象优先落内部 RAM，
  减少 PSRAM 自旋锁路径被触发的机会（第 3 次崩溃正是 `cpu.c:205` PSRAM CAS 分支）。
- 触摸任务读 I2C 时避免与 LVGL 刷屏同核争抢（当前 UI 优先级已降到 10）。
